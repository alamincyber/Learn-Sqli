    API সিকিউরিটি (API Security) ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Basic থেকে Advanced API Security শেখার গাইড — API আর্কিটেকচার, Authentication mechanism, OWASP API Security Top 10 (2023), ম্যানুয়াল টেস্টিং এবং বাগ বাউন্টি ওয়ার্কফ্লো পর্যন্ত, ১৫টি অধ্যায়ে সাজানো।

    API Security নিয়ে সংক্ষিপ্ত কথা

    আজকের প্রায় প্রতিটি আধুনিক অ্যাপ্লিকেশন — মোবাইল অ্যাপ, SPA (Single Page Application), থার্ড-পার্টি ইন্টিগ্রেশন, IoT ডিভাইস — এর ভেতরে একটি API (Application Programming Interface) লুকিয়ে থাকে, যা আসল ডেটা ও বিজনেস লজিকের সাথে যোগাযোগ করে। ঐতিহ্যবাহী ওয়েব অ্যাপের মতো API-তে সাধারণত কোনো রেন্ডার করা HTML UI থাকে না — তাই অনেক ডেভেলপার মনে করেন API "সরাসরি ইউজার দেখে না, তাই কম ঝুঁকিপূর্ণ"। বাস্তবে উল্টো — API প্রায়ই সরাসরি ডেটাবেজ ও business logic-এর কাছাকাছি থাকে, এবং একটি দুর্বল API, গোটা ব্যাকএন্ড পর্যন্ত আক্রমণকারীর রাস্তা খুলে দিতে পারে।

    এই ডকুমেন্টেশনে ধাপে ধাপে দেখানো হয়েছে — API আসলে কী ও কীভাবে কাজ করে, REST/GraphQL/SOAP-এর পার্থক্য, API Key/OAuth/JWT-ভিত্তিক Authentication কীভাবে কাজ করে, OWASP API Security Top 10 (2023)-এর প্রতিটি ক্যাটাগরি বাস্তব উদাহরণসহ, Postman ও Burp Suite দিয়ে ম্যানুয়াল API টেস্টিং, এবং সবশেষে একটি দায়িত্বশীল bug bounty workflow।

    API সিকিউরিটির ভিত্তি (API Security Fundamentals)

    API আসলে কী, কেন এটি আলাদাভাবে গুরুত্বপূর্ণ একটি attack surface, এবং ওয়েব অ্যাপ সিকিউরিটি থেকে API সিকিউরিটি কীভাবে আলাদা — এই অধ্যায়ে সেই ভিত্তিটা তৈরি হবে।

    ⚖️

    আইনি নোটিশ: এই অধ্যায়ে উল্লেখিত যেকোনো ধারণা বা উদাহরণ শুধুমাত্র নিজের তৈরি lab, অনুমোদিত training platform (OWASP crAPI, PortSwigger, Juice Shop ইত্যাদি) অথবা স্পষ্টভাবে scope-ভুক্ত bug bounty প্রোগ্রামে প্রয়োগ করুন। অনুমতি ছাড়া কোনো সিস্টেমে প্রয়োগ করলে তা আইনত দণ্ডনীয় অপরাধ।

    API কী

    API (Application Programming Interface) হলো দুটি সফটওয়্যার সিস্টেমের মধ্যে যোগাযোগের একটি সুনির্দিষ্ট নিয়মাবলী। একটি মোবাইল অ্যাপ যখন সার্ভার থেকে প্রোফাইল তথ্য আনে, একটি ওয়েবসাইট যখন পেমেন্ট গেটওয়েতে রিকোয়েস্ট পাঠায়, বা একটি SPA (React/Vue অ্যাপ) যখন ব্যাকএন্ড থেকে ডেটা fetch করে — প্রতিটির পেছনেই একটি API কাজ করছে। সহজভাবে বললে, API হলো একটি "চুক্তি" (contract) — কোন endpoint-এ, কোন ফরম্যাটে রিকোয়েস্ট পাঠালে, কী response ফেরত আসবে।

    আধুনিক অ্যাপ্লিকেশন আর্কিটেকচারে frontend (UI) ও backend (business logic + database) সম্পূর্ণ আলাদা হয়ে গেছে — এই দুটিকে সংযুক্ত করে API। তাই API হলো literally সেই দরজা, যার মধ্য দিয়ে বাইরের দুনিয়া আপনার সার্ভারের ডেটা ও কার্যকারিতার সাথে interact করে।

    কেন API আলাদাভাবে ঝুঁকিপূর্ণ

    ঐতিহ্যবাহী ওয়েব অ্যাপে attacker একটি HTML পৃষ্ঠা দেখেন, যেখানে ফর্ম, বাটন, লিংক — সবকিছু দৃশ্যমান, তাই attack surface অনেকটা "ইউজার যা দেখেন তার মধ্যে সীমাবদ্ধ"। কিন্তু API-তে এই দৃশ্যমানতা নেই — client শুধু JSON/XML ডেটা পায়, UI রেন্ডার হয় client-side-এ। ফলে সার্ভার-সাইডে এমন অনেক endpoint, field বা parameter থাকতে পারে, যা UI-তে কখনো দেখানো হয় না, কিন্তু API সরাসরি কল করলে এখনও কাজ করে।

    🖥️ ওয়েব অ্যাপ (Traditional)

    UI-তে যা দেখানো হয়, সাধারণত ততটুকুই attack surface হিসেবে স্পষ্ট থাকে। Validation প্রায়ই client-side এবং server-side দুই জায়গাতেই থাকে বলে অনুমান করা হয়।

    🔌 API

    Client কোনো কিছু রেন্ডার করে না — তাই "hidden" field, debug endpoint, বা internal-only route থাকলেও তা UI-তে প্রকাশ পায় না। Developer-রা প্রায়ই ভুল করে মনে করেন "UI-তে না দেখালে নিরাপদ" — এটিই Security through Obscurity-এর ফাঁদ।

    API আক্রমণের বাস্তব প্রভাব

    ২০১৯ সালে Facebook-এর একটি API bug লক্ষ লক্ষ ফোন নম্বর ফাঁস করেছিল। T-Mobile, Peloton, Instagram, USPS — সবারই বড় ডেটা লিক হয়েছে একটি দুর্বল API endpoint থেকে। কারণ একটিই: API সরাসরি ডেটাবেজ ও business logic-এর সবচেয়ে কাছাকাছি স্তরে কাজ করে, তাই একটি ফাঁক গোটা ব্যাকএন্ডে পৌঁছানোর সবচেয়ে ছোট রাস্তা হয়ে যায়।

    অনুশীলন

    আপনার পরিচিত কোনো একটি মোবাইল অ্যাপ (যেমন একটি ফুড ডেলিভারি বা রাইড-শেয়ারিং অ্যাপ) এর ব্রাউজার DevTools বা একটি proxy টুল (পরে শিখবেন) দিয়ে নেটওয়ার্ক ট্যাব খুলুন (শুধু observe করুন, কোনো রিকোয়েস্ট পরিবর্তন করবেন না) — কতগুলো আলাদা API call হচ্ছে তা লক্ষ করুন এবং চিন্তা করুন, এর মধ্যে কোনগুলো "sensitive" ডেটা বহন করছে বলে মনে হয়।

    সারসংক্ষেপ

    API হলো দুটি সিস্টেমের মধ্যে যোগাযোগের চুক্তি, যা আধুনিক অ্যাপ্লিকেশনের মেরুদণ্ড। UI না থাকার কারণে API-এর attack surface অনেক সময় লুকানো থাকে — এবং এটিই এর সবচেয়ে বড় ঝুঁকি, কারণ "দেখা যায় না" মানে "নিরাপদ" নয়।

    API আর্কিটেকচার ও প্রকারভেদ

    REST, GraphQL, SOAP ও gRPC — প্রতিটি কীভাবে কাজ করে, তাদের মধ্যে পার্থক্য, এবং HTTP মেথড/স্ট্যাটাস কোডের ভূমিকা।

    REST (Representational State Transfer)

    আজকের সবচেয়ে জনপ্রিয় API স্টাইল। REST API-তে প্রতিটি রিসোর্স (ইউজার, প্রোডাক্ট, অর্ডার) একটি URL (endpoint) দিয়ে চিহ্নিত হয়, আর HTTP মেথড (GET, POST, PUT, PATCH, DELETE) দিয়ে সেই রিসোর্সের উপর কী action নেওয়া হবে তা বোঝানো হয়।

    REST API — উদাহরণ এন্ডপয়েন্ট (ধারণাগত)
    GET    /api/users/42        → ইউজার ৪২-এর তথ্য দেখান
POST   /api/users           → নতুন ইউজার তৈরি করুন
PUT    /api/users/42        → ইউজার ৪২-কে সম্পূর্ণ আপডেট করুন
PATCH  /api/users/42        → ইউজার ৪২-এর অংশবিশেষ আপডেট করুন
DELETE /api/users/42        → ইউজার ৪২ মুছে ফেলুন

    GraphQL

    REST-এ প্রতিটি endpoint একটি নির্দিষ্ট ডেটা শেপ ফেরত দেয়, কিন্তু GraphQL-এ একটিই endpoint (সাধারণত /graphql) থাকে, আর client নিজেই নির্দিষ্ট করে দেয় তার ঠিক কোন কোন field দরকার। এটি flexible, কিন্তু সিকিউরিটির দৃষ্টিকোণ থেকে একটি নতুন ঝুঁকি তৈরি করে — over-fetching/nested query abuse, যেখানে একটি জটিল nested query দিয়ে attacker একসাথে অনেক ডেটাবেজ রিসোর্স টেনে এনে DoS ঘটাতে পারেন, বা access control bypass করতে পারেন যদি প্রতিটি field resolver-এ আলাদা authorization check না থাকে।

    SOAP ও gRPC

    SOAP (Simple Object Access Protocol)

    XML-ভিত্তিক, কঠোর কন্ট্রাক্ট (WSDL) মেনে চলে। ব্যাংকিং ও legacy enterprise সিস্টেমে এখনও ব্যবহৃত হয়। REST-এর তুলনায় বেশি verbose, কিন্তু built-in standards (WS-Security) দিয়ে strong typing ও কিছু সিকিউরিটি ফিচার আগে থেকেই থাকে।

    gRPC

    Google-এর তৈরি, Protocol Buffers (binary format) ব্যবহার করে, HTTP/2-এর উপর চলে। Microservices-এর মধ্যে দ্রুত যোগাযোগের জন্য জনপ্রিয়। JSON-এর মতো human-readable নয় বলে সরাসরি browser থেকে inspect করা কঠিন, কিন্তু proxy টুল দিয়ে এখনও intercept করা যায়।

    Authentication ও Authorization মেকানিজম

    API Key, Basic Auth, OAuth 2.0 ও JWT — API-তে "আপনি কে" (authentication) এবং "আপনি কী করতে পারেন" (authorization) কীভাবে যাচাই করা হয়।

    ⚠️

    সবচেয়ে গুরুত্বপূর্ণ পার্থক্য: Authentication মানে "আপনি কে, তা প্রমাণ করা"। Authorization মানে "আপনার এই নির্দিষ্ট জিনিসটি করার/দেখার অনুমতি আছে কি না, তা যাচাই করা"। একটি API অনেক সময় authentication ঠিকভাবে করে, কিন্তু প্রতিটি রিসোর্সে আলাদাভাবে authorization check করতে ভুলে যায় — এটিই পরবর্তী অধ্যায়গুলোর (BOLA, BFLA) মূল ভিত্তি।

    API Key

    একটি সাধারণ string, যা প্রতিটি রিকোয়েস্টের সাথে পাঠানো হয় (header, query parameter, বা body-তে)। এটি সাধারণত কোন অ্যাপ্লিকেশন/প্রজেক্ট রিকোয়েস্ট পাঠাচ্ছে তা সনাক্ত করে — কোন নির্দিষ্ট ইউজারকে নয়। তাই API Key একা থাকলে প্রায়ই rate-limiting ও billing ট্র্যাক করার জন্য ব্যবহৃত হয়, শক্তিশালী ইউজার-লেভেল authentication হিসেবে নয়।

    API Key — সাধারণ ব্যবহার
    GET /api/weather?city=Dhaka HTTP/1.1
Host: api.example.com
X-API-Key: sk_live_9f8a7b6c5d4e3f2a1b

    Basic Auth

    Username:password-কে Base64-এ এনকোড করে Authorization header-এ পাঠানো হয়। মনে রাখা জরুরি — Base64 এনক্রিপশন নয়, এটি শুধু এনকোডিং, যে কেউ সহজে ডিকোড করতে পারে। তাই Basic Auth শুধুমাত্র HTTPS-এর সাথেই ব্যবহার করা উচিত, কখনোই HTTP-তে নয়।

    OAuth 2.0

    OAuth 2.0 হলো একটি delegation framework — এটি "password শেয়ার না করে" একটি সার্ভিসকে আরেকটি সার্ভিসের উপর সীমিত অ্যাক্সেস দেওয়ার মান। যেমন "Google দিয়ে Login" করার সময়, আপনি আপনার Google password কখনোই তৃতীয় পক্ষের অ্যাপে দেন না — বরং Google আপনার পক্ষ থেকে একটি সীমিত-ক্ষমতার access token ইস্যু করে।

    Authorization Code Flow

    সবচেয়ে নিরাপদ, server-to-server flow — প্রথমে একটি সংক্ষিপ্ত-জীবনকালের authorization code পাওয়া যায়, তারপর সেটি backend থেকে access token-এর সাথে বিনিময় করা হয়।

    Implicit Flow (Deprecated)

    সরাসরি browser-এ access token রিটার্ন হতো — URL fragment-এ token এক্সপোজ হওয়ার ঝুঁকির কারণে OAuth 2.1-এ এটি বাদ দেওয়া হয়েছে।

    Scope হলো OAuth-এর একটি গুরুত্বপূর্ণ ধারণা — এটি নির্ধারণ করে একটি token দিয়ে ঠিক কতটুকু অ্যাক্সেস পাওয়া যাবে (যেমন read:profile বনাম write:payments)। একটি সাধারণ bug হলো সার্ভার scope সঠিকভাবে enforce না করা — অর্থাৎ একটি read:profile scope-এর token দিয়েও write endpoint কল করা গেলে, তা একটি গুরুতর authorization ত্রুটি।

    JWT (JSON Web Token)

    JWT একটি self-contained token ফরম্যাট — তিনটি Base64URL-এনকোডেড অংশ (header.payload.signature) নিয়ে গঠিত, যা ডট (.) দিয়ে আলাদা করা হয়। Server একে ডিক্রিপ্ট না করেই, শুধু signature যাচাই করে বুঝতে পারে token-টি বৈধ কি না এবং payload-এ কী আছে।

    JWT গঠন (ধারণাগত, lab-only ডেমো টোকেন)
    eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjQyLCJyb2xlIjoidXNlciJ9.4f8a2b...

→ Header:  {"alg":"HS256"}
→ Payload: {"userId":42,"role":"user"}
→ Signature: HMAC(header + "." + payload, secret_key)

    গুরুত্বপূর্ণ: JWT-এর payload অংশ শুধু Base64-এনকোডেড, এনক্রিপ্টেড নয় — তাই যে কেউ payload ডিকোড করে পড়তে পারে (কিন্তু signature ছাড়া পরিবর্তন করতে পারবে না, যদি সার্ভার সঠিকভাবে যাচাই করে)। তাই JWT payload-এ কখনো পাসওয়ার্ড বা অন্য sensitive সিক্রেট রাখা উচিত নয়।

    🚨

    পরিচিত JWT দুর্বলতা: alg:none attack (সার্ভার যদি "কোনো সিগনেচার নেই" এমন algorithm গ্রহণ করে), algorithm confusion (RS256 থেকে HS256-এ পরিবর্তন করে public key-কে secret হিসেবে ব্যবহার), weak/leaked signing secret, এবং expired token যাচাই না করা — এগুলো বাস্তব bug bounty প্রোগ্রামে বারবার পাওয়া যায়।

    অনুশীলন

    উপরের উদাহরণ JWT payload-টি ({"userId":42,"role":"user"}) চিন্তা করুন — যদি সার্ভার শুধু payload-এর role ফিল্ড দেখে admin অ্যাক্সেস দেয়, কিন্তু signature ঠিকমতো যাচাই না করে, তাহলে একজন attacker কী করতে পারবেন বলে মনে করেন?

    সারসংক্ষেপ

    Authentication প্রমাণ করে "আপনি কে", Authorization নির্ধারণ করে "আপনি কী করতে পারেন" — এই দুটি সম্পূর্ণ আলাদা ধাপ, এবং শক্তিশালী authentication (যেমন OAuth/JWT) থাকলেও, প্রতিটি রিসোর্সে আলাদা authorization check না থাকলে অ্যাপ্লিকেশন এখনও গুরুতরভাবে vulnerable থাকতে পারে।

    প্রায় প্রতিটি bug bounty প্রোগ্রামের API স্কোপে, এই ১০টি ক্যাটাগরিই সবচেয়ে বেশি পাওয়া যায় ও সবচেয়ে বেশি পুরস্কৃত হয় — কারণ এগুলো প্রায়ই business logic-এর সরাসরি অপব্যবহারের রাস্তা খুলে দেয় (শুধু "একটি পেজ ক্র্যাশ" নয়, বরং সরাসরি অন্য ইউজারের ডেটা চুরি বা অ্যাকাউন্ট টেকওভার)।

    অনুশীলন

    উপরের টেবিল থেকে, কোন তিনটি ক্যাটাগরি সরাসরি "Authorization" সম্পর্কিত বলে মনে হয়, এবং কেন তারা একে অপরের থেকে আলাদা (object-level vs property-level vs function-level) তা নিজের ভাষায় লিখুন।

    সারসংক্ষেপ

    OWASP API Security Top 10 (2023) হলো API ঝুঁকি বোঝার আন্তর্জাতিক স্ট্যান্ডার্ড ফ্রেমওয়ার্ক। এর মধ্যে Authorization-সম্পর্কিত তিনটি ক্যাটাগরি (BOLA, Property-level, BFLA) সবচেয়ে বেশি পাওয়া যায় এবং সবচেয়ে গুরুতর প্রভাব ফেলে। পরবর্তী অধ্যায়গুলোতে প্রতিটি ক্যাটাগরি বিস্তারিতভাবে আলোচিত হবে।

    BOLA — Broken Object Level Authorization

    OWASP API Security Top 10-এর #১ ঝুঁকি — এবং বাস্তবে সবচেয়ে বেশি পাওয়া যাওয়া API vulnerability।

    ⚖️

    আইনি নোটিশ: এই অধ্যায়ের সকল উদাহরণ শুধুমাত্র নিজের lab বা অনুমোদিত scope-এ পরীক্ষা করুন।

    BOLA কী

    BOLA (আগে IDOR — Insecure Direct Object Reference নামে পরিচিত ছিল) ঘটে, যখন একটি API endpoint একটি object ID (যেমন user ID, order ID, invoice ID) গ্রহণ করে, কিন্তু যাচাই করে না — "যে রিকোয়েস্ট পাঠাচ্ছে, তার কি সত্যিই এই নির্দিষ্ট ID-এর রিসোর্স অ্যাক্সেস করার অনুমতি আছে?" ফলে শুধু URL বা body-তে ID পরিবর্তন করে attacker অন্য যেকোনো ইউজারের ডেটা দেখতে বা পরিবর্তন করতে পারেন।

    BOLA — ক্লাসিক উদাহরণ (lab-only, ধারণাগত)
    // আপনার নিজের, বৈধ রিকোয়েস্ট
GET /api/invoices/1024 HTTP/1.1
Authorization: Bearer <your-valid-token>

→ 200 OK: আপনার নিজের ইনভয়েস

// শুধু ID পরিবর্তন করলেন
GET /api/invoices/1025 HTTP/1.1
Authorization: Bearer <your-valid-token>

→ 200 OK: অন্য একজন গ্রাহকের ইনভয়েস — BOLA!

    লক্ষণীয়, token/authentication সম্পূর্ণ বৈধ ও সঠিক — সমস্যাটি authentication-এ নয়, বরং সার্ভার 1025 নম্বর ইনভয়েসটি request করা ইউজারের নিজের কি না, তা কখনো যাচাই করেনি।

    কেন এত ব্যাপকভাবে পাওয়া যায়

    অনেক ডেভেলপার object-level authorization-কে "already handled" ধরে নেন, কারণ URL-এ authentication token যাচাই হচ্ছে। কিন্তু authentication শুধু বলে "এই ইউজারটি বৈধ" — এটি বলে না "এই ইউজারের এই নির্দিষ্ট object-এর উপর অধিকার আছে"। প্রতিটি single object-returning endpoint-এ আলাদা ownership check লাগবে — এটিই সবচেয়ে বেশি miss হয়।

    Sequential ও Predictable ID

    অনেক সিস্টেম auto-increment integer ID ব্যবহার করে (1, 2, 3...), যা অনুমান করা সহজ। এটি BOLA-কে আরও সহজে exploit করার সুযোগ দেয় — attacker শুধু ID পরপর বাড়িয়ে পুরো ডেটাবেজ enumerate করতে পারেন। UUID ব্যবহার করলেও (যা অনুমানযোগ্য নয়) — যদি কোথাও সেই UUID leak হয় (যেমন অন্য একটি endpoint-এর response-এ), তাহলেও BOLA ঘটতে পারে।

    ⚠️

    ভুল ধারণা: "আমি UUID ব্যবহার করছি, তাই BOLA থেকে নিরাপদ" — এটি সত্য নয়। UUID শুধু ID অনুমান করা কঠিন করে তোলে, কিন্তু যদি সার্ভার তবুও ownership check না করে, এবং অন্য কোনোভাবে (লিক হওয়া লিংক, অন্য API response, লগ ফাইল) সেই UUID পাওয়া যায়, BOLA তখনও সম্ভব।

    কোথায় BOLA খুঁজবেন

    • প্রতিটি endpoint যা একটি ID গ্রহণ করে — URL path (/users/{id}), query parameter (?userId=42), বা request body-তে।
    • GET (ডেটা পড়া), PUT/PATCH (ডেটা পরিবর্তন), DELETE (ডেটা মোছা) — সব ধরনের method-এ।
    • Export/download/report ফিচার, যেখানে প্রায়ই অতিরিক্ত ID parameter থাকে।
    • একাধিক ইউজার অ্যাকাউন্ট (দুটি সাইন-আপ করা test ইউজার) দিয়ে একটির token দিয়ে অন্যটির object অ্যাক্সেসের চেষ্টা করা — এটিই BOLA টেস্টিংয়ের সবচেয়ে সাধারণ পদ্ধতি।

    প্রতিরোধ

    ✅ প্রতিটি অ্যাক্সেসে ownership check

    প্রতিটি object fetch/update/delete-এর আগে সার্ভার-সাইডে যাচাই করুন — "এই object-টি কি সত্যিই এই authenticated ইউজারের?" — token-এর user ID-এর সাথে object-এর owner ID মিলিয়ে।

    ✅ Indirect reference

    যেখানে সম্ভব, সরাসরি ডেটাবেজ ID expose না করে একটি session-scoped indirect reference ব্যবহার করুন, যাতে ID অনুমান করলেও সরাসরি কাজ না করে।

    অনুশীলন

    একটি hypothetical ফুড ডেলিভারি API-তে GET /api/orders/{orderId}/track endpoint আছে। এই endpoint-এ BOLA আছে কি না যাচাই করতে আপনি কী কী ধাপ অনুসরণ করবেন, তালিকা করুন (নিজের lab/অনুমোদিত স্কোপে ভেবে লিখুন, বাস্তবে কোথাও প্রয়োগ করবেন না)।

    সারসংক্ষেপ

    BOLA ঘটে যখন API একটি object ID গ্রহণ করে কিন্তু রিকোয়েস্ট পাঠানো ইউজারের সেই object-এর উপর প্রকৃত অধিকার আছে কি না যাচাই করে না। Authentication বৈধ থাকলেও এই ত্রুটি ঘটতে পারে — কারণ এটি authentication নয়, authorization-এর সমস্যা। OWASP API Top 10-এর সবচেয়ে সাধারণ ও সবচেয়ে বেশি পুরস্কৃত ক্যাটাগরি এটি।

    Broken Authentication

    যখন API-এর identity-যাচাই প্রক্রিয়া নিজেই দুর্বল — attacker অন্য ইউজার হিসেবে "হয়ে ওঠার" সুযোগ পায়।

    Broken Authentication-এর সাধারণ রূপ

    • দুর্বল টোকেন জেনারেশন: Predictable বা low-entropy session token/API key, যা brute-force বা অনুমান করা যায়।
    • Token expiration না থাকা: একবার ইস্যু হওয়া token চিরকাল বৈধ থাকলে, একটি leak হওয়া token চিরকাল ঝুঁকি তৈরি করে।
    • Credential stuffing-এ দুর্বলতা: Login endpoint-এ rate limiting বা CAPTCHA না থাকলে, leaked password list দিয়ে automated attack চালানো সহজ হয়ে যায়।
    • দুর্বল পাসওয়ার্ড/API key পলিসি: ছোট, সহজ, বা ডিফল্ট API key অনুমোদিত হওয়া।
    • JWT দুর্বলতা: আগের অধ্যায়ে আলোচিত alg:none, algorithm confusion, weak secret ইত্যাদি।

    বাস্তব উদাহরণ — Password Reset Token

    দুর্বল পাসওয়ার্ড রিসেট ফ্লো (ধারণাগত, lab-only)
    POST /api/password-reset HTTP/1.1
Content-Type: application/json

{"email":"victim@example.com"}

→ Response: {"resetToken":"482917"}   ← ৬-ডিজিটের OTP, কোনো rate limit নেই

POST /api/password-reset/confirm HTTP/1.1
{"email":"victim@example.com","token":"482917","newPassword":"Attacker123!"}

    এই উদাহরণে দুটি সমস্যা: (১) ৬-ডিজিটের OTP মাত্র ১০ লক্ষ সম্ভাবনা, যা rate-limiting ছাড়া brute-force-যোগ্য; (২) response-এ সরাসরি token ফেরত দেওয়া হচ্ছে, যা কখনোই করা উচিত নয় — token শুধু registered ইমেইল/SMS-এ পাঠানো উচিত।

    Credential Stuffing ও Rate Limiting

    যেহেতু লক্ষ লক্ষ leaked username/password combination ইন্টারনেটে পাওয়া যায়, attacker-রা প্রায়ই "credential stuffing" করেন — automated script দিয়ে হাজার হাজার জানা কম্বিনেশন একটি লগইন endpoint-এ try করা। যদি login endpoint-এ rate limiting, account lockout, বা CAPTCHA না থাকে, এই আক্রমণ সহজেই সফল হতে পারে, এমনকি সব পাসওয়ার্ড নিজে থেকে "দুর্বল" না হলেও।

    🚨

    মনে রাখবেন: Authentication endpoint (login, register, password reset, OTP verify) সাধারণত সবচেয়ে বেশি আক্রমণের লক্ষ্য হয় — কারণ সফল হলে সরাসরি অ্যাকাউন্ট টেকওভার পাওয়া যায়। এই endpoint-গুলোতে rate limiting থাকা কি না, তা যেকোনো API সিকিউরিটি রিভিউয়ের প্রথম ধাপগুলোর একটি হওয়া উচিত।

    প্রতিরোধ

    🔒 Strong token entropy

    Cryptographically random, যথেষ্ট দীর্ঘ session token/API key ব্যবহার করুন।

    ⏱️ Rate limiting

    সব authentication endpoint-এ IP/account-ভিত্তিক rate limiting ও lockout প্রয়োগ করুন।

    ⏳ Token expiration

    Short-lived access token + refresh token প্যাটার্ন ব্যবহার করুন, যাতে leak হলেও ক্ষতির পরিধি সীমিত থাকে।

    অনুশীলন

    উপরের OTP উদাহরণে, কীভাবে এই ফ্লো-টিকে নিরাপদ করা যায় তার তিনটি নির্দিষ্ট পরিবর্তন লিখুন।

    সারসংক্ষেপ

    Broken Authentication ঘটে যখন API-এর identity-যাচাই প্রক্রিয়া (token generation, password reset, rate limiting) নিজেই দুর্বল। এটি সরাসরি অ্যাকাউন্ট টেকওভারের রাস্তা খুলে দেয়, তাই authentication-সম্পর্কিত প্রতিটি endpoint বিশেষ যত্নের সাথে ডিজাইন করা উচিত।

    Broken Object Property Level Authorization — যখন API প্রয়োজনের চেয়ে বেশি ডেটা ফেরত দেয়, অথবা না-অনুমোদিত field পরিবর্তনের সুযোগ দেয়।

    Excessive Data Exposure — প্রয়োজনের চেয়ে বেশি ডেটা

    অনেক API ডেভেলপার backend-এ পুরো ডেটাবেজ object সরাসরি সিরিয়ালাইজ করে client-কে পাঠিয়ে দেন, এবং ভরসা করেন যে frontend UI শুধু প্রয়োজনীয় field-গুলো দেখাবে, বাকিগুলো লুকিয়ে রাখবে। কিন্তু attacker কখনো UI-এর মধ্য দিয়ে API কল করেন না — তিনি সরাসরি raw response দেখেন, যেখানে সব field-ই থাকে।

    Excessive Data Exposure — উদাহরণ (ধারণাগত, lab-only)
    GET /api/users/42/profile HTTP/1.1

→ Response (UI শুধু name ও avatar দেখায়, কিন্তু আসল response এরকম):
{
  "id": 42,
  "name": "Rahim Uddin",
  "avatar": "...",
  "email": "rahim@example.com",
  "passwordHash": "$2b$10$abcdef...",
  "isAdmin": false,
  "internalNotes": "flagged for refund fraud review"
}

    এই উদাহরণে passwordHash, isAdmin, এবং internalNotes — কোনোটাই UI-তে দেখানো হয় না, কিন্তু raw API response-এ উপস্থিত। এটি একটি গুরুতর তথ্য ফাঁস, এবং isAdmin-এর মতো field থাকলে পরবর্তী ধাপে mass assignment-এর জন্যও সংকেত দিতে পারে।

    Mass Assignment — না-অনুমোদিত field পরিবর্তন

    Mass assignment ঘটে যখন একটি API অটোমেটিকভাবে request body-এর সব field সরাসরি একটি object-এ bind করে দেয় (অনেক modern framework-এ ডিফল্ট আচরণ), সেই object-এর কোন কোন field ইউজারের পরিবর্তন করার অনুমতি আছে, তা allowlist না করেই।

    Mass Assignment — উদাহরণ (ধারণাগত, lab-only)
    // স্বাভাবিক প্রোফাইল আপডেট রিকোয়েস্ট
PATCH /api/users/42 HTTP/1.1
Content-Type: application/json

{"name": "Rahim Uddin", "bio": "Software Engineer"}

// attacker একটি অতিরিক্ত field যোগ করলেন, যা UI-তে কখনো দেখানো হয় না
PATCH /api/users/42 HTTP/1.1
Content-Type: application/json

{"name": "Rahim Uddin", "bio": "Software Engineer", "isAdmin": true}

→ যদি সার্ভার allowlist না করে, "isAdmin" সরাসরি আপডেট হয়ে যেতে পারে!

    এটি কীভাবে কাজ করে বোঝার জন্য: attacker অনুমান করেন backend object-এ এমন কিছু field (isAdmin, role, balance, verified) আছে, যা API response-এ হয়তো কখনো দেখানো হয়েছিল (Excessive Data Exposure থেকে পাওয়া তথ্য!) — এবং সেই field নাম অনুমান করে request body-তে যোগ করে পাঠান।

    ⚠️

    লক্ষণীয় সংযোগ: Excessive Data Exposure (একটি response-এ internal field দেখা) প্রায়ই mass assignment আবিষ্কারের প্রথম ধাপ — কারণ response-এ field নাম দেখলে attacker জানেন ঠিক কোন নাম দিয়ে request body-তে পাঠাতে হবে। এই দুটি vulnerability তাই প্রায়ই একসাথে পাওয়া যায়।

    প্রতিরোধ

    ✅ Allowlist response fields

    প্রতিটি endpoint-এ একটি নির্দিষ্ট DTO/schema দিয়ে শুধু প্রয়োজনীয় field সিরিয়ালাইজ করুন — কখনো পুরো ORM object সরাসরি পাঠাবেন না।

    ✅ Allowlist writable fields

    Update/create endpoint-এ শুধু নির্দিষ্ট, pre-approved field-গুলো বাইন্ড হতে দিন — isAdmin, role, balance-এর মতো sensitive field কখনো client input থেকে সরাসরি সেট হওয়া উচিত নয়।

    অনুশীলন

    একটি API response-এ আপনি {"id":7,"username":"nabila","role":"customer","accountBalance":500} দেখতে পেলেন একটি GET endpoint-এ। এই তথ্যের ভিত্তিতে, একটি PATCH request কীভাবে ডিজাইন করবেন mass assignment টেস্ট করার জন্য (শুধু ধারণাগতভাবে, নিজের lab-এ)?

    সারসংক্ষেপ

    Excessive Data Exposure ঘটে API response-এ প্রয়োজনের বেশি field থাকলে। Mass Assignment ঘটে request body-এর সব field অটো-বাইন্ড হলে, writable field allowlist না থাকায়। দুটোই "object property-level" authorization-এর অভাব থেকে আসে, এবং প্রায়ই একে অপরকে খুঁজে পেতে সাহায্য করে।

    Unrestricted Resource Consumption

    Rate limiting ও pagination-এর অভাব কীভাবে DoS, খরচ বিস্ফোরণ, এবং ব্রুট-ফোর্স আক্রমণের রাস্তা খুলে দেয়।

    সমস্যাটি কী

    প্রতিটি API রিকোয়েস্ট সার্ভারে কিছু না কিছু রিসোর্স ব্যবহার করে — CPU, মেমরি, ডেটাবেজ কোয়েরি, ব্যান্ডউইথ, এমনকি থার্ড-পার্টি API কল (যা টাকা খরচ করে)। যদি একটি API-তে এই ব্যবহারের কোনো সীমা (rate limit, pagination limit, request size limit) না থাকে, একজন attacker সহজেই সীমাহীন বা অস্বাভাবিক রিকোয়েস্ট পাঠিয়ে সিস্টেমকে overload করতে পারেন, অথবা সংস্থার খরচ বাড়িয়ে দিতে পারেন।

    বাস্তব রূপ

    🔢 Pagination অভাব

    একটি GET /api/products endpoint যদি লিমিট ছাড়া পুরো ডেটাবেজ একবারে ফেরত দেয়, একটি single request-ই সার্ভার মেমরি শেষ করে দিতে পারে।

    🚫 Rate limiting অভাব

    Login, OTP verify, search, বা expensive report-generation endpoint-এ rate limit না থাকলে, brute-force বা automated abuse সহজ হয়ে যায়।

    📦 Payload size সীমা অভাব

    Upload বা bulk-create endpoint-এ request body-র আকার সীমিত না থাকলে, একটি বিশাল payload পাঠিয়ে সার্ভার মেমরি/ডিস্ক শেষ করে দেওয়া সম্ভব।

    💸 থার্ড-পার্টি API কল খরচ

    যদি একটি endpoint প্রতি রিকোয়েস্টে একটি paid third-party API (যেমন SMS, email, বা AI API) কল করে এবং rate limit না থাকে, attacker সংস্থার বিল কৃত্রিমভাবে বাড়িয়ে দিতে পারেন ("Denial of Wallet")।

    GraphQL-এ বিশেষ ঝুঁকি

    আগের অধ্যায়ে উল্লেখ করা হয়েছে, GraphQL-এ nested/recursive query পাঠিয়ে একটি একক request-ই হাজার হাজার ডেটাবেজ অপারেশন ট্রিগার করতে পারে (query depth/complexity সীমা না থাকলে) — এটি resource consumption আক্রমণের একটি বিশেষভাবে শক্তিশালী রূপ।

    💡

    টেস্টিং টিপ: Rate limiting যাচাই করার সময়, শুধু "কতগুলো request block হলো" তা নয়, বরং কতক্ষণ পর আবার অনুমোদিত হলো (reset window) এবং IP-ভিত্তিক নাকি account-ভিত্তিক (একটি bypass প্রায়ই rate limit IP-ভিত্তিক হলে, একাধিক IP/proxy ব্যবহার করে এড়ানো যায়) তাও লক্ষ করুন।

    প্রতিরোধ

    • সব endpoint-এ যুক্তিসঙ্গত rate limiting (IP + account উভয় স্তরে) প্রয়োগ করুন।
    • লিস্ট-রিটার্নিং endpoint-এ বাধ্যতামূলক pagination ও সর্বোচ্চ page size নির্ধারণ করুন।
    • Request body/upload-এর জন্য যুক্তিসঙ্গত সাইজ লিমিট সেট করুন।
    • GraphQL-এ query depth ও complexity limiting প্রয়োগ করুন।

    অনুশীলন

    একটি SMS-OTP পাঠানো endpoint (POST /api/send-otp) যদি rate-limit ছাড়া থাকে, তাহলে কীভাবে এটি সংস্থার আর্থিক ক্ষতি করতে পারে তা ব্যাখ্যা করুন ("Denial of Wallet" ধারণা ব্যবহার করে)।

    সারসংক্ষেপ

    Unrestricted Resource Consumption ঘটে যখন API কোনো রিকোয়েস্ট/ডেটা/খরচের সীমা প্রয়োগ করে না। এটি শুধু availability (DoS)-কেই নয়, সরাসরি আর্থিক ক্ষতিও (Denial of Wallet) করতে পারে — তাই rate limiting, pagination ও payload-size লিমিট প্রতিটি প্রোডাকশন API-এর মৌলিক প্রয়োজনীয়তা।

    Broken Function Level Authorization (BFLA)

    BOLA যদি হয় "ভুল ব্যক্তির ডেটা দেখা", BFLA হলো "ভুল ব্যক্তির ফাংশন চালানো" — যেমন একজন সাধারণ ইউজার admin-only action সম্পন্ন করতে পারা।

    BOLA বনাম BFLA

    এই দুটি প্রায়ই গুলিয়ে ফেলা হয়, কিন্তু পার্থক্যটা গুরুত্বপূর্ণ:

    BOLA (API1)BFLA (API5)
    প্রশ্ন"এই নির্দিষ্ট object-টি কি আমার?""এই action/endpoint-টি চালানোর অনুমতি কি আমার আছে?"

    Undocumented/Hidden Admin Endpoint

    অনেক সময় admin panel-এর জন্য আলাদা API endpoint তৈরি করা হয় (/api/admin/*), যেগুলো public documentation-এ উল্লেখ নেই — কিন্তু frontend JS bundle বা mobile app-এর ভেতরে স্ট্রিং হিসেবে endpoint path লুকানো থাকে। সঠিক role check না থাকলে, এই endpoint-গুলো URL অনুমান করেই (JS bundle analyze করে, বা common path wordlist দিয়ে) অ্যাক্সেস করা যেতে পারে।

    HTTP Method-ভিত্তিক BFLA

    একটি কমন প্যাটার্ন: একই endpoint-এ GET (read) সুরক্ষিত, কিন্তু DELETE/PUT (write) method-এ role check বাদ পড়ে গেছে — বা উল্টোটা। তাই BFLA টেস্ট করার সময় একই URL-এ সব HTTP method আলাদাভাবে চেক করা জরুরি।

    ⚠️

    টেস্টিং পদ্ধতি: Admin role-এর একটি অ্যাকাউন্ট দিয়ে Burp Suite-এর মতো proxy টুলে সব endpoint ক্যাপচার করুন, তারপর একই রিকোয়েস্টগুলো একটি সাধারণ (non-admin) ইউজারের টোকেন দিয়ে replay করুন (শুধু নিজের lab/অনুমোদিত স্কোপে) — যদি response একই রকম সফল হয়, সেটি BFLA।

    প্রতিরোধ

    ✅ Centralized authorization middleware

    প্রতিটি endpoint-এ স্বতন্ত্রভাবে role check লেখার বদলে, একটি কেন্দ্রীয় middleware/policy ইঞ্জিন ব্যবহার করুন, যা deny-by-default নীতি মেনে চলে।

    ✅ Deny by default

    নতুন endpoint তৈরি হলে, স্পষ্টভাবে অনুমতি না দেওয়া পর্যন্ত ডিফল্ট আচরণ হওয়া উচিত "প্রত্যাখ্যান", "অনুমোদন" নয়।

    অনুশীলন

    একটি API-তে GET /api/admin/reports সুরক্ষিত (403 দেয় non-admin-এর জন্য), কিন্তু POST /api/admin/reports/generate সুরক্ষিত নয়। এই অসঙ্গতির সম্ভাব্য কারণ কী হতে পারে বলে মনে করেন?

    সারসংক্ষেপ

    BFLA ঘটে যখন একটি নির্দিষ্ট ফাংশন/action-level অনুমতি (সাধারণত role-ভিত্তিক) ঠিকভাবে যাচাই করা হয় না। BOLA object-level, BFLA function/role-level — দুটোই authorization-এর অভাব, কিন্তু আলাদা স্তরে কাজ করে এবং আলাদাভাবে টেস্ট করতে হয়।

    Knowledge-check

    1. BOLA ও BFLA-এর মধ্যে মূল পার্থক্য কী?
    2. একই endpoint-এ ভিন্ন HTTP method-এ ভিন্ন authorization থাকতে পারে কেন?
    3. "Deny by default" নীতি কীভাবে BFLA প্রতিরোধে সাহায্য করে?

    Business Flow Abuse ও SSRF ঝুঁকি

    যখন সঠিক authentication ও authorization থাকার পরও, business logic নিজেই অপব্যবহারযোগ্য — এবং যখন API নিজেই একটি আক্রমণের মাধ্যম হয়ে ওঠে।

    Unrestricted Access to Sensitive Business Flows (API6)

    এই ক্যাটাগরি অন্যগুলোর থেকে আলাদা — এখানে কোনো "technical bug" নেই, authentication/authorization সব ঠিক আছে, কিন্তু একটি legitimate business flow-কে automation/bot দিয়ে অস্বাভাবিক স্কেলে অপব্যবহার করা হয়।

    🎫 Ticket Scalping

    একটি bot concert ticket booking API-কে এত দ্রুত কল করে যে, কয়েক সেকেন্ডেই সব টিকিট কিনে ফেলে, সাধারণ মানুষের কেনার সুযোগ না দিয়ে।

    🎁 Promo Code Abuse

    একটি নতুন ইউজারের জন্য "first order discount" endpoint-কে বারবার নতুন (fake) অ্যাকাউন্ট তৈরি করে বারবার ব্যবহার করা।

    📊 Bulk Scraping

    Product listing/pricing API-কে স্বয়ংক্রিয়ভাবে বারবার কল করে পুরো ক্যাটালগ স্ক্র্যাপ করা, প্রতিযোগী ব্যবসার জন্য।

    এই ধরনের অপব্যবহার প্রতিরোধ করা প্রযুক্তিগতভাবে কঠিন, কারণ প্রতিটি individual request সম্পূর্ণ বৈধ দেখায় — পার্থক্যটা বোঝা যায় শুধু pattern ও স্কেল দেখে (একটি একক IP/ডিভাইস থেকে অস্বাভাবিক গতিতে একই action বারবার)।

    Server Side Request Forgery — SSRF (API7)

    SSRF ঘটে যখন একটি API server-কে প্রতারিত করে এমন একটি HTTP request পাঠাতে বাধ্য করা হয়, যা attacker নির্ধারণ করেন — সাধারণত সেই সার্ভারের internal নেটওয়ার্ক বা localhost-এর দিকে, যেখানে বাইরে থেকে সরাসরি অ্যাক্সেস করা যায় না।

    SSRF — ক্লাসিক উদাহরণ (ধারণাগত, lab-only)
    // একটি "URL থেকে প্রোফাইল ছবি ইম্পোর্ট" ফিচার
POST /api/users/profile-image-from-url HTTP/1.1
Content-Type: application/json

{"imageUrl": "https://example.com/photo.jpg"}   ← স্বাভাবিক ব্যবহার

// attacker যদি internal URL পাঠান
{"imageUrl": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"}
                     ↑ cloud metadata endpoint — AWS/GCP/Azure credential leak-এর
                       একটি সুপরিচিত SSRF লক্ষ্যবস্তু

    যদি সার্ভার এই URL-টি নিজে fetch করে (যেমন ছবি ডাউনলোড করার জন্য), এবং সার্ভারটি একটি cloud পরিবেশে চলে, তাহলে attacker সরাসরি cloud IAM credential চুরি করতে পারেন — যা দিয়ে পুরো cloud অ্যাকাউন্ট compromise হতে পারে। এটি SSRF-কে সবচেয়ে বিপজ্জনক vulnerability ক্যাটাগরিগুলোর একটি করে তোলে।

    SSRF কোথায় সাধারণত পাওয়া যায়

    • Webhook URL কনফিগারেশন (ইউজার নিজের webhook endpoint সেট করতে পারেন)
    • "URL থেকে ফাইল ইম্পোর্ট" বা "লিংক প্রিভিউ" ফিচার
    • PDF/document generation (যা external resource fetch করে)
    • থার্ড-পার্টি API ইন্টিগ্রেশন, যেখানে endpoint URL ইউজার কনফিগার করতে পারেন
    🚨

    প্রতিরোধ: যদি কোনো ফিচারে সার্ভারকে user-supplied URL fetch করতে হয়, একটি কঠোর allowlist (শুধু নির্দিষ্ট ডোমেইন/প্রোটোকল) ব্যবহার করুন, internal/private IP range (127.0.0.1, 169.254.x.x, 10.x.x.x, 192.168.x.x) ব্লক করুন, এবং DNS rebinding-এর মতো bypass কৌশল মাথায় রেখে redirect-ও যাচাই করুন।

    অনুশীলন

    একটি API-তে "Slack-এ নোটিফিকেশন পাঠান" ফিচার আছে, যেখানে ইউজার নিজের Slack webhook URL দিতে পারেন। এই ফিচারটি কীভাবে SSRF-এর জন্য অপব্যবহার হতে পারে, এবং এটি প্রতিরোধে কী allowlist নীতি প্রযোজ্য হতে পারে, লিখুন।

    সারসংক্ষেপ

    Business flow abuse প্রমাণ করে যে সব vulnerability "technical bug" নয় — কখনো কখনো legitimate ফাংশনকে স্কেলে অপব্যবহার করাই সমস্যা। SSRF ঘটে যখন সার্ভার নিজে attacker-নিয়ন্ত্রিত URL-এ রিকোয়েস্ট পাঠায়, যা cloud পরিবেশে অত্যন্ত বিপজ্জনক হতে পারে।

    Knowledge-check

    1. কেন business flow abuse প্রতিরোধ করা প্রযুক্তিগতভাবে কঠিন?
    2. SSRF-এ 169.254.169.254 ঠিকানাটি কেন বিশেষভাবে গুরুত্বপূর্ণ টার্গেট?
    3. SSRF প্রতিরোধে allowlist পদ্ধতি কেন blocklist-এর চেয়ে বেশি নির্ভরযোগ্য?

    Security Misconfiguration

    সঠিক কোড লেখা হলেও, ভুল কনফিগারেশন একটি সুরক্ষিত API-কেও সহজেই vulnerable করে তুলতে পারে।

    CORS ভুল কনফিগারেশন

    CORS (Cross-Origin Resource Sharing) নির্ধারণ করে কোন ডোমেইন থেকে browser-ভিত্তিক JavaScript একটি API কল করতে পারবে। একটি সাধারণ ভুল হলো Access-Control-Allow-Origin: * সেট করা, বিশেষ করে Access-Control-Allow-Credentials: true-এর সাথে একসাথে — যা তাত্ত্বিকভাবে যেকোনো ওয়েবসাইটকে, ভিকটিমের ব্রাউজার থেকে, ভিকটিমের credential-সহ, সেই API কল করার অনুমতি দিয়ে দেয়।

    বিপজ্জনক CORS কনফিগারেশন (ধারণাগত)
    Access-Control-Allow-Origin: https://evil-attacker.example
Access-Control-Allow-Credentials: true

← সার্ভার request-এর Origin header reflect করে দিচ্ছে, যাচাই না করেই।
   যেকোনো ডোমেইন থেকে credential-সহ cross-origin request সফল হবে।

    অপ্রয়োজনীয় HTTP মেথড সক্রিয় থাকা

    Web server/framework-এর ডিফল্ট কনফিগারেশনে প্রায়ই TRACE, OPTIONS, বা এমনকি PUT/DELETE মেথড সক্রিয় থাকে, যদিও সেগুলো ব্যবহারের প্রয়োজন নেই। প্রতিটি অব্যবহৃত মেথড একটি অতিরিক্ত attack surface।

    ভার্বোজ Error Message

    Development পরিবেশে debug করার সুবিধার জন্য প্রায়ই পূর্ণ stack trace, ডেটাবেজ query, বা internal file path error response-এ দেখানো হয় — কিন্তু production-এ এটি একই রকম রয়ে গেলে, attacker সরাসরি internal আর্কিটেকচার, লাইব্রেরি ভার্সন, এমনকি SQL query গঠন সম্পর্কে তথ্য পেয়ে যান।

    ভার্বোজ error — উদাহরণ (ধারণাগত)
    HTTP/1.1 500 Internal Server Error
{
  "error": "SequelizeDatabaseError: column \"usr_eml\" does not exist",
  "stack": "at Query.run (/app/node_modules/sequelize/lib/dialects/postgres/query.js:76:25)...",
  "sql": "SELECT * FROM users WHERE usr_eml = '...'"
}

    Missing Security Headers ও Default Credentials

    • Security header অনুপস্থিতি: Content-Security-Policy, X-Content-Type-Options, Strict-Transport-Security ইত্যাদি API response-এও গুরুত্বপূর্ণ (বিশেষ করে যদি response কখনো browser-এ সরাসরি রেন্ডার হয়)।
    • Default credential: Admin panel/internal tool-এ ডিফল্ট username/password (যেমন admin/admin) বদলানো হয়নি।
    • Outdated software/dependency: পুরনো, known-vulnerable লাইব্রেরি বা framework ভার্সন চালু রাখা।
    • Directory listing সক্রিয় থাকা: ভুলবশত সার্ভার কনফিগারেশন ফাইল লিস্টিং expose করা।
    💡

    কেন এই ক্যাটাগরি গুরুত্বপূর্ণ: Security misconfiguration-এর বেশিরভাগই কোনো জটিল কোডিং ত্রুটি নয় — বরং "ডিফল্ট সেটিংস পরিবর্তন করা হয়নি" ধরনের ভুল। এগুলো খুঁজে পাওয়া তুলনামূলক সহজ (তাই bug bounty-তে কম পুরস্কৃত হয়), কিন্তু production checklist থেকে বাদ পড়লে গুরুতর প্রভাব ফেলতে পারে।

    অনুশীলন

    উপরের CORS কনফিগারেশন উদাহরণটি দেখুন — এটি কেন বিশেষভাবে বিপজ্জনক তা Access-Control-Allow-Credentials: true অংশটি বিবেচনা করে ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Security Misconfiguration এমন একটি ক্যাটাগরি, যেখানে কোডের লজিক সঠিক হলেও ডিপ্লয়মেন্ট/কনফিগারেশন ভুল গুরুতর ঝুঁকি তৈরি করে — ভুল CORS, ভার্বোজ error, অপ্রয়োজনীয় HTTP method, ডিফল্ট credential। একটি নিয়মিত production security checklist এই সমস্যাগুলোর বেশিরভাগই প্রতিরোধ করতে পারে।

    Knowledge-check

    1. Access-Control-Allow-Origin: * এবং Access-Control-Allow-Credentials: true একসাথে কেন বিপজ্জনক?
    2. Production-এ ভার্বোজ error message দেখালে attacker কী ধরনের সুবিধা পান?
    3. Security misconfiguration bug bounty-তে তুলনামূলক কম পুরস্কৃত হয় কেন বলে মনে করেন?

    Shadow API, Improper Inventory ও Unsafe Consumption

    যে API-গুলোর অস্তিত্ব সম্পর্কে সংস্থা নিজেই অবগত নয় — এবং যখন একটি API অন্য থার্ড-পার্টি API-কে অন্ধভাবে বিশ্বাস করে।

    Improper Inventory Management (API9)

    বড় সংস্থায় সময়ের সাথে API-এর অনেক ভার্সন তৈরি হয় — v1, v2, v3, স্টেজিং এনভায়রনমেন্ট, পার্টনার-নির্দিষ্ট endpoint, ডেপ্রিকেটেড ফিচার। যদি পুরনো ভার্সন ঠিকভাবে বন্ধ (decommission) না করা হয়, সেগুলো ইন্টারনেটে চালু থেকে যায় — প্রায়ই নতুন ভার্সনের মতো একই নিরাপত্তা প্যাচ ও মনিটরিং ছাড়াই।

    👻 Shadow API

    Documentation-এ নেই এমন API — হয়তো একটি দ্রুত পরীক্ষামূলক ফিচারের জন্য তৈরি হয়েছিল, কখনো আনুষ্ঠানিকভাবে ট্র্যাক করা হয়নি, কিন্তু এখনও প্রোডাকশনে চালু।

    🧟 Zombie API

    পুরনো, deprecated ভার্সন (যেমন /api/v1/), যা নতুন /api/v3/ চালু হওয়ার পরেও বন্ধ করা হয়নি — এবং প্রায়ই v1-এ এমন সব bug ফিক্স করা হয়নি, যা v3-এ ইতিমধ্যে সারানো হয়েছে।

    Attacker-রা প্রায়ই একটি অ্যাপের সাম্প্রতিক ভার্সন টেস্ট করার আগে, পুরনো API ভার্সন (v1, v0, beta, internal) আছে কি না তা চেক করেন — কারণ এগুলোতে প্রায়ই দুর্বলতর সিকিউরিটি কন্ট্রোল থাকে, একই ডেটাবেজে অ্যাক্সেসসহ।

    পুরনো API ভার্সন খোঁজা (ধারণাগত টেস্টিং আইডিয়া)

    Unsafe Consumption of APIs (API10)

    আধুনিক অ্যাপ্লিকেশন প্রায়ই নিজেরাও অন্য থার্ড-পার্টি API ব্যবহার করে (পেমেন্ট গেটওয়ে, ম্যাপ সার্ভিস, AI API, শিপিং পার্টনার)। অনেক ডেভেলপার ধরে নেন "থার্ড-পার্টি API মানেই বিশ্বস্ত সোর্স", এবং তাদের response যাচাই ছাড়াই সরাসরি প্রসেস করেন বা ব্যবহারকারীর কাছে ফরওয়ার্ড করেন — এটিই Unsafe Consumption।

    • Response ভ্যালিডেশন ছাড়া trust: থার্ড-পার্টি API থেকে আসা ডেটা সরাসরি ডেটাবেজে সেভ করা বা ব্যবহারকারীকে দেখানো, sanitize/validate না করেই — যদি সেই থার্ড-পার্টি compromise হয়, সেই দূষিত ডেটা আপনার সিস্টেমেও প্রবেশ করবে।
    • Redirect-এর উপর অন্ধ বিশ্বাস: একটি থার্ড-পার্টি API redirect URL ফেরত দিলে তা যাচাই ছাড়া follow করা (open redirect/SSRF-এর সংযোগস্থল)।
    • কম সুরক্ষিত ইন্টিগ্রেশন চ্যানেল: থার্ড-পার্টি API-এর সাথে যোগাযোগে TLS যাচাই বা authentication দুর্বল রাখা, কারণ "এটা তো শুধু internal integration"।
    ⚠️

    মূলনীতি: যেকোনো external ইনপুট — তা একজন ইউজার পাঠাক, বা একটি "বিশ্বস্ত" থার্ড-পার্টি API — একই নিয়মে validate/sanitize করা উচিত। "এটা আমাদের নিজস্ব পার্টনার API" এই ধারণা কখনোই ইনপুট ভ্যালিডেশন বাদ দেওয়ার যুক্তি হতে পারে না।

    অনুশীলন

    সারসংক্ষেপ

    Improper Inventory Management ঘটে পুরনো/undocumented API ভার্সন চালু থেকে গেলে — এগুলো প্রায়ই সবচেয়ে দুর্বল entry point। Unsafe Consumption ঘটে যখন থার্ড-পার্টি API-কে অন্ধভাবে বিশ্বাস করা হয়, তাদের response যাচাই ছাড়াই। উভয় ক্ষেত্রেই মূল শিক্ষা — "পরিচিত/অভ্যন্তরীণ" মানেই নিরাপদ নয়।

    Postman, Burp Suite ও OWASP ZAP দিয়ে কীভাবে ম্যানুয়াল API সিকিউরিটি টেস্টিং করা হয়, এবং অনুশীলনের জন্য কোথায় নিরাপদে প্র্যাকটিস করবেন।

    Postman — API Exploration ও ম্যানুয়াল টেস্টিং

    Postman একটি GUI টুল, যা দিয়ে সহজে API request তৈরি, সংরক্ষণ ও পুনরায় পাঠানো যায়। API সিকিউরিটি টেস্টিংয়ে Postman বিশেষভাবে উপযোগী, যখন একটি API-এর OpenAPI/Swagger স্পেক পাওয়া যায় — Postman সরাসরি সেই স্পেক ইম্পোর্ট করে সব endpoint-এর একটি collection তৈরি করে দিতে পারে, যা ম্যানুয়ালি প্রতিটি endpoint খুঁজে বের করার চেয়ে অনেক দ্রুত।

    Environment Variables

    একাধিক ইউজারের token (admin, regular user, user A, user B) আলাদা environment variable হিসেবে সংরক্ষণ করুন — BOLA/BFLA টেস্ট করার সময় দ্রুত একটি থেকে আরেকটিতে সুইচ করতে সাহায্য করে।

    Collection Runner

    একটি সম্পূর্ণ collection একসাথে চালিয়ে, বিভিন্ন টোকেন দিয়ে systematic authorization টেস্ট অটোমেট করা যায়।

    Burp Suite — Intercepting Proxy দিয়ে গভীর টেস্টিং

    Burp Suite-এর Proxy ফিচার দিয়ে mobile app বা SPA থেকে যাওয়া প্রতিটি API রিকোয়েস্ট intercept, পরিবর্তন ও replay করা যায় — এটিই BOLA, mass assignment, BFLA-এর মতো vulnerability টেস্ট করার মূল পদ্ধতি।

    🔁 Repeater

    একটি নির্দিষ্ট রিকোয়েস্ট বারবার সামান্য পরিবর্তন করে পাঠানো — যেমন object ID বা একটি field পরিবর্তন করে response তুলনা করা।

    🎯 Intruder

    একটি request-এর নির্দিষ্ট অংশে automated payload list পাঠানো — যেমন sequential ID range টেস্ট করার জন্য, বা rate limiting যাচাইয়ের জন্য।

    📜 Logger / HTTP History

    একটি mobile app ব্যবহারের সময় কোন কোন API কল হচ্ছে তা পুরোপুরি ক্যাপচার করে, পরে বিশ্লেষণ করা।

    OWASP ZAP

    Burp Suite-এর একটি ফ্রি, ওপেন-সোর্স বিকল্প — একই ধরনের intercepting proxy ও automated scanning ফিচার দেয়, যা API endpoint স্ক্যান করে কিছু common misconfiguration (যেমন missing security header) স্বয়ংক্রিয়ভাবে ধরতে পারে।

    JWT বিশ্লেষণের জন্য টুল

    JWT-এর header/payload দ্রুত ডিকোড ও বিশ্লেষণ করার জন্য jwt.io-এর মতো টুল ব্যবহার করা যায় (অফলাইন/নিজস্ব instance ব্যবহার করুন sensitive টোকেনের ক্ষেত্রে) — এটি দিয়ে algorithm, expiration, ও payload field দ্রুত পরীক্ষা করা যায়।

    API সিকিউরিটি টেস্টিংয়ের সাধারণ workflow

    1. Reconnaissance: টার্গেট API-এর সব endpoint ম্যাপ করুন — public documentation, Swagger/OpenAPI স্পেক, mobile app-এর JS bundle বিশ্লেষণ করে।
    2. Authentication বোঝা: API Key/OAuth/JWT কোনটি ব্যবহৃত হচ্ছে, এবং টোকেনের গঠন/scope কেমন তা নোট করুন।
    3. একাধিক টেস্ট অ্যাকাউন্ট তৈরি: ন্যূনতম দুটি ভিন্ন role/ইউজারের অ্যাকাউন্ট তৈরি করুন — cross-account টেস্টিংয়ের (BOLA/BFLA) জন্য অপরিহার্য।
    4. OWASP Top 10 চেকলিস্ট অনুসরণ করুন: প্রতিটি endpoint-এ BOLA, mass assignment, rate limiting, BFLA — পদ্ধতিগতভাবে যাচাই করুন।
    5. Impact নথিভুক্ত করুন: শুধু "bug আছে" তা নয়, কী ধরনের ডেটা/action এর মাধ্যমে প্রভাবিত হয়, তা স্পষ্টভাবে লিখুন।

    প্রশ্ন ১ — পরিস্থিতি বিশ্লেষণ

    একটি API endpoint GET /api/invoices/{id}/download একটি PDF ফাইল ফেরত দেয়। এটি authentication যাচাই করে (401 ছাড়া কল করা যায় না), কিন্তু অন্য কোনো চেক করে না। এটি কোন ক্যাটাগরির ঝুঁকি, এবং কীভাবে টেস্ট করবেন?

    প্রশ্ন ২ — কোড রিভিউ

    একটি endpoint-এর response-এ {"id":5,"name":"Fatima","role":"support_agent","internalId":"EMP-0219"} পাওয়া গেল, যদিও UI শুধু নাম দেখায়। একই endpoint-এ PATCH request পাঠানো যায়। এই পরিস্থিতিতে কোন দুটি ভিন্ন OWASP ক্যাটাগরির ঝুঁকি একসাথে বিবেচনা করা উচিত?

    প্রশ্ন ৩ — ডিজাইন রিভিউ

    একটি নতুন ফিচার ডিজাইন করা হচ্ছে, যেখানে ইউজার একটি external RSS feed URL দিতে পারবেন এবং সার্ভার সেটি periodically fetch করে সামারি দেখাবে। এই ফিচার ডিজাইনে কোন ঝুঁকি মাথায় রাখা উচিত এবং কীভাবে তা প্রশমন করবেন?

    একটি কার্যকর API bug bounty workflow হলো — পদ্ধতিগত reconnaissance, একাধিক টেস্ট অ্যাকাউন্ট দিয়ে OWASP Top 10 চেকলিস্ট অনুসরণ, এবং clear, reproducible, impact-ফোকাসড রিপোর্টিং। দায়িত্বশীল disclosure সবসময় স্কোপ ও নৈতিকতার সীমার মধ্যে থাকা উচিত।

    BOLABroken Object Level Authorization — অন্যের object-এ অননুমোদিত অ্যাক্সেস

    Shadow APIDocumentation-এ নেই এমন undocumented, কিন্তু চালু থাকা API

    Rate Limitingনির্দিষ্ট সময়ে একটি client কতগুলো রিকোয়েস্ট পাঠাতে পারবে তার সীমা

    CORSCross-Origin Resource Sharing — কোন ডোমেইন থেকে browser API কল করতে পারবে তার নিয়ম

    প্রায়ই জিজ্ঞাসিত প্রশ্ন (FAQ)

    API সিকিউরিটি শেখার আগে কি ওয়েব অ্যাপ্লিকেশন ফান্ডামেন্টালস জানা জরুরি?

    হ্যাঁ, অত্যন্ত সহায়ক। HTTP, client-server মডেল, authentication/session-এর মৌলিক ধারণা না থাকলে এই ডকুমেন্টেশনের অনেক অংশ বুঝতে কষ্ট হতে পারে। learn.alamincyber.com-এর Web Application Fundamentals ডকুমেন্টেশনটি আগে পড়ে নেওয়ার পরামর্শ দেওয়া হয়।

    BOLA আর IDOR কি একই জিনিস?

    মূলত হ্যাঁ — BOLA হলো IDOR-এর আধুনিক, API-নির্দিষ্ট নামকরণ (OWASP API Security Top 10-এ ব্যবহৃত)। ধারণাগতভাবে একই: ভুল object ID দিয়ে অননুমোদিত অ্যাক্সেস।

    GraphQL কি REST-এর চেয়ে বেশি নিরাপদ নাকি কম?

    কোনোটিই স্বাভাবিকভাবে বেশি নিরাপদ নয় — উভয়েই একই ধরনের authorization ভুলের শিকার হতে পারে। তবে GraphQL-এর flexible query structure অতিরিক্ত ঝুঁকি (nested query abuse, query complexity) যোগ করে, যা সঠিকভাবে ডিজাইন ও limit না করলে সমস্যা তৈরি করতে পারে।

    আমি কি আমার নিজের তৈরি API নিজেই টেস্ট করতে পারি?

    অবশ্যই — নিজের তৈরি বা নিজের মালিকানাধীন API যেকোনো সময় টেস্ট করা সম্পূর্ণ বৈধ। অনুমতির প্রশ্ন আসে তখনই, যখন অন্য কারো মালিকানাধীন সিস্টেম টেস্ট করতে চান — তখন লিখিত অনুমতি বা bug bounty স্কোপ আবশ্যক।

    API সিকিউরিটি শেখার পর পরবর্তী ধাপ কী?

    OWASP crAPI/VAmPI-এর মতো প্ল্যাটফর্মে নিয়মিত হাতে-কলমে প্র্যাকটিস করুন, PortSwigger Web Security Academy-এর API/GraphQL ল্যাবগুলো সম্পন্ন করুন, এবং ধীরে ধীরে পাবলিক bug bounty প্রোগ্রামের API স্কোপে (যেখানে স্পষ্ট অনুমতি আছে) অংশগ্রহণ শুরু করুন।

    চূড়ান্ত মনে রাখার কথা

    API সিকিউরিটির প্রায় সব ঝুঁকিই একটি মূল সত্যে ফিরে যায়: authentication থাকা মানেই authorization নিশ্চিত নয়। প্রতিটি object, property ও function-level-এ আলাদা করে "এই নির্দিষ্ট ইউজারের এটি করার অধিকার আছে কি না" যাচাই করাই সবচেয়ে গুরুত্বপূর্ণ নীতি — এবং সবসময় দায়িত্বশীলভাবে, অনুমোদিত স্কোপের মধ্যে থেকে এই জ্ঞান প্রয়োগ করুন।
