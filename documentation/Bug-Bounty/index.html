    Bug Bounty Methodology ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি গাইড — কীভাবে একজন বাগ বাউন্টি হান্টার একটি প্রোগ্রাম বেছে নেন, scope বোঝেন, systematically reconnaissance ও টেস্টিং করেন, এবং একটি পেশাদার, গ্রহণযোগ্য রিপোর্ট তৈরি করেন — ১৫টি অধ্যায়ে সাজানো।

    Bug Bounty Methodology নিয়ে সংক্ষিপ্ত কথা

    এই সিরিজের আগের ডকুমেন্টেশনগুলোতে (XSS, CSRF, SQLi, API Security, Common Web Vulnerabilities, Hacking Tools) আমরা কী কী দুর্বলতা থাকে এবং কোন টুল ব্যবহার করতে হয় তা শিখেছি। এই ডকুমেন্টেশনটি ভিন্ন প্রশ্নের উত্তর দেয় — একজন পেশাদার বাগ বাউন্টি হান্টার কীভাবে, কোন ধাপে, কোন পদ্ধতিতে কাজ করেন, যাতে এলোমেলোভাবে না খুঁজে একটি সংগঠিত, পুনরাবৃত্তিযোগ্য পদ্ধতি অনুসরণ করা যায়।

    এখানে ধাপে ধাপে দেখানো হয়েছে — একটি প্রোগ্রাম নির্বাচন ও scope বিশ্লেষণ, reconnaissance ও subdomain enumeration, content discovery, একটি অ্যাটাক সারফেস ম্যাপিং, ম্যানুয়াল ও API টেস্টিং পদ্ধতি, automation ও স্ক্রিপ্টিং, vulnerability triage ও priority নির্ধারণ, Proof of Concept তৈরি, রিপোর্ট লেখার কৌশল, এবং responsible disclosure workflow।

    Bug Bounty কী

    Bug Bounty Program একটি প্রতিষ্ঠানের আনুষ্ঠানিক উদ্যোগ, যেখানে তারা স্বাধীন নিরাপত্তা গবেষকদের (hunters) আমন্ত্রণ জানায় তাদের সিস্টেমে দুর্বলতা খুঁজে বের করতে, এবং বৈধ, গ্রহণযোগ্য রিপোর্টের বিনিময়ে স্বীকৃতি বা আর্থিক পুরস্কার প্রদান করে। এটি Hacking Tools ডকুমেন্টেশনে আলোচিত এথিক্যাল হ্যাকিং-এর একটি সুনির্দিষ্ট, কাঠামোবদ্ধ রূপ।

    বাগ বাউন্টির সুবিধা — উভয় পক্ষের জন্য

    কেন "Methodology" গুরুত্বপূর্ণ

    একজন নতুন হান্টার প্রায়ই এলোমেলোভাবে একটি টার্গেটে "কিছু খোঁজার চেষ্টা" করেন — এটি অদক্ষ ও হতাশাজনক। একজন অভিজ্ঞ হান্টার একটি সংগঠিত, পুনরাবৃত্তিযোগ্য পদ্ধতি অনুসরণ করেন — recon থেকে report পর্যন্ত — যা প্রতিটি টার্গেটে সামঞ্জস্যপূর্ণভাবে প্রয়োগ করা যায়, কোনো গুরুত্বপূর্ণ ধাপ মিস না করে।

    💡

    এই ডকুমেন্টেশনের লক্ষ্য: প্রতিটি পরবর্তী অধ্যায়ে একটি নির্দিষ্ট ধাপ আলোচনা করা হবে — scope বোঝা থেকে শুরু করে, recon, টেস্টিং, এবং সবশেষে রিপোর্ট লেখা পর্যন্ত — যাতে একটি সম্পূর্ণ, বাস্তব-জগতের ওয়ার্কফ্লো তৈরি হয়।

    সারসংক্ষেপ

    Bug Bounty প্রোগ্রাম প্রতিষ্ঠানগুলোকে বিশ্বব্যাপী গবেষকদের থেকে ক্রমাগত, ফলাফল-ভিত্তিক নিরাপত্তা টেস্টিং পেতে সাহায্য করে। একজন সফল হান্টারের জন্য একটি সংগঠিত methodology — এলোমেলো চেষ্টার বদলে ধাপে ধাপে recon থেকে report পর্যন্ত একটি পুনরাবৃত্তিযোগ্য প্রক্রিয়া — অপরিহার্য।

    Program Selection ও Scope বিশ্লেষণ

    কোনো টেস্টিং শুরু করার আগে সবচেয়ে গুরুত্বপূর্ণ ধাপ — এবং সবচেয়ে বেশি অবহেলিত ধাপ।

    ⚖️

    আইনি নোটিশ: Scope ভুল বোঝা বা উপেক্ষা করা একজন হান্টারের সবচেয়ে বড় আইনি ঝুঁকি — scope-এর বাইরে টেস্ট করলে, এমনকি অনিচ্ছাকৃতভাবে হলেও, তা অননুমোদিত অ্যাক্সেস হিসেবে বিবেচিত হতে পারে।

    একটি প্রোগ্রাম নির্বাচন করার মানদণ্ড

    📊 প্রোগ্রামের কার্যকলাপ

    সাম্প্রতিক response time, resolved reports-এর সংখ্যা — একটি সক্রিয়, দ্রুত-সাড়া দেওয়া প্রোগ্রাম কাজ করার জন্য বেশি উপযোগী।

    🎯 আপনার দক্ষতার সাথে মিল

    যদি আপনি API টেস্টিং-এ দক্ষ হন, একটি বড় REST API scope-যুক্ত প্রোগ্রাম বেছে নেওয়া ভালো — নিজের শক্তির জায়গায় কাজ করুন।

    Scope Document-এর মূল উপাদান

    উপাদানকী বোঝায়
    In-Scope Assetsকোন কোন ডোমেইন, সাবডোমেইন, অ্যাপ, API টেস্ট করা অনুমোদিত
    Out-of-Scopeস্পষ্টভাবে বাদ দেওয়া সিস্টেম (প্রায়ই থার্ড-পার্টি ইন্টিগ্রেশন)
    Allowed Vulnerability Typesকোন ধরনের দুর্বলতা গ্রহণযোগ্য (অনেক প্রোগ্রাম কিছু ক্যাটাগরি, যেমন rate-limiting issue, বাদ দেয়)
    Testing Restrictionsনিষিদ্ধ কৌশল — যেমন automated scanning সীমিত/নিষিদ্ধ, social engineering নিষিদ্ধ
    Safe Harborscope-এর মধ্যে থেকে, নিয়ম মেনে টেস্ট করলে আইনি সুরক্ষার প্রতিশ্রুতি
    একটি Scope ঘোষণার ধারণাগত উদাহরণ
    In-Scope:   *.example.com, api.example.com
Out-of-Scope: blog.example.com (third-party hosted), status.example.com
Testing Restrictions: কোনো automated DoS-style scanning নয়

    Wildcard Scope বোঝা

    অনেক প্রোগ্রাম wildcard scope ব্যবহার করে, যেমন *.example.com — এর মানে example.com-এর যেকোনো সাবডোমেইন in-scope। এটি অধ্যায় ৪-এ আলোচিত subdomain enumeration-কে একটি গুরুত্বপূর্ণ ধাপ করে তোলে, কারণ wildcard scope-এর অধীনে একটি কম পরিচিত সাবডোমেইনও বৈধ টার্গেট হতে পারে।

    সাধারণ Out-of-Scope আইটেম

    • Third-party সার্ভিস (যেমন একটি embedded payment widget, যা ভিন্ন কোম্পানির)
    • Denial of Service (DoS) ধরনের টেস্টিং, যা সার্ভিস ব্যাহত করতে পারে
    • Social Engineering ও Physical Security টেস্টিং, যদি না স্পষ্টভাবে অনুমোদিত
    • পুরনো/deprecated সাবডোমেইন, যা স্পষ্টভাবে বাদ দেওয়া আছে

    "Scope creep" থেকে সতর্ক থাকুন: একটি in-scope অ্যাপ্লিকেশনের মধ্যে একটি লিংক পেয়ে, সেই লিংক অনুসরণ করে একটি সম্পূর্ণ ভিন্ন, out-of-scope ডোমেইনে চলে যাওয়া এবং সেখানে টেস্ট চালিয়ে যাওয়া একটি সাধারণ ভুল — প্রতিটি পদক্ষেপে বর্তমান টার্গেট scope-এর মধ্যে আছে কি না তা পুনরায় নিশ্চিত করা জরুরি।

    অনুশীলন

    একটি জনপ্রিয় বাগ বাউন্টি প্ল্যাটফর্মে গিয়ে একটি পাবলিক প্রোগ্রাম বেছে নিন এবং তার scope document সম্পূর্ণ পড়ুন — in-scope, out-of-scope, এবং testing restrictions আলাদা করে নোট করুন।

    সারসংক্ষেপ

    কোনো টেস্টিং শুরুর আগে scope document সম্পূর্ণ পড়া ও বোঝা অপরিহার্য — in-scope/out-of-scope assets, অনুমোদিত vulnerability type, ও testing restrictions জানা থাকতে হবে। Wildcard scope-এর অধীনে কম পরিচিত সাবডোমেইনও বৈধ টার্গেট হতে পারে।

    Reconnaissance Methodology

    একটি টার্গেট সম্পর্কে যতটা সম্ভব তথ্য সংগ্রহ করা — একজন ভালো হান্টারকে একজন গড় হান্টার থেকে আলাদা করে এই ধাপটাই।

    কেন Recon-এ এত সময় বিনিয়োগ করা হয়

    অনেক নতুন হান্টার দ্রুত "টেস্টিং" শুরু করতে চান, কিন্তু অভিজ্ঞ হান্টাররা জানেন — একটি টার্গেট সম্পর্কে যত বেশি ও গভীর তথ্য জানা থাকবে (কী টেকনোলজি ব্যবহার হচ্ছে, কী কী সাবডোমেইন/এন্ডপয়েন্ট আছে, কোথায় কম পরীক্ষিত অংশ থাকতে পারে), ততই ভালো findings-এর সম্ভাবনা বাড়ে — কারণ হাজার হাজার অন্য হান্টার একই প্রধান পৃষ্ঠাগুলো ইতিমধ্যে পরীক্ষা করে ফেলেছেন।

    Passive বনাম Active Reconnaissance

    🕵️ Passive Recon

    টার্গেটের সার্ভারে সরাসরি কোনো request না পাঠিয়ে তথ্য সংগ্রহ করা — পাবলিক ডেটাবেজ, সার্চ ইঞ্জিন, ঐতিহাসিক রেকর্ড ব্যবহার করে (Hacking Tools ডকুমেন্টেশনে বিস্তারিত আলোচিত)।

    🔍 Active Recon

    সরাসরি টার্গেটে request পাঠিয়ে তথ্য সংগ্রহ (স্ক্যানিং, ব্রাউজিং) — scope ও testing restriction মেনে চালাতে হয়।

    Recon ওয়ার্কফ্লোর একটি সাধারণ কাঠামো

    উচ্চ-স্তরের ধাপ
    1. Company/Organization Footprint
   - সংশ্লিষ্ট সব ডোমেইন ও ব্র্যান্ড শনাক্তকরণ
2. Subdomain Enumeration (অধ্যায় ৪-এ বিস্তারিত)
3. Technology Stack Fingerprinting
   - কোন সার্ভার, framework, CMS, library ব্যবহৃত হচ্ছে
4. Content Discovery (অধ্যায় ৫-এ বিস্তারিত)
5. Historical Data Review
   - পুরনো সংস্করণ, archive.org-এর মতো সোর্স থেকে ভুলে যাওয়া endpoint খোঁজা

    Technology Fingerprinting

    একটি টার্গেটের server header, JavaScript লাইব্রেরি, CMS-এর চিহ্ন (যেমন WordPress-এর নির্দিষ্ট ফাইল পাথ) বিশ্লেষণ করে বোঝা যায় কোন টেকনোলজি স্ট্যাক ব্যবহৃত হচ্ছে — এটি গুরুত্বপূর্ণ, কারণ Vulnerable ও Outdated Components (Common Web Vulnerabilities ডকুমেন্টেশনের অধ্যায় ১০) একটি পরিচিত দুর্বলতাযুক্ত সংস্করণ ব্যবহার করছে কি না তা জানতে সাহায্য করে।

    Why "Boring" Recon Often Wins

    💡

    বাস্তব অভিজ্ঞতা: সবচেয়ে চমকপ্রদ vulnerability খুঁজে পাওয়ার গল্পগুলোর একটি বড় অংশ শুরু হয় একটি "বিরক্তিকর", ধৈর্য্যসহকারে করা recon ধাপ দিয়ে — একটি ভুলে যাওয়া staging সাবডোমেইন, বা একটি পুরনো API ভার্সন খুঁজে পাওয়া, যা প্রধান অ্যাপ্লিকেশনের চেয়ে অনেক কম পরীক্ষিত।

    অনুশীলন

    কেন একটি wildcard scope (*.example.com) প্রোগ্রামে, subdomain enumeration-এ বেশি সময় বিনিয়োগ করা একজন হান্টারের জন্য বিশেষভাবে লাভজনক হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Reconnaissance হলো একটি টার্গেট সম্পর্কে Passive ও Active পদ্ধতিতে বিস্তারিত তথ্য সংগ্রহের ধাপ — subdomain enumeration, technology fingerprinting, content discovery, ও historical data review এর অংশ। গভীর recon প্রায়ই কম পরীক্ষিত, বেশি সুযোগপূর্ণ জায়গা খুঁজে পেতে সাহায্য করে।

    Subdomain Enumeration ও Asset Discovery

    একটি wildcard scope-এর পুরো সুবিধা নিতে, টার্গেটের সম্ভাব্য সবচেয়ে বেশি সাবডোমেইন/অ্যাসেট খুঁজে বের করা।

    কেন Subdomain Enumeration গুরুত্বপূর্ণ

    একটি বড় প্রতিষ্ঠানের শত শত, কখনো হাজার হাজার সাবডোমেইন থাকতে পারে — অনেকগুলো ভুলে যাওয়া staging সার্ভার, পুরনো মার্কেটিং পৃষ্ঠা, বা internal টুল, যেগুলো প্রধান ওয়েবসাইটের চেয়ে কম সুরক্ষিত ও কম পরীক্ষিত হতে পারে।

    Subdomain Enumeration-এর পদ্ধতি

    পদ্ধতিবর্ণনা
    Certificate Transparency Logsপ্রতিটি পাবলিক SSL সার্টিফিকেট একটি পাবলিক লগে রেকর্ড হয় — এখান থেকে crt.sh-এর মতো টুল দিয়ে একটি ডোমেইনের জন্য ইস্যু করা সব সাবডোমেইন সার্টিফিকেট খুঁজে পাওয়া যায়
    DNS Brute-forcingএকটি wordlist ব্যবহার করে সাধারণ সাবডোমেইন নাম (dev, staging, api) try করে দেখা তারা resolve হয় কি না
    Search Engine DorkingGoogle/Bing-এর মাধ্যমে ইনডেক্স হওয়া সাবডোমেইন খুঁজে বের করা (Hacking Tools ডকুমেন্টেশনে আলোচিত)
    Third-party AggregatorShodan, Censys-এর মতো সার্ভিস, যা ইতিমধ্যে ইন্টারনেট-ব্যাপী স্ক্যান করা ডেটা সরবরাহ করে

    Enumeration Tools (ধারণাগত পরিচিতি)

    জনপ্রিয় টুলের নাম ও কাজ
    Sublist3r   — একাধিক উৎস (সার্চ ইঞ্জিন, Certificate Transparency) একত্রিত করে
Amass       — অত্যন্ত ব্যাপক, OSINT + active enumeration একত্রিত করে
Subfinder   — দ্রুত, একাধিক passive API ব্যবহার করে

    Live Host Verification

    শুধু একটি সাবডোমেইন খুঁজে পাওয়াই যথেষ্ট নয় — সেটি আসলে একটি "live" (সক্রিয়, response দেয়) হোস্ট কি না যাচাই করা জরুরি। এই ধাপে হাজার হাজার সম্ভাব্য সাবডোমেইনের তালিকা থেকে, শুধু বাস্তবে সক্রিয় সাবডোমেইনগুলো ফিল্টার করে বের করা হয় — যা পরবর্তী ধাপের (content discovery, testing) জন্য প্রস্তুত তালিকা তৈরি করে।

    Asset Discovery — শুধু সাবডোমেইনের বাইরেও

    • Mobile Apps: একটি কোম্পানির Android/iOS অ্যাপ, যা প্রায়ই একই backend API ব্যবহার করে (API Security ডকুমেন্টেশনে আলোচিত)
    • Cloud Storage: publicly accessible S3 bucket বা অনুরূপ cloud storage (Common Web Vulnerabilities ডকুমেন্টেশনের Security Misconfiguration অধ্যায়ে আলোচিত)
    • Code Repositories: পাবলিক GitHub রিপোজিটরি, যেখানে ভুলবশত API key বা internal তথ্য leak হতে পারে
    💡

    বাস্তব প্রয়োগ: অনেক গুরুত্বপূর্ণ findings আসে এমন একটি সাবডোমেইন থেকে, যা সার্চ ইঞ্জিনে ইনডেক্স হয়নি এবং সহজে দেখা যায় না, কিন্তু Certificate Transparency Log বা DNS brute-forcing দিয়ে খুঁজে পাওয়া যায় — এটি প্রমাণ করে কেন ব্যাপক, বহু-পদ্ধতির enumeration এত গুরুত্বপূর্ণ।

    অনুশীলন

    Certificate Transparency Log কীভাবে কাজ করে এবং কেন এটি একটি "passive" (টার্গেটে সরাসরি request না পাঠিয়ে) পদ্ধতি হিসেবে বিবেচিত হয় তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Subdomain Enumeration একটি wildcard scope-এর পূর্ণ সুবিধা নিতে Certificate Transparency Logs, DNS brute-forcing, ও third-party aggregator ব্যবহার করে। Live Host Verification দিয়ে প্রকৃত সক্রিয় টার্গেট শনাক্ত করা হয়, এবং Asset Discovery সাবডোমেইনের বাইরেও mobile app, cloud storage, code repository পর্যন্ত বিস্তৃত।

    2. Live Host Verification কেন একটি প্রয়োজনীয় ধাপ?
    3. Asset Discovery-তে সাবডোমেইনের বাইরে আর কী কী অন্তর্ভুক্ত হতে পারে?

    Content Discovery ও Directory Fuzzing

    একটি নির্দিষ্ট ওয়েব অ্যাপ্লিকেশনের মধ্যে লুকানো, অপ্রকাশিত পৃষ্ঠা ও endpoint খুঁজে বের করা।

    Content Discovery কী

    Subdomain Enumeration (অধ্যায় ৪) একটি সংস্থার কোন কোন সাবডোমেইন আছে তা খুঁজে বের করে — Content Discovery এক ধাপ গভীরে যায়: একটি নির্দিষ্ট ওয়েবসাইট/অ্যাপ্লিকেশনের মধ্যে কোন কোন পৃষ্ঠা, ডিরেক্টরি, ফাইল বা API endpoint আছে, যা সাধারণ navigation দিয়ে সহজে দেখা যায় না।

    Directory/File Fuzzing

    একটি wordlist (সাধারণ ডিরেক্টরি/ফাইল নামের তালিকা, যেমন admin, backup, .git, config.php.bak) ব্যবহার করে, প্রতিটি সম্ভাব্য পাথে একটি request পাঠিয়ে দেখা হয় সার্ভার কী response দেয় — একটি 200 OK response একটি বিদ্যমান, সম্ভবত অপ্রকাশিত রিসোর্স নির্দেশ করে।

    ধারণাগত উদাহরণ (lab/অনুমোদিত স্কোপে)
    GET /admin/           → 403 Forbidden (অস্তিত্ব আছে, কিন্তু অ্যাক্সেস সীমাবদ্ধ — আগ্রহের বিষয়)
GET /backup.zip       → 404 Not Found (নেই)

    Attack Surface Mapping

    সংগৃহীত সব তথ্যকে একটি সংগঠিত, কার্যকরী কাঠামোতে রূপান্তর করা — টেস্টিং শুরু করার ঠিক আগের ধাপ।

    Attack Surface কী

    Attack Surface হলো একটি অ্যাপ্লিকেশনের সব সম্ভাব্য পয়েন্টের সমষ্টি, যেখানে একজন attacker ইন্টারঅ্যাক্ট করতে পারেন — প্রতিটি ইনপুট ফিল্ড, API endpoint, ফাইল আপলোড ফিচার, authentication মেকানিজম। অধ্যায় ৩-৫-এ সংগ্রহ করা তথ্য (সাবডোমেইন, endpoint, JavaScript-এ পাওয়া রুট) এই ধাপে একত্রিত হয়ে একটি সম্পূর্ণ মানচিত্র তৈরি করে।

    কেন Mapping একটি আলাদা ধাপ

    📋 সংগঠন

    Recon ধাপে সংগৃহীত বিক্ষিপ্ত তথ্য (সাবডোমেইন তালিকা, endpoint তালিকা, টেকনোলজি নোট) একটি কাঠামোবদ্ধ ডকুমেন্টে সংগঠিত করা, যাতে কিছু হারিয়ে না যায়।

    🎯 অগ্রাধিকার

    কোন অংশগুলো সবচেয়ে আকর্ষণীয় (নতুন ফিচার, কম পরীক্ষিত এলাকা, authentication-সম্পর্কিত ফাংশনালিটি) তা চিহ্নিত করে টেস্টিং-এর ক্রম ঠিক করা।

    Burp Suite দিয়ে ম্যাপিং

    Hacking Tools ডকুমেন্টেশনে আলোচিত Burp Suite-এর Spider/Crawler ফিচার ব্যবহার করে, একটি অ্যাপ্লিকেশনের মধ্য দিয়ে সিস্টেমেটিকভাবে browse করে (proxy-এর মাধ্যমে) একটি Site Map তৈরি করা হয় — প্রতিটি request/response, parameter, ও কুকি স্বয়ংক্রিয়ভাবে সংরক্ষিত হয়, যা পরবর্তী ম্যানুয়াল টেস্টিং-এর ভিত্তি তৈরি করে।

    Functionality-ভিত্তিক শ্রেণিবিভাগ

    ক্যাটাগরিকেন গুরুত্বপূর্ণ
    Authentication/SessionBroken Authentication-এর সম্ভাব্য পয়েন্ট (Common Web Vulnerabilities-এর অধ্যায় ৯)
    Access Control Boundariesভিন্ন role/permission-এর মধ্যে সীমানা — IDOR-এর সম্ভাব্য পয়েন্ট
    File Upload/DownloadFile Upload দুর্বলতার সম্ভাব্য পয়েন্ট
    External Integration PointsSSRF-এর সম্ভাব্য পয়েন্ট (যেখানে সার্ভার বাহ্যিক URL fetch করে)
    💡

    একটি কার্যকর কৌশল: প্রতিটি functionality-কে "এখানে কী ভুল হতে পারে" প্রশ্ন দিয়ে বিশ্লেষণ করুন — এই ডকুমেন্টেশন সিরিজে আলোচিত প্রতিটি vulnerability ক্যাটাগরি (Common Web Vulnerabilities ডকুমেন্টেশন) এক একটি নির্দিষ্ট ধরনের ফাংশনালিটির সাথে সম্পর্কিত। Attack Surface Map-এ প্রতিটি অংশের পাশে "কোন ধরনের দুর্বলতা এখানে সম্ভব" নোট রাখা একটি কার্যকর অভ্যাস।

    অনুশীলন

    একটি কাল্পনিক ই-কমার্স অ্যাপ্লিকেশনের Attack Surface Map তৈরি করুন — কমপক্ষে ৫টি functionality ক্যাটাগরি ও প্রতিটির সাথে সম্ভাব্য vulnerability টাইপ যুক্ত করুন।

    সারসংক্ষেপ

    Attack Surface Mapping সংগৃহীত recon তথ্যকে একটি সংগঠিত কাঠামোতে রূপান্তর করে, Burp Suite Site Map-এর মতো টুলের সাহায্যে। Functionality-ভিত্তিক শ্রেণিবিভাগ ও প্রতিটি অংশে সম্ভাব্য vulnerability টাইপ চিহ্নিত করা টেস্টিং-এর অগ্রাধিকার ঠিক করতে সাহায্য করে।

    Manual Web Testing Methodology

    Attack Surface Map ব্যবহার করে, পদ্ধতিগতভাবে প্রতিটি functionality পরীক্ষা করা — এই ডকুমেন্টেশন সিরিজের বাকি সব জ্ঞান এখানে একত্রিত হয়।

    কেন Manual Testing এখনও অপরিহার্য

    Automated scanner (Hacking Tools ডকুমেন্টেশনের অধ্যায় ৫) পরিচিত প্যাটার্ন দ্রুত শনাক্ত করতে পারে, কিন্তু business logic-নির্ভর দুর্বলতা (যেমন Broken Access Control, যা Common Web Vulnerabilities ডকুমেন্টেশনে OWASP #1 হিসেবে আলোচিত) বুঝতে একজন মানুষের বিচার-বুদ্ধি প্রয়োজন — এই কারণে সবচেয়ে গুরুত্বপূর্ণ ও উচ্চ-মূল্যের findings প্রায়ই ম্যানুয়াল টেস্টিং থেকে আসে।

    একটি Systematic Testing চেকলিস্ট কাঠামো

    ক্যাটাগরিকী পরীক্ষা করা হয়
    Input Handlingপ্রতিটি ইনপুট ফিল্ডে XSS, SQLi payload পরীক্ষা (XSS/SQLi ডকুমেন্টেশনে বিস্তারিত)
    Access Controlএকটি কম-privilege অ্যাকাউন্ট দিয়ে অন্য ইউজারের object ID অ্যাক্সেসের চেষ্টা (IDOR)
    State-Changing ActionsCSRF token/SameSite protection আছে কি না যাচাই
    File OperationsFile Upload দুর্বলতা পরীক্ষা
    Business Logicঅ্যাপ্লিকেশনের নির্দিষ্ট কার্যপ্রণালী অপব্যবহারযোগ্য কি না (যেমন একটি discount code একাধিকবার প্রয়োগ করা)

    Business Logic Vulnerability — একটি বিশেষ ক্যাটাগরি

    Business Logic Vulnerability কোনো OWASP Top 10-এর একক ক্যাটাগরি নয় — এটি অ্যাপ্লিকেশনের নির্দিষ্ট কার্যপ্রণালীর একটি ত্রুটিপূর্ণ অনুমান কাজে লাগায়, যা কোনো automated scanner ধরতে পারে না, কারণ এটি "সঠিকভাবে কাজ করা" কোডের একটি অপ্রত্যাশিত ব্যবহার — যেমন একটি checkout প্রক্রিয়ায় negative quantity প্রবেশ করিয়ে মূল্য কমানোর চেষ্টা।

    Proxy-Driven Testing ওয়ার্কফ্লো

    উচ্চ-স্তরের ধাপ (Burp Suite-কেন্দ্রিক)

    💡

    সবকিছু যাচাই করার মানসিকতা: একজন অভিজ্ঞ হান্টার কোনো input/response-কে "স্বাভাবিক" ধরে নেন না — প্রতিটি parameter, header, cookie-কে সম্ভাব্য manipulation পয়েন্ট হিসেবে বিবেচনা করেন, এবং প্রতিটি response মনোযোগ সহকারে পড়েন, শুধু status code নয়।

    API Testing Methodology

    আধুনিক বাগ বাউন্টিতে API-ভিত্তিক findings ক্রমবর্ধমান গুরুত্বপূর্ণ — API Security ডকুমেন্টেশনের ব্যবহারিক প্রয়োগ।

    কেন API Testing আলাদা গুরুত্ব পায়

    আধুনিক অ্যাপ্লিকেশনের একটি বড় অংশ API-চালিত (web frontend, mobile app, এবং third-party integration — সবাই একই backend API ব্যবহার করে)। API-তে প্রায়ই web frontend-এর চেয়ে কম strict ভ্যালিডেশন থাকে (কারণ ডেভেলপাররা ধরে নেন শুধু "বিশ্বস্ত" app থেকেই কল আসবে), যা এটিকে একটি উচ্চ-মূল্যের টেস্টিং টার্গেট করে তোলে।

    API Testing চেকলিস্ট (API Security ডকুমেন্টেশন থেকে প্রয়োগ)

    চেকলক্ষ্য
    BOLA/IDOR পরীক্ষাএকটি ID পরিবর্তন করে অন্য ইউজারের রিসোর্স অ্যাক্সেস সম্ভব কি না
    Mass Assignment পরীক্ষাঅতিরিক্ত, অনুমোদিত নয় এমন field (যেমন "isAdmin": true) request body-তে যোগ করে দেখা
    Rate Limiting পরীক্ষাএকই endpoint-এ দ্রুত, পুনরাবৃত্ত request পাঠিয়ে সীমা আছে কি না যাচাই
    HTTP Method Fuzzingএকই endpoint-এ ভিন্ন HTTP method (GET-এর বদলে PUT/DELETE) try করে দেখা অপ্রত্যাশিত আচরণ হয় কি না
    API Version Discoveryপুরনো, deprecated API ভার্সন (/v1/ এখনও সক্রিয় কি না) খোঁজা — প্রায়ই কম সুরক্ষিত

    Mobile App API Traffic বিশ্লেষণ

    একটি মোবাইল অ্যাপের ট্রাফিক Burp Suite-এর মতো proxy দিয়ে intercept করলে, প্রায়ই এমন API endpoint পাওয়া যায় যা ওয়েব ভার্সনে ব্যবহৃত হয় না — এই "mobile-only" endpoint প্রায়ই কম পরীক্ষিত হয়, কারণ বেশিরভাগ হান্টার শুধু ওয়েব অ্যাপ্লিকেশনে ফোকাস করেন।

    GraphQL-নির্দিষ্ট টেস্টিং

    যদি টার্গেট GraphQL ব্যবহার করে, নির্দিষ্ট কিছু অতিরিক্ত চেক প্রাসঙ্গিক — Introspection সক্রিয় কি না, Batch Query দিয়ে rate limiting bypass সম্ভব কি না, এবং field-level authorization সঠিকভাবে প্রয়োগ হচ্ছে কি না (একটি query-তে একাধিক resource type থাকতে পারে, প্রতিটির জন্য আলাদা authorization check প্রয়োজন)।

    💡

    একটি কার্যকর কৌশল: API-র Swagger/OpenAPI ডকুমেন্টেশন (যদি পাওয়া যায়) পড়ে প্রতিটি endpoint-এর প্রত্যাশিত parameter ও response বোঝা, তারপর প্রতিটি endpoint-এ অধ্যায় ৩-এর অধ্যায় "Broken Access Control" ও API Security ডকুমেন্টেশনের চেকলিস্ট পদ্ধতিগতভাবে প্রয়োগ করা।

    অনুশীলন

    কেন মোবাইল অ্যাপের API endpoint প্রায়ই ওয়েব endpoint-এর চেয়ে কম সুরক্ষিত/কম পরীক্ষিত হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    API Testing-এ BOLA/IDOR, Mass Assignment, Rate Limiting, HTTP Method Fuzzing, ও পুরনো API ভার্সন পরীক্ষা করা হয়। Mobile app traffic বিশ্লেষণ প্রায়ই কম পরীক্ষিত "hidden" endpoint প্রকাশ করে, এবং GraphQL-এর জন্য আলাদা নির্দিষ্ট চেক প্রয়োজন।

    Automation ও Custom Scripting

    বড় স্কেলে recon ও পুনরাবৃত্ত কাজ দ্রুত করতে স্বয়ংক্রিয়করণের ব্যবহারিক ভূমিকা।

    Automation কেন প্রয়োজন

    একটি বড় wildcard scope-এ শত শত সাবডোমেইন, হাজার হাজার endpoint থাকতে পারে — প্রতিটি ম্যানুয়ালি পরীক্ষা করা অসম্ভব। Automation ব্যবহার করা হয় পুনরাবৃত্ত, বড়-স্কেল কাজ (সাবডোমেইন enumeration, live host check, basic fingerprinting) দ্রুত করতে — যাতে মূল্যবান ম্যানুয়াল সময় সবচেয়ে প্রতিশ্রুতিশীল টার্গেটগুলোতে ব্যয় করা যায়।

    কী Automate করা উচিত, কী নয়

    ✅ Automation-এর জন্য উপযুক্ত

    Subdomain enumeration, live host verification, known-CVE স্ক্যানিং, নিয়মিত পুনরাবৃত্ত monitoring (নতুন সাবডোমেইন এলে notify করা)।

    ❌ ম্যানুয়াল থাকা উচিত

    Business logic বিশ্লেষণ, complex access control পরীক্ষা, সূক্ষ্ম context-নির্ভর সিদ্ধান্ত — এগুলো মানুষের বিচার-বুদ্ধি দাবি করে।

    Custom Scripting-এর মূল্য

    অনেক অভিজ্ঞ হান্টার নিজের প্রয়োজন অনুযায়ী ছোট ছোট স্ক্রিপ্ট (Python/Bash) লেখেন — যেমন একাধিক টুলের আউটপুট একত্রিত করা, একটি নির্দিষ্ট প্যাটার্নের জন্য হাজার হাজার response দ্রুত ফিল্টার করা, বা একটি নির্দিষ্ট প্রোগ্রামের জন্য একটি কাস্টম monitoring সিস্টেম তৈরি করা — এটি একজন হান্টারকে প্রতিযোগীদের থেকে আলাদা করতে পারে।

    Continuous Monitoring

    একটি wildcard scope প্রোগ্রামে, একটি নতুন সাবডোমেইন বা নতুন কোড পরিবর্তন প্রায়ই নতুন দুর্বলতার সুযোগ তৈরি করে। অনেক হান্টার একটি স্বয়ংক্রিয় সিস্টেম সেট করেন, যা নিয়মিত (দৈনিক) নতুন সাবডোমেইন/পরিবর্তন খুঁজে বের করে notify করে — যাতে তারা অন্য হান্টারদের আগে সেই নতুন অংশ পরীক্ষা করতে পারেন।

    ⚠️

    সতর্কতা: যেকোনো automated টুল/স্ক্রিপ্ট চালানোর আগে, scope document-এ automated scanning সম্পর্কিত restriction আছে কি না যাচাই করুন — অনেক প্রোগ্রাম aggressive automated scanning সীমিত বা নিষিদ্ধ করে, rate limiting মেনে চলার শর্তে।

    অনুশীলন

    কেন "সবকিছু automate করা" একটি ভালো কৌশল নয় — কোন ধরনের findings-এর জন্য মানুষের বিচার-বুদ্ধি অপরিবর্তনীয়ভাবে প্রয়োজন তা উদাহরণসহ ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Automation বড়-স্কেল, পুনরাবৃত্ত কাজ (recon, monitoring) দ্রুত করে, মূল্যবান ম্যানুয়াল সময় সংরক্ষণ করে — কিন্তু business logic ও জটিল access control বিশ্লেষণ মানুষের বিচার-বুদ্ধি দাবি করে। Custom scripting ও continuous monitoring একজন হান্টারকে প্রতিযোগিতামূলক সুবিধা দিতে পারে।

    Vulnerability Triage ও Prioritization

    একটি সম্ভাব্য দুর্বলতা খুঁজে পাওয়ার পর, রিপোর্ট করার আগে নিজেকে কী প্রশ্ন করা উচিত।

    Triage কী

    একটি সম্ভাব্য findings খুঁজে পাওয়ার পর, সরাসরি রিপোর্ট লিখতে বসার আগে, একজন অভিজ্ঞ হান্টার একটি Triage ধাপ অনুসরণ করেন — এই findings আসলে কতটা বাস্তব, কতটা গুরুত্বপূর্ণ, এবং রিপোর্ট করার যোগ্য কি না তা যাচাই করা।

    প্রতিটি Findings-এর জন্য জিজ্ঞাসা করার প্রশ্ন

    ✅ এটি কি বাস্তব?

    False positive নয় তো? আবার যাচাই করে, ভিন্ন সময়ে, নিশ্চিত হন যে আচরণটি পুনরুৎপাদনযোগ্য (reproducible)।

    📋 এটি কি scope-এর মধ্যে?

    টার্গেট ও vulnerability type উভয়ই প্রোগ্রামের scope document অনুযায়ী গ্রহণযোগ্য কি না পুনরায় যাচাই করুন।

    Impact Assessment — "তাহলে কী হবে?"

    শুধু "একটি বাগ পেয়েছি" বলা যথেষ্ট নয় — triage-এর একটি গুরুত্বপূর্ণ অংশ হলো স্পষ্টভাবে বোঝা এই দুর্বলতার বাস্তব প্রভাব কী। একটি IDOR যা শুধু একটি ইউজারের প্রোফাইল ছবি দেখায়, এবং একটি IDOR যা একটি ইউজারের সম্পূর্ণ ব্যক্তিগত তথ্য/পেমেন্ট ডেটা প্রকাশ করে — দুটোই "IDOR" হলেও তাদের severity সম্পূর্ণ ভিন্ন।

    CVSS দিয়ে Severity নির্ধারণ

    Hacking Tools ডকুমেন্টেশনে আলোচিত CVSS (Common Vulnerability Scoring System) স্কোরিং সিস্টেম ব্যবহার করে একটি দুর্বলতার তীব্রতা পরিমাপযোগ্যভাবে প্রকাশ করা যায় — Attack Vector, Attack Complexity, Privileges Required, User Interaction, এবং Impact (Confidentiality/Integrity/Availability)-এর মতো factor বিবেচনা করে।

    CVSS রেঞ্জSeverity
    9.0 – 10.0Critical
    7.0 – 8.9High
    4.0 – 6.9Medium
    0.1 – 3.9Low

    প্ল্যাটফর্ম-নির্দিষ্ট Taxonomy

    CVSS ছাড়াও, অনেক প্ল্যাটফর্ম (যেমন Bugcrowd-এর VRT — Vulnerability Rating Taxonomy) নিজস্ব classification সিস্টেম ব্যবহার করে। একটি নির্দিষ্ট প্রোগ্রামে রিপোর্ট করার আগে, সেই প্রোগ্রাম কোন সিস্টেম ব্যবহার করে তা জেনে নেওয়া সাহায্য করে — এটি একটি findings কীভাবে presented ও received হবে তা প্রভাবিত করতে পারে।

    ⚠️

    অতিরঞ্জন এড়িয়ে চলুন: একটি কম-গুরুত্বের findings-কে "Critical" হিসেবে overstate করা একজন হান্টারের বিশ্বাসযোগ্যতা দ্রুত ক্ষতিগ্রস্ত করে। সঠিক, বাস্তবসম্মত impact assessment দীর্ঘমেয়াদে একজন হান্টারের reputation তৈরি করে।

    অনুশীলন

    একই ধরনের vulnerability (IDOR) দুটি ভিন্ন প্রেক্ষাপটে কীভাবে সম্পূর্ণ ভিন্ন severity পেতে পারে তার দুটি উদাহরণ তৈরি করুন।

    সারসংক্ষেপ

    Triage-এ একটি findings বাস্তব, scope-এর মধ্যে, এবং তার প্রকৃত impact কতটা তা যাচাই করা হয়। CVSS স্কোরিং ও প্ল্যাটফর্ম-নির্দিষ্ট taxonomy ব্যবহার করে severity পরিমাপযোগ্যভাবে প্রকাশ করা হয় — সঠিক, বাস্তবসম্মত মূল্যায়ন বিশ্বাসযোগ্যতা তৈরি করে।

    Knowledge-check

    1. Triage ধাপে কোন প্রশ্নগুলো জিজ্ঞাসা করা উচিত?
    2. CVSS স্কোরিং-এ কোন factor গুলো বিবেচনা করা হয়?
    3. একটি findings-এর severity অতিরঞ্জন করা কেন ক্ষতিকর হতে পারে?

    Proof of Concept (PoC) তৈরি

    একটি দুর্বলতা শুধু "বলা" নয়, স্পষ্টভাবে "দেখানো" — একটি ভালো PoC রিপোর্ট দ্রুত গ্রহণযোগ্য হতে সাহায্য করে।

    PoC কী এবং কেন গুরুত্বপূর্ণ

    Proof of Concept (PoC) হলো একটি নির্দিষ্ট, পুনরুৎপাদনযোগ্য প্রদর্শনী, যা একটি দুর্বলতা বাস্তবে কাজ করে তা প্রমাণ করে। একটি প্রোগ্রামের triage টিম প্রতিদিন অনেক রিপোর্ট পান — একটি স্পষ্ট, সহজে পুনরুৎপাদনযোগ্য PoC, একটি অস্পষ্ট বর্ণনার চেয়ে অনেক দ্রুত পর্যালোচিত ও গৃহীত হয়।

    ⚠️

    নিজের টেস্ট অ্যাকাউন্ট ব্যবহার করুন: যেখানেই সম্ভব, একটি দুর্বলতা প্রমাণ করতে নিজের তৈরি করা (বা প্রোগ্রাম-প্রদত্ত) টেস্ট অ্যাকাউন্ট ব্যবহার করুন — বাস্তব ইউজারের ডেটা স্পর্শ করা এড়িয়ে চলুন, এমনকি যদি তা শুধু "দেখার" জন্যও হয়।

    Video PoC কখন ব্যবহার করবেন

    জটিল, multi-step vulnerability (যেমন একটি multi-request CSRF chain, বা একটি জটিল business logic bypass) একটি স্ক্রিন রেকর্ডিং দিয়ে অনেক বেশি স্পষ্টভাবে বোঝানো যায়, স্থির স্ক্রিনশটের তুলনায় — বিশেষত যখন টাইমিং বা দ্রুত ধারাবাহিক অ্যাকশন গুরুত্বপূর্ণ।

    অনুশীলন

    কেন "Non-Destructive Testing" নীতি অনুসরণ করা শুধু নৈতিক নয়, বরং কৌশলগতভাবেও একজন হান্টারের জন্য লাভজনক তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Report Writing Methodology

    একটি কারিগরিভাবে সঠিক findings-ও, যদি ভালোভাবে লেখা না হয়, গৃহীত না-ও হতে পারে — রিপোর্ট লেখা নিজেই একটি দক্ষতা।

    একটি রিপোর্টের স্ট্যান্ডার্ড কাঠামো

    অংশকী থাকে
    Titleসংক্ষিপ্ত, নির্দিষ্ট — "IDOR in /api/invoices allows accessing other users' invoices" (শুধু "IDOR found" নয়)
    Summary২-৩ বাক্যে vulnerability ও তার impact-এর সংক্ষিপ্ত বিবরণ
    SeverityCVSS স্কোর/রেটিং ও তার যুক্তি (অধ্যায় ১০-এ আলোচিত)
    Steps to ReproducePoC (অধ্যায় ১১-এ আলোচিত) — নম্বরযুক্ত, স্পষ্ট ধাপ
    Impactএই দুর্বলতা বাস্তবে কাজে লাগালে কী ঘটতে পারে তার বিস্তারিত ব্যাখ্যা
    Remediation Suggestion(ঐচ্ছিক কিন্তু মূল্যবান) কীভাবে এই দুর্বলতা ঠিক করা যেতে পারে তার সংক্ষিপ্ত প্রস্তাবনা

    লেখার মান — কেন গুরুত্বপূর্ণ

    ⏱️ Triage টিমের সময় সাশ্রয়

    একটি স্পষ্ট, সংগঠিত রিপোর্ট triage টিমকে দ্রুত বুঝতে ও verify করতে সাহায্য করে — দ্রুত response পাওয়ার সম্ভাবনা বাড়ায়।

    🏆 Reputation তৈরি

    ধারাবাহিকভাবে উচ্চমানের রিপোর্ট জমা দেওয়া হান্টার, প্ল্যাটফর্মে একটি ভালো reputation তৈরি করেন, যা ভবিষ্যতে private program invitation-এর সুযোগ বাড়ায়।

    সাধারণ লেখার ভুল যা এড়ানো উচিত

    • অস্পষ্ট বর্ণনা ("এটি একটি নিরাপত্তা সমস্যা") — নির্দিষ্ট, প্রযুক্তিগত ভাষা ব্যবহার করুন
    • Impact ছাড়া শুধু টেকনিক্যাল বিবরণ — triage টিমকে "তাই কী হবে" বুঝতে সাহায্য করুন
    • Reproducible না হওয়া ধাপ — নিজে প্রথমে আবার টেস্ট করে নিশ্চিত হন প্রতিটি ধাপ কাজ করে
    • অপ্রয়োজনীয়ভাবে দীর্ঘ, অগোছালো বর্ণনা — সংক্ষিপ্ত ও কেন্দ্রীভূত রাখুন

    Remediation Suggestion যোগ করার মূল্য

    যদিও বাধ্যতামূলক নয়, একটি সংক্ষিপ্ত, প্রাসঙ্গিক remediation পরামর্শ (যেমন "parameterized queries ব্যবহার করুন" বা "server-side ownership check যোগ করুন") যোগ করা রিপোর্টের মান বাড়ায় এবং দেখায় হান্টার শুধু সমস্যা খুঁজে পাননি, সমাধানও বোঝেন — এই ডকুমেন্টেশন সিরিজের প্রতিটি vulnerability-র প্রতিরোধ অংশ এই ক্ষেত্রে সরাসরি কাজে লাগে।

    💡

    একটি কার্যকর অভ্যাস: রিপোর্ট জমা দেওয়ার আগে, নিজেকে একজন triage engineer-এর জায়গায় বসিয়ে রিপোর্টটি আবার পড়ুন — "এই রিপোর্ট পড়ে, আমি কি দুর্বলতাটি দ্রুত বুঝতে ও verify করতে পারব?"

    অনুশীলন

    একটি কাল্পনিক IDOR findings-এর জন্য একটি সম্পূর্ণ রিপোর্ট টেমপ্লেট (Title, Summary, Severity, Steps to Reproduce, Impact) লিখুন।

    সারসংক্ষেপ

    একটি ভালো রিপোর্টে স্পষ্ট Title, Summary, Severity, Steps to Reproduce, Impact, এবং ঐচ্ছিকভাবে Remediation থাকে। স্পষ্ট, সংক্ষিপ্ত, reproducible লেখা দ্রুত response ও একটি ভালো হান্টার reputation তৈরি করে।

    2. কেন শুধু টেকনিক্যাল বিবরণ যথেষ্ট নয় — আর কী থাকা উচিত?
    3. Remediation Suggestion যোগ করা কেন একটি ভালো অভ্যাস?

    Communication ও Disclosure Workflow

    রিপোর্ট জমা দেওয়ার পর কী ঘটে — এবং কীভাবে পেশাদারভাবে এই প্রক্রিয়ার মধ্য দিয়ে যেতে হয়।

    Report Lifecycle

    একটি সাধারণ রিপোর্টের জীবনচক্র
    Submitted → Triaging → Triaged/Accepted (বা Not Applicable/Duplicate)
    → Resolved → Disclosed (ঐচ্ছিক, উভয়পক্ষের সম্মতিতে)

    প্রতিটি স্ট্যাটাসের অর্থ

    স্ট্যাটাসঅর্থ
    Triagingটিম রিপোর্টটি পর্যালোচনা ও verify করছে
    Triaged/Acceptedদুর্বলতা নিশ্চিত হয়েছে, severity নির্ধারিত হয়েছে
    Not Applicable (N/A)টিম এটিকে একটি বৈধ নিরাপত্তা দুর্বলতা হিসেবে বিবেচনা করছে না
    Duplicateঅন্য কোনো হান্টার একই দুর্বলতা আগে রিপোর্ট করেছেন
    Resolvedদুর্বলতাটি ঠিক করা হয়েছে

    Not Applicable/Duplicate পাওয়ার পর পেশাদার আচরণ

    একজন হান্টার হিসেবে, একটি N/A বা Duplicate response পাওয়া স্বাভাবিক ও অনিবার্য — এমনকি অভিজ্ঞ হান্টারদেরও হয়। গুরুত্বপূর্ণ হলো কীভাবে প্রতিক্রিয়া জানানো হয়: যদি আপনি মনে করেন সিদ্ধান্তটি ভুল, একটি শান্ত, তথ্য-ভিত্তিক ব্যাখ্যা সহ ভদ্রভাবে একটি clarification অনুরোধ করা যেতে পারে — কখনো আক্রমণাত্মক বা অধৈর্য হওয়া উচিত নয়, কারণ এটি triage টিমের সাথে সম্পর্ক নষ্ট করে।

    Responsible Disclosure নীতি

    Responsible Disclosure (বা Coordinated Disclosure) হলো একটি নীতি, যেখানে একজন গবেষক একটি দুর্বলতা প্রথমে সরাসরি প্রতিষ্ঠানকে জানান এবং তাদের একটি যুক্তিসঙ্গত সময় দেন ঠিক করার জন্য, পাবলিকলি প্রকাশ করার আগে। এর বিপরীত হলো Full Disclosure (সরাসরি পাবলিক প্রকাশ, কোনো অপেক্ষা ছাড়া), যা সাধারণত অনৈতিক বা ঝুঁকিপূর্ণ বিবেচিত হয়, কারণ এটি সাধারণ ইউজারদের অরক্ষিত অবস্থায় ফেলে।

    ⚖️

    Disclosure নিয়ম মেনে চলুন: একটি দুর্বলতা পাবলিকলি প্রকাশ করার আগে (ব্লগ পোস্ট, সোশ্যাল মিডিয়া, কনফারেন্স টক), প্রোগ্রামের disclosure policy পড়ুন — অনেক প্রোগ্রাম স্পষ্ট অনুমতি ছাড়া পাবলিক disclosure নিষিদ্ধ করে, এবং তা লঙ্ঘন করলে প্রোগ্রাম থেকে ব্যান বা আইনি জটিলতা হতে পারে।

    Professional Communication-এর মূল নীতি

    • ধৈর্যশীল থাকুন — একটি বড় প্রোগ্রামে প্রতিদিন শত শত রিপোর্ট আসতে পারে, response-এ সময় লাগা স্বাভাবিক
    • Follow-up পাঠানোর আগে প্রোগ্রামের ঘোষিত SLA (Service Level Agreement) সময় মেনে চলুন
    • কখনো একটি সিদ্ধান্তে অসন্তুষ্ট হয়ে hostile বা threatening ভাষা ব্যবহার করবেন না

    অনুশীলন

    কেন Full Disclosure (অপেক্ষা ছাড়া সরাসরি পাবলিক প্রকাশ) সাধারণত অনৈতিক বিবেচিত হয় — এটি কাদের ক্ষতি করতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    একটি রিপোর্ট Submitted থেকে Resolved পর্যন্ত বিভিন্ন স্ট্যাটাসের মধ্য দিয়ে যায়। N/A/Duplicate পাওয়ার পরও পেশাদার আচরণ বজায় রাখা জরুরি। Responsible Disclosure নীতি অনুযায়ী, প্রতিষ্ঠানকে ঠিক করার সুযোগ দিয়ে, তাদের policy মেনে চলে পাবলিক প্রকাশ করতে হয়।

    সাধারণ ভুল ও Duplicate এড়ানো

    নতুন হান্টাররা যে ভুলগুলো বারবার করেন, এবং কীভাবে Duplicate পাওয়ার সম্ভাবনা কমানো যায়।

    নতুন হান্টারদের সাধারণ ভুল

    ভুলকেন ক্ষতিকর
    Scope না পড়েই টেস্ট শুরু করাআইনি ঝুঁকি, এবং সময়ের অপচয় (out-of-scope findings গৃহীত হয় না)
    শুধু "সহজ" টার্গেটে ভিড় করাজনপ্রিয়, নতুন প্রোগ্রামে হাজার হাজার হান্টার একসাথে চেষ্টা করেন — duplicate-এর সম্ভাবনা অনেক বেশি
    Automated scanner-এর ফলাফল না যাচাই করে সরাসরি রিপোর্ট করাFalse positive রিপোর্ট করলে বিশ্বাসযোগ্যতা কমে যায়
    Low-severity issue বারবার রিপোর্ট করাঅনেক প্রোগ্রামে একটি নির্দিষ্ট "noise" সীমা থাকে, অতিরিক্ত কম-মূল্যের রিপোর্ট সম্পর্ক নষ্ট করে

    Duplicate কমানোর কৌশল

    🎯 কম পরীক্ষিত এলাকা খোঁজা

    অধ্যায় ৩-৬-এ আলোচিত গভীর recon ও asset discovery — একটি নতুন, কম পরিচিত সাবডোমেইন/ফিচার অনেক কম duplicate পায়।

    ⏰ নতুন ফিচার দ্রুত পরীক্ষা করা

    একটি প্রোগ্রাম সম্প্রতি একটি নতুন ফিচার লঞ্চ করলে, সেটি দ্রুত পরীক্ষা করা — কম হান্টার এখনও সেখানে পৌঁছেছেন।

    "Low-Hanging Fruit" বনাম গভীর বিশ্লেষণ

    নতুন হান্টাররা প্রায়ই শুধু সহজে চিহ্নিতযোগ্য দুর্বলতা (যেমন একটি ফর্মে basic XSS payload try করা) খোঁজেন — কিন্তু জনপ্রিয় প্রোগ্রামে এই "low-hanging fruit" প্রায় সবসময় আগেই খুঁজে পাওয়া হয়ে গেছে। একটি নির্দিষ্ট ফাংশনালিটিতে গভীরভাবে সময় বিনিয়োগ করে, সেই ফিচারের ব্যবসায়িক যুক্তি (business logic) গভীরভাবে বোঝা, প্রায়ই বেশি মূল্যবান, কম-duplicate findings এনে দেয়।

    Persistence — হতাশ না হওয়া

    💡

    বাস্তবতা: প্রায় প্রতিটি সফল বাগ বাউন্টি হান্টারের শুরুর দিকে অনেক N/A ও Duplicate অভিজ্ঞতা হয়েছে — এটি স্বাভাবিক শেখার প্রক্রিয়ার অংশ। প্রতিটি রিপোর্ট (এমনকি একটি Duplicate হলেও) একজন হান্টারকে একটি অ্যাপ্লিকেশন সম্পর্কে আরও গভীরভাবে বুঝতে সাহায্য করে, যা ভবিষ্যতের findings-এর ভিত্তি তৈরি করে।

    অনুশীলন

    কেন একটি "low-hanging fruit" দুর্বলতা একটি জনপ্রিয়, দীর্ঘদিনের প্রোগ্রামে প্রায় সবসময় ইতিমধ্যে খুঁজে পাওয়া হয়ে গেছে তা ব্যাখ্যা করুন, এবং এর বিকল্প কৌশল কী হতে পারে।

    সারসংক্ষেপ

    নতুন হান্টাররা প্রায়ই scope উপেক্ষা, জনপ্রিয় টার্গেটে ভিড়, ও unverified findings রিপোর্ট করার ভুল করেন। গভীর recon, নতুন ফিচার দ্রুত পরীক্ষা, এবং business logic-এ গভীরভাবে সময় বিনিয়োগ করা Duplicate কমাতে সাহায্য করে। Persistence ও ধারাবাহিক শেখা দীর্ঘমেয়াদে সফলতার চাবিকাঠি।

    এই সম্পূর্ণ ডকুমেন্টেশনের গুরুত্বপূর্ণ শব্দ ও ধারণার একটি দ্রুত রেফারেন্স।

    শব্দকোষ

    শব্দসংক্ষিপ্ত অর্থ
    Scopeএকটি প্রোগ্রামে কোন সিস্টেম/vulnerability টাইপ টেস্ট করার অনুমতি আছে তার সংজ্ঞা
    Safe Harborscope মেনে টেস্ট করলে আইনি সুরক্ষার প্রতিশ্রুতি
    Reconnaissance (Recon)একটি টার্গেট সম্পর্কে তথ্য সংগ্রহের প্রাথমিক ধাপ
    Subdomain Enumerationএকটি ডোমেইনের সব সাবডোমেইন খুঁজে বের করা
    Content Discoveryএকটি অ্যাপ্লিকেশনের লুকানো পৃষ্ঠা/endpoint খুঁজে বের করা
    Attack Surfaceএকটি অ্যাপ্লিকেশনের সব সম্ভাব্য ইন্টারঅ্যাকশন পয়েন্টের সমষ্টি
    Business Logic Vulnerabilityঅ্যাপ্লিকেশনের নির্দিষ্ট কার্যপ্রণালীর ত্রুটিপূর্ণ অনুমান কাজে লাগানো দুর্বলতা
    Triageএকটি findings বাস্তব, গুরুত্বপূর্ণ, ও scope-এর মধ্যে কি না যাচাই করা
    PoC (Proof of Concept)একটি দুর্বলতা বাস্তবে কাজ করে তার পুনরুৎপাদনযোগ্য প্রদর্শনী
    CVSSএকটি দুর্বলতার তীব্রতা পরিমাপের মানদণ্ড স্কোর
    Responsible Disclosureপ্রতিষ্ঠানকে ঠিক করার সুযোগ দিয়ে, পরে দায়িত্বশীলভাবে প্রকাশ করার নীতি
    Duplicateএকই দুর্বলতা আগে অন্য কেউ রিপোর্ট করেছেন

    প্রায়শই জিজ্ঞাসিত প্রশ্ন (FAQ)

    বাগ বাউন্টি শুরু করার জন্য আগে কী জানা দরকার?

    এই সিরিজের XSS, CSRF, SQLi, Common Web Vulnerabilities, ও API Security ডকুমেন্টেশনে আলোচিত মৌলিক vulnerability ধারণাগুলো, এবং Hacking Tools ডকুমেন্টেশনে আলোচিত Burp Suite-এর মতো টুলের ব্যবহারিক জ্ঞান একটি শক্ত ভিত্তি দেয়।

    কোন প্রোগ্রাম দিয়ে শুরু করা উচিত?

    নতুনদের জন্য public, well-documented প্রোগ্রাম বা VDP (Vulnerability Disclosure Program — যেখানে আর্থিক পুরস্কার না থাকলেও স্বীকৃতি পাওয়া যায়) দিয়ে শুরু করা ভালো, যেখানে চাপ কম এবং শেখার সুযোগ বেশি।

    কতদিনে প্রথম বৈধ findings পাওয়া যায়?

    এটি ব্যক্তিভেদে ভিন্ন — অনেকের কয়েক সপ্তাহ, অনেকের কয়েক মাস লাগে। ধারাবাহিকতা ও একটি systematic methodology (এই ডকুমেন্টেশনে আলোচিত) অনুসরণ করা সবচেয়ে গুরুত্বপূর্ণ, দ্রুত ফলাফলের প্রত্যাশার চেয়ে।

    এই ডকুমেন্টেশন সিরিজের সম্পূর্ণ চিত্র

    এই "Bug Bounty Methodology" ডকুমেন্টেশন এই সিরিজের একটি সমাপনী দলিল — এটি XSS, CSRF, SQLi, Common Web Vulnerabilities, API Security, Authentication & Authorization, এবং Hacking Tools ডকুমেন্টেশনগুলোতে আলোচিত সব জ্ঞানকে একটি বাস্তব, কাঠামোবদ্ধ ওয়ার্কফ্লোতে একত্রিত করে — কী জানতে হবে থেকে কীভাবে কাজ করতে হবে পর্যন্ত।

    💡

    চূড়ান্ত পরামর্শ: একটি সংগঠিত methodology অনুসরণ করা, ধৈর্য ধরে রাখা, এবং প্রতিটি findings (এমনকি একটি Duplicate বা N/A) থেকে শেখা — এই অভ্যাসগুলোই দীর্ঘমেয়াদে একজন সফল বাগ বাউন্টি হান্টারকে গড়ে তোলে।

    সম্পূর্ণ ডকুমেন্টেশনের সারসংক্ষেপ

    একজন সফল বাগ বাউন্টি হান্টার scope সঠিকভাবে বোঝা দিয়ে শুরু করেন, গভীর ও পদ্ধতিগত reconnaissance করেন, systematically manual ও API টেস্টিং করেন, automation বুদ্ধিমানের সাথে ব্যবহার করেন, প্রতিটি findings যত্নসহকারে triage করেন, একটি স্পষ্ট PoC তৈরি করেন, পেশাদারভাবে রিপোর্ট লেখেন, এবং পুরো প্রক্রিয়া জুড়ে দায়িত্বশীল, নৈতিক আচরণ বজায় রাখেন।

    2. কেন একটি সংগঠিত methodology এলোমেলো টেস্টিং-এর চেয়ে বেশি কার্যকর?
