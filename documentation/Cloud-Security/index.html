    Cloud Security ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Cloud Security গাইড — AWS/Azure/GCP-এর মতো ক্লাউড পরিবেশে ডেটা ও অ্যাপ্লিকেশন কীভাবে সুরক্ষিত রাখা হয়, Shared Responsibility Model কী, এবং IAM থেকে Container/Kubernetes Security পর্যন্ত আধুনিক ক্লাউড-নেটিভ নিরাপত্তা অনুশীলন — ১৫টি অধ্যায়ে সাজানো।

    Cloud Security নিয়ে সংক্ষিপ্ত কথা

    এই সিরিজের আগের ডকুমেন্টেশনগুলো (Network Security, Common Web Vulnerabilities, API Security) মূলত traditional পরিকাঠামো ও অ্যাপ্লিকেশন নিরাপত্তা নিয়ে আলোচনা করেছে। আধুনিক প্রতিষ্ঠানের একটি বিশাল অংশ এখন AWS, Azure, Google Cloud Platform-এর মতো cloud provider-এর উপর নির্ভরশীল — এবং cloud পরিবেশের নিরাপত্তা মডেল traditional on-premise পরিকাঠামো থেকে উল্লেখযোগ্যভাবে ভিন্ন।

    এখানে ধাপে ধাপে দেখানো হয়েছে — Shared Responsibility Model (কোন নিরাপত্তা দায়িত্ব cloud provider-এর, কোনটি গ্রাহকের), IAM (Identity and Access Management), Cloud Storage Security, Cloud Network Security, সাধারণ Cloud Misconfiguration, Container ও Kubernetes Security, Serverless Security, Cloud Monitoring/Logging, Encryption, Compliance, এবং Multi-Cloud/Hybrid পরিবেশের নিরাপত্তা বিবেচনা।

    💡

    এই ডকুমেন্টেশনের প্রকৃতি: এই গাইডটি মূলত ধারণাগত ও provider-নিরপেক্ষ (AWS/Azure/GCP-এর মূল নীতিগুলো সাধারণত একই) — Network Security ডকুমেন্টেশনে আলোচিত Firewall, VLAN, VPN-এর ধারণাগুলো এখানে cloud প্রেক্ষাপটে পুনরায় প্রয়োগ হয়েছে, এবং Common Web Vulnerabilities ডকুমেন্টেশনের Security Misconfiguration অধ্যায়ের সাথে সরাসরি সম্পর্কিত।

    Cloud Computing ও Cloud Security-র ভিত্তি

    নিজের সার্ভার কেনার বদলে, কারো সার্ভার ভাড়া নিয়ে ব্যবহার করলে নিরাপত্তার সমীকরণ কীভাবে বদলে যায়।

    Cloud Computing কী

    Cloud Computing হলো ইন্টারনেটের মাধ্যমে কম্পিউটিং রিসোর্স (সার্ভার, স্টোরেজ, ডেটাবেজ, নেটওয়ার্কিং) অন-ডিমান্ড ব্যবহার করার মডেল — নিজের ফিজিক্যাল সার্ভার কেনা ও রক্ষণাবেক্ষণ করার বদলে, একটি Cloud Provider (AWS, Microsoft Azure, Google Cloud Platform) থেকে প্রয়োজন অনুযায়ী রিসোর্স ভাড়া নেওয়া হয়।

    Cloud Service মডেলের তিনটি প্রধান ধরন

    মডেলকী সরবরাহ করেউদাহরণ
    IaaS (Infrastructure as a Service)শুধু ভার্চুয়াল সার্ভার/স্টোরেজ — বাকি সব (OS, সফটওয়্যার) গ্রাহক নিজে পরিচালনা করেনAWS EC2, Azure VM
    PaaS (Platform as a Service)একটি সম্পূর্ণ ডেভেলপমেন্ট/রানটাইম পরিবেশ — গ্রাহক শুধু কোড ডেপ্লয় করেনAWS Elastic Beanstalk, Heroku
    SaaS (Software as a Service)সম্পূর্ণ প্রস্তুত সফটওয়্যার, সরাসরি ব্যবহারযোগ্যGmail, Salesforce

    Public, Private ও Hybrid Cloud

    🌐 Public Cloud

    একটি cloud provider-এর শেয়ার্ড পরিকাঠামো, যা একাধিক গ্রাহক ব্যবহার করেন (AWS, Azure)।

    🔒 Private Cloud

    একটি একক প্রতিষ্ঠানের জন্য নিবেদিত cloud পরিকাঠামো, নিজস্ব ডেটা সেন্টারে বা dedicated hosted।

    🔀 Hybrid Cloud

    Public ও Private উভয়ের সংমিশ্রণ — সংবেদনশীল ডেটা private-এ, বাকি কাজ public cloud-এ।

    কেন Cloud Security আলাদাভাবে গুরুত্বপূর্ণ

    Network Security ডকুমেন্টেশনে আলোচিত ঐতিহ্যগত "Castle-and-Moat" মডেলে, একটি প্রতিষ্ঠান তার নিজস্ব ফিজিক্যাল পরিকাঠামোর সম্পূর্ণ নিয়ন্ত্রণে থাকত। Cloud পরিবেশে, পরিকাঠামোর একটি উল্লেখযোগ্য অংশ cloud provider নিয়ন্ত্রণ করেন — এই পরিবর্তন একটি সম্পূর্ণ নতুন নিরাপত্তা মডেল দাবি করে, যা পরবর্তী অধ্যায়ে (Shared Responsibility Model) বিস্তারিত আলোচিত হবে।

    💡

    একটি গুরুত্বপূর্ণ ভুল ধারণা: অনেকে মনে করেন "cloud মানেই বেশি নিরাপদ, কারণ একটি বড় কোম্পানি (AWS/Google) এটি পরিচালনা করছে" — এটি আংশিক সত্য। Cloud provider তাদের নিজস্ব পরিকাঠামো অত্যন্ত দক্ষতার সাথে সুরক্ষিত রাখে, কিন্তু গ্রাহকের নিজের কনফিগারেশনের ভুল (misconfiguration) — যেমন একটি পাবলিক S3 bucket — সম্পূর্ণভাবে গ্রাহকের নিজের দায়িত্ব, এবং এটিই সবচেয়ে বেশি data breach-এর কারণ।

    অনুশীলন

    IaaS, PaaS, ও SaaS মডেলে, প্রতিটিতে গ্রাহকের নিয়ন্ত্রণের পরিমাণ কীভাবে ভিন্ন তা একটি তুলনামূলক তালিকা তৈরি করুন।

    সারসংক্ষেপ

    Cloud Computing ইন্টারনেটের মাধ্যমে অন-ডিমান্ড কম্পিউটিং রিসোর্স সরবরাহ করে — IaaS, PaaS, SaaS তিনটি প্রধান মডেল, এবং Public/Private/Hybrid তিনটি ডেপ্লয়মেন্ট ধরন। Cloud পরিবেশে নিরাপত্তা দায়িত্ব cloud provider ও গ্রাহকের মধ্যে ভাগ হয়ে যায়, যা একটি নতুন নিরাপত্তা মডেল দাবি করে।

    Shared Responsibility Model

    Cloud Security বোঝার সবচেয়ে গুরুত্বপূর্ণ একক ধারণা — কোন নিরাপত্তা কাজ কার দায়িত্ব।

    Shared Responsibility Model কী

    Shared Responsibility Model স্পষ্টভাবে সংজ্ঞায়িত করে একটি cloud পরিবেশের নিরাপত্তার কোন অংশ Cloud Provider-এর দায়িত্ব, এবং কোন অংশ গ্রাহক-এর দায়িত্ব। এই বিভাজন না বোঝা একটি অত্যন্ত সাধারণ ও বিপজ্জনক ভুল — "আমরা ভেবেছিলাম AWS এটি সুরক্ষিত রাখবে" একটি বাস্তব data breach-এর সাধারণ কারণ।

    "Security OF the Cloud" বনাম "Security IN the Cloud"

    🏢 Security OF the Cloud (Provider-এর দায়িত্ব)

    ফিজিক্যাল ডেটা সেন্টার নিরাপত্তা, hardware, নেটওয়ার্ক পরিকাঠামো, এবং virtualization layer — এই "নিচের" স্তরগুলোর নিরাপত্তা সম্পূর্ণভাবে cloud provider-এর দায়িত্ব।

    👤 Security IN the Cloud (গ্রাহকের দায়িত্ব)

    ডেটা encryption, IAM কনফিগারেশন, অ্যাপ্লিকেশন কোড, নেটওয়ার্ক কনফিগারেশন (Security Group), ও OS-level patching (IaaS-এ) — এগুলো গ্রাহকের নিজের দায়িত্ব।

    দায়িত্ব বিভাজন সার্ভিস মডেল অনুযায়ী পরিবর্তিত হয়

    যত বেশি একটি সার্ভিস মডেল "ম্যানেজড" (SaaS সবচেয়ে বেশি, IaaS সবচেয়ে কম), ততই বেশি নিরাপত্তা দায়িত্ব provider বহন করেন — কিন্তু Data ও Access Management সবসময়ই গ্রাহকের দায়িত্ব থেকে যায়, যেকোনো মডেলে।

    বাস্তব উদাহরণ — কোথায় ভুল হয়

    ⚠️

    একটি সাধারণ ঘটনা প্রবাহ: AWS একটি S3 bucket-কে অত্যন্ত নিরাপদ পরিকাঠামোতে হোস্ট করে (provider-এর দায়িত্ব, সঠিকভাবে পালিত) — কিন্তু গ্রাহক সেই bucket-এর অ্যাক্সেস সেটিং ভুলবশত "public" করে রাখেন (গ্রাহকের দায়িত্ব, পালিত হয়নি)। ফলাফল একটি data breach, কিন্তু এটি AWS-এর দোষ নয় — এটি Common Web Vulnerabilities ডকুমেন্টেশনের Security Misconfiguration অধ্যায়ে আলোচিত একই ধরনের ভুল, cloud প্রেক্ষাপটে।

    Shared Responsibility বোঝার ব্যবহারিক মূল্য

    একজন নিরাপত্তা পেশাদার হিসেবে, একটি cloud পরিবেশ মূল্যায়ন করার সময়, প্রথম প্রশ্ন হওয়া উচিত — "এই নির্দিষ্ট নিয়ন্ত্রণটি কার দায়িত্ব?" যদি এটি গ্রাহকের দায়িত্ব হয় (যেমন IAM নীতি, encryption সেটিং), তাহলে সেটি সরাসরি পরীক্ষা ও audit করা প্রয়োজন — provider-এর নিরাপত্তার উপর ভরসা করে বসে থাকলে চলবে না।

    অনুশীলন

    IaaS মডেলে OS-level patching কার দায়িত্ব, এবং SaaS মডেলে (যেমন Gmail) একই দায়িত্ব কার — এই পার্থক্যের কারণ ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Shared Responsibility Model নির্ধারণ করে কোন নিরাপত্তা দায়িত্ব cloud provider-এর ("Security OF the Cloud") ও কোনটি গ্রাহকের ("Security IN the Cloud")। Data ও Access Management সবসময় গ্রাহকের দায়িত্বে থাকে, এবং এই বিভাজন ভুল বোঝাই অনেক বাস্তব breach-এর কারণ।

    IAM — Identity and Access Management

    Cloud Security-তে সবচেয়ে গুরুত্বপূর্ণ একক নিয়ন্ত্রণ ব্যবস্থা — "কে, কী করতে পারবে" তার সূক্ষ্ম নিয়ন্ত্রণ।

    IAM কী

    IAM (Identity and Access Management) একটি cloud পরিবেশে প্রতিটি ইউজার, সার্ভিস, বা অ্যাপ্লিকেশনের পরিচয় যাচাই (authentication) ও তাদের কী করার অনুমতি আছে (authorization) তা নিয়ন্ত্রণ করে। Authentication & Authorization ডকুমেন্টেশনে আলোচিত RBAC/ABAC-এর ধারণাগুলো cloud IAM-এ সরাসরি প্রয়োগ হয়, কিন্তু আরও বড় স্কেলে — একটি একক cloud অ্যাকাউন্টে হাজার হাজার রিসোর্স ও অনুমতি থাকতে পারে।

    IAM-এর মূল উপাদান

    উপাদানবর্ণনা
    Userএকজন ব্যক্তি, যার cloud console/API অ্যাক্সেস আছে
    Roleএকটি নির্দিষ্ট permission set, যা একটি user বা service "assume" করতে পারে — নির্দিষ্ট সময়ের জন্য, স্থায়ী credential ছাড়া
    Policyএকটি নির্দিষ্ট অনুমতির ঘোষণা (JSON ফরম্যাটে প্রায়ই) — কোন resource-এ কোন action অনুমোদিত
    Groupএকাধিক user-কে একত্রিত করে একসাথে policy প্রয়োগের সুবিধা

    Principle of Least Privilege — IAM-এর কেন্দ্রীয় নীতি

    Network Security ডকুমেন্টেশনের Zero Trust অধ্যায়ে আলোচিত Least Privilege নীতি IAM-এর ভিত্তি — প্রতিটি user/service-কে শুধুমাত্র তার কাজের জন্য ঠিক ততটুকু অনুমতি দেওয়া উচিত, কোনো অতিরিক্ত "just in case" অনুমতি নয়। একটি অ্যাপ্লিকেশন যদি শুধু একটি নির্দিষ্ট S3 bucket থেকে পড়ার প্রয়োজন হয়, তাকে পুরো cloud অ্যাকাউন্টে admin অনুমতি দেওয়া একটি গুরুতর ভুল।

    একটি IAM Policy-র ধারণাগত উদাহরণ

    ধারণাগত Policy কাঠামো
    {
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-specific-bucket/*"
}
// এই নীতি শুধুমাত্র একটি নির্দিষ্ট bucket থেকে অবজেক্ট পড়ার
// অনুমতি দেয় — পুরো S3 সার্ভিসে নয়, এবং লেখা/মোছার অনুমতি নেই

    Over-privileged IAM — একটি সাধারণ ও বিপজ্জনক ভুল

    🚨

    বাস্তব ঝুঁকি: একজন ডেভেলপার দ্রুত কাজ করতে গিয়ে প্রায়ই একটি অ্যাপ্লিকেশন/service account-কে প্রয়োজনের চেয়ে বেশি অনুমতি (যেমন সম্পূর্ণ "AdministratorAccess") দিয়ে দেন, যাতে "permission error" নিয়ে বারবার বিরক্ত না হতে হয়। কিন্তু যদি এই অ্যাপ্লিকেশনের একটি দুর্বলতা (যেমন SSRF, Common Web Vulnerabilities ডকুমেন্টেশনে আলোচিত) কাজে লাগিয়ে attacker সেই credential হাতিয়ে নেন, তিনি পুরো cloud অ্যাকাউন্টের নিয়ন্ত্রণ পেয়ে যেতে পারেন — একটি ছোট অ্যাপ্লিকেশন দুর্বলতা থেকে সম্পূর্ণ cloud takeover।

    MFA (Multi-Factor Authentication) — IAM-এর জন্য অপরিহার্য

    Authentication ডকুমেন্টেশনে আলোচিত MFA, cloud IAM-এর ক্ষেত্রে বিশেষভাবে গুরুত্বপূর্ণ — বিশেষত root/administrator অ্যাকাউন্টের জন্য, কারণ একটি আপোসকৃত cloud admin অ্যাকাউন্ট পুরো প্রতিষ্ঠানের সব ডেটা ও পরিকাঠামোতে অ্যাক্সেস দিতে পারে।

    অনুশীলন

    কেন একটি অ্যাপ্লিকেশনকে "just in case" অতিরিক্ত IAM অনুমতি দেওয়া, একটি একক দুর্বলতার impact-কে ব্যাপকভাবে বাড়িয়ে দিতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    IAM একটি cloud পরিবেশে প্রতিটি identity-র পরিচয় ও অনুমতি নিয়ন্ত্রণ করে — User, Role, Policy, Group প্রধান উপাদান। Principle of Least Privilege কেন্দ্রীয় নীতি, এবং Over-privileged IAM configuration সবচেয়ে সাধারণ ও বিপজ্জনক cloud নিরাপত্তা ভুলগুলোর একটি।

    Cloud Storage Security

    একটি একক ভুল কনফিগারেশন কীভাবে কোটি কোটি রেকর্ডের একটি ডেটা ব্রিচ ঘটাতে পারে।

    Object Storage কী

    Cloud Storage-এর সবচেয়ে পরিচিত ফর্ম হলো Object Storage (AWS S3, Azure Blob Storage, Google Cloud Storage) — ফাইল, ছবি, ব্যাকআপ, লগ ডেটা সংরক্ষণের জন্য ব্যবহৃত একটি অত্যন্ত scalable স্টোরেজ সিস্টেম, যেখানে প্রতিটি ফাইল একটি "bucket"-এর মধ্যে সংরক্ষিত হয়।

    সবচেয়ে সাধারণ ও বিপজ্জনক ভুল — Public Bucket

    🚨

    বাস্তব প্যাটার্ন: একটি S3 bucket ডিফল্টভাবে প্রাইভেট থাকে, কিন্তু একজন ডেভেলপার প্রায়ই দ্রুত টেস্টিং বা সহজ অ্যাক্সেসের জন্য bucket-কে "public" করে দেন, এবং পরে প্রোডাকশনে সেই সেটিং ফিরিয়ে আনতে ভুলে যান। এই একক ভুল — Common Web Vulnerabilities ডকুমেন্টেশনের Security Misconfiguration অধ্যায়ে আলোচিত একই প্যাটার্ন — ইতিহাসে একাধিক বড় data breach-এর কারণ হয়েছে, যেখানে কোটি কোটি ইউজার রেকর্ড সরাসরি ইন্টারনেটে উন্মুক্ত হয়ে গিয়েছিল, কোনো "হ্যাকিং" ছাড়াই।

    Bucket Security Checklist

    চেকলক্ষ্য
    Public Access Blockনিশ্চিত করা bucket-টি আকস্মিকভাবে পাবলিক না হয়ে যায়, এমনকি individual object policy দিয়েও
    Bucket Policy ও ACL পর্যালোচনাকোন user/role-এর অ্যাক্সেস আছে তা নিয়মিত অডিট করা
    Encryption at Restসংরক্ষিত ডেটা এনক্রিপ্টেড কি না নিশ্চিত করা (অধ্যায় ১১-এ বিস্তারিত)
    Versioning ও Loggingকোন ফাইল কখন অ্যাক্সেস/পরিবর্তিত হয়েছে তার ট্র্যাক রাখা
    MFA Deleteগুরুত্বপূর্ণ bucket থেকে ফাইল মোছার জন্য অতিরিক্ত MFA যাচাই বাধ্যতামূলক করা

    স্বয়ংক্রিয় স্ক্যানিং টুলের ভূমিকা

    যেহেতু একটি বড় প্রতিষ্ঠানের হাজার হাজার bucket থাকতে পারে, ম্যানুয়ালি প্রতিটি যাচাই করা অবাস্তব — Cloud Security Posture Management (CSPM) টুল স্বয়ংক্রিয়ভাবে পুরো cloud অ্যাকাউন্ট স্ক্যান করে, কোনো bucket ভুলভাবে public কি না, বা encryption বন্ধ আছে কি না স্বয়ংক্রিয়ভাবে শনাক্ত করে সতর্ক করে — অনেকটা Hacking Tools ডকুমেন্টেশনের Vulnerability Scanner-এর মতোই, কিন্তু cloud কনফিগারেশনের জন্য বিশেষায়িত।

    Bug Bounty হান্টারদের জন্য একটি প্রাসঙ্গিক সংযোগ

    Bug Bounty Methodology ডকুমেন্টেশনে আলোচিত Asset Discovery-র একটি গুরুত্বপূর্ণ অংশ হলো পাবলিকলি accessible cloud storage bucket খুঁজে বের করা — একটি ভুলভাবে কনফিগার করা bucket, যদি in-scope হয়, একজন হান্টারের জন্য একটি উচ্চ-মূল্যের findings হতে পারে।

    💡

    Default Deny নীতি এখানেও প্রযোজ্য: Network Security ডকুমেন্টেশনের Firewall অধ্যায়ে আলোচিত "Deny by Default, Allow by Exception" নীতি cloud storage-এও সমানভাবে প্রযোজ্য — bucket-কে ডিফল্টভাবে প্রাইভেট রেখে, শুধু স্পষ্টভাবে প্রয়োজনীয় ক্ষেত্রে, সুনির্দিষ্টভাবে অ্যাক্সেস খুলে দেওয়া উচিত।

    অনুশীলন

    কেন একটি CSPM টুল একটি বড় প্রতিষ্ঠানের জন্য প্রায় অপরিহার্য, যেখানে শত শত ডেভেলপার স্বাধীনভাবে নতুন cloud রিসোর্স তৈরি করছেন তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Public Bucket একটি অত্যন্ত সাধারণ ও বিপজ্জনক cloud storage ভুল, যা বহু বড় data breach-এর কারণ হয়েছে। Bucket Security Checklist (Public Access Block, Policy Review, Encryption, Logging, MFA Delete) ও CSPM টুল ব্যবহার করে এই ঝুঁকি কমানো যায়।

    Cloud Network Security

    Network Security ডকুমেন্টেশনের Firewall/VLAN-এর ধারণাগুলো cloud পরিবেশে কীভাবে ভিন্নভাবে বাস্তবায়িত হয়।

    VPC — Virtual Private Cloud

    VPC একটি গ্রাহকের নিজস্ব, যৌক্তিকভাবে বিচ্ছিন্ন (logically isolated) নেটওয়ার্ক পরিবেশ, cloud provider-এর বৃহত্তর অবকাঠামোর মধ্যে — এটি Network Security ডকুমেন্টেশনে আলোচিত VLAN/Network Segmentation-এর ধারণার cloud সংস্করণ, যেখানে গ্রাহক নিজের IP রেঞ্জ, সাবনেট, ও রাউটিং নিয়ম নিজে সংজ্ঞায়িত করতে পারেন।

    Security Group ও Network ACL

    উপাদানকাজFirewall-এর সাথে তুলনা
    Security Groupএকটি individual instance/resource-এর জন্য stateful ফায়ারওয়াল নিয়মNetwork Security ডকুমেন্টেশনের Host-based Firewall-এর মতো
    Network ACLএকটি পুরো সাবনেটের জন্য stateless নিয়মএকটি নেটওয়ার্ক পর্যায়ের Packet-Filtering Firewall-এর মতো

    Public বনাম Private Subnet

    🌐 Public Subnet

    সরাসরি ইন্টারনেট থেকে অ্যাক্সেসযোগ্য — সাধারণত load balancer, বা পাবলিক-facing সার্ভিস এখানে থাকে (Network Security ডকুমেন্টেশনের DMZ-এর মতো)।

    🔒 Private Subnet

    সরাসরি ইন্টারনেট থেকে অ্যাক্সেসযোগ্য নয় — ডেটাবেজ, অভ্যন্তরীণ অ্যাপ্লিকেশন সার্ভার এখানে রাখা হয়, শুধুমাত্র public subnet থেকেই অ্যাক্সেসযোগ্য।

    একটি সাধারণ, নিরাপদ VPC কাঠামোর উদাহরণ

    ধারণাগত কাঠামো
    Internet
   ↓
Load Balancer (Public Subnet)
   ↓
Application Servers (Private Subnet)
   ↓
Database (Private Subnet, সবচেয়ে সীমাবদ্ধ অ্যাক্সেস)

    এই কাঠামো Network Security ডকুমেন্টেশনের DMZ ও Network Segmentation নীতির সরাসরি cloud প্রয়োগ — ডেটাবেজ কখনো সরাসরি ইন্টারনেট থেকে অ্যাক্সেসযোগ্য নয়।

    VPC Peering ও Transit Gateway

    একাধিক VPC-কে নিরাপদে সংযুক্ত করার প্রয়োজন হলে (যেমন ভিন্ন টিমের ভিন্ন VPC-র মধ্যে যোগাযোগ প্রয়োজন), VPC Peering বা Transit Gateway-এর মতো সার্ভিস ব্যবহৃত হয় — তবে প্রতিটি নতুন সংযোগ একটি নতুন সম্ভাব্য আক্রমণ পথ, তাই শুধু প্রয়োজনীয় সংযোগই তৈরি করা উচিত (Least Privilege নীতির নেটওয়ার্ক-স্তরের প্রয়োগ)।

    সাধারণ ভুল: একটি Security Group-এ সহজে ডিবাগ করার জন্য "0.0.0.0/0" (যেকোনো IP থেকে) একটি সংবেদনশীল পোর্টে (যেমন ডেটাবেজ পোর্ট) অ্যাক্সেস খুলে দেওয়া, এবং পরে তা বন্ধ করতে ভুলে যাওয়া — এটি Network Security ডকুমেন্টেশনে আলোচিত "Deny by Default" নীতির সরাসরি লঙ্ঘন।

    অনুশীলন

    কেন একটি ডেটাবেজ সার্ভারকে সবসময় Private Subnet-এ রাখা উচিত, Public Subnet-এ নয়, তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    VPC একটি গ্রাহকের যৌক্তিকভাবে বিচ্ছিন্ন cloud নেটওয়ার্ক পরিবেশ তৈরি করে। Security Group ও Network ACL ট্রাফিক নিয়ন্ত্রণ করে, এবং Public/Private Subnet বিভাজন Network Security ডকুমেন্টেশনের DMZ/Segmentation নীতির সরাসরি cloud প্রয়োগ।

    সাধারণ Cloud Misconfiguration

    Cloud breach-এর সবচেয়ে বড় কারণ — জটিল আক্রমণ নয়, বরং সাধারণ, এড়ানো যায় এমন কনফিগারেশন ভুল।

    কেন Misconfiguration সবচেয়ে বড় ঝুঁকি

    একাধিক শিল্প রিপোর্ট ধারাবাহিকভাবে দেখিয়েছে যে বেশিরভাগ cloud data breach সরাসরি কোনো sophisticated exploit বা zero-day vulnerability-র কারণে ঘটে না — বরং সাধারণ, মানবিক ভুলের কারণে ঘটে। Cloud পরিবেশের জটিলতা (শত শত সেটিং, একাধিক সার্ভিস) এই ঝুঁকি আরও বাড়িয়ে দেয়।

    সবচেয়ে সাধারণ Cloud Misconfiguration

    Misconfigurationঝুঁকি
    Publicly accessible storage bucketসরাসরি ডেটা লিক (অধ্যায় ৪-এ বিস্তারিত)
    Overly permissive IAM policyএকটি একক আপোসকৃত credential দিয়ে ব্যাপক ক্ষতি (অধ্যায় ৩-এ বিস্তারিত)

    Default credentials পরিবর্তন না করাHacking Tools ডকুমেন্টেশনের Security Misconfiguration অধ্যায়ের একই সমস্যা, cloud সার্ভিসে
    Logging/Monitoring নিষ্ক্রিয় রাখাএকটি breach ঘটলেও তা শনাক্ত করতে না পারা (অধ্যায় ১০-এ বিস্তারিত)

    "Shadow IT" ও Unmanaged Cloud Resources

    একটি বড় প্রতিষ্ঠানে, বিভিন্ন টিম স্বাধীনভাবে নতুন cloud রিসোর্স তৈরি করতে পারে — কখনো কখনো কেন্দ্রীয় IT/Security টিমের অজান্তেই। এই Shadow IT রিসোর্সগুলো প্রায়ই hardening checklist অনুসরণ করে না, এবং একটি প্রতিষ্ঠানের সম্পূর্ণ cloud attack surface-এর একটি "অদৃশ্য" অংশ তৈরি করে — Bug Bounty Methodology ডকুমেন্টেশনের Asset Discovery অধ্যায়ের ধারণার একটি প্রাসঙ্গিক প্রতিফলন।

    Infrastructure as Code (IaC) — একটি সমাধান

    💡

    IaC কীভাবে সাহায্য করে: Cloud পরিকাঠামো ম্যানুয়ালি console-এ ক্লিক করে তৈরি করার বদলে, যদি কোড (Terraform, CloudFormation-এর মতো টুল দিয়ে) আকারে সংজ্ঞায়িত করা হয়, তাহলে প্রতিটি পরিবর্তন রিভিউ ও version control-এর মধ্য দিয়ে যায় — এটি মানবিক ভুল কমায় এবং সব রিসোর্স একটি সামঞ্জস্যপূর্ণ, auditable নিরাপত্তা স্ট্যান্ডার্ড অনুসরণ করে তা নিশ্চিত করতে সাহায্য করে।

    নিয়মিত Configuration Audit-এর গুরুত্ব

    অধ্যায় ৪-এ আলোচিত CSPM টুলের মতো, একটি প্রতিষ্ঠানের নিয়মিত (স্বয়ংক্রিয়, ক্রমাগত) পুরো cloud পরিবেশ স্ক্যান করে misconfiguration শনাক্ত করা উচিত — এটি একবারের অডিট নয়, বরং Network Security ডকুমেন্টেশনের Hardening অধ্যায়ে আলোচিত "পুনরাবৃত্তিমূলক প্রক্রিয়া" নীতির cloud সংস্করণ।

    অনুশীলন

    কেন "Shadow IT" রিসোর্স একটি প্রতিষ্ঠানের নিরাপত্তা দলের জন্য বিশেষভাবে উদ্বেগজনক তা ব্যাখ্যা করুন — এগুলো কীভাবে সনাক্ত করা যেতে পারে?

    সারসংক্ষেপ

    Cloud data breach-এর প্রধান কারণ sophisticated আক্রমণ নয়, বরং সাধারণ misconfiguration — public bucket, overly permissive IAM, unencrypted data, disabled logging। Infrastructure as Code ও নিয়মিত automated audit এই ঝুঁকি উল্লেখযোগ্যভাবে কমাতে সাহায্য করে।

    Container Security

    আধুনিক cloud-নেটিভ অ্যাপ্লিকেশনের মৌলিক বিল্ডিং ব্লক — এবং তার নিজস্ব নিরাপত্তা বিবেচনা।

    Container কী

    Container (Docker-এর মাধ্যমে জনপ্রিয়) একটি অ্যাপ্লিকেশন ও তার সব dependency (লাইব্রেরি, কনফিগারেশন)-কে একটি একক, পোর্টেবল প্যাকেজে বন্দী করে — এটি একটি পূর্ণাঙ্গ ভার্চুয়াল মেশিনের তুলনায় অনেক হালকা, কারণ একাধিক container একই অপারেটিং সিস্টেম kernel শেয়ার করে।

    VM বনাম Container — একটি দ্রুত তুলনা

    💻 Virtual Machine

    প্রতিটি VM তার নিজস্ব সম্পূর্ণ OS নিয়ে চলে — ভারী, কিন্তু শক্তিশালী isolation দেয়।

    📦 Container

    একই OS kernel শেয়ার করে — হালকা ও দ্রুত, কিন্তু isolation VM-এর তুলনায় তুলনামূলক কম শক্তিশালী।

    Container Image Security

    একটি container একটি Image থেকে তৈরি হয় — এবং Common Web Vulnerabilities ডকুমেন্টেশনের Vulnerable Components অধ্যায়ের একই নীতি এখানে প্রযোজ্য: যদি একটি container image একটি পুরনো, দুর্বলতাযুক্ত base OS বা লাইব্রেরি ব্যবহার করে, সেই দুর্বলতা প্রতিটি তৈরি হওয়া container-এ বহন হয়ে যায়।

    Container নিরাপত্তার মূল নীতি

    নীতিকেন গুরুত্বপূর্ণ
    Minimal Base Image ব্যবহারযত কম সফটওয়্যার, ততই কম সম্ভাব্য দুর্বলতা ও attack surface
    Container Root User হিসেবে না চালানোContainer escape হলেও, host-এ root অ্যাক্সেস পাওয়া কঠিন হয়
    Immutable Containersএকটি running container-এর ভেতরে সরাসরি পরিবর্তন না করা — পরিবর্তন করতে হলে নতুন image তৈরি করে redeploy করা
    Secrets সরাসরি Image-এ হার্ডকোড না করাCommon Web Vulnerabilities ডকুমেন্টেশনের Sensitive Data Exposure অধ্যায়ের একই নীতি — API key/password আলাদা secret management সিস্টেমে রাখা
    ⚠️

    Container Escape-এর ঝুঁকি: যদিও বিরল, একটি গুরুতর দুর্বলতা একজন attacker-কে container-এর isolation ভেঙে হোস্ট মেশিনে প্রবেশের সুযোগ দিতে পারে — Minimal Privilege নীতি (non-root user, সীমিত capabilities) এই ঝুঁকির প্রভাব কমাতে সাহায্য করে।

    অনুশীলন

    কেন একটি container-কে root user হিসেবে না চালানো একটি গুরুত্বপূর্ণ নিরাপত্তা অনুশীলন তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Container একটি অ্যাপ্লিকেশনকে dependency-সহ প্যাকেজ করে, VM-এর চেয়ে হালকা কিন্তু কম isolation দেয়। Image Scanning দুর্বলতাযুক্ত component CI/CD pipeline-এই শনাক্ত করে, এবং Minimal Base Image, Non-root User, Immutability মূল নিরাপত্তা নীতি।

    Kubernetes ও Orchestration Security

    শত শত container একসাথে পরিচালনা করার সময়, নিরাপত্তা জটিলতা একটি নতুন স্তরে পৌঁছায়।

    Orchestration কেন প্রয়োজন

    একটি বড় অ্যাপ্লিকেশনে শত শত, হাজার হাজার container চলতে পারে — এগুলো ম্যানুয়ালি পরিচালনা করা অসম্ভব। Kubernetes (K8s) একটি container orchestration platform, যা স্বয়ংক্রিয়ভাবে container deploy, scale, ও manage করে।

    Kubernetes-এর মূল উপাদান (সংক্ষিপ্ত)

    উপাদানবর্ণনা
    PodKubernetes-এর সবচেয়ে ছোট deployable একক, এক বা একাধিক container ধারণ করে
    Nodeএকটি ফিজিক্যাল/ভার্চুয়াল মেশিন, যেখানে Pod চলে
    Clusterএকাধিক Node-এর সমষ্টি, যা একসাথে Kubernetes পরিচালনা করে
    API Serverপুরো cluster-এর কেন্দ্রীয় নিয়ন্ত্রণ পয়েন্ট — সব অ্যাডমিনিস্ট্রেটিভ request এখানে আসে

    RBAC in Kubernetes

    অধ্যায় ৩-এ আলোচিত IAM-এর নীতি Kubernetes-এও প্রযোজ্য — Kubernetes RBAC (Role-Based Access Control) নির্ধারণ করে কোন user/service কোন resource-এ কী অ্যাকশন করতে পারবে। একটি ভুলভাবে কনফিগার করা RBAC নীতি (অতিরিক্ত অনুমতি) একটি একক আপোসকৃত Pod থেকে পুরো cluster নিয়ন্ত্রণের সুযোগ তৈরি করতে পারে।

    Network Policy — Pod-পর্যায়ের Segmentation

    ডিফল্টভাবে, একটি Kubernetes cluster-এর মধ্যে সব Pod একে অপরের সাথে অবাধে যোগাযোগ করতে পারে — Network Security ডকুমেন্টেশনের "Flat Network" সমস্যার একটি Kubernetes সংস্করণ। Network Policy ব্যবহার করে, কোন Pod কোন অন্য Pod-এর সাথে যোগাযোগ করতে পারবে তা সীমাবদ্ধ করা যায় — Network Segmentation নীতির একটি granular, Pod-পর্যায়ের প্রয়োগ।

    Secrets Management

    ⚠️

    Kubernetes Secrets সম্পর্কে একটি গুরুত্বপূর্ণ সতর্কতা: Kubernetes-এর built-in "Secret" অবজেক্ট ডিফল্টভাবে শুধু base64-encoded, এনক্রিপ্টেড নয় — base64 encoding কোনো নিরাপত্তা দেয় না, এটি শুধু একটি encoding ফরম্যাট (যে কেউ সহজেই decode করতে পারেন)। সংবেদনশীল তথ্যের জন্য additional encryption at rest, অথবা একটি dedicated secret management সার্ভিস (HashiCorp Vault, AWS Secrets Manager) ব্যবহার করা উচিত।

    Kubernetes Dashboard ও API Server Exposure

    Hacking Tools ডকুমেন্টেশনে আলোচিত reconnaissance কৌশলের একটি বাস্তব প্রয়োগ — একটি ভুলভাবে কনফিগার করা, সরাসরি ইন্টারনেট থেকে অ্যাক্সেসযোগ্য Kubernetes API Server বা Dashboard (authentication ছাড়া বা দুর্বল authentication সহ) একজন attacker-কে পুরো cluster-এর নিয়ন্ত্রণ দিতে পারে — এটি ইতিহাসে একাধিক বাস্তব breach-এর কারণ হয়েছে।

    অনুশীলন

    কেন Kubernetes-এর ডিফল্ট "সব Pod একে অপরের সাথে কথা বলতে পারে" আচরণ একটি নিরাপত্তা ঝুঁকি, এবং Network Policy কীভাবে এটি সমাধান করে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Kubernetes শত শত container পরিচালনা করে, কিন্তু নিজস্ব নিরাপত্তা জটিলতা নিয়ে আসে — RBAC misconfiguration, flat network-এর মতো Pod-communication, এবং Secrets শুধু base64-encoded (এনক্রিপ্টেড নয়) থাকার ঝুঁকি। Network Policy ও সঠিক RBAC এই ঝুঁকি কমাতে সাহায্য করে।

    Serverless Security

    "সার্ভার নেই" মানে এই নয় যে "নিরাপত্তা নিয়ে ভাবতে হবে না" — শুধু ঝুঁকিগুলো ভিন্ন জায়গায় সরে যায়।

    Serverless কী

    Serverless Computing (যেমন AWS Lambda, Azure Functions) -এ ডেভেলপার শুধু কোড লেখেন (একটি "ফাংশন"), এবং cloud provider সম্পূর্ণভাবে পরিচালনা করেন — কোনো সার্ভার provision, scale, বা patch করার প্রয়োজন নেই। ফাংশনটি শুধুমাত্র প্রয়োজনের সময় চালু হয় (event-driven), এবং ব্যবহার অনুযায়ী বিল হয়।

    Shared Responsibility Model-এ Serverless-এর অবস্থান

    অধ্যায় ২-এ আলোচিত Shared Responsibility Model-এ, Serverless সবচেয়ে বেশি দায়িত্ব cloud provider-কে দেয় — OS patching, runtime management সম্পূর্ণ provider-এর দায়িত্ব। কিন্তু Data ও Access Management সবসময় গ্রাহকের দায়িত্বে থেকে যায় — এমনকি serverless-এও।

    Serverless-নির্দিষ্ট নিরাপত্তা ঝুঁকি

    ঝুঁকিবর্ণনা
    Over-permissioned Functionএকটি ফাংশনকে প্রয়োজনের চেয়ে বেশি IAM অনুমতি দেওয়া (অধ্যায় ৩-এর Over-privileged IAM সমস্যার একই প্যাটার্ন)
    Insecure Dependenciesএকটি ফাংশন প্রায়ই অনেক third-party package ব্যবহার করে — Common Web Vulnerabilities ডকুমেন্টেশনের Vulnerable Components ঝুঁকি এখানেও প্রযোজ্য
    Event InjectionInjection ভালনারেবিলিটির একটি নতুন রূপ — একটি ফাংশন যদি event ডেটা (যেমন একটি queue message) যাচাই ছাড়া বিশ্বাস করে
    Insecure Secrets StorageAPI key/credential ফাংশন কোডে হার্ডকোড করা, environment variable-এ unencrypted রাখা
    Excessive Function Timeout/Resourcesএকটি দুর্বলতা কাজে লাগিয়ে, অপ্রয়োজনীয়ভাবে দীর্ঘ-চলমান ফাংশন ট্রিগার করে খরচ বাড়িয়ে দেওয়া (Denial of Wallet আক্রমণ)

    Attack Surface পরিবর্তন — প্রতিটি Function একটি Entry Point

    💡

    একটি গুরুত্বপূর্ণ দৃষ্টিভঙ্গি পরিবর্তন: একটি traditional অ্যাপ্লিকেশনে Attack Surface Mapping (Bug Bounty Methodology ডকুমেন্টেশনে আলোচিত) মূলত একটি একক অ্যাপ্লিকেশনের endpoint নিয়ে কাজ করত। Serverless আর্কিটেকচারে, একটি অ্যাপ্লিকেশন শত শত ছোট, independent ফাংশনে বিভক্ত হতে পারে — প্রতিটি ফাংশন একটি পৃথক entry point, এবং প্রতিটির নিজস্ব IAM permission, input validation, ও monitoring প্রয়োজন।

    "Denial of Wallet" — একটি Serverless-নির্দিষ্ট ঝুঁকি

    Network Security ডকুমেন্টেশনে আলোচিত DDoS সাধারণত সার্ভিস অনুপলব্ধ করে দেয় (Denial of Service) — Serverless-এ একটি নতুন সম্পর্কিত ঝুঁকি আছে, Denial of Wallet: যেহেতু serverless ব্যবহার অনুযায়ী বিল হয়, একটি attacker ইচ্ছাকৃতভাবে একটি ফাংশন বারবার ট্রিগার করে একটি প্রতিষ্ঠানের cloud বিল অস্বাভাবিকভাবে বাড়িয়ে দিতে পারেন, সার্ভিস ব্যাহত না করেও।

    অনুশীলন

    কেন serverless আর্কিটেকচারে প্রতিটি individual function-এর জন্য আলাদা, সূক্ষ্ম IAM permission নির্ধারণ করা (একটি একক broad permission-এর বদলে) গুরুত্বপূর্ণ তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Serverless Computing OS/runtime management cloud provider-কে দেয়, কিন্তু Data ও Access Management গ্রাহকের দায়িত্বে থাকে। Over-permissioned function, insecure dependencies, event injection, ও Denial of Wallet serverless-নির্দিষ্ট ঝুঁকি, এবং প্রতিটি function-কে একটি পৃথক entry point হিসেবে বিবেচনা করা জরুরি।

    Cloud Monitoring ও Logging

    Network Security ডকুমেন্টেশনের SIEM নীতি cloud পরিবেশে কীভাবে প্রয়োগ হয় — "কী ঘটছে" ক্রমাগত জানা।

    কেন Cloud Logging বিশেষভাবে গুরুত্বপূর্ণ

    একটি cloud পরিবেশে, একটি অ্যাকশন (একটি নতুন IAM user তৈরি, একটি Security Group পরিবর্তন, একটি bucket পাবলিক করা) মাত্র কয়েক সেকেন্ডে, একটি API call দিয়ে ঘটতে পারে — কোনো ফিজিক্যাল প্রমাণ ছাড়াই। যদি এই পরিবর্তনগুলো লগ করা না থাকে, একটি breach-এর পর "কী ঘটেছিল" পুনর্গঠন করা প্রায় অসম্ভব হয়ে যায়।

    Activity Logging — কে, কী, কখন করেছেন

    প্রতিটি প্রধান cloud provider একটি কেন্দ্রীয় activity logging সার্ভিস সরবরাহ করে (AWS CloudTrail, Azure Monitor, GCP Cloud Audit Logs) — এটি প্রতিটি API call রেকর্ড করে: কোন user/role, কোন সময়, কোন resource-এ, কী action করেছেন। Hacking Tools ডকুমেন্টেশনের Digital Forensics অধ্যায়ে আলোচিত "Chain of Custody"-র ধারণা এখানেও প্রাসঙ্গিক — এই লগগুলো প্রায়ই একটি incident investigation-এর প্রাথমিক উৎস।

    Monitoring-এর স্তর

    স্তরকী মনিটর করে
    Activity/Audit Logsকে, কখন, কোন প্রশাসনিক অ্যাকশন নিয়েছেন (API-level)
    Application Logsএকটি নির্দিষ্ট অ্যাপ্লিকেশনের ভেতরের ঘটনা (error, request)
    Network Flow LogsVPC-র মধ্যে ট্রাফিক প্যাটার্ন (অধ্যায় ৫-এর Network Security-র সাথে সম্পর্কিত)
    Threat Detectionস্বয়ংক্রিয়ভাবে সন্দেহজনক প্যাটার্ন শনাক্তকারী সার্ভিস (যেমন AWS GuardDuty)

    Alerting — শুধু লগ রাখা যথেষ্ট নয়

    ⚠️

    একটি সাধারণ ভুল: অনেক প্রতিষ্ঠান logging সক্রিয় করে, কিন্তু কেউ নিয়মিত সেই লগ পর্যালোচনা করেন না — ফলে একটি breach মাসের পর মাস অলক্ষিত থেকে যেতে পারে, যদিও সব প্রমাণ লগে বিদ্যমান ছিল। Network Security ডকুমেন্টেশনের SIEM অধ্যায়ের নীতি অনুযায়ী, সক্রিয় Alerting (নির্দিষ্ট সন্দেহজনক প্যাটার্নে স্বয়ংক্রিয় সতর্কতা) ছাড়া logging-এর ব্যবহারিক মূল্য অনেক কম।

    একটি গুরুত্বপূর্ণ Alert-এর উদাহরণ

    ধারণাগত Alert Rule
    IF (root/admin অ্যাকাউন্ট থেকে একটি অস্বাভাবিক সময়ে লগইন)
   OR (একটি IAM policy-তে ব্যাপক নতুন অনুমতি যোগ করা হয়েছে)
   OR (একটি Security Group-এ 0.0.0.0/0 থেকে একটি সংবেদনশীল পোর্ট খোলা হয়েছে)
THEN ALERT: নিরাপত্তা টিমকে তাৎক্ষণিক সতর্ক করা

    Log Immutability ও Centralization

    একজন attacker, যদি একটি সিস্টেম আপোস করতে সক্ষম হন, প্রায়ই নিজের কার্যকলাপের প্রমাণ মুছে ফেলার চেষ্টা করেন। তাই লগগুলো একটি পৃথক, সীমিত-অ্যাক্সেস কেন্দ্রীয় অবস্থানে সংরক্ষণ করা উচিত (যেখানে স্বাভাবিক অ্যাডমিন অ্যাক্সেসও সেগুলো মুছতে পারে না) — এটি Chain of Custody-র integrity বজায় রাখে।

    অনুশীলন

    কেন শুধু logging সক্রিয় করা যথেষ্ট নয় — সক্রিয় Alerting ছাড়া logging-এর ব্যবহারিক সীমাবদ্ধতা কী তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Cloud Activity Logging (CloudTrail-এর মতো) প্রতিটি API call রেকর্ড করে, যা incident investigation-এর ভিত্তি তৈরি করে। Monitoring একাধিক স্তরে (Activity, Application, Network, Threat Detection) কাজ করে, এবং সক্রিয় Alerting ছাড়া শুধু logging-এর ব্যবহারিক মূল্য সীমিত।

    Encryption at Rest ও in Transit — একটি পুনরালোচনা

    Common Web Vulnerabilities ডকুমেন্টেশনে আলোচিত এই দুটি ধারণা cloud-এ সরাসরি প্রযোজ্য — at Rest (storage-এ সংরক্ষিত ডেটা এনক্রিপ্টেড) ও in Transit (নেটওয়ার্কে প্রবাহিত ডেটা এনক্রিপ্টেড, TLS দিয়ে — Network Security ডকুমেন্টেশনে বিস্তারিত)। একটি সম্পূর্ণ cloud নিরাপত্তা কৌশলে উভয়ই নিশ্চিত করা প্রয়োজন।

    Cloud-এ Encryption সহজ করার একটি সুবিধা

    💡

    Cloud-এর একটি বাস্তব সুবিধা: ঐতিহ্যগত on-premise পরিকাঠামোতে, সঠিকভাবে encryption বাস্তবায়ন করা জটিল ছিল — cloud provider এখন প্রায় প্রতিটি storage সার্ভিসে "one-click" encryption at rest সরবরাহ করে। এই সুবিধা থাকা সত্ত্বেও, অধ্যায় ৬-এ আলোচিত misconfiguration-এর কারণে অনেক প্রতিষ্ঠান এটি সক্রিয় করতে ভুলে যান — একটি সহজলভ্য সুরক্ষা অব্যবহৃত থেকে যায়।

    KMS — Key Management Service

    KMS একটি কেন্দ্রীভূত সার্ভিস, যা encryption key তৈরি, সংরক্ষণ, ও ঘোরানো (rotation) পরিচালনা করে — Authentication ডকুমেন্টেশনে আলোচিত key management-এর একটি cloud-নেটিভ সমাধান। KMS ব্যবহার করলে, ডেভেলপারদের নিজেদের cryptography বাস্তবায়ন করতে হয় না (যা প্রায়ই ভুলভাবে করা হয়), বরং একটি পরীক্ষিত, প্রতিষ্ঠিত সিস্টেম ব্যবহার করা যায়।

    Customer-Managed Key বনাম Provider-Managed Key

    ধরননিয়ন্ত্রণট্রেড-অফ
    Provider-Managed KeyCloud provider সম্পূর্ণ key lifecycle পরিচালনা করেসহজ, কিন্তু কম নিয়ন্ত্রণ
    Customer-Managed Key (CMK)গ্রাহক নিজে key তৈরি, rotation নীতি, ও অ্যাক্সেস নিয়ন্ত্রণ করেনবেশি নিয়ন্ত্রণ ও compliance flexibility, কিন্তু বেশি দায়িত্ব

    Key Rotation-এর গুরুত্ব

    একটি encryption key দীর্ঘদিন ধরে অপরিবর্তিত থাকলে, যদি কোনোভাবে সেই key আপোস হয়, সব historical ডেটা ঝুঁকিতে পড়ে। নিয়মিত Key Rotation (পুরনো key নিষ্ক্রিয় করে নতুন key দিয়ে প্রতিস্থাপন) এই ঝুঁকি সীমিত করে — একটি আপোসকৃত পুরনো key দিয়ে শুধু একটি নির্দিষ্ট সময়সীমার ডেটা প্রভাবিত হয়, সবকিছু নয়।

    Field-Level Encryption

    পুরো ডেটাবেজ এনক্রিপ্ট করার পাশাপাশি, বিশেষভাবে সংবেদনশীল ক্ষেত্র (যেমন ক্রেডিট কার্ড নম্বর, SSN) আলাদাভাবে, অতিরিক্ত স্তরে এনক্রিপ্ট করা যেতে পারে — এটি Common Web Vulnerabilities ডকুমেন্টেশনের Defense in Depth নীতির একটি প্রয়োগ, যেখানে একটি একক দুর্বলতা (ডেটাবেজ-লেভেল এনক্রিপশন bypass হলেও) সবচেয়ে সংবেদনশীল ডেটা উন্মুক্ত করে না।

    অনুশীলন

    কেন নিয়মিত Key Rotation একটি স্ট্যাটিক, কখনো-পরিবর্তিত-না-হওয়া encryption key-র চেয়ে বেশি নিরাপদ তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Cloud provider encryption at rest/in transit সহজলভ্য করেছে, কিন্তু সক্রিয় করা গ্রাহকের দায়িত্ব। KMS কেন্দ্রীভূতভাবে encryption key পরিচালনা করে, Customer-Managed Key অতিরিক্ত নিয়ন্ত্রণ দেয়, এবং নিয়মিত Key Rotation ও Field-Level Encryption অতিরিক্ত সুরক্ষা স্তর তৈরি করে।

    Cloud Compliance ও Governance

    শুধু "নিরাপদ" হওয়া যথেষ্ট নয় — অনেক ক্ষেত্রে নির্দিষ্ট আইনি ও শিল্প মানদণ্ড মেনে চলার প্রমাণও দিতে হয়।

    Compliance কী এবং কেন গুরুত্বপূর্ণ

    Compliance হলো নির্দিষ্ট আইন, রেগুলেশন, বা শিল্প মানদণ্ডের প্রয়োজনীয়তা পূরণ করা — একটি প্রতিষ্ঠান শুধু "নিরাপদ অনুভব করা" যথেষ্ট নয়, বরং নির্দিষ্ট, auditable মানদণ্ড মেনে চলার প্রমাণ দিতে সক্ষম হতে হয়, বিশেষত যদি তারা সংবেদনশীল ডেটা (স্বাস্থ্য তথ্য, আর্থিক তথ্য) পরিচালনা করে।

    পরিচিত Compliance Framework

    Frameworkকাদের জন্য প্রাসঙ্গিক
    GDPRইউরোপীয় ইউজারদের ব্যক্তিগত ডেটা পরিচালনাকারী যেকোনো প্রতিষ্ঠান
    PCI-DSSক্রেডিট কার্ড ডেটা পরিচালনাকারী প্রতিষ্ঠান
    HIPAAস্বাস্থ্য তথ্য পরিচালনাকারী প্রতিষ্ঠান (মার্কিন যুক্তরাষ্ট্র)
    ISO 27001একটি সাধারণ তথ্য নিরাপত্তা ব্যবস্থাপনা মানদণ্ড, বিশ্বব্যাপী স্বীকৃত
    SOC 2SaaS/cloud সার্ভিস প্রদানকারীদের জন্য একটি সাধারণ মানদণ্ড, গ্রাহকদের আস্থা প্রদানের জন্য

    Compliance বনাম Security — একটি গুরুত্বপূর্ণ পার্থক্য

    ⚠️

    "Compliant মানেই সম্পূর্ণ নিরাপদ নয়": একটি প্রতিষ্ঠান একটি নির্দিষ্ট compliance checklist-এর সব আইটেম পূরণ করেও, এখনও গুরুতর নিরাপত্তা দুর্বলতার শিকার হতে পারে — compliance একটি ন্যূনতম বেসলাইন নির্ধারণ করে, নিরাপত্তার সর্বোচ্চ মান নয়। Compliance-কে "চেকবক্স টিক দেওয়া" হিসেবে না দেখে, প্রকৃত নিরাপত্তা অনুশীলনের একটি উপসেট হিসেবে দেখা উচিত।

    Cloud Governance — নীতি কেন্দ্রীয়ভাবে প্রয়োগ করা

    Governance হলো একটি প্রতিষ্ঠানের নির্ধারিত নিরাপত্তা/compliance নীতি পুরো cloud পরিবেশে ধারাবাহিকভাবে প্রয়োগের প্রক্রিয়া। Policy as Code-এর মতো টুল (Open Policy Agent-এর মতো) ব্যবহার করে, একটি প্রতিষ্ঠান স্বয়ংক্রিয়ভাবে নিশ্চিত করতে পারে যে নতুন তৈরি হওয়া কোনো resource প্রতিষ্ঠানের নীতি লঙ্ঘন করছে না (যেমন encryption বাধ্যতামূলক, নির্দিষ্ট region-এর বাইরে resource তৈরি নিষিদ্ধ)।

    Audit-এর জন্য প্রস্তুতি

    একটি compliance audit-এর সময়, একটি প্রতিষ্ঠানকে প্রমাণ দেখাতে হয় যে তারা তাদের নীতি অনুসরণ করছেন — এই কারণে অধ্যায় ১০-এ আলোচিত Activity Logging এত গুরুত্বপূর্ণ: একটি সুসংগঠিত, centralized লগ সিস্টেম একটি audit-এর সময় প্রয়োজনীয় প্রমাণ দ্রুত সরবরাহ করতে সাহায্য করে।

    অনুশীলন

    কেন "আমরা ISO 27001 compliant" একটি প্রতিষ্ঠানকে সম্পূর্ণভাবে breach-প্রুফ প্রমাণ করে না তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Compliance Framework (GDPR, PCI-DSS, HIPAA, ISO 27001, SOC 2) নির্দিষ্ট আইনি/শিল্প মানদণ্ড নির্ধারণ করে, কিন্তু compliance সর্বোচ্চ নিরাপত্তার গ্যারান্টি নয়, একটি ন্যূনতম বেসলাইন। Cloud Governance ও Policy as Code নীতি পুরো cloud পরিবেশে ধারাবাহিকভাবে প্রয়োগ করতে সাহায্য করে।

    Multi-Cloud ও Hybrid Cloud Security

    একাধিক cloud provider বা cloud ও on-premise একসাথে ব্যবহার করলে কী অতিরিক্ত ঝুঁকি তৈরি হয়।

    Multi-Cloud ও Hybrid Cloud কী

    পরিভাষাসংজ্ঞা
    Multi-Cloudএকাধিক cloud provider (যেমন AWS + Azure) একসাথে ব্যবহার করা
    Hybrid CloudPublic cloud ও প্রতিষ্ঠানের নিজস্ব on-premise পরিকাঠামো একসাথে ব্যবহার করা

    প্রতিষ্ঠানগুলো এই পথ বেছে নেয় বিভিন্ন কারণে — vendor lock-in এড়ানো, নির্দিষ্ট সার্ভিসের জন্য সেরা provider বেছে নেওয়া, বা নির্দিষ্ট ডেটা আইনগত কারণে on-premise রাখার প্রয়োজন।

    বাড়তি জটিলতা, বাড়তি ঝুঁকি

    ⚠️

    মূল চ্যালেঞ্জ — সামঞ্জস্য (Consistency): প্রতিটি cloud provider-এর নিজস্ব IAM মডেল, নিজস্ব নিরাপত্তা টুল, নিজস্ব terminology আছে। একটি একক, সামঞ্জস্যপূর্ণ নিরাপত্তা নীতি একাধিক পরিবেশে বজায় রাখা কঠিন — একটি পরিবেশে কঠোর একটি নিয়ম অন্য পরিবেশে ভুলবশত অনুপস্থিত থাকতে পারে, যা একটি অসামঞ্জস্যপূর্ণ আক্রমণ-তল (attack surface) তৈরি করে।

    Multi-Cloud/Hybrid-এর সাধারণ নিরাপত্তা সমস্যা

    • অসামঞ্জস্যপূর্ণ Access Control — একটি provider-এ একটি user-এর অনুমতি সীমিত, কিন্তু অন্য provider-এ ভুলভাবে বিস্তৃত
    • দৃশ্যমানতার ফাঁক (Visibility Gap) — একটি একক কেন্দ্রীয় ড্যাশবোর্ড ছাড়া, কোন পরিবেশে কী ঘটছে তা পুরোপুরি বোঝা কঠিন (অধ্যায় ১০-এর Monitoring সমস্যার একটি বর্ধিত রূপ)
    • ডেটা ট্রান্সফার ঝুঁকি — পরিবেশের মধ্যে ডেটা স্থানান্তরের সময় encryption in transit (অধ্যায় ১১) নিশ্চিত করা আবশ্যক
    • বিভিন্ন Compliance প্রয়োজনীয়তা — ভিন্ন region/provider ভিন্ন compliance নিয়ম মেনে চলতে পারে

    সমাধানের দিকনির্দেশ

    কেন্দ্রীয় Identity Provider

    একটি একক Identity Provider (SSO) দিয়ে সব cloud পরিবেশে অ্যাক্সেস নিয়ন্ত্রণ করলে, একাধিক আলাদা IAM সিস্টেম পরিচালনার জটিলতা কমে — Authentication ডকুমেন্টেশনের SSO অধ্যায়ের প্রয়োগ।

    Cross-Cloud CSPM

    একটি CSPM টুল (অধ্যায় ৪-এ আলোচিত) যা একাধিক provider জুড়ে misconfiguration স্ক্যান করতে পারে, একটি একক দৃশ্যমানতা স্তর তৈরি করে।

    Infrastructure as Code-এর ভূমিকা

    অধ্যায় ৬-এ আলোচিত Infrastructure as Code (IaC) multi-cloud পরিবেশেও সহায়ক — একটি প্রমিত, সংস্করণ-নিয়ন্ত্রিত টেমপ্লেট ব্যবহার করে, একটি প্রতিষ্ঠান বিভিন্ন provider জুড়ে একই নিরাপত্তা নীতি ধারাবাহিকভাবে প্রয়োগ করতে পারে, মানবিক ভুলের সম্ভাবনা কমিয়ে।

    অনুশীলন

    কেন একাধিক cloud provider ব্যবহার করলে "সামঞ্জস্যপূর্ণ নিরাপত্তা নীতি" বজায় রাখা বিশেষভাবে চ্যালেঞ্জিং হয়ে ওঠে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Multi-Cloud ও Hybrid Cloud পরিবেশ vendor lock-in এড়ানো ও flexibility দেয়, কিন্তু সামঞ্জস্যপূর্ণ Access Control, কেন্দ্রীভূত দৃশ্যমানতা, ও ডেটা ট্রান্সফার নিরাপত্তা নিশ্চিত করা কঠিন করে তোলে — কেন্দ্রীয় Identity Provider, Cross-Cloud CSPM, ও Infrastructure as Code এই জটিলতা কমাতে সাহায্য করে।

    Cloud Security Hardening Checklist

    এই ডকুমেন্টেশনের সব অধ্যায়ের ধারণা একত্র করে, একটি ব্যবহারিক চেকলিস্ট।

    কেন একটি চেকলিস্ট

    এখন পর্যন্ত আলোচিত প্রতিটি ধারণা (IAM, Storage, Network, Container, Monitoring, Encryption, Compliance) একত্র করে, একটি সহজে অনুসরণযোগ্য checklist তৈরি করা হয়েছে — এটি কোনো প্রতিষ্ঠানের জন্য "কোথা থেকে শুরু করব" প্রশ্নের একটি ব্যবহারিক উত্তর, যদিও এটি একটি সম্পূর্ণ নিরাপত্তা অডিটের বিকল্প নয়।

    Identity ও Access

    আইটেমবিস্তারিত
    Root/Master অ্যাকাউন্টে MFAপ্রাথমিক, সবচেয়ে শক্তিশালী অ্যাকাউন্টে MFA বাধ্যতামূলক
    Principle of Least Privilegeপ্রতিটি role/policy পর্যায়ক্রমে পর্যালোচনা করে অপ্রয়োজনীয় অনুমতি সরানো
    অব্যবহৃত credential সরানোপুরনো access key ও অব্যবহৃত user অ্যাকাউন্ট নিষ্ক্রিয় করা

    Storage ও Network

    আইটেমবিস্তারিত
    Public Access Blockসব storage bucket-এ ডিফল্টভাবে পাবলিক অ্যাক্সেস বন্ধ
    Encryption at Rest সক্রিয়সব storage ও database-এ এনক্রিপশন সক্রিয় করা
    Security Group auditকোনো নিয়মে 0.0.0.0/0 অপ্রয়োজনীয়ভাবে খোলা আছে কিনা পরীক্ষা

    Container/Kubernetes ও Serverless

    আইটেমবিস্তারিত
    Image scanningCI/CD pipeline-এ স্বয়ংক্রিয় vulnerability স্ক্যান
    RBAC কনফিগারেশনKubernetes-এ সঠিকভাবে Role-Based Access Control সেট করা
    Serverless function অনুমতিপ্রতিটি function-এর জন্য ন্যূনতম প্রয়োজনীয় IAM অনুমতি

    Monitoring ও Governance

    আইটেমবিস্তারিত
    Activity Logging সক্রিয়সব গুরুত্বপূর্ণ অ্যাকশন লগ হচ্ছে তা নিশ্চিত করা
    Alerting কনফিগার করাসন্দেহজনক প্যাটার্নে স্বয়ংক্রিয় সতর্কতা
    Infrastructure as Code ব্যবহারসামঞ্জস্যপূর্ণ, auditable কনফিগারেশন
    💡

    এই checklist একটি শুরুর বিন্দু — প্রকৃত বাস্তবায়নে, প্রতিটি প্রতিষ্ঠানের নিজস্ব risk assessment অনুযায়ী অগ্রাধিকার ঠিক করা উচিত, এবং Common Web Vulnerabilities ডকুমেন্টেশনের Vulnerability Management অধ্যায়ে আলোচিত নিয়মিত পর্যালোচনা প্রক্রিয়ার অংশ হিসেবে এটি ব্যবহার করা উচিত।

    মূল শব্দকোষ

    পরিভাষাব্যাখ্যা
    IaaS/PaaS/SaaSCloud সার্ভিস মডেল — পরিকাঠামো, প্ল্যাটফর্ম, সফটওয়্যার
    Shared Responsibility ModelProvider ও গ্রাহকের মধ্যে নিরাপত্তা দায়িত্বের বিভাজন

    Least Privilegeশুধু প্রয়োজনীয় ন্যূনতম অনুমতি দেওয়ার নীতি
    VPCVirtual Private Cloud — cloud-এ একটি বিচ্ছিন্ন নেটওয়ার্ক পরিবেশ
    Security Group / NACLCloud নেটওয়ার্ক ট্রাফিক নিয়ন্ত্রণকারী ফায়ারওয়াল-জাতীয় নিয়ম
    CSPMCloud Security Posture Management — misconfiguration স্বয়ংক্রিয় শনাক্তকারী টুল

    RBACRole-Based Access Control
    Serverlessপরিকাঠামো পরিচালনা ছাড়াই কোড চালানোর মডেল (যেমন AWS Lambda)
    KMSKey Management Service — encryption key কেন্দ্রীয়ভাবে পরিচালনা

    প্রায়শই জিজ্ঞাসিত প্রশ্ন

    Cloud কি on-premise-এর চেয়ে বেশি নিরাপদ?

    না বা হ্যাঁ — কোনোটিই সরলভাবে সঠিক নয়। Cloud provider-রা সাধারণত অবকাঠামোগত নিরাপত্তায় (অধ্যায় ২) বিশাল বিনিয়োগ করে, কিন্তু Shared Responsibility Model-এর "গ্রাহকের অংশ" (কনফিগারেশন, IAM) ভুল হলে একটি cloud পরিবেশও সমানভাবে ঝুঁকিপূর্ণ হতে পারে।

    একজন শিক্ষার্থী হিসেবে Cloud Security শেখা কীভাবে শুরু করব?

    একটি ফ্রি-টিয়ার cloud অ্যাকাউন্ট (AWS/Azure/GCP) তৈরি করে, ছোট প্রজেক্টে IAM, Security Group, ও S3-জাতীয় storage কনফিগার করার মাধ্যমে ব্যবহারিক অভিজ্ঞতা অর্জন করা যায় — তবে সবসময় free-tier সীমার মধ্যে থেকে, যাতে অপ্রত্যাশিত বিল না আসে।

    এই ডকুমেন্টেশনের সাথে এই সিরিজের অন্য কোন ডকুমেন্টেশন সম্পর্কিত?

    Network Security (VPC/Firewall-এর ভিত্তি), Common Web Vulnerabilities (Security Misconfiguration, Encryption), Authentication/Authorization (MFA, SSO), এবং Bug Bounty Methodology (Attack Surface Mapping, Asset Discovery) — এই চারটি ডকুমেন্টেশনের সাথে এই গাইডের ধারণাগুলো সরাসরি সংযুক্ত।

    কোর্স সম্পন্ন!

    অভিনন্দন — আপনি Cloud Security ডকুমেন্টেশনের সবগুলো অধ্যায় সম্পন্ন করেছেন। Shared Responsibility Model থেকে শুরু করে IAM, Storage/Network Security, Container/Kubernetes/Serverless Security, Monitoring, Encryption, Compliance, ও Multi-Cloud পরিবেশ পর্যন্ত — আপনি এখন আধুনিক cloud-নেটিভ নিরাপত্তার একটি দৃঢ় ভিত্তি অর্জন করেছেন।
