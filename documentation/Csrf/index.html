    Cross-Site Request Forgery (CSRF) ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Basic থেকে Advanced CSRF শেখার গাইড — থিওরি, attack PoC অ্যানালাইসিস, Burp Suite দিয়ে ম্যানুয়াল টেস্টিং, টোকেন/SameSite ভিত্তিক প্রতিরক্ষা এবং বাগ বাউন্টি ওয়ার্কফ্লো পর্যন্ত, ১৫টি অধ্যায়ে সাজানো।

    CSRF নিয়ে সংক্ষিপ্ত কথা

    Cross-Site Request Forgery (CSRF) একটি ওয়েব অ্যাপ্লিকেশন vulnerability, যেখানে attacker ভিকটিমের ব্রাউজারকে প্রতারিত করে, ভিকটিমের অজান্তে, তার নিজের অথেন্টিকেটেড সেশন ব্যবহার করে একটি অনিচ্ছাকৃত request পাঠাতে বাধ্য করে। XSS-এর মতো এখানে কোনো কোড ইনজেকশন লাগে না — বরং ব্রাউজারের একটি স্বাভাবিক আচরণ (প্রতিটি request-এর সাথে স্বয়ংক্রিয়ভাবে cookie পাঠানো) কাজে লাগানো হয়।

    এই ডকুমেন্টেশনে ধাপে ধাপে দেখানো হয়েছে — CSRF কেন ঘটে, browser কীভাবে request ও cookie হ্যান্ডেল করে, GET/POST/JSON/Login/Logout CSRF-এর পার্থক্য, vulnerable endpoint শনাক্তকরণ, CSRF token ও SameSite cookie কীভাবে কাজ করে এবং কীভাবে bypass হতে পারে, Burp Suite দিয়ে বাস্তব ম্যানুয়াল টেস্টিং, আধুনিক SPA/REST API/GraphQL-এ CSRF-এর ঝুঁকি, impact assessment, secure coding, এবং সবশেষে একটি দায়িত্বশীল bug bounty workflow।

    CSRF এর ভিত্তি (CSRF Fundamentals)

    Cross-Site Request Forgery আসলে কী, কেন ঘটে এবং অন্যান্য vulnerability থেকে এটি কীভাবে আলাদা — এই অধ্যায়ে সেই ভিত্তিটা তৈরি হবে।

    ⚖️

    আইনি নোটিশ: এই অধ্যায়ে উল্লেখিত যেকোনো ধারণা বা উদাহরণ শুধুমাত্র নিজের তৈরি lab, অনুমোদিত training platform (PortSwigger, OWASP Juice Shop, DVWA ইত্যাদি) অথবা স্পষ্টভাবে scope-ভুক্ত bug bounty প্রোগ্রামে প্রয়োগ করুন। অনুমতি ছাড়া কোনো সিস্টেমে প্রয়োগ করলে তা আইনত দণ্ডনীয় অপরাধ।

    CSRF কী এবং কেন ঘটে

    সংজ্ঞা: Cross-Site Request Forgery (CSRF) হলো একটি vulnerability, যেখানে একটি দূষিত ওয়েবসাইট, ইমেইল বা লিঙ্ক ভিকটিমের ব্রাউজারকে প্রতারিত করে এমন একটি HTTP request পাঠাতে বাধ্য করে, যা একটি সম্পূর্ণ ভিন্ন (target) ওয়েবসাইটে পৌঁছায় — এবং ভিকটিম যেহেতু সেই target সাইটে আগে থেকেই লগইন করা আছেন, ব্রাউজার স্বয়ংক্রিয়ভাবে সেই request-এর সাথে ভিকটিমের session cookie জুড়ে পাঠিয়ে দেয়। ফলে target সাইট request-টিকে ভিকটিমের নিজের, ইচ্ছাকৃত action হিসেবে গ্রহণ করে।

    কেন ঘটে: ব্রাউজারের একটি মৌলিক, বহু পুরনো আচরণ হলো — কোনো ওয়েবসাইটে request পাঠানোর সময়, সেই ওয়েবসাইটের জন্য সংরক্ষিত cookie স্বয়ংক্রিয়ভাবে সংযুক্ত করে দেওয়া, request-টি কোন পৃষ্ঠা থেকে (কোন origin থেকে) এসেছে তা বিবেচনা না করেই। যদি সার্ভার শুধুমাত্র "একটি বৈধ session cookie আছে কি না" যাচাই করে, কিন্তু request-টি সত্যিই ভিকটিম নিজে, নিজের সাইট থেকে, ইচ্ছাকৃতভাবে পাঠিয়েছেন কি না তা যাচাই না করে — তখনই CSRF সম্ভব হয়।

    একটি সহজ উদাহরণ (Beginner-friendly)

    ধরা যাক একটি ব্যাংকিং অ্যাপ্লিকেশনে টাকা ট্রান্সফারের জন্য এই এন্ডপয়েন্ট ব্যবহৃত হয়:

    BankMock — ট্রান্সফার এন্ডপয়েন্ট (lab-only, ধারণাগত)
    GET https://bankmock.example/transfer?to=rahim&amount=5000

(কোনো CSRF token নেই, শুধু session cookie দিয়ে ইউজার identify করা হয়)

    ভিকটিম যদি লগইন করা অবস্থায় (session cookie ব্রাউজারে সক্রিয়) একটি দূষিত সাইট ভিজিট করেন, এবং সেই সাইটে এমন একটি HTML থাকে:

    Lab-only CSRF PoC (harmless demonstration)
    <img src="https://bankmock.example/transfer?to=attacker&amount=5000" width="0" height="0">

    তাহলে ব্রাউজার স্বয়ংক্রিয়ভাবে সেই image URL-এ একটি GET request পাঠাবে — এবং সেই request-এর সাথে bankmock.example-এর জন্য সংরক্ষিত session cookie-ও যুক্ত হয়ে যাবে, ভিকটিমের কোনো সচেতন ক্লিক বা সম্মতি ছাড়াই। BankMock সার্ভার শুধু cookie দেখে ভিকটিমকে চিনবে এবং request-টি বৈধ ধরে নিয়ে টাকা ট্রান্সফার করে দিতে পারে। এই উদাহরণের মূল শিক্ষা: আক্রমণকারীর সাইট কখনো ভিকটিমের cookie "দেখে"ও না, "চুরি"ও করে না — সে শুধু ব্রাউজারকে cookie-সহ একটি request পাঠাতে প্ররোচিত করে।

    Browser কীভাবে Request ও Cookie হ্যান্ডেল করে

    CSRF বোঝার জন্য একটি মূল নীতি মনে রাখা জরুরি: ব্রাউজার যখন কোনো ডোমেইনে request পাঠায় (তা <img>, <form>, fetch(), বা সরাসরি নেভিগেশন — যেভাবেই হোক), সে স্বয়ংক্রিয়ভাবে সেই ডোমেইনের জন্য সংরক্ষিত সব cookie সংযুক্ত করে, request-টি কোথা থেকে initiate হয়েছে তা না দেখেই (যদি না বিশেষ cookie attribute বা CORS নীতি এটি সীমিত করে)। এই "ambient authority" (প্রেক্ষাপট-নির্বিশেষে স্বয়ংক্রিয় কর্তৃত্ব) আচরণটাই CSRF-এর মূল কারণ।

    User-Controlled Input বনাম Server-Controlled Value

    XSS-এ attacker-এর লক্ষ্য থাকে ইনপুট ডেটার মধ্য দিয়ে কোড execute করা; CSRF-এ attacker কোনো ইনপুট ডেটা পাঠান না — বরং তিনি সম্পূর্ণ request-টাই নিজে তৈরি করেন এবং ভিকটিমের ব্রাউজারকে সেটি পাঠাতে বাধ্য করেন। এখানে "attacker-controlled" জিনিসটা হলো request-এর গন্তব্য, মেথড ও parameter — ভিকটিমের একমাত্র অবদান হলো তার browser session (এবং প্রায়ই, একটি দূষিত লিঙ্কে ক্লিক করা বা দূষিত পৃষ্ঠা ভিজিট করা)।

    CSRF-এর তিনটি পূর্বশর্ত

    ১. Relevant action

    এমন একটি state-changing action থাকতে হবে, যা ঘটলে কোনো প্রভাব পড়ে — পাসওয়ার্ড পরিবর্তন, ইমেইল পরিবর্তন, টাকা ট্রান্সফার, কমেন্ট পোস্ট করা ইত্যাদি।

    ২. Cookie-based session handling

    Authentication সম্পূর্ণভাবে cookie-নির্ভর হতে হবে, এবং ব্রাউজার যেন অন্য কোনো origin থেকে আসা request-এও স্বয়ংক্রিয়ভাবে সেই cookie পাঠায়।

    ৩. কোনো অননুমানযোগ্য parameter নেই

    Request-টি সফল হওয়ার জন্য এমন কোনো parameter দরকার না হওয়া উচিত নয়, যা attacker আগে থেকে জানেন না বা অনুমান করতে পারেন না — যেমন একটি CSRF token।

    CSRF, XSS ও Clickjacking-এর পার্থক্য

    Vulnerabilityলক্ষ্যমূল পার্থক্য
    CSRFServer-side state-changing actionকোনো কোড ইনজেকশন বা UI কারসাজি লাগে না — শুধু cookie-সহ একটি অনিচ্ছাকৃত request
    XSS (Cross-Site Scripting)ভিকটিমের ব্রাউজার (client-side)Attacker-এর কোড ভিকটিমের ব্রাউজারে execute হয় — অনেক বেশি শক্তিশালী, কারণ এটি CSRF token-ও পড়ে ফেলতে পারে
    Clickjackingভিকটিমের একটি নির্দিষ্ট ক্লিকভিকটিমকে একটি অদৃশ্য/ছদ্মবেশী UI-তে ক্লিক করানো হয় — request-এর বিষয়বস্তু attacker স্বাধীনভাবে নিয়ন্ত্রণ করতে পারেন না, শুধু ভিকটিমের ক্লিক hijack করেন

    লক্ষণীয়, যদি কোথাও XSS থাকে, সেটি প্রায় সবসময় CSRF protection (token-ভিত্তিক হলেও) সম্পূর্ণ বাইপাস করে দিতে পারে — কারণ XSS থাকলে attacker ভিকটিমের ব্রাউজার থেকেই, page-এর DOM থেকে CSRF token পড়ে, সঠিক token-সহ request পাঠাতে পারেন। তাই CSRF defense কখনো XSS-এর বিকল্প নয়, বরং পরিপূরক।

    CSRF-এর সম্ভাব্য Impact

    • Account takeover: ভিকটিমের ইমেইল/পাসওয়ার্ড পরিবর্তন করে অ্যাকাউন্ট দখল করা।
    • Financial fraud: অনুমতি ছাড়া টাকা ট্রান্সফার, পণ্য ক্রয়, বা পেমেন্ট মেথড পরিবর্তন।
    • Data manipulation: ভিকটিমের হয়ে কমেন্ট/পোস্ট করা, সেটিংস পরিবর্তন করা।
    • Privilege escalation: যদি ভিকটিম admin হন, তার সেশন ব্যবহার করে নতুন admin তৈরি বা permission পরিবর্তন করা।
    • Login CSRF: ভিকটিমকে, না জানিয়ে, attacker-এর নিজের অ্যাকাউন্টে লগইন করিয়ে দেওয়া (অধ্যায় ৩-এ বিস্তারিত)।

    আসল impact নির্ভর করে — কোন endpoint vulnerable, সেই action-এর গুরুত্ব কতটা, এবং ভিকটিম কে (সাধারণ ইউজার নাকি admin) তার উপর।

    অনুশীলন

    নিচের এন্ডপয়েন্টটি দেখুন। এটি CSRF-এর তিনটি পূর্বশর্ত পূরণ করে কি না বিশ্লেষণ করুন:

    সারসংক্ষেপ

    CSRF ঘটে কারণ ব্রাউজার প্রতিটি request-এর সাথে স্বয়ংক্রিয়ভাবে cookie পাঠায়, origin নির্বিশেষে, আর সার্ভার যদি শুধু cookie-এর উপর ভরসা করে request-এর সত্যতা যাচাই না করে, তাহলে একটি দূষিত পৃষ্ঠা ভিকটিমের ব্রাউজারকে দিয়ে অনিচ্ছাকৃত action চালিয়ে নিতে পারে। এর জন্য তিনটি পূর্বশর্ত লাগে: relevant action, cookie-based session, এবং অননুমানযোগ্য কোনো parameter-এর অনুপস্থিতি।

    HTTP Requests, Sessions, Cookies এবং Browser Behavior

    CSRF পেলোড/PoC কাজ করে কি না তা নির্ভর করে ব্রাউজার ঠিক কীভাবে request পাঠায় এবং cookie attach করে তার উপর — এই অধ্যায়ে সেই প্রক্রিয়াটা ভেঙে দেখানো হয়েছে।

    ⚖️

    আইনি নোটিশ: এখানে দেখানো সব উদাহরণ শুধুমাত্র নিজের lab বা অনুমোদিত পরিবেশে পরীক্ষা করুন। অনুমতি ছাড়া অন্য কোনো সিস্টেমে প্রয়োগ নিষিদ্ধ ও আইনত দণ্ডনীয়।

    HTTP Request-এর গঠন (সংক্ষিপ্ত পুনরালোচনা)

    একটি HTTP request-এ থাকে একটি method (GET, POST, PUT, DELETE ইত্যাদি), একটি URL/path, কিছু header (যেমন Cookie, Content-Type, Origin, Referer), এবং ঐচ্ছিকভাবে একটি body (POST/PUT-এর ক্ষেত্রে ফর্ম ডেটা বা JSON)। CSRF-এর জন্য গুরুত্বপূর্ণ হলো — ব্রাউজার কোন কোন ধরনের request, কোন কোন HTML element দিয়ে, কোন ধরনের header/body নিয়ে স্বয়ংক্রিয়ভাবে পাঠাতে পারে — যেহেতু attacker-কে ভিকটিমের ব্রাউজার দিয়েই পুরো request তৈরি করাতে হয়, কোনো script execution ছাড়াই (classic CSRF-এ)।

    কোন HTML Element দিয়ে কোন ধরনের Request পাঠানো যায়

    HTML ElementMethodContent-Type নিয়ন্ত্রণCross-origin থেকে কাজ করে?
    <img src="...">, <script src="...">শুধু GETনা (কোনো body নেই)হ্যাঁ
    <form> (method="GET")GETনাহ্যাঁ
    <form> (method="POST")POSTসীমিত — শুধু application/x-www-form-urlencoded, multipart/form-data, text/plainহ্যাঁ

    লক্ষণীয় বিষয়: সাধারণ HTML ফর্ম দিয়ে Content-Type: application/json সেট করে POST পাঠানো যায় না — এই সীমাবদ্ধতাই নির্ধারণ করে classic form-based CSRF শুধুমাত্র নির্দিষ্ট কিছু Content-Type-এর বিরুদ্ধেই সরাসরি কাজ করে (অধ্যায় ৪ ও ৮-এ bypass কৌশল নিয়ে আলোচনা)।

    Session ও Cookie কীভাবে কাজ করে

    বেশিরভাগ ওয়েব অ্যাপ্লিকেশন ইউজারকে "মনে রাখার" জন্য একটি session cookie ব্যবহার করে — লগইন সফল হলে সার্ভার একটি ইউনিক session identifier সেট করে (Set-Cookie: session=abc123), এবং এরপর ব্রাউজার প্রতিটি পরবর্তী request-এর সাথে সেই cookie স্বয়ংক্রিয়ভাবে পাঠায় — যতক্ষণ না সেই ডোমেইনের জন্য cookie-এর scope (domain, path) মেলে।

    Cookie Attribute যা CSRF-কে প্রভাবিত করে

    Attributeপ্রভাব
    SameSite=StrictCookie শুধুমাত্র সেই cookie-এর নিজস্ব সাইট থেকে আসা navigation/request-এ পাঠানো হয় — cross-site request-এ (এমনকি লিঙ্কে ক্লিক করেও) পাঠানো হয় না। সবচেয়ে কড়া প্রতিরক্ষা, কিন্তু UX-এ প্রভাব ফেলতে পারে (যেমন অন্য সাইট থেকে লিঙ্কে ক্লিক করে এলে লগআউট দেখানো)।
    SameSite=LaxTop-level GET navigation (যেমন লিঙ্কে ক্লিক করা)-এ cookie পাঠানো হয়, কিন্তু cross-site POST, বা সাব-রিসোর্স request (<img>, <iframe>, AJAX)-এ পাঠানো হয় না। এটি আধুনিক ব্রাউজারের ডিফল্ট আচরণ।
    SameSite=None; SecureCookie সব ধরনের cross-site request-এও পাঠানো হয় (এই attribute সেট না থাকলে, অনেক ব্রাউজার এখন ডিফল্টভাবে Lax ধরে নেয়)। সাধারণত থার্ড-পার্টি ইন্টিগ্রেশন (payment widget, embedded content)-এর জন্য ইচ্ছাকৃতভাবে ব্যবহৃত হয় — কিন্তু CSRF-এর ঝুঁকি পুরোপুরি ফিরিয়ে আনে।
    HttpOnlyCSRF-এর সাথে সরাসরি সম্পর্কিত না (এটি মূলত XSS-এর বিরুদ্ধে), কিন্তু একই cookie security আলোচনার অংশ।
    💡

    আধুনিক ব্রাউজার (Chrome, Firefox, Edge) এখন SameSite attribute উল্লেখ না থাকলে ডিফল্টভাবে Lax আচরণ করে — এটি classic cross-site POST CSRF-এর বিরুদ্ধে একটি উল্লেখযোগ্য browser-level প্রতিরক্ষা তৈরি করেছে, কিন্তু এটি সম্পূর্ণ সুরক্ষা নয় (অধ্যায় ৮-এ GET-based/top-level-navigation bypass আলোচিত হয়েছে)।

    Same-Origin Policy বনাম CSRF

    Same-Origin Policy (SOP) মূলত নিয়ন্ত্রণ করে — একটি origin-এর script অন্য origin-এর response পড়তে পারবে কি না। কিন্তু SOP request পাঠানো আটকায় না — একটি দূষিত পৃষ্ঠা অন্য origin-এ request পাঠাতে পারে, শুধু সেই response পড়তে পারে না। CSRF-এ attacker-এর response পড়ার প্রয়োজনই হয় না — তিনি শুধু চান request-টি target সার্ভারে পৌঁছাক এবং সেই server-side action ঘটে যাক। এই কারণেই SOP একা CSRF প্রতিরোধ করতে পারে না।

    Origin ও Referer Header

    প্রতিটি cross-origin request-এর সাথে ব্রাউজার স্বয়ংক্রিয়ভাবে Origin (এবং প্রায়ই Referer) header যুক্ত করে, যা থেকে সার্ভার বুঝতে পারে request-টি কোন ডোমেইন থেকে এসেছে। এই header দুটো CSRF defense-এর একটি গুরুত্বপূর্ণ স্তর (অধ্যায় ৬-এ বিস্তারিত), কিন্তু এদেরও কিছু সীমাবদ্ধতা আছে — যেমন কিছু পুরনো ব্রাউজার/প্রক্সি কনফিগারেশনে এই header অনুপস্থিত থাকতে পারে, এবং সার্ভার যদি এই header-এর অনুপস্থিতিকে "allow" হিসেবে treat করে, একটি ফাঁক তৈরি হয়।

    অনুশীলন

    নিচের দুটি action-এর মধ্যে কোনটি classic HTML <form> দিয়ে সরাসরি CSRF-exploitable, এবং কোনটির জন্য আলাদা কৌশল (যেমন fetch() বা Flash-era trick) লাগতে পারে — ব্যাখ্যা করুন:

POST /settings/update
Content-Type: application/x-www-form-urlencoded
email=new@example.com

// B
POST /settings/update
Content-Type: application/json
{"email":"new@example.com"}

    CSRF-এর সম্ভাব্যতা নির্ভর করে ব্রাউজার কোন HTML element দিয়ে কোন ধরনের request/Content-Type পাঠাতে পারে, এবং cookie-এর SameSite attribute request-টিকে অনুমতি দেয় কি না তার উপর। Origin/Referer header একটি গুরুত্বপূর্ণ defense সিগন্যাল, কিন্তু একমাত্র নির্ভরযোগ্য উপায় নয়।

    ১. GET-Based CSRF

    Root cause: একটি state-changing action (যেমন ডেটা পরিবর্তন/মোছা) ভুলভাবে একটি GET request দিয়ে ইমপ্লিমেন্ট করা হয়েছে — যেখানে GET request সাধারণত শুধু ডেটা পড়ার (read-only, "safe method") জন্য ব্যবহার করার কথা।

    কেন এটি সবচেয়ে সহজে exploit হয়: একটি GET request শুধুমাত্র একটি <img>, <iframe>, বা এমনকি একটি সাধারণ <a href> লিঙ্কের মাধ্যমেই trigger করা যায় — কোনো জাভাস্ক্রিপ্ট বা ফর্ম সাবমিশন ছাড়াই, এবং এটি আধুনিক ব্রাউজারের SameSite=Lax ডিফল্টকেও (সাব-রিসোর্স লোডের ক্ষেত্রে আংশিকভাবে, top-level navigation-এর ক্ষেত্রে সম্পূর্ণভাবে) ফাঁকি দিতে পারে, কারণ Lax টপ-লেভেল GET navigation অনুমোদন করে।

    গুরুত্বপূর্ণ: আধুনিক ব্রাউজারে ডিফল্ট SameSite=Lax এই ধরনের cross-site POST-কে ইতিমধ্যে ব্লক করে দেয় (cookie পাঠানো হবে না), যদি না সার্ভার ইচ্ছাকৃতভাবে SameSite=None সেট করে থাকে। তাই Lax ডিফল্ট সক্রিয় থাকা অ্যাপ্লিকেশনে এই classic আক্রমণ এখন কম কার্যকর — কিন্তু token-ভিত্তিক defense তবুও অপরিহার্য, কারণ cookie attribute misconfiguration, পুরনো ব্রাউজার, বা অন্য bypass (অধ্যায় ৮) এখনও সম্ভব।

    Remediation: সিঙ্ক্রোনাইজার টোকেন প্যাটার্ন (per-session বা per-request CSRF token) + SameSite=Lax/Strict cookie।

    ৩. JSON CSRF

    Root cause: একটি API endpoint যা Content-Type: application/json body গ্রহণ করে, কিন্তু Content-Type header কড়াভাবে যাচাই করে না, এবং CSRF token-ও ব্যবহার করে না।

    চ্যালেঞ্জ: সাধারণ HTML <form> দিয়ে সরাসরি application/json Content-Type পাঠানো যায় না (অধ্যায় ২)। তাই attacker-কে একটি কৌশল ব্যবহার করতে হয় — enctype="text/plain" সহ একটি ফর্ম, যার body-কে সাবধানে এমনভাবে সাজানো হয় যেন সেটি valid JSON-এর মতো দেখতে লাগে এবং সার্ভার যদি Content-Type কড়াভাবে না মেলায়, body-কে JSON হিসেবে parse করে ফেলে।

    Lab-only text/plain JSON-shaped PoC
    <form id="csrf-poc" action="https://shopmock.example/api/profile" method="POST" enctype="text/plain">
  <input type="hidden" name='{"email":"attacker@evil.example","ignore":"' value='"}'>
</form>
<script>document.getElementById('csrf-poc').submit();</script>

<!-- পাঠানো raw body হয়ে যায় (আনুমানিক):
{"email":"attacker@evil.example","ignore":"="}
যা অনেক lenient JSON parser-এর কাছে বৈধ JSON মনে হতে পারে। -->

    Remediation: সার্ভার-সাইডে কড়াভাবে Content-Type: application/json যাচাই করুন (ভুল হলে request reject করুন), এবং এখানেও CSRF token/custom header-ভিত্তিক protection (অধ্যায় ৬) প্রয়োগ করুন।

    ৪. Login CSRF

    Root cause: লগইন ফর্মেও CSRF protection না থাকলে, attacker ভিকটিমকে — না জানিয়ে — attacker-এর নিজের (পরিচিত credential-সহ) অ্যাকাউন্টে লগইন করিয়ে দিতে পারেন।

    কেন বিপজ্জনক: ভিকটিম, না জেনেই, attacker-এর অ্যাকাউন্টে কার্যক্রম চালাতে থাকেন (যেমন সার্চ হিস্ট্রি, সেভ করা তথ্য, ক্রেডিট কার্ড তথ্য যোগ করা) — যা পরবর্তীতে attacker অ্যাক্সেস করতে পারেন। এটি একটি কম আলোচিত কিন্তু বাস্তব ঝুঁকি।

    Remediation: লগইন ফর্মেও CSRF token যুক্ত করুন — অনেক ডেভেলপার ভুলবশত মনে করেন "লগইন ফর্মে token লাগে না যেহেতু ইউজার তখনও authenticated না", কিন্তু ঝুঁকিটা থাকে ভিন্ন দিক থেকে।

    ৫. Logout CSRF

    Root cause: Logout endpoint কোনো token ছাড়া GET/POST-এ উন্মুক্ত থাকা।

    Impact: সরাসরি তেমন গুরুতর মনে না হলেও (শুধু ভিকটিমকে লগ-আউট করে দেয়), এটি অন্য আক্রমণের (যেমন Login CSRF বা session fixation) সাথে চেইন করার একটি প্রাথমিক ধাপ হতে পারে, অথবা ধারাবাহিক বিরক্তিকর denial-of-service-এর মতো প্রভাব ফেলতে পারে।

    ৬. Multi-Step CSRF

    Root cause: একটি multi-step wizard (যেমন checkout flow)-এর প্রতিটি ধাপ আলাদাভাবে CSRF-vulnerable হতে পারে, অথবা শুধুমাত্র প্রথম ধাপে token যাচাই হয়, পরের ধাপগুলোতে না।

    কীভাবে কাজ করে: Attacker একাধিক auto-submitting form/request চেইন করে (প্রতিটি ধাপ একে একে ট্রিগার করে, প্রয়োজনে মাঝে delay/redirect ব্যবহার করে) পুরো multi-step flow সম্পূর্ণ করিয়ে দিতে পারেন, ভিকটিমের একটি মাত্র পৃষ্ঠা ভিজিট থেকেই।

    ধারণাগত চেইন (lab-only)
    Step 1: POST /checkout/address   (auto-submit form #1)
Step 2: POST /checkout/payment   (auto-submit form #2, 1 সেকেন্ড পরে JS দিয়ে ট্রিগার)
Step 3: POST /checkout/confirm   (auto-submit form #3, ২ সেকেন্ড পরে)

    Remediation: প্রতিটি ধাপে আলাদাভাবে CSRF token যাচাই করুন, এবং গুরুত্বপূর্ণ চূড়ান্ত ধাপে (যেমন payment confirm) পুনরায় authentication বা একটি অতিরিক্ত নিশ্চিতকরণ (re-auth/step-up) বিবেচনা করুন।

    Vulnerable Endpoint শনাক্তকরণ

    একটি অ্যাপ্লিকেশনে CSRF-এর জন্য আসলে কোন endpoint গুলো পরীক্ষা করা উচিত, এবং কীভাবে দ্রুত স্ক্রিন করবেন।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র নিজের অনুমোদিত scope-এর মধ্যে endpoint স্ক্যান/টেস্ট করুন।

    কোন ধরনের Endpoint লক্ষ্য করবেন

    • State-changing action: প্রোফাইল/ইমেইল/পাসওয়ার্ড পরিবর্তন, অ্যাকাউন্ট ডিলিট, পেমেন্ট/ট্রান্সফার, রোল পরিবর্তন।
    • কম গুরুত্বপূর্ণ মনে হওয়া action: like/follow/subscribe toggle, কমেন্ট পোস্ট, নোটিফিকেশন সেটিং — এগুলোও chaining-এর অংশ হতে পারে।
    • Admin panel action: ইউজার তৈরি/ডিলিট, permission পরিবর্তন — একজন admin ভিকটিম হলে impact অনেক বেশি।
    • Login/Logout endpoint: অধ্যায় ৩-এ আলোচিত Login/Logout CSRF।

    Checklist — প্রতিটি Endpoint-এ যা যাচাই করবেন

    ১. CSRF Token আছে কি?

    Request body/header-এ কোনো token parameter (যেমন csrf_token, _token, X-CSRF-Token) আছে কি না দেখুন।

    ২. Token বাদ দিলে কী হয়?

    Token parameter সম্পূর্ণ বাদ দিয়ে request পাঠান — সার্ভার reject করে কি না।

    ৩. Token অন্য সেশনের হলে কী হয়?

    একটি দ্বিতীয় অ্যাকাউন্টের token ব্যবহার করে প্রথম অ্যাকাউন্টের সেশনে request পাঠান (per-session validation যাচাই)।

    ৪. Cookie-এর SameSite মান কী?

    DevTools/Burp দিয়ে session cookie-এর SameSite attribute দেখুন — None/অনুপস্থিত থাকলে ঝুঁকি বেশি।

    ৫. Origin/Referer যাচাই হয় কি?

    Header বাদ দিয়ে বা ভুল মান দিয়ে request পাঠিয়ে দেখুন সার্ভার reject করে কি না।

    ৬. Method ঠিক আছে কি?

    State-changing action GET-এ ঘটছে কি না, বা GET দিয়েও POST-এর কাজ করানো যায় কি না (method override) দেখুন।

    Burp Suite দিয়ে দ্রুত Triage (প্রিভিউ — বিস্তারিত অধ্যায় ৭)

    Proxy history-তে সব POST/PUT/DELETE request ফিল্টার করে, প্রতিটিতে CSRF token পরামিতি আছে কি না স্ক্যান করা একটি দ্রুত প্রাথমিক ধাপ। Burp-এর "CSRF PoC generator" (রাইট-ক্লিক মেনু) প্রতিটি সন্দেহজনক request-এর জন্য তাৎক্ষণিকভাবে একটি টেস্ট HTML তৈরি করে দেয়।

    False Positive এড়ানো

    শুধু "token নেই" মানেই vulnerable নয় — নিচের বিষয়গুলো বিবেচনা করুন:

    • SameSite=Strict/Lax ইতিমধ্যে সক্রিয়: cross-site POST/সাব-রিসোর্স ইতিমধ্যে ব্লক হচ্ছে কি না Burp/ব্রাউজার দিয়ে যাচাই করুন।
    • Custom header requirement: যদি API শুধুমাত্র XHR/fetch দিয়ে কল হয় এবং একটি custom header (যেমন X-Requested-With) বাধ্যতামূলক হয় যা সাধারণ HTML form/image দিয়ে পাঠানো যায় না, তাহলে classic CSRF কঠিন হয়ে যায় (যদিও fetch-ভিত্তিক bypass-এর সম্ভাবনা থাকতে পারে)।
    • Re-authentication প্রয়োজন: কিছু sensitive action-এ (পাসওয়ার্ড পরিবর্তনের আগে current password চাওয়া) CSRF-এর impact সীমিত হয়ে যায়, কারণ attacker সেই মান জানেন না।

    CSRF Token, SameSite Cookie এবং Bypass Analysis

    কীভাবে CSRF token ও SameSite cookie কাজ করে, এবং বাস্তবে কোন ভুল implementation-এ এরা bypass হয়ে যায়।

    ⚖️

    আইনি নোটিশ: নিচের bypass প্যাটার্নগুলো শুধুমাত্র defensive বোঝাপড়ার জন্য এবং নিজের lab/অনুমোদিত পরিবেশে validation-এর জন্য।

    CSRF Token-এর প্রধান প্যাটার্ন

    Synchronizer Token Pattern

    সার্ভার প্রতিটি session-এর জন্য (বা প্রতিটি request-এর জন্য) একটি random token তৈরি করে, যা page-এ embed করা হয় এবং প্রতিটি state-changing request-এ ফেরত পাঠাতে হয়। সার্ভার session-এ সংরক্ষিত token-এর সাথে মিলিয়ে যাচাই করে।

    Double-Submit Cookie Pattern

    একটি random token cookie হিসেবে সেট করা হয়, এবং একই মান request body/header-এও পাঠাতে হয়। সার্ভার দুটো মিলিয়ে দেখে। সুবিধা: server-side state রাখার দরকার নেই — কিন্তু সাবধানে implement না করলে দুর্বল হয়ে পড়ে (নিচে দেখুন)।

    টোকেন Implementation-এর সাধারণ ভুল (Bypass সম্ভাবনা)

    ভুলকেন এটি bypass তৈরি করে
    Token-টি request parameter হিসেবে অনুপস্থিত থাকলেও request গ্রহণ করা হয়Attacker শুধু token parameter বাদ দিয়ে request পাঠালেই যথেষ্ট
    Token-টি per-session না হয়ে static/একটি সাধারণ মানAttacker নিজে লগইন করে একবার token সংগ্রহ করে সেটাই সব সময় ব্যবহার করতে পারেন
    Token যাচাই হয় কিন্তু তা session-এর সাথে bind করা হয় না (শুধু "কোনো বৈধ token আছে কি না" দেখা হয়)Attacker নিজের অ্যাকাউন্টের token নিয়ে ভিকটিমের সেশনে পাঠালেও গ্রহণ হয়ে যেতে পারে
    Double-submit cookie pattern-এ, cookie-টি attacker নিজেও set করতে পারেন (যেমন একটি sibling subdomain-এ XSS/cookie injection থাকলে)Attacker নিজের পছন্দমতো token cookie ও matching parameter দুটোই পাঠিয়ে দিতে পারেন
    Token শুধু GET request-এ পাঠানো হয় (URL-এ) এবং Referer/leak-prone channel দিয়ে বের হয়ে যায়Referer header বা browser history-র মাধ্যমে token leak হতে পারে
    Token যাচাই conditionally (যেমন শুধু নির্দিষ্ট Content-Type-এর জন্য) করা হয়Content-Type পরিবর্তন করে (JSON CSRF কৌশলের মতো) validation এড়ানো যেতে পারে

    SameSite Cookie Bypass প্যাটার্ন

    • Top-level GET navigation (Lax-এও কাজ করে): SameSite=Lax top-level navigation-এ (যেমন একটি লিঙ্কে ক্লিক) cookie পাঠায় — তাই GET-based state-changing endpoint এখনও exploitable।
    • Subdomain-related issue: যদি cookie domain scope ব্যাপক হয় (যেমন .example.com) এবং কোনো sibling subdomain compromise হয়, সেই subdomain থেকে পাঠানো request "same-site" ধরা হবে — SameSite protection পুরোপুরি বাইপাস হয়ে যেতে পারে।
    • পুরনো ব্রাউজার: যেসব ব্রাউজার SameSite attribute বোঝে না, তারা cookie-টিকে সবসময় পাঠায় (অর্থাৎ ডিফল্টভাবে None-এর মতো আচরণ) — তাই SameSite-কে একমাত্র defense হিসেবে ব্যবহার করা উচিত না।
    • Method override trick: যদি সার্ভার _method=POST-এর মতো একটি parameter দিয়ে GET request-কে POST হিসেবে treat করে, তাহলে attacker top-level GET navigation (যা Lax অনুমতি দেয়) ব্যবহার করেই কার্যত একটি POST action ঘটাতে পারেন।

    Origin/Referer Validation Bypass

    • Null Origin: কিছু কনটেক্সটে (sandboxed iframe, data: URI, redirect-এর পর) Origin header null হয়ে যায় — যদি সার্ভার null-কে "trusted" হিসেবে allowlist-এ রাখে, bypass সম্ভব।
    • Substring/suffix matching ভুল: সার্ভার যদি শুধু Origin.endsWith("example.com")-এর মতো দুর্বল চেক করে, evilexample.com সহজেই pass করে যেতে পারে।
    • Referer অনুপস্থিত থাকলে allow করা: কিছু privacy-focused সেটআপ/প্রক্সিতে Referer header strip হয়ে যায় — যদি সার্ভার "Referer নেই" মানে "allow" ধরে নেয়, এটি একটি গুরুতর ফাঁক।

    অনুশীলন

    নিচের server-side validation লজিক-এ কোন bypass সম্ভব চিহ্নিত করুন:

    if (request.origin == null || request.origin.includes("shopmock.example")) {
  allowRequest();
}

    ধাপ ১ — Request ক্যাপচার করুন

    Burp Proxy intercept চালু করে, টার্গেট অ্যাপ্লিকেশনে একটি state-changing action (যেমন প্রোফাইল আপডেট) সম্পন্ন করুন। Proxy history-তে সেই request খুঁজে বের করুন — এটি রাইট-ক্লিক করে "Send to Repeater"-এ পাঠান।

    ধাপ ২ — Token/Header বিশ্লেষণ করুন

    Repeater-এ request body/header-এ কোনো CSRF token parameter আছে কি না পর্যবেক্ষণ করুন। থাকলে, সেই parameter মুছে/খালি করে request পাঠান — response দেখুন সার্ভার এখনও request গ্রহণ করে কি না।

    ধাপ ৩ — Session Validation যাচাই করুন

    দুটো ভিন্ন ব্রাউজার সেশন (বা Burp-এ দুটো ভিন্ন cookie jar) দিয়ে লগইন করুন। একটি সেশনের token নিয়ে, অন্য সেশনের cookie দিয়ে request পাঠিয়ে দেখুন token session-bound কি না।

    ধাপ ৪ — Built-in "Generate CSRF PoC" ব্যবহার করুন

    Repeater/Proxy history-তে যেকোনো request-এ রাইট-ক্লিক করে "Engagement tools → Generate CSRF PoC" অপশন বেছে নিলে Burp স্বয়ংক্রিয়ভাবে একটি সম্পূর্ণ HTML PoC তৈরি করে দেয় (auto-submit form-সহ), যা "Test in browser" বাটনে ক্লিক করে সরাসরি একটি built-in ব্রাউজারে যাচাই করা যায়।

    </form>
    <script>history.pushState('', '', '/'); document.forms[0].submit();</script>
  </body>
</html>

    Double-Submit Cookie-এর গভীর দুর্বলতা

    Double-submit cookie pattern ধরে নেয়, attacker cookie-টির মান জানতে/সেট করতে পারবেন না। কিন্তু এই ধারণা ভেঙে যায় যখন:

    • Related-domain cookie injection: যদি একই parent domain-এর অন্য কোনো subdomain-এ attacker কোনোভাবে cookie সেট করতে পারেন (misconfigured subdomain, XSS, বা CRLF injection), তিনি main domain-এর জন্য একটি নিজস্ব CSRF cookie ইনজেক্ট করে দিতে পারেন, কারণ cookie-এর domain scope প্রায়ই .example.com আকারে ব্যাপক থাকে।
    • Network attacker (non-HTTPS context): যদি কোনো অংশ HTTP-তে পরিবেশিত হয়, একটি man-in-the-middle attacker cookie ইনজেক্ট করতে পারেন।

    CORS Misconfiguration ও CSRF-এর সংযোগ

    সাধারণ CSRF-এ attacker response পড়তে পারেন না — তিনি শুধু "blind" request পাঠান। কিন্তু যদি target API নিচের মতো ভুল কনফিগারেশন ব্যবহার করে:

    ভুল CORS কনফিগারেশন (উদাহরণ)
    Access-Control-Allow-Origin: https://evil.example   (request-এর Origin reflect করা)
Access-Control-Allow-Credentials: true

    তাহলে attacker-এর পৃষ্ঠা একটি credentialed fetch() দিয়ে শুধু action-ই ঘটাতে পারেন না — response-ও পড়তে পারেন, যা sensitive ডেটা (API key, personal info, এমনকি নতুন CSRF token) চুরির সুযোগ তৈরি করে। এটি classic CSRF-এর চেয়ে গুরুতর, কারণ এটি read এবং write — দুটোই সম্ভব করে।

    WebSocket এবং CSRF (Cross-Site WebSocket Hijacking)

    WebSocket handshake (ws:///wss://) একটি সাধারণ HTTP request হিসেবে শুরু হয়, এবং এতেও browser cookie স্বয়ংক্রিয়ভাবে সংযুক্ত করে। যদি সার্ভার handshake-এর সময় Origin header যাচাই না করে, একটি দূষিত পৃষ্ঠা ভিকটিমের cookie ব্যবহার করে একটি WebSocket সংযোগ খুলে ফেলতে পারে — এবং তারপর সেই সংযোগের মাধ্যমে ভিকটিমের হয়ে বার্তা পাঠাতে/পড়তে পারে। একে বলা হয় Cross-Site WebSocket Hijacking (CSWSH)।

    Content-Type Sniffing Bypass

    কিছু ব্যাকএন্ড ফ্রেমওয়ার্ক নমনীয়ভাবে request body parse করে — Content-Type header যা-ই থাকুক, body-এর structure দেখে অনুমান করে এটি JSON নাকি form-data। এই "lenient parsing" আচরণই JSON CSRF-এর text/plain কৌশলকে সম্ভব করে তোলে (অধ্যায় ৩, ৪)। গবেষণার দৃষ্টিকোণ থেকে, প্রতিটি ফ্রেমওয়ার্কের parsing আচরণ আলাদা হতে পারে — তাই টার্গেট স্ট্যাক শনাক্ত করা testing-এর একটি গুরুত্বপূর্ণ অংশ।

    Referrer-Policy এবং Token Leakage

    যদি একটি CSRF token URL parameter হিসেবে পাঠানো হয় (GET-এ), এবং পৃষ্ঠায় কোনো third-party resource লোড হয়, দুর্বল Referrer-Policy (যেমন unsafe-url) সেই token-সহ পুরো URL third-party সার্ভারের কাছে leak করে দিতে পারে — যা token-কে আংশিকভাবে অকার্যকর করে দেয়।

    অনুশীলন

    একটি hypothetical API response হেডারে Access-Control-Allow-Origin: https://attacker-controlled-reflected-origin.example এবং Access-Control-Allow-Credentials: true দেখলে, এটি ঠিক কী ধরনের অতিরিক্ত ঝুঁকি তৈরি করে, classic CSRF-এর তুলনায় — ব্যাখ্যা করুন।

    সারসংক্ষেপ

    CSRF গবেষণার অ্যাডভান্সড স্তরে — double-submit cookie-এর subdomain-related দুর্বলতা, CORS misconfiguration-এর সাথে সংযোগ, WebSocket hijacking, এবং lenient content-type parsing — সবই দেখায় যে CSRF defense-কে শুধু "token আছে কি না" দিয়ে বিচার করা যথেষ্ট নয়।

    Single Page Application (SPA) ও Token-Based Auth

    অনেক আধুনিক SPA cookie-ভিত্তিক session-এর বদলে localStorage/sessionStorage-এ JWT (JSON Web Token) রেখে, প্রতিটি request-এ ম্যানুয়ালি Authorization: Bearer <token> header যোগ করে। যেহেতু এটি browser-এর স্বয়ংক্রিয় cookie-attach আচরণের উপর নির্ভর করে না, classic CSRF এখানে অকার্যকর — attacker-এর পৃষ্ঠা সেই token জানেই না, তাই সঠিক header দিয়ে request পাঠাতে পারেন না।

    💡

    তবে এর মানে এই নয় যে token-based auth স্বয়ংক্রিয়ভাবে নিরাপদ — যদি token localStorage-এ রাখা হয়, তাহলে একটি XSS vulnerability সেই token সরাসরি চুরি করতে পারে, যা CSRF-এর চেয়েও গুরুতর impact তৈরি করে। এছাড়া, অনেক SPA এখনও authentication-এর জন্য cookie (session বা refresh-token cookie) ব্যবহার করে, যেখানে CSRF ঝুঁকি পুরোপুরি বহাল থাকে।

    REST API-তে CSRF

    যদি একটি REST API cookie-ভিত্তিক session ব্যবহার করে (বিশেষত browser-based SPA backend-এর জন্য common), classic CSRF ঝুঁকি প্রযোজ্য থাকে। Custom header requirement (যেমন X-Requested-With: XMLHttpRequest) একটি হালকা প্রতিরক্ষা হতে পারে, কারণ সাধারণ HTML form/image দিয়ে custom header পাঠানো যায় না — কিন্তু fetch()/XHR দিয়ে cross-origin request-এ custom header যোগ করলে একটি CORS preflight ট্রিগার হয়, যা সার্ভার-সাইড origin চেকের সুযোগ তৈরি করে।

    GraphQL Endpoint-এ CSRF

    অনেক GraphQL endpoint একটি একক URL-এ (যেমন /graphql) সব query/mutation গ্রহণ করে, cookie-ভিত্তিক session দিয়ে। যদি endpoint GET method-ও সমর্থন করে (query parameter-এ query পাঠিয়ে), এবং CSRF token/strict Content-Type validation না থাকে, একটি GET-based CSRF দিয়ে mutation চালানো সম্ভব হতে পারে — যদিও বেশিরভাগ production GraphQL সার্ভার mutation-এর জন্য শুধু POST + application/json বাধ্যতামূলক করে, যা classic form-based CSRF-কে কঠিন করে তোলে (তবে JSON CSRF কৌশল এখনও প্রাসঙ্গিক থাকতে পারে, যদি Content-Type কড়াভাবে validate না হয়)।

    Mobile WebView-এ CSRF

    অনেক মোবাইল অ্যাপ একটি embedded WebView-তে ওয়েব কনটেন্ট দেখায়, যেখানে সেই WebView-এর নিজস্ব cookie jar থাকতে পারে। যদি WebView-টি attacker-নিয়ন্ত্রিত কনটেন্ট (যেমন একটি বহিরাগত লিঙ্ক) লোড করতে পারে, এবং সেই WebView-তে আগে থেকেই একটি authenticated session cookie থাকে, একই ধরনের CSRF ঝুঁকি প্রযোজ্য হতে পারে — কখনো কখনো আরও বেশি, কারণ মোবাইল WebView-তে SameSite প্রয়োগ কম consistent হতে পারে।

    Multi-Step Wizard ও SPA Routing

    SPA-তে client-side routing (যেমন React Router) ব্যবহার করলেও, প্রতিটি "ধাপ" আসলে একটি backend API call-এ পরিণত হয় — এবং প্রতিটি API call-এর নিজস্ব CSRF/auth validation প্রয়োজন, client-side routing এটি প্রতিস্থাপন করে না।

    • Under-rating: "Logout CSRF" বলে উড়িয়ে দেওয়া, যখন আসলে সেটি একটি chained attack-এর অংশ হতে পারে।
    • Proof ছাড়া claim করা: শুধু "token নেই" বলাই যথেষ্ট নয় — before/after state দিয়ে প্রমাণ করতে হবে action সত্যিই ঘটেছে।

    অনুশীলন

    নিচের দুটি CSRF ফাইন্ডিং-এর মধ্যে কোনটির severity বেশি হওয়া উচিত এবং কেন, যুক্তিসহ লিখুন:

    1. একটি GET-based CSRF, যা ইউজারের নিউজলেটার সাবস্ক্রিপশন বন্ধ করে দেয়।
    2. একটি POST-based CSRF, যা ইউজারের অ্যাকাউন্টের রিকভারি ইমেইল পরিবর্তন করে (re-authentication ছাড়া)।

    সারসংক্ষেপ

    একটি দায়িত্বশীল CSRF severity assessment মানে শুধু vulnerability-এর অস্তিত্ব প্রমাণ করা নয় — action-এর ব্যবসায়িক প্রভাব, ভিকটিমের সম্ভাব্য role, এবং exploit-এর সহজতা একসাথে বিবেচনা করা।

    CSRF Prevention এবং Secure Coding

    ডেভেলপারদের জন্য — CSRF ঠেকানোর নির্ভরযোগ্য, স্তরবিন্যস্ত (layered) পদ্ধতি।

    ⚖️

    আইনি নোটিশ: এই অধ্যায়টি সম্পূর্ণভাবে defensive/remediation-কেন্দ্রিক — নিজের অ্যাপ্লিকেশনে প্রয়োগ করার জন্য স্বাধীনভাবে ব্যবহারযোগ্য।

    স্তর ১ — CSRF Token (Synchronizer Token Pattern)

    প্রতিটি authenticated session-এর জন্য একটি cryptographically random token তৈরি করুন, server-side session store-এ রাখুন, এবং প্রতিটি state-changing form/API call-এ embed করুন। সার্ভার প্রতিটি request-এ token-টি session-এর সাথে মিলিয়ে কড়াভাবে যাচাই করবে (অনুপস্থিত/ভুল হলে reject)।

    ধারণাগত সার্ভার-সাইড লজিক (pseudo-code)
    function validateCsrfToken(request, session) {
  const submitted = request.body.csrf_token;
  if (!submitted || submitted !== session.csrfToken) {
    throw new Error("Invalid CSRF token");
  }
}

    স্তর ২ — SameSite Cookie সঠিকভাবে সেট করুন

    প্রস্তাবিত cookie সেটিং
    Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/

    যেসব endpoint-এ cross-site context থেকে cookie আসার কোনো বৈধ প্রয়োজন নেই, সেখানে SameSite=Strict আরও কড়া প্রতিরক্ষা দেয়। SameSite=None শুধুমাত্র প্রকৃত প্রয়োজনে (যেমন বৈধ থার্ড-পার্টি embed) এবং সবসময় Secure-এর সাথে ব্যবহার করুন।

    স্তর ৩ — Origin/Referer Validation (Defense in Depth)

    Token/SameSite-এর পাশাপাশি, state-changing request-এ Origin (প্রাধান্য) বা Referer header যাচাই করুন — exact match (allowlist), শুধু substring/suffix matching নয়।

    নিরাপদ Origin validation (pseudo-code)
    const ALLOWED_ORIGINS = new Set(["https://shopmock.example"]);
function validateOrigin(request) {
  const origin = request.headers.origin;
  if (!origin || !ALLOWED_ORIGINS.has(origin)) {
    throw new Error("Invalid or missing Origin header");
  }
}

    স্তর ৪ — Content-Type কড়াভাবে Validate করুন

    যদি একটি API শুধুমাত্র application/json গ্রহণ করার কথা, সার্ভার-সাইডে সেই Content-Type exact match বাধ্যতামূলক করুন এবং না মিললে request reject করুন — lenient/best-effort parsing এড়িয়ে চলুন, যা JSON CSRF bypass-এর সুযোগ তৈরি করে (অধ্যায় ৩, ৮)।

    স্তর ৫ — State-Changing Action-এ সঠিক HTTP Method

    REST সেম্যান্টিক্স কড়াভাবে অনুসরণ করুন — GET/HEAD কখনো কোনো অবস্থা পরিবর্তন করবে না (idempotent/"safe" method)। State পরিবর্তনকারী সব action POST/PUT/PATCH/DELETE-এ রাখুন, এবং method-override parameter (যেমন _method) থাকলে তা কড়াভাবে নিয়ন্ত্রণ করুন।

    স্তর ৬ — Sensitive Action-এ Re-Authentication

    পাসওয়ার্ড পরিবর্তন, ইমেইল/রিকভারি তথ্য পরিবর্তন, আর্থিক লেনদেনের মতো high-impact action-এ current password বা একটি OTP/step-up verification বাধ্যতামূলক করুন — এটি CSRF, session hijacking উভয়ের বিরুদ্ধেই একটি শক্তিশালী অতিরিক্ত স্তর।

    স্তর ৭ — Framework-এর বিল্ট-ইন Protection ব্যবহার করুন

    অধিকাংশ আধুনিক ফ্রেমওয়ার্কে বিল্ট-ইন CSRF protection আছে — এগুলো নিজে থেকে implement করার চেয়ে ব্যবহার করা বেশি নির্ভরযোগ্য, যতক্ষণ এটি সঠিকভাবে সব route-এ enable থাকে এবং disable করা না হয়।

    Framework/Ecosystemবিল্ট-ইন প্রক্রিয়া (সাধারণ ধারণা)
    DjangoMiddleware-ভিত্তিক CSRF token, টেমপ্লেট ট্যাগ দিয়ে ফর্মে embed
    Ruby on Railsprotect_from_forgery, authenticity token স্বয়ংক্রিয়ভাবে ফর্মে যুক্ত হয়
    Spring (Java)Spring Security CSRF filter, token হিডেন ইনপুট/হেডারে
    Express.js (Node)আলাদা মিডলওয়্যার (csurf-এর বিকল্প) যুক্ত করতে হয়, built-in না

    সম্পূর্ণ Checklist

    ✅ অবশ্যই করণীয়

    Per-session CSRF token + session-bound validation, SameSite=Lax/Strict cookie, কড়া Origin validation, exact Content-Type match, state-changing action কখনো GET-এ না রাখা, sensitive action-এ re-auth।

    ❌ এড়িয়ে চলুন

    শুধু Referer-এর উপর নির্ভর করা (একমাত্র defense হিসেবে), substring-based Origin matching, "Referer নেই মানে allow" নীতি, static/non-session-bound token।

    অনুশীলন

    আপনার পরিচিত যেকোনো একটি ফ্রেমওয়ার্কে (Django, Rails, Express, বা অন্য কিছু), CSRF protection কীভাবে enable/configure করা হয় তা ডকুমেন্টেশন থেকে খুঁজে বের করে সংক্ষেপে নোট করুন।

    সারসংক্ষেপ

    নির্ভরযোগ্য CSRF প্রতিরক্ষা কোনো একক ব্যবস্থা নয়, বরং স্তরবিন্যস্ত প্রতিরক্ষা — token + SameSite + Origin validation + strict Content-Type + সঠিক HTTP method + sensitive action-এ re-authentication — একসাথে মিলে একটি শক্তিশালী defense তৈরি করে।

    টার্মসংজ্ঞা
    CSRF (Cross-Site Request Forgery)ভিকটিমের ব্রাউজারকে প্রতারিত করে, তার সেশন ব্যবহার করে একটি অনিচ্ছাকৃত request পাঠানো।
    Synchronizer Token PatternServer-side session-bound random token যাচাই করে CSRF ঠেকানোর পদ্ধতি।
    Double-Submit CookieCookie ও request parameter-এ একই random token মিলিয়ে যাচাই করার পদ্ধতি।
    SameSite Cookie AttributeCookie কোন ধরনের cross-site request-এ পাঠানো হবে তা নিয়ন্ত্রণকারী attribute (Strict/Lax/None)।
    Ambient Authorityব্রাউজারের স্বয়ংক্রিয় cookie-attach আচরণ, যা request-এর উৎস বিবেচনা না করেই কর্তৃত্ব (session) প্রয়োগ করে — CSRF-এর মূল কারণ।
    Login CSRFভিকটিমকে, না জানিয়ে, attacker-এর নিজস্ব অ্যাকাউন্টে লগইন করিয়ে দেওয়া।
    CSWSH (Cross-Site WebSocket Hijacking)Origin যাচাই না করা WebSocket handshake-এর মাধ্যমে ভিকটিমের cookie ব্যবহার করে সংযোগ হাইজ্যাক করা।
    Origin HeaderRequest কোন ডোমেইন থেকে এসেছে তা নির্দেশকারী browser-controlled HTTP header।

    চিট শিট — ডিফেন্ডারদের জন্য (এক নজরে)

    CSRF Defense Checklist
    [✓] প্রতিটি state-changing request-এ per-session CSRF token + session-bound validation
[✓] Session cookie-তে SameSite=Lax (বা Strict, প্রযোজ্য হলে) + Secure + HttpOnly
[✓] Origin header exact-match allowlist যাচাই (Referer fallback হিসেবে)
[✓] Content-Type কড়াভাবে validate (lenient/best-effort parsing এড়িয়ে চলুন)
[✓] State-changing action কখনো GET/HEAD-এ না রাখা
[✓] Sensitive action-এ re-authentication/step-up verification
[✓] WebSocket handshake-এও Origin validation
[✓] Framework-এর বিল্ট-ইন CSRF protection সব route-এ enable আছে কি না পর্যায়ক্রমে অডিট করা

    চিট শিট — টেস্টারদের জন্য (এক নজরে)

    CSRF Testing Checklist
    [ ] সব state-changing endpoint-এ CSRF token আছে কি না স্ক্যান করুন
[ ] Token বাদ দিয়ে/খালি করে request পাঠিয়ে দেখুন
[ ] Token অন্য সেশনের হলেও গ্রহণ হয় কি না যাচাই করুন (session-binding)
[ ] Cookie-এর SameSite attribute পরীক্ষা করুন
[ ] Origin/Referer বাদ দিয়ে/পরিবর্তন করে যাচাই করুন
[ ] HTTP method GET-এ state পরিবর্তন হয় কি না দেখুন
[ ] Content-Type পরিবর্তন করে (JSON↔text/plain) bypass সম্ভব কি না যাচাই করুন
[ ] Burp দিয়ে PoC তৈরি করে বাস্তবে নিজের টেস্ট অ্যাকাউন্টে কনফার্ম করুন

    Frequently Asked Questions (FAQ)

    CSRF টোকেন থাকলেই কি অ্যাপ্লিকেশন সম্পূর্ণ নিরাপদ?

    না। Token যদি session-bound না হয়, যদি অনুপস্থিত থাকলেও request গ্রহণ হয়, বা যদি অ্যাপ্লিকেশনে কোথাও XSS থাকে (যা token-ই পড়ে ফেলতে পারে), তাহলে token থাকা সত্ত্বেও CSRF সম্ভব থাকতে পারে।

    SameSite=Lax থাকলে কি CSRF token-এর আর দরকার নেই?

    না। SameSite=Lax top-level GET navigation-এ এখনও cookie পাঠায়, তাই GET-based CSRF এখনও সম্ভব। এছাড়া পুরনো ব্রাউজার এটি সমর্থন নাও করতে পারে। Token + SameSite একসাথে ব্যবহার করাই সবচেয়ে নিরাপদ।

    CSRF ও XSS-এর মধ্যে কোনটি বেশি গুরুত্বপূর্ণ?

    দুটোই গুরুত্বপূর্ণ এবং একে অপরের পরিপূরক — XSS সাধারণত বেশি শক্তিশালী (এমনকি CSRF defense-ও বাইপাস করতে পারে), কিন্তু CSRF-এর জন্য আলাদা, স্বাধীন defense প্রয়োজন কারণ কোনো অ্যাপ্লিকেশনেই XSS "শূন্য" থাকার নিশ্চয়তা দেওয়া যায় না।

    JWT-ভিত্তিক Authorization header auth ব্যবহার করলে কি CSRF নিয়ে একদমই চিন্তা করতে হয় না?

    Classic cookie-based CSRF ঝুঁকি কমে যায়, কিন্তু যদি refresh token cookie-তে রাখা হয়, বা token localStorage-এ রেখে XSS-এর ঝুঁকি বাড়ানো হয়, তাহলে ভিন্ন ধরনের ঝুঁকি তৈরি হয় — তাই সম্পূর্ণ নিশ্চিন্ত হওয়া ঠিক না।

    Bug bounty-তে CSRF রিপোর্ট করার আগে সবচেয়ে গুরুত্বপূর্ণ কাজ কী?

    প্রোগ্রামের scope/policy ভালোভাবে পড়া, এবং শুধুমাত্র নিজের টেস্ট অ্যাকাউন্টে, বাস্তব before/after প্রমাণসহ PoC যাচাই করা — অনুমান বা না-যাচাই-করা claim রিপোর্ট করা থেকে বিরত থাকা।
