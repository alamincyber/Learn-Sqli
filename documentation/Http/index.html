    HTTP, HTTPS, IP, DNS ও Cookies — ওয়েব ফান্ডামেন্টালস

    বাংলায় সম্পূর্ণ, বিস্তারিত একটি গাইড — ইন্টারনেট ও ওয়েব আসলে কীভাবে কাজ করে তার ভিত্তি থেকে শুরু করে IP addressing, DNS resolution, HTTP/HTTPS protocol, TLS encryption, এবং cookie/session-এর গভীর বিশ্লেষণ পর্যন্ত, ১২টি অধ্যায়ে সাজানো।

    কেন এই ডকুমেন্টেশন গুরুত্বপূর্ণ

    XSS, CSRF, SQL Injection-এর মতো যেকোনো ওয়েব সিকিউরিটি বিষয় বোঝার আগে, ওয়েব আসলে নিচের স্তরে কীভাবে কাজ করে তা স্পষ্টভাবে জানা অপরিহার্য। একটি ব্রাউজারে URL লেখার পর পর্দায় পৃষ্ঠা আসার আগে অনেকগুলো ধাপ ঘটে — DNS দিয়ে ডোমেইন নাম থেকে IP address বের করা, সেই IP-তে একটি TCP সংযোগ তৈরি করা, TLS দিয়ে এনক্রিপ্টেড চ্যানেল স্থাপন করা, এবং তারপর HTTP request/response আদান-প্রদান করা — আর পুরো সময়জুড়ে cookie দিয়ে ইউজারের session/state মনে রাখা। এই ডকুমেন্টেশন সেই পুরো যাত্রাটা ধাপে ধাপে ব্যাখ্যা করে।

    এই ডকুমেন্টেশন কীভাবে ব্যবহার করবেন

    🟢 নেটওয়ার্ক স্তর (১–৩)

    ইন্টারনেট কীভাবে কাজ করে, IP addressing, এবং DNS resolution বিস্তারিতভাবে।

    🟡 প্রোটোকল স্তর (৪–৭)

    HTTP request/response, method/status/header, HTTPS, TLS handshake ও certificate।

    🔴 অ্যাপ্লিকেশন স্তর (৮–১২)

    Cookie, session, browser storage, same-origin policy/CORS, DevTools দিয়ে প্র্যাকটিক্যাল বিশ্লেষণ, এবং রেফারেন্স।

    ℹ️

    ব্যবহারের নোটিশ: এই ডকুমেন্টেশনটি সম্পূর্ণভাবে শিক্ষামূলক উদ্দেশ্যে তৈরি — ইন্টারনেট ও ওয়েব প্রোটোকল কীভাবে কাজ করে তা বোঝানোর জন্য। যেখানে নেটওয়ার্ক বিশ্লেষণ/ডিবাগিং টুল (Browser DevTools, packet capture ইত্যাদি) ব্যবহারের কথা বলা হয়েছে, তা শুধুমাত্র নিজের তৈরি সিস্টেম, নিজের ট্রাফিক, বা স্পষ্ট অনুমতি-থাকা পরিবেশে প্রয়োগ করুন। অন্য কারো নেটওয়ার্ক ট্রাফিক/ডিভাইস পর্যবেক্ষণ করার আগে সবসময় প্রাসঙ্গিক আইন ও অনুমতি বিবেচনা করুন।

    ইন্টারনেট ও ওয়েব কীভাবে কাজ করে

    ব্রাউজারে একটি URL লেখার পর পর্দায় পৃষ্ঠা আসার আগে, পর্দার আড়ালে ঠিক কী কী ঘটে — একটি সম্পূর্ণ ওভারভিউ।

    ইন্টারনেট কী?

    ইন্টারনেট হলো বিশ্বব্যাপী সংযুক্ত কম্পিউটার নেটওয়ার্কের একটি বিশাল জাল — লক্ষ লক্ষ ডিভাইস (সার্ভার, রাউটার, ব্যক্তিগত কম্পিউটার, মোবাইল ফোন) একে অপরের সাথে প্রমিত (standardized) প্রোটোকল ব্যবহার করে যোগাযোগ করে। ওয়েব (World Wide Web) ইন্টারনেটের একটি অংশ মাত্র — এটি নির্দিষ্ট করে HTTP/HTTPS প্রোটোকল ব্যবহার করে ডকুমেন্ট (ওয়েব পেজ) আদান-প্রদানের সিস্টেম। ইন্টারনেট দিয়ে ইমেইল, ফাইল ট্রান্সফার, ভিডিও কল-ও চলে — কিন্তু ওয়েব শুধু HTTP-ভিত্তিক অংশটুকু।

    Client-Server মডেল

    ওয়েব মূলত একটি client-server স্থাপত্যের উপর দাঁড়িয়ে আছে:

    • Client: সাধারণত একটি ব্রাউজার (Chrome, Firefox) — যা ইউজারের পক্ষ থেকে request পাঠায়।
    • Server: একটি কম্পিউটার যা সবসময় চালু থাকে, request শোনে, এবং response (সাধারণত HTML/CSS/JS/ছবি/ডেটা) ফেরত পাঠায়।

    একাধিক client একই server-এর সাথে একইসাথে যোগাযোগ করতে পারে — এটাই একটি ওয়েবসাইট একসাথে হাজারো ইউজারকে সেবা দেওয়ার ভিত্তি।

    URL লেখার পর যা ঘটে — ধাপে ধাপে

    ধরা যাক আপনি ব্রাউজারে https://example.com লিখে Enter চাপলেন। নিচে পুরো প্রক্রিয়াটা সংক্ষেপে দেখানো হলো — প্রতিটি ধাপ পরবর্তী অধ্যায়গুলোতে বিস্তারিত আলোচিত হবে:

    ১. DNS Resolution

    ব্রাউজার example.com ডোমেইন নামটিকে একটি সংখ্যাসূচক IP address-এ রূপান্তর করে, যা DNS সিস্টেম দিয়ে হয় (অধ্যায় ৩)।

    ২. TCP সংযোগ স্থাপন

    ব্রাউজার সেই IP address-এর সাথে একটি TCP সংযোগ তৈরি করে (সাধারণত port 443-এ HTTPS-এর জন্য), একটি "three-way handshake"-এর মাধ্যমে।

    ৩. TLS Handshake (HTTPS হলে)

    ব্রাউজার ও সার্ভার একটি এনক্রিপ্টেড চ্যানেল স্থাপন করে, সার্ভারের পরিচয় certificate দিয়ে যাচাই করে (অধ্যায় ৬–৭)।

    ৪. HTTP Request পাঠানো

    ব্রাউজার একটি HTTP request পাঠায় (method, headers, cookie-সহ), সার্ভার সেই অনুযায়ী প্রয়োজনীয় ডেটা তৈরি করে response পাঠায় (অধ্যায় ৪–৫)।

    ৫. Response Parse ও Render

    ব্রাউজার HTML পায়, তা parse করে, এতে উল্লেখিত CSS/JS/ছবি-র জন্য আরও request পাঠায় (প্রতিটির জন্য আবার উপরের ধাপগুলো, সংযোগ পুনঃব্যবহার-সহ), এবং অবশেষে পর্দায় রেন্ডার করে।

    ৬. Cookie/Session বজায় রাখা

    সার্ভার response-এ cookie সেট করতে পারে, যা ব্রাউজার পরবর্তী সব request-এ স্বয়ংক্রিয়ভাবে ফেরত পাঠায় — এভাবেই লগইন অবস্থা/state মনে রাখা হয় (অধ্যায় ৮–৯)।

    প্রোটোকল স্তর (Layered মডেল — সংক্ষিপ্ত ধারণা)

    ইন্টারনেট যোগাযোগ কয়েকটি স্তরে ভাগ করা — প্রতিটি স্তর নির্দিষ্ট একটি দায়িত্ব পালন করে এবং নিচের স্তরের উপর নির্ভর করে:

    স্তর (সরলীকৃত)দায়িত্বউদাহরণ প্রোটোকল
    Applicationপ্রকৃত ডেটা/বার্তা — ওয়েব পেজ, ইমেইলHTTP, HTTPS, DNS, SMTP
    Transportডেটা নির্ভরযোগ্যভাবে পৌঁছানো, ক্রম বজায় রাখাTCP, UDP
    Internet/Networkডেটা সঠিক ডিভাইসে রুট করা (addressing)IP (IPv4/IPv6)
    Link/Physicalপ্রকৃত সিগন্যাল — তার, ওয়াইফাই, ফাইবারEthernet, Wi-Fi

    একটি ওয়েব অনুরোধ এই স্তরগুলোর মধ্য দিয়ে যায় — HTTP ডেটা TCP-তে মোড়ানো হয়, TCP ডেটা IP প্যাকেটে মোড়ানো হয়, এবং IP প্যাকেট শারীরিক মাধ্যম (তার/ওয়াইফাই) দিয়ে পাঠানো হয়। প্রতিটি স্তর শুধু নিজের দায়িত্ব পালন করে, নিচের/উপরের স্তর কী করছে তা নিয়ে মাথা ঘামায় না — এই বিচ্ছিন্নতাই (abstraction) ইন্টারনেটকে এত নমনীয় করে তুলেছে।

    HTTP/HTTPS সাধারণত TCP-এর উপর চলে, কারণ একটি ওয়েব পেজের ডেটা অবিকৃত ও সঠিক ক্রমে পৌঁছানো জরুরি। তবে আধুনিক HTTP/3 প্রোটোকল QUIC নামক একটি UDP-ভিত্তিক প্রোটোকল ব্যবহার করে, যা TCP-এর নির্ভরযোগ্যতা রাখে কিন্তু কিছু বিলম্ব (latency) সমস্যা কমায়।

    অনুশীলন

    নিজের ব্রাউজারে একটি নতুন ট্যাব খুলে DevTools-এর Network ট্যাব চালু করুন (F12 চাপুন), তারপর যেকোনো ওয়েবসাইট ভিজিট করুন। লক্ষ্য করুন প্রথম request-টি কী (সাধারণত মূল HTML ডকুমেন্ট), এবং তারপর আর কতগুলো অতিরিক্ত request (CSS, JS, ছবি) পাঠানো হচ্ছে।

    সারসংক্ষেপ

    ওয়েব একটি client-server মডেলের উপর দাঁড়িয়ে, যা স্তরবিন্যস্ত প্রোটোকল (DNS → TCP → TLS → HTTP) ব্যবহার করে কাজ করে। একটি সাধারণ পেজ লোডে DNS resolution, সংযোগ স্থাপন, এনক্রিপশন, এবং ডেটা আদান-প্রদান — এই প্রতিটি ধাপ জড়িত, যা পরবর্তী অধ্যায়গুলোতে বিস্তারিতভাবে আলোচিত হবে।

    IP Address ও নেটওয়ার্কিং ভিত্তি

    ইন্টারনেটে প্রতিটি ডিভাইস কীভাবে একে অপরকে খুঁজে পায় — IPv4, IPv6, পাবলিক/প্রাইভেট address, port, এবং NAT।

    IP Address কী?

    IP (Internet Protocol) address হলো একটি সংখ্যাসূচক লেবেল, যা ইন্টারনেটে সংযুক্ত প্রতিটি ডিভাইসকে অদ্বিতীয়ভাবে চিহ্নিত করে — অনেকটা একটি ডাকঠিকানার মতো, যা দিয়ে ডেটা সঠিক গন্তব্যে পৌঁছায়। যখন আপনার ব্রাউজার একটি সার্ভারে request পাঠায়, সেই request-এ আপনার ডিভাইসের IP address (source) এবং সার্ভারের IP address (destination) দুটোই থাকে, যাতে response সঠিক পথে ফিরে আসতে পারে।

    IPv4

    IPv4 address চারটি সংখ্যা (০–২৫৫) দিয়ে গঠিত, বিন্দু দিয়ে আলাদা করা — যেমন 192.168.1.1। প্রতিটি সংখ্যা ৮ বিট (এক byte), মোট ৩২ বিট। এর মানে সর্বোচ্চ প্রায় ৪.৩ বিলিয়ন অদ্বিতীয় address সম্ভব — যা আধুনিক বিশ্বে ইন্টারনেট-সংযুক্ত ডিভাইসের তুলনায় যথেষ্ট কম, এই সীমাবদ্ধতার কারণেই IPv6-এর প্রয়োজন হয়েছে।

    IPv4 address উদাহরণ
    192.168.1.1      — সাধারণ home router-এর local address
8.8.8.8          — Google Public DNS সার্ভার
127.0.0.1        — localhost (নিজের কম্পিউটার)

    IPv6

    IPv6 address ১২৮ বিটের, আট গ্রুপে hexadecimal সংখ্যা দিয়ে লেখা হয়, কোলন দিয়ে আলাদা — যেমন 2001:0db8:85a3:0000:0000:8a2e:0370:7334। এতে প্রায় ৩৪০ undecillion (৩৪ এর পর ৩৭টি শূন্য) অদ্বিতীয় address সম্ভব — ভবিষ্যতের জন্য কার্যত সীমাহীন। সংক্ষিপ্ত লেখার জন্য ধারাবাহিক শূন্যগুলো :: দিয়ে একবার বাদ দেওয়া যায়।

    IPv6 address — সংক্ষিপ্ত ফর্ম
    2001:0db8:85a3:0000:0000:8a2e:0370:7334
সংক্ষিপ্ত: 2001:db8:85a3::8a2e:370:7334

::1   — IPv6-এ localhost

    Publicউপরের রেঞ্জের বাইরে সবকিছুইন্টারনেটে সরাসরি দৃশ্যমান/পৌঁছানো যায় — যেমন ওয়েব সার্ভার

    NAT (Network Address Translation)

    আপনার বাসার রাউটারের একটিমাত্র public IP address থাকে, কিন্তু বাসার ভেতরে অনেকগুলো ডিভাইস (ফোন, ল্যাপটপ, স্মার্ট TV) থাকতে পারে, প্রতিটির নিজস্ব private IP address নিয়ে। NAT হলো সেই প্রযুক্তি, যা রাউটারকে একাধিক private-IP ডিভাইসের ট্রাফিক একটিমাত্র public IP দিয়ে ইন্টারনেটে পাঠাতে ও সঠিকভাবে ফেরত রাউট করতে সাহায্য করে — port number ব্যবহার করে কোন response কোন internal ডিভাইসের জন্য তা ট্র্যাক রেখে।

    Port নম্বর

    একটি IP address একটি ডিভাইস চিহ্নিত করে, কিন্তু একটি ডিভাইসে একসাথে অনেক সার্ভিস চলতে পারে (ওয়েব সার্ভার, ইমেইল সার্ভার, SSH)। Port সংখ্যা (০–৬৫৫৩৫) নির্দিষ্ট করে কোন সার্ভিসের সাথে যোগাযোগ হবে।

    Portসাধারণ ব্যবহার

    443HTTPS (এনক্রিপ্টেড ওয়েব ট্রাফিক)
    22SSH (নিরাপদ রিমোট অ্যাক্সেস)

    একটি সম্পূর্ণ "ঠিকানা" তাই আসলে IP address + port-এর সমন্বয় — একে বলা হয় socket। https://example.com মানে ব্রাউজার আসলে সেই ডোমেইনের IP address-এর port 443-এ সংযুক্ত হয়।

    💡

    URL-এ port সাধারণত দেখা যায় না কারণ HTTP/HTTPS-এর জন্য ডিফল্ট port (80/443) ব্রাউজার নিজে থেকেই ব্যবহার করে। কিন্তু ডেভেলপমেন্টের সময় প্রায়ই দেখা যায় http://localhost:3000-এর মতো URL, যেখানে port স্পষ্টভাবে উল্লেখ করা থাকে কারণ সেটি ডিফল্ট নয়।

    অনুশীলন

    নিজের কম্পিউটারের টার্মিনাল/কমান্ড প্রম্পটে ipconfig (Windows) বা ifconfig/ip addr (Linux/Mac) চালিয়ে নিজের ডিভাইসের local IP address খুঁজে বের করুন — এটি private রেঞ্জের মধ্যে পড়ে কি না যাচাই করুন।

    সারসংক্ষেপ

    IP address প্রতিটি ডিভাইসকে ইন্টারনেটে অদ্বিতীয়ভাবে চিহ্নিত করে; IPv4 সীমিত (৩২ বিট), IPv6 কার্যত সীমাহীন (১২৮ বিট)। Private IP শুধু স্থানীয় নেটওয়ার্কে ব্যবহৃত হয়, NAT দিয়ে একটি public IP-এর মাধ্যমে ইন্টারনেটে যুক্ত হয়। Port নম্বর একই ডিভাইসে চলা বিভিন্ন সার্ভিসকে আলাদা করে।

    DNS — Domain Name System বিস্তারিত

    মানুষের জন্য সহজে মনে রাখার মতো ডোমেইন নাম (যেমন example.com) কীভাবে সংখ্যাসূচক IP address-এ রূপান্তরিত হয় — DNS-এর পুরো প্রক্রিয়া।

    DNS কী এবং কেন প্রয়োজন?

    DNS (Domain Name System)-কে প্রায়ই ইন্টারনেটের "ফোনবুক" বলা হয় — এটি মানুষের জন্য মনে রাখা সহজ এমন ডোমেইন নাম (যেমন google.com) কে কম্পিউটারের বোঝার উপযোগী সংখ্যাসূচক IP address-এ (যেমন 142.250.195.78) রূপান্তর করে। DNS ছাড়া, প্রতিটি ওয়েবসাইট ভিজিট করতে আমাদের তার IP address মুখস্থ রাখতে হতো — যা বাস্তবে অসম্ভব।

    DNS Resolution-এর ধাপে ধাপে প্রক্রিয়া

    ধরা যাক আপনি প্রথমবার www.example.com ভিজিট করছেন (কোনো cache নেই):

    ১. Browser/OS Cache চেক

    ব্রাউজার প্রথমে নিজের ও অপারেটিং সিস্টেমের DNS cache-এ খুঁজে দেখে, আগে থেকে জানা আছে কি না।

    ২. Recursive Resolver-এ Query

    না পেলে, request যায় একটি recursive DNS resolver-এর কাছে (সাধারণত ISP-এর, বা Google 8.8.8.8/Cloudflare 1.1.1.1-এর মতো পাবলিক resolver)।

    ৩. Root Server-এ Query

    Resolver-এর কাছেও cache না থাকলে, সে একটি root DNS server-কে জিজ্ঞাসা করে — root server বলে দেয় কোন TLD (.com) server-এর কাছে যেতে হবে।

    ৪. TLD Server-এ Query

    TLD (Top-Level Domain) server (.com-এর জন্য) resolver-কে বলে দেয় example.com-এর authoritative nameserver কোনটি।

    ৫. Authoritative Server-এ Query

    Authoritative nameserver-ই আসল উত্তর জানে — সে www.example.com-এর প্রকৃত IP address resolver-কে ফেরত পাঠায়।

    ৬. ফলাফল Cache ও ফেরত

    Resolver এই উত্তর নির্দিষ্ট সময়ের (TTL) জন্য cache করে রাখে এবং ব্রাউজারকে পাঠিয়ে দেয়। ব্রাউজার এখন সেই IP address-এ সংযোগ করতে পারে।

    এই পুরো প্রক্রিয়া সাধারণত কয়েক মিলিসেকেন্ডের মধ্যে ঘটে, এবং বেশিরভাগ ক্ষেত্রে caching-এর কারণে অনেক ধাপ এড়িয়ে যাওয়া যায়।

    DNS Record-এর প্রধান ধরন

    Record Typeউদ্দেশ্যউদাহরণ
    Aডোমেইন থেকে IPv4 addressexample.com → 93.184.216.34
    AAAAডোমেইন থেকে IPv6 addressexample.com → 2606:2800:220:1::1
    CNAMEএকটি ডোমেইনকে অন্য ডোমেইনের "alias" বানানোwww.example.com → example.com
    MXকোন সার্ভার সেই ডোমেইনের ইমেইল গ্রহণ করেexample.com → mail.example.com
    TXTস্বেচ্ছাসেবী টেক্সট তথ্য — প্রায়ই verification/SPF-এর জন্য"v=spf1 include:_spf.example.com ~all"
    NSকোন nameserver এই ডোমেইনের জন্য authoritativeexample.com → ns1.examplehost.com

    TTL (Time To Live) ও Caching

    প্রতিটি DNS record-এর একটি TTL থাকে (সেকেন্ডে), যা নির্ধারণ করে resolver কতক্ষণ সেই উত্তর cache-এ রাখবে, আবার জিজ্ঞাসা না করে। কম TTL (যেমন ৬০ সেকেন্ড) মানে পরিবর্তন দ্রুত ছড়ায় কিন্তু resolver-এ বেশি লোড; বেশি TTL (যেমন ২৪ ঘণ্টা) মানে দ্রুততর resolution কিন্তু পরিবর্তন ছড়াতে সময় লাগে।

    DNS-সম্পর্কিত নিরাপত্তা ঝুঁকি (সংক্ষিপ্ত পরিচয়)

    DNS Spoofing / Cache Poisoning

    একজন আক্রমণকারী DNS resolver-এর cache-এ ভুয়া record ঢুকিয়ে দিতে পারলে, ইউজারকে একটি দূষিত সার্ভারে পাঠিয়ে দিতে পারে — যদিও ইউজার সঠিক ডোমেইন নাম-ই টাইপ করেছেন।

    DNSSEC (DNS Security Extensions)

    DNS response-কে ডিজিটাল স্বাক্ষর দিয়ে যাচাইযোগ্য করে তোলে, যাতে resolver নিশ্চিত হতে পারে উত্তরটি আসল authoritative server থেকেই এসেছে এবং পথে পরিবর্তিত হয়নি।

    DNS resolution সাধারণত এনক্রিপ্টেড নয় (plain UDP-তে পাঠানো হয়), যার কারণে কেউ নেটওয়ার্কে আড়ি পাতলে বুঝে যেতে পারে আপনি কোন ডোমেইন ভিজিট করছেন। DNS over HTTPS (DoH) ও DNS over TLS (DoT) — এই দুটি আধুনিক প্রযুক্তি DNS query-কে এনক্রিপ্ট করে এই গোপনীয়তা সমস্যার সমাধান করে।

    অনুশীলন

    টার্মিনালে nslookup example.com বা dig example.com কমান্ড চালিয়ে দেখুন — এটি কোন IP address ফেরত দেয়, এবং TTL মান কত দেখায়।

    সারসংক্ষেপ

    DNS ডোমেইন নামকে IP address-এ রূপান্তর করে, recursive resolver থেকে root → TLD → authoritative server পর্যন্ত একটি ধাপে ধাপে query প্রক্রিয়ার মাধ্যমে। বিভিন্ন record type (A, AAAA, CNAME, MX, TXT, NS) ভিন্ন ভিন্ন তথ্য বহন করে, এবং TTL নির্ধারণ করে caching-এর সময়কাল। DNS-এর নিজস্ব নিরাপত্তা ঝুঁকি (spoofing) আছে, যা DNSSEC/DoH/DoT দিয়ে প্রশমিত করা যায়।

    HTTP Fundamentals — Request ও Response

    HTTP প্রোটোকলের মূল গঠন — request কীভাবে তৈরি হয়, সার্ভার কীভাবে response পাঠায়, এবং HTTP methods-এর ব্যবহার।

    HTTP কী?

    HTTP (HyperText Transfer Protocol) হলো সেই নিয়মাবলি (protocol), যা নির্ধারণ করে ব্রাউজার (client) ও সার্ভার কীভাবে একে অপরের সাথে কথা বলবে। এটি একটি request-response প্রোটোকল — client একটি request পাঠায়, server একটি response ফেরত পাঠায়। HTTP নিজে stateless — অর্থাৎ প্রতিটি request স্বাধীন, সার্ভার আগের request মনে রাখে না (যদি না cookie/session দিয়ে স্পষ্টভাবে state বজায় রাখা হয়, যা অধ্যায় ৮–৯-এ আলোচিত)।

    একটি request-এর তিনটি মূল অংশ:

    • Request line: method (GET), path (/products?category=books), এবং HTTP version (HTTP/1.1)।
    • Headers: key-value জোড়া, যা request সম্পর্কে অতিরিক্ত তথ্য বহন করে (অধ্যায় ৫-এ বিস্তারিত)।
    • Body (ঐচ্ছিক): POST/PUT-এর মতো method-এ পাঠানো প্রকৃত ডেটা (যেমন ফর্মের মান)। GET-এ সাধারণত body থাকে না।

    HTTP Methods বিস্তারিত

    Methodউদ্দেশ্যBody থাকে?Idempotent?*

    PUTসম্পূর্ণ রিসোর্স প্রতিস্থাপন/আপডেট করাহ্যাঁহ্যাঁ

    *Idempotent মানে একই request একাধিকবার পাঠালেও ফলাফল একই থাকে (প্রথমবার পাঠানোর পরের অবস্থার মতোই) — যেমন একটি রিসোর্স মুছে ফেলা (DELETE) একবার করলে বা দশবার করলে ফলাফল একই (রিসোর্সটি নেই)। কিন্তু POST দিয়ে একটি নতুন অর্ডার তৈরি করলে, দশবার পাঠালে দশটি আলাদা অর্ডার তৈরি হতে পারে — তাই এটি idempotent নয়।

    HTTP Status Code বিস্তারিত

    Status code তিন অঙ্কের একটি সংখ্যা, যার প্রথম অঙ্ক বিস্তৃত বিভাগ নির্দেশ করে:

    1xx — Informational

    100 Continue — server client-কে বলছে request body পাঠাতে থাকুন।

    2xx — Success

    200 OK (সফল), 201 Created (নতুন রিসোর্স তৈরি হয়েছে), 204 No Content (সফল কিন্তু ফেরত দেওয়ার মতো body নেই)।

    3xx — Redirection

    301 Moved Permanently, 302 Found (সাময়িক redirect), 304 Not Modified (cache থেকে ব্যবহার করুন)।

    4xx — Client Error

    400 Bad Request, 401 Unauthorized (authentication দরকার), 403 Forbidden (অনুমতি নেই), 404 Not Found।

    5xx — Server Error

    500 Internal Server Error (সার্ভারে অপ্রত্যাশিত সমস্যা), 502 Bad Gateway, 503 Service Unavailable।

    401 বনাম 403

    401 মানে — আপনি কে তা প্রমাণিত না (লগইন করুন); 403 মানে — আপনাকে চেনা গেছে, কিন্তু আপনার এই রিসোর্স দেখার অনুমতি নেই।

    HTTP/1.1, HTTP/2, HTTP/3 — সংক্ষিপ্ত তুলনা

    ভার্সনমূল বৈশিষ্ট্য
    HTTP/1.1Text-ভিত্তিক, প্রতিটি সংযোগে একসাথে একটি request (keep-alive দিয়ে সংযোগ পুনঃব্যবহার সম্ভব, কিন্তু head-of-line blocking সমস্যা থাকে)
    HTTP/2Binary প্রোটোকল, multiplexing (একই সংযোগে একসাথে একাধিক request/response), header compression
    HTTP/3TCP-এর বদলে QUIC (UDP-ভিত্তিক) ব্যবহার করে, connection-level head-of-line blocking সমস্যা আরও কমায়, দ্রুততর সংযোগ স্থাপন

    HTTP একটি stateless request-response প্রোটোকল। প্রতিটি request-এ একটি method (GET/POST/...), headers, ও ঐচ্ছিক body থাকে; প্রতিটি response-এ একটি status code (সফলতা/ত্রুটি নির্দেশক), headers, ও body থাকে। HTTP-এর নতুন ভার্সনগুলো (HTTP/2, HTTP/3) মূলত গতি ও দক্ষতা বাড়ানোর দিকে কেন্দ্রীভূত।

    HTTP Headers বিস্তারিত

    Request ও response-এ ব্যবহৃত গুরুত্বপূর্ণ header-গুলো — content negotiation, caching, এবং নিরাপত্তা-সম্পর্কিত header।

    গুরুত্বপূর্ণ Request Headers

    Headerউদ্দেশ্য
    Hostকোন ডোমেইনের জন্য request — একই IP-তে একাধিক ওয়েবসাইট হোস্ট করা থাকলে সার্ভার এটি দিয়ে বুঝতে পারে কোনটি দেখাতে হবে
    User-Agentক্লায়েন্ট সফটওয়্যার (ব্রাউজার/OS) সম্পর্কে তথ্য
    Acceptক্লায়েন্ট কোন ধরনের response content (HTML, JSON ইত্যাদি) গ্রহণ করতে পারে
    Accept-Languageপছন্দের ভাষা — content negotiation-এর জন্য
    Cookieআগে সেট করা cookie-গুলো ফেরত পাঠানো (অধ্যায় ৮)
    AuthorizationAuthentication token/credential (যেমন Bearer <token>)
    OriginRequest কোন origin থেকে এসেছে — cross-origin request-এ ব্রাউজার স্বয়ংক্রিয়ভাবে যোগ করে
    Refererকোন পৃষ্ঠা থেকে এই request-টি initiate হয়েছে (বানানে ঐতিহাসিক টাইপো — আসলে "Referrer")

    গুরুত্বপূর্ণ Response Headers

    Headerউদ্দেশ্য
    Content-TypeResponse body-এর ধরন (text/html, application/json, image/png ইত্যাদি)
    Content-LengthResponse body-এর আকার (byte-এ)
    Set-Cookieব্রাউজারকে একটি cookie সংরক্ষণ করতে বলা (অধ্যায় ৮)
    Cache-ControlResponse কতক্ষণ/কীভাবে cache করা যাবে তা নির্দেশ করা
    Location3xx redirect response-এ, কোথায় redirect করতে হবে তা জানানো
    Access-Control-Allow-OriginCORS — কোন origin থেকে এই রিসোর্স পড়ার অনুমতি আছে (অধ্যায় ১০)
    Strict-Transport-SecurityHSTS — ব্রাউজারকে ভবিষ্যতে সবসময় HTTPS ব্যবহার করতে বাধ্য করা (অধ্যায় ৬)

    Content Negotiation

    একই URL ভিন্ন ভিন্ন ফরম্যাটে content দিতে পারে, ক্লায়েন্টের চাহিদা অনুযায়ী — একে বলা হয় content negotiation। ক্লায়েন্ট Accept header দিয়ে জানায় সে কী পছন্দ করে, এবং সার্ভার সেই অনুযায়ী সবচেয়ে উপযুক্ত ফরম্যাট বেছে response-এর Content-Type header দিয়ে জানিয়ে দেয়।

    Content Negotiation — উদাহরণ
    Request:  Accept: application/json
Response: Content-Type: application/json

Request:  Accept: text/html
Response: Content-Type: text/html; charset=UTF-8

    Caching Headers বিস্তারিত

    ব্রাউজার বারবার একই রিসোর্স না ডাউনলোড করার জন্য caching ব্যবহার করে — এটি গতি বাড়ায় এবং সার্ভারে লোড কমায়।

    • Cache-Control: max-age=3600: এই রিসোর্স ১ ঘণ্টা (৩৬০০ সেকেন্ড) পর্যন্ত নতুন request ছাড়াই cache থেকে ব্যবহার করা যাবে।
    • Cache-Control: no-store: কখনো cache করা যাবে না — sensitive ডেটার জন্য ব্যবহৃত।
    • ETag: রিসোর্সের একটি "ফিঙ্গারপ্রিন্ট" (hash)। পরবর্তী request-এ ব্রাউজার এই ETag পাঠায়, সার্ভার তুলনা করে বলে দেয় রিসোর্স বদলেছে কি না — না বদলালে 304 Not Modified পাঠিয়ে পুরো body আবার পাঠানো এড়ানো যায়।

    নিরাপত্তা-সম্পর্কিত Response Headers (সংক্ষিপ্ত)

    Headerউদ্দেশ্য
    Content-Security-Policyকোন উৎস থেকে script/style/ছবি লোড করা যাবে তা সীমাবদ্ধ করে — XSS-এর impact কমাতে সাহায্য করে
    X-Content-Type-Options: nosniffব্রাউজারকে Content-Type "অনুমান" (MIME sniffing) করতে নিষেধ করে
    X-Frame-Optionsপৃষ্ঠাটি অন্য সাইটের <iframe>-এ embed করা যাবে কি না নিয়ন্ত্রণ করে (clickjacking প্রতিরোধ)

    অনুশীলন

    DevTools-এর Network ট্যাবে যেকোনো একটি request-এর Headers ট্যাব খুলে দেখুন — কতগুলো আলাদা header আছে চিহ্নিত করুন, এবং চেষ্টা করুন কোনটা Cache-Control, কোনটা Set-Cookie খুঁজে বের করতে।

    HTTP header-গুলো request/response সম্পর্কে অতিরিক্ত metadata বহন করে — কনটেন্টের ধরন, cookie, caching নির্দেশনা, এবং নিরাপত্তা নীতি। এগুলো বোঝা একজন ডেভেলপার/সিকিউরিটি বিশ্লেষকের জন্য মৌলিক দক্ষতা, কারণ বেশিরভাগ ওয়েব আচরণ (cookie, cache, CORS, security policy) header-এর মাধ্যমেই নিয়ন্ত্রিত হয়।

    HTTPS ও TLS/SSL এনক্রিপশন

    HTTP কীভাবে এনক্রিপ্টেড হয়ে HTTPS-এ পরিণত হয়, এবং TLS handshake-এর ভেতরে ঠিক কী ঘটে।

    HTTP বনাম HTTPS

    HTTPS (HTTP Secure) হলো HTTP-এর একটি সুরক্ষিত সংস্করণ, যেখানে client ও server-এর মধ্যে আদান-প্রদান হওয়া সব ডেটা TLS (Transport Layer Security) দিয়ে এনক্রিপ্ট করা থাকে। সাধারণ HTTP-তে ডেটা plain text-এ পাঠানো হয় — অর্থাৎ নেটওয়ার্কে কেউ আড়ি পাতলে (man-in-the-middle) সরাসরি পড়ে ফেলতে পারে, এমনকি পরিবর্তনও করতে পারে। HTTPS এই ঝুঁকি দূর করে তিনটি মূল গ্যারান্টি দিয়ে:

    🔒 Confidentiality

    ডেটা এনক্রিপ্টেড, তাই মাঝপথে কেউ পড়তে পারে না।

    ✅ Integrity

    ডেটা পথে পরিবর্তিত হলে তা ধরা পড়ে যাবে — কেউ অজান্তে বদলে দিতে পারবে না।

    🪪 Authentication

    Certificate দিয়ে নিশ্চিত হওয়া যায় আপনি প্রকৃতপক্ষে যে সার্ভারের সাথে কথা বলছেন বলে মনে করছেন, সেটির সাথেই কথা বলছেন।

    TLS Handshake — ধাপে ধাপে (সরলীকৃত)

    HTTPS সংযোগ স্থাপনের সময় একটি "handshake" ঘটে, যেখানে client ও server একটি নিরাপদ, এনক্রিপ্টেড চ্যানেল তৈরির জন্য সম্মত হয়:

    ১. Client Hello

    Client সার্ভারকে জানায় সে কোন কোন TLS version ও encryption algorithm (cipher suite) সমর্থন করে, এবং একটি random মান পাঠায়।

    ২. Server Hello + Certificate

    Server একটি cipher suite বেছে নেয়, তার নিজস্ব random মান পাঠায়, এবং তার SSL/TLS certificate পাঠায় (যা তার পরিচয় প্রমাণ করে — অধ্যায় ৭)।

    ৩. Certificate যাচাই

    Client certificate-টি যাচাই করে — এটি কি বিশ্বস্ত একটি Certificate Authority (CA) দিয়ে স্বাক্ষরিত, মেয়াদ শেষ হয়নি তো, এবং ডোমেইন নাম মিলছে কি না।

    ৪. Key Exchange

    Client ও server একটি পদ্ধতির (যেমন Diffie-Hellman) মাধ্যমে একটি শেয়ার্ড "session key" তৈরি করে, যা শুধু তারাই জানবে — এমনকি কেউ পুরো হ্যান্ডশেক শুনলেও এই key বের করতে পারবে না।

    ৫. Symmetric Encryption শুরু

    এখন থেকে সব ডেটা সেই session key দিয়ে দ্রুত symmetric encryption ব্যবহার করে এনক্রিপ্ট/ডিক্রিপ্ট করা হয় — পুরো সংযোগ জুড়ে।

    ৬. এনক্রিপ্টেড HTTP ট্রাফিক

    এখন প্রকৃত HTTP request/response এই এনক্রিপ্টেড চ্যানেলের ভেতর দিয়ে আদান-প্রদান হয় — বাইরে থেকে শুধু এনক্রিপ্টেড বাইট দেখা যায়, আসল content নয়।

    লক্ষণীয়, এই পুরো হ্যান্ডশেক সাধারণত কয়েক মিলিসেকেন্ডে ঘটে এবং ইউজার কিছুই টের পান না — শুধু URL বারে একটি তালার আইকন দেখেন।

    Symmetric বনাম Asymmetric Encryption (সংক্ষিপ্ত)

    ধরনবর্ণনাTLS-এ ব্যবহার
    Asymmetric (public/private key)একটি পাবলিক key দিয়ে এনক্রিপ্ট, শুধু সংশ্লিষ্ট প্রাইভেট key দিয়ে ডিক্রিপ্ট করা যায় — ধীর কিন্তু key exchange-এর জন্য নিরাপদHandshake-এর সময় certificate যাচাই ও session key নিরাপদে বিনিময়ে ব্যবহৃত
    Symmetric (একই key)একই key দিয়ে এনক্রিপ্ট ও ডিক্রিপ্ট — দ্রুতHandshake-এর পর প্রকৃত ডেটা (HTTP content) এনক্রিপ্ট করতে ব্যবহৃত

    TLS দুটোর সুবিধাই নেয় — ধীরগতির asymmetric encryption শুধু শুরুতে একটি নিরাপদ "key exchange"-এর জন্য ব্যবহার করে, তারপর দ্রুতগতির symmetric encryption দিয়ে প্রকৃত ডেটা আদান-প্রদান করে।

    HSTS (HTTP Strict Transport Security)

    প্রথমবার যদি কেউ http://example.com (HTTPS ছাড়া) ভিজিট করে, তাহলে একটি সাময়িক মুহূর্তের জন্য সংযোগ অরক্ষিত থাকতে পারে, যতক্ষণ না সার্ভার HTTPS-এ redirect করে। HSTS header (Strict-Transport-Security) এই ফাঁক বন্ধ করে — সার্ভার একবার ব্রাউজারকে বলে দেয় "ভবিষ্যতে এই ডোমেইনের জন্য সবসময় শুধু HTTPS ব্যবহার করো", এবং ব্রাউজার সেই নির্দেশ মনে রাখে, এমনকি ইউজার পরেরবার http:// লিখলেও স্বয়ংক্রিয়ভাবে HTTPS-এ পাঠিয়ে দেয়, সার্ভারকে জিজ্ঞাসা না করেই।

    অনুশীলন

    নিজের ব্রাউজারে যেকোনো HTTPS ওয়েবসাইট ভিজিট করুন, URL বারের তালা আইকনে ক্লিক করুন, এবং certificate-এর তথ্য দেখুন — কোন CA এটি ইস্যু করেছে, এবং মেয়াদ কতদিন।

    সারসংক্ষেপ

    HTTPS = HTTP + TLS। TLS handshake-এর মাধ্যমে client ও server একটি নিরাপদ, এনক্রিপ্টেড চ্যানেল তৈরি করে — certificate দিয়ে পরিচয় যাচাই (asymmetric encryption), এবং তারপর দ্রুতগতির symmetric encryption দিয়ে প্রকৃত ডেটা সুরক্ষিত রাখা। HSTS নিশ্চিত করে ব্রাউজার কখনো অনিচ্ছাকৃতভাবে অরক্ষিত HTTP-তে ফিরে না যায়।

    SSL/TLS Certificate ও Certificate Authority

    একটি ওয়েবসাইটের পরিচয় কীভাবে ডিজিটালভাবে প্রমাণিত হয় — certificate, Certificate Authority, এবং "chain of trust"।

    SSL/TLS Certificate কী?

    একটি SSL/TLS certificate হলো একটি ডিজিটাল "পরিচয়পত্র", যা একটি ডোমেইনকে তার পাবলিক key-এর সাথে সংযুক্ত করে এবং একটি বিশ্বস্ত তৃতীয় পক্ষ দিয়ে ডিজিটাল স্বাক্ষরিত থাকে। এটি ব্রাউজারকে নিশ্চিত করতে সাহায্য করে — "আপনি যে ডোমেইনে যেতে চেয়েছিলেন, আপনি আসলেই সেই ডোমেইনের সাথে কথা বলছেন, কোনো প্রতারক সার্ভারের সাথে নয়"।

    Certificate Authority (CA) ও Chain of Trust

    একটি Certificate Authority (CA) হলো এমন একটি বিশ্বস্ত প্রতিষ্ঠান (যেমন Let's Encrypt, DigiCert), যারা একটি ডোমেইনের মালিকানা যাচাই করে certificate ইস্যু করে। ব্রাউজার/অপারেটিং সিস্টেমে আগে থেকেই কিছু "root CA"-এর তালিকা থাকে, যাদের ব্রাউজার স্বয়ংক্রিয়ভাবে বিশ্বাস করে।

    Root CA

    সবচেয়ে বিশ্বস্ত স্তর — তাদের নিজস্ব certificate নিজেরাই স্বাক্ষর করে (self-signed), এবং ব্রাউজার/OS-এ built-in থাকে।

    Intermediate CA

    Root CA কর্তৃক স্বাক্ষরিত, যারা প্রকৃতপক্ষে ওয়েবসাইটগুলোকে certificate ইস্যু করে (নিরাপত্তার জন্য root key সরাসরি ব্যবহার না করে)।

    Leaf/Server Certificate

    নির্দিষ্ট একটি ডোমেইনের জন্য ইস্যু করা certificate, intermediate CA দিয়ে স্বাক্ষরিত — এটাই সার্ভার browser-কে পাঠায়।

    ব্রাউজার এই পুরো শৃঙ্খল (chain of trust) যাচাই করে — leaf certificate → intermediate CA → root CA, প্রতিটি স্বাক্ষর পর্যন্ত নিশ্চিত হওয়া পর্যন্ত। শৃঙ্খলের যেকোনো একটি লিঙ্ক অবৈধ হলে, ব্রাউজার একটি সতর্কতা দেখায় ("Your connection is not private")।

    Certificate-এ কী কী তথ্য থাকে

    Certificate-এর মূল ক্ষেত্র (সরলীকৃত)
    Subject:        CN=example.com
Issuer:         CN=Let's Encrypt Authority
Valid From:     2026-01-01
Valid Until:    2026-04-01
Public Key:     [সার্ভারের পাবলিক key]
Signature:      [CA-এর ডিজিটাল স্বাক্ষর]
Subject Alt Names: example.com, www.example.com

    Certificate-এর ধরন (Validation Level)

    ধরনযাচাইয়ের মাত্রা
    Domain Validation (DV)শুধু ডোমেইনের মালিকানা যাচাই — দ্রুত, প্রায়ই বিনামূল্যে (Let's Encrypt)
    Organization Validation (OV)ডোমেইনের পাশাপাশি প্রতিষ্ঠানের বৈধতাও যাচাই করা হয়
    Extended Validation (EV)সবচেয়ে কঠোর যাচাই প্রক্রিয়া — ব্যবসায়িক নিবন্ধন পর্যন্ত যাচাই করা হয়

    Self-Signed Certificate ও এর ঝুঁকি

    একটি self-signed certificate কোনো স্বীকৃত CA দিয়ে স্বাক্ষরিত নয় — এটি নিজে নিজেই তৈরি ও স্বাক্ষর করা। Development/testing-এর জন্য এটি স্বাভাবিক, কিন্তু একটি production/public ওয়েবসাইটে self-signed certificate ব্যবহার করলে ব্রাউজার একটি বড় সতর্কতা দেখায়, কারণ ব্রাউজার যাচাই করতে পারে না এই পরিচয়পত্র আসলেই বিশ্বস্ত কি না — এটি man-in-the-middle আক্রমণের একটি সাধারণ লক্ষণও হতে পারে।

    Certificate Pinning (সংক্ষিপ্ত পরিচয়)

    কিছু অ্যাপ্লিকেশন (বিশেষত মোবাইল অ্যাপ) certificate pinning ব্যবহার করে — অর্থাৎ শুধু সাধারণ CA যাচাই-ই নয়, বরং একটি নির্দিষ্ট, প্রত্যাশিত certificate/public key-এর সাথে হুবহু মিলতে হবে। এটি অতিরিক্ত সুরক্ষা দেয় একটি compromised/দুর্বল CA-এর বিরুদ্ধে, কিন্তু certificate পরিবর্তনের সময় সাবধানে ব্যবস্থাপনা করতে হয়, নাহলে অ্যাপ নিজেই ভেঙে যেতে পারে।

    অনুশীলন

    নিজের ব্রাউজারে কোনো HTTPS ওয়েবসাইটের certificate দেখুন (তালা আইকনে ক্লিক করে) এবং Issuer, Subject, এবং Valid From/Until তারিখ খুঁজে বের করুন।

    সারসংক্ষেপ

    SSL/TLS certificate একটি ডোমেইনের পরিচয় প্রমাণ করে, Certificate Authority-এর একটি শৃঙ্খলবদ্ধ (chain of trust) ডিজিটাল স্বাক্ষরের মাধ্যমে। Validation level (DV/OV/EV) যাচাইয়ের গভীরতা নির্দেশ করে, এবং self-signed certificate সাধারণত শুধু development-এর জন্যই উপযুক্ত — production-এ এটি একটি বিশ্বাসযোগ্যতার ফাঁক তৈরি করে।

    Cookies বিস্তারিত

    HTTP স্বভাবে "stateless" হওয়া সত্ত্বেও ওয়েবসাইট কীভাবে আপনাকে মনে রাখে — cookie-এর গঠন, attribute, এবং ব্যবহারিক দিক।

    Cookie কী এবং কেন প্রয়োজন?

    অধ্যায় ৪-এ দেখেছি, HTTP stateless — প্রতিটি request স্বাধীন, সার্ভার আগের request মনে রাখে না। কিন্তু বাস্তবে আমরা চাই ওয়েবসাইট আমাদের লগইন অবস্থা, শপিং কার্ট, বা পছন্দ মনে রাখুক। Cookie হলো একটি ছোট্ট key-value তথ্যের টুকরা, যা সার্ভার ব্রাউজারকে সংরক্ষণ করতে বলে, এবং ব্রাউজার পরবর্তী প্রতিটি request-এ (একই ডোমেইনের জন্য) সেই cookie স্বয়ংক্রিয়ভাবে ফেরত পাঠায় — এভাবেই "statelessness" সমস্যার একটি ব্যবহারিক সমাধান তৈরি হয়।

    Cookie কীভাবে সেট ও পাঠানো হয়

    Server cookie সেট করছে
    HTTP/1.1 200 OK
Set-Cookie: session=abc123; Max-Age=3600; Path=/; HttpOnly; Secure; SameSite=Lax
    পরবর্তী request-এ ব্রাউজার স্বয়ংক্রিয়ভাবে ফেরত পাঠাচ্ছে
    GET /dashboard HTTP/1.1
Host: example.com
Cookie: session=abc123

    লক্ষণীয়, একবার সার্ভার cookie সেট করলে, client-side JavaScript কিছু না করলেও ব্রাউজার নিজে থেকেই প্রতিটি পরবর্তী request-এ এটি যোগ করে — এই "স্বয়ংক্রিয় সংযুক্তি" আচরণটাই CSRF-এর মতো ঝুঁকির ভিত্তি (যা আলাদা CSRF ডকুমেন্টেশনে বিস্তারিত আলোচিত)।

    Cookie Attribute বিস্তারিত

    Attributeউদ্দেশ্য
    Expires / Max-AgeCookie কতক্ষণ বৈধ থাকবে — না দিলে এটি একটি "session cookie" হয়, ব্রাউজার বন্ধ করলে মুছে যায়
    Domainকোন ডোমেইন (ও তার সাবডোমেইন) এই cookie পাবে
    Pathডোমেইনের কোন path-এ cookie পাঠানো হবে (যেমন /admin-এ সীমাবদ্ধ করা যায়)
    SecureCookie শুধু HTTPS সংযোগে পাঠানো হবে, সাধারণ HTTP-তে না — নেটওয়ার্কে আড়িপাতা থেকে রক্ষা করে
    HttpOnlyJavaScript (document.cookie) দিয়ে এই cookie পড়া/পরিবর্তন করা যাবে না — শুধু HTTP request-এর মাধ্যমে পাঠানো হয়। XSS থাকলেও সরাসরি এই cookie চুরি করা কঠিন হয়ে যায়
    SameSiteCookie কোন ধরনের cross-site request-এ পাঠানো হবে তা নিয়ন্ত্রণ করে (নিচে বিস্তারিত)

    SameSite Attribute বিস্তারিত

    Strict

    Cookie শুধুমাত্র সেই সাইটের নিজস্ব navigation/request-এ পাঠানো হয় — অন্য সাইট থেকে লিঙ্কে ক্লিক করে এলেও না। সবচেয়ে কড়া, কিন্তু ইউজার অভিজ্ঞতায় প্রভাব ফেলতে পারে।

    Lax

    Top-level navigation (লিঙ্কে ক্লিক করে আসা)-এ cookie পাঠানো হয়, কিন্তু cross-site POST বা সাব-রিসোর্স (ছবি, iframe) request-এ পাঠানো হয় না। আধুনিক ব্রাউজারের ডিফল্ট।

    সব cross-site request-এও cookie পাঠানো হয় (অবশ্যই Secure-এর সাথে ব্যবহার করতে হয়) — থার্ড-পার্টি embed/widget-এর জন্য ইচ্ছাকৃতভাবে ব্যবহৃত, কিন্তু অতিরিক্ত ঝুঁকি বহন করে।

    ধরনবর্ণনা
    Session Cookieকোনো Expires/Max-Age নেই — ব্রাউজার বন্ধ করলে মুছে যায়
    Persistent Cookieনির্দিষ্ট মেয়াদ আছে — ব্রাউজার বন্ধ করলেও থেকে যায় (যেমন "আমাকে মনে রাখো" ফিচার)
    First-Party Cookieযে ডোমেইন ভিজিট করছেন সেই ডোমেইনই এটি সেট করেছে
    Third-Party Cookieবর্তমান পৃষ্ঠায় embed করা অন্য একটি ডোমেইন (যেমন একটি বিজ্ঞাপন নেটওয়ার্ক) এটি সেট করেছে — আধুনিক ব্রাউজারগুলো ক্রমশ এগুলো ব্লক/সীমাবদ্ধ করছে, গোপনীয়তার উদ্বেগের কারণে

    Cookie-এর আকার ও সংখ্যার সীমাবদ্ধতা

    প্রতিটি cookie সাধারণত সর্বোচ্চ ৪KB পর্যন্ত হতে পারে, এবং প্রতিটি ডোমেইনের জন্য ব্রাউজার একটি সর্বোচ্চ সংখ্যক cookie (সাধারণত প্রায় ৫০) সংরক্ষণ করে। এই সীমাবদ্ধতার কারণেই বড় ডেটার জন্য cookie-এর বদলে server-side session storage বা client-side localStorage ব্যবহার করা হয় (অধ্যায় ৯)।

    💡

    প্রতিটি request-এর সাথে cookie পাঠানো মানে cookie-এর আকার সরাসরি network overhead বাড়ায় — তাই অপ্রয়োজনীয় বড় ডেটা cookie-তে না রেখে, শুধু একটি ছোট session identifier (যেমন একটি random token) cookie-তে রাখা এবং প্রকৃত ডেটা server-side সংরক্ষণ করাই সাধারণ ভালো অভ্যাস।

    অনুশীলন

    DevTools-এ Application/Storage ট্যাবে গিয়ে Cookies সেকশন দেখুন — যেকোনো লগইন-করা ওয়েবসাইটের cookie-গুলোর নাম, মেয়াদ, এবং HttpOnly/Secure/SameSite মান পর্যবেক্ষণ করুন।

    সারসংক্ষেপ

    Cookie HTTP-এর stateless সীমাবদ্ধতা অতিক্রম করে ওয়েবসাইটকে ইউজারের state মনে রাখতে সাহায্য করে। HttpOnly, Secure, এবং SameSite attribute সঠিকভাবে ব্যবহার করলে cookie চুরি/অপব্যবহারের ঝুঁকি উল্লেখযোগ্যভাবে কমে যায় — এগুলো আধুনিক ওয়েব নিরাপত্তার একটি মৌলিক স্তম্ভ।

    Session, Token ও Browser Storage

    Cookie ছাড়াও ইউজারের state মনে রাখার আরও উপায় — session মেকানিজম, authentication token, এবং localStorage/sessionStorage।

    Server-Side Session কীভাবে কাজ করে

    সবচেয়ে প্রচলিত পদ্ধতিতে, ইউজার লগইন করলে সার্ভার একটি random, অননুমানযোগ্য session ID তৈরি করে, সার্ভারের নিজস্ব storage-এ (মেমোরি/database) সেই session-এর সাথে সম্পর্কিত তথ্য (ইউজার ID, লগইন সময় ইত্যাদি) সংরক্ষণ করে, এবং শুধু সেই session ID-টি একটি cookie আকারে ব্রাউজারে পাঠায়। পরবর্তী প্রতিটি request-এ ব্রাউজার সেই session ID ফেরত পাঠায়, সার্ভার সেটি দিয়ে তার নিজস্ব storage থেকে ইউজারের তথ্য খুঁজে বের করে।

    ধারণাগত session flow
    ১. ইউজার লগইন করেন → সার্ভার session তৈরি করেন (সার্ভারে সংরক্ষিত)
২. সার্ভার পাঠান: Set-Cookie: session_id=xyz789
৩. ব্রাউজার প্রতিটি পরবর্তী request-এ পাঠান: Cookie: session_id=xyz789
৪. সার্ভার session_id দিয়ে নিজের storage-এ ইউজারকে শনাক্ত করেন

    এই পদ্ধতির সুবিধা — সার্ভার যেকোনো সময় একটি session বাতিল (invalidate) করতে পারে (যেমন লগআউট/পাসওয়ার্ড পরিবর্তনের সময়)। অসুবিধা — একাধিক সার্ভার (load-balanced) থাকলে, session তথ্য সব সার্ভারে শেয়ার করতে হয় (বা একটি কেন্দ্রীয় session store ব্যবহার করতে হয়)।

    Token-Based Authentication (JWT)

    আধুনিক API/SPA (Single Page Application)-এ প্রায়ই token-based পদ্ধতি ব্যবহৃত হয়, যেখানে সার্ভার সার্ভার-সাইডে কোনো session সংরক্ষণ করে না — বরং একটি স্ব-নির্ভর (self-contained) টোকেন (সাধারণত JWT — JSON Web Token) তৈরি করে, যাতে ইউজারের তথ্য ও একটি ডিজিটাল স্বাক্ষর এনকোড করা থাকে।

    JWT-এর গঠন (সরলীকৃত)
    header.payload.signature

উদাহরণ (ডিকোড করা payload):
{
  "userId": 42,
  "role": "user",
  "exp": 1735689600
}

    ক্লায়েন্ট সাধারণত এই token-টি Authorization: Bearer <token> header দিয়ে প্রতিটি request-এ পাঠায় (cookie-এর বদলে)। সুবিধা — সার্ভার-সাইড state-হীন (stateless), তাই scale করা সহজ। অসুবিধা — token বাতিল করা কঠিন (মেয়াদ শেষ না হওয়া পর্যন্ত এটি বৈধ থাকে, যদি না আলাদা একটি "blacklist" ব্যবস্থা রাখা হয়)।

    সারসংক্ষেপ

    Session মেকানিজম (server-side state) ও token-based authentication (stateless, JWT) — দুটোই ইউজারকে "মনে রাখার" ভিন্ন ভিন্ন পদ্ধতি, প্রতিটির নিজস্ব সুবিধা-অসুবিধা। Cookie, localStorage, sessionStorage — প্রতিটি browser storage-এর নিজস্ব বৈশিষ্ট্য ও সীমাবদ্ধতা আছে, যা সঠিক ব্যবহারের জন্য বোঝা জরুরি।

    Same-Origin Policy ও CORS

    ব্রাউজার কীভাবে ঠিক করে কোন ওয়েবসাইট অন্য কোন ওয়েবসাইটের ডেটা পড়তে পারবে — একটি মৌলিক নিরাপত্তা সীমারেখা।

    Origin কী?

    একটি origin গঠিত হয় তিনটি অংশ দিয়ে — scheme (protocol), host (domain), এবং port। দুটো URL তখনই "একই origin" যখন তিনটি অংশই হুবহু মেলে।

    URL ১URL ২একই Origin?কারণ
    https://example.comhttps://example.com/pageহ্যাঁPath ভিন্ন হলেও origin-এর অংশ না
    https://example.comhttp://example.comনাScheme ভিন্ন (https বনাম http)
    https://example.comhttps://api.example.comনাHost ভিন্ন (সাবডোমেইনও ভিন্ন origin)
    https://example.comhttps://example.com:8080নাPort ভিন্ন

    Same-Origin Policy (SOP) কী?

    Same-Origin Policy হলো ব্রাউজারের একটি মৌলিক নিরাপত্তা নীতি, যা নির্ধারণ করে — একটি origin-এর JavaScript কোড অন্য origin-এর ডেটা (যেমন একটি iframe-এর content, বা একটি fetch response) পড়তে পারবে না, যদি না সেই অন্য origin স্পষ্টভাবে অনুমতি দেয়। এটি ছাড়া, একটি দূষিত ওয়েবসাইট আপনার অন্য ট্যাবে খোলা (যেমন আপনার ব্যাংক অ্যাকাউন্ট) পৃষ্ঠার ডেটা সহজেই চুরি করে ফেলতে পারত।

    💡

    গুরুত্বপূর্ণ একটি ভুল ধারণা: SOP request পাঠানো আটকায় না — এটি শুধু response পড়া আটকায়। একটি cross-origin request এখনো পাঠানো যায় এবং সার্ভারে পৌঁছায়, ব্রাউজার শুধু JavaScript-কে সেই response-এর content পড়তে বাধা দেয় (যদি CORS অনুমতি না থাকে)।

    CORS (Cross-Origin Resource Sharing) কী?

    CORS হলো একটি প্রক্রিয়া, যার মাধ্যমে একটি সার্ভার স্পষ্টভাবে বলতে পারে — "অমুক অন্য origin থেকে আসা JavaScript কোড আমার response পড়ার অনুমতি পাবে"। এটি করা হয় নির্দিষ্ট response header দিয়ে।

    CORS অনুমতি দেওয়ার উদাহরণ
    Response Headers:
Access-Control-Allow-Origin: https://trusted-app.example
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST

    Simple Request বনাম Preflighted Request

    CORS-এ দুই ধরনের cross-origin request আছে:

    Simple Request

    শুধুমাত্র নির্দিষ্ট কিছু শর্ত পূরণ করলে (method GET/POST/HEAD, নির্দিষ্ট কিছু header, সাধারণ Content-Type) — ব্রাউজার সরাসরি request পাঠায়, response আসার পর CORS header যাচাই করে পড়ার অনুমতি দেয় কি না ঠিক করে।

    Preflighted Request

    অন্য যেকোনো ক্ষেত্রে (যেমন PUT method, custom header, বা application/json body) — ব্রাউজার প্রথমে একটি OPTIONS request পাঠিয়ে "অনুমতি আছে কি না" জিজ্ঞাসা করে, তারপরই আসল request পাঠায়।

    Preflight OPTIONS request — উদাহরণ
    OPTIONS /api/data HTTP/1.1
Origin: https://trusted-app.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type

Response:
Access-Control-Allow-Origin: https://trusted-app.example
Access-Control-Allow-Methods: PUT, GET
Access-Control-Allow-Headers: Content-Type

    CORS Misconfiguration-এর ঝুঁকি (সংক্ষিপ্ত)

    যদি একটি সার্ভার Access-Control-Allow-Origin: * (সব origin) এবং Access-Control-Allow-Credentials: true একসাথে ব্যবহার করার চেষ্টা করে — ব্রাউজার আসলে এই সংমিশ্রণ প্রত্যাখ্যান করে (স্পেসিফিকেশন অনুযায়ী এটি অবৈধ)। কিন্তু অনেক সার্ভার request-এর Origin header যা-ই আসুক তা সরাসরি Access-Control-Allow-Origin-এ "reflect" করে দেয় — যা কার্যকরভাবে যেকোনো ওয়েবসাইটকে অনুমতি দেওয়ার সমতুল্য, একটি গুরুতর নিরাপত্তা দুর্বলতা।

    অনুশীলন

    DevTools Console-এ, একটি ভিন্ন origin-এর API-তে fetch() দিয়ে request পাঠানোর চেষ্টা করুন (যেমন কোনো পাবলিক API যা CORS অনুমতি দেয় না) — Console-এ CORS error বার্তা দেখুন এবং এটি কী বলছে বিশ্লেষণ করুন।

    সারসংক্ষেপ

    Same-Origin Policy ব্রাউজারের একটি মৌলিক সীমারেখা, যা cross-origin response পড়া আটকায় (পাঠানো নয়)। CORS হলো সার্ভারের পক্ষ থেকে নির্দিষ্ট header দিয়ে সেই সীমারেখা নিয়ন্ত্রিতভাবে শিথিল করার প্রক্রিয়া। Preflight request জটিল cross-origin call-এর আগে একটি অতিরিক্ত নিরাপত্তা যাচাই যোগ করে।

    Browser DevTools দিয়ে Network বিশ্লেষণ

    এই ডকুমেন্টেশনের সব তাত্ত্বিক ধারণা (DNS, HTTP, HTTPS, cookie) নিজের ব্রাউজারে হাতে-কলমে পর্যবেক্ষণ করার ব্যবহারিক গাইড।

    ℹ️

    ব্যবহারের নোটিশ: নিচের সব অনুশীলন শুধুমাত্র নিজের ব্রাউজার সেশন ও নিজের ভিজিট করা পাবলিক ওয়েবসাইটে করুন — এটি কোনো আক্রমণাত্মক কৌশল নয়, শুধুমাত্র আপনার নিজের ট্রাফিক পর্যবেক্ষণের একটি স্বাভাবিক, বৈধ পদ্ধতি।

    DevTools খোলা ও Network ট্যাব

    প্রায় সব আধুনিক ব্রাউজারে (Chrome, Firefox, Edge) F12 বা Ctrl+Shift+I (Mac-এ Cmd+Option+I) চাপলে Developer Tools খোলে। Network ট্যাবে গেলে, পৃষ্ঠা রিফ্রেশ করলে প্রতিটি request রিয়েল-টাইমে তালিকাভুক্ত হতে দেখা যায়।

    একটি Request বিশ্লেষণ করা

    তালিকায় যেকোনো একটি request-এ ক্লিক করলে বিস্তারিত তথ্য দেখা যায়:

    Headers ট্যাব

    Request ও response headers (যা অধ্যায় ৫-এ আলোচিত হয়েছে) — method, status code, Content-Type, Set-Cookie ইত্যাদি সরাসরি দেখা যায়।

    Payload/Request ট্যাব

    POST/PUT request-এ পাঠানো body/form ডেটা — যা backend-এ কী পাঠানো হচ্ছে তা যাচাই করতে কাজে লাগে।

    Response ট্যাব

    সার্ভার থেকে ফেরত আসা প্রকৃত content (HTML/JSON/ইত্যাদি) — raw আকারে দেখা যায়।

    Timing ট্যাব

    DNS lookup, TCP connection, TLS handshake, এবং প্রকৃত request/response — প্রতিটি ধাপে কত সময় লেগেছে তার একটি breakdown — অধ্যায় ১-এ আলোচিত পুরো প্রক্রিয়াটা সরাসরি চোখে দেখা যায়।

    Application/Storage ট্যাব

    এখানে একটি ওয়েবসাইটের সব cookie, localStorage, sessionStorage entry তালিকা আকারে দেখা যায় — নাম, মান, এবং cookie-এর ক্ষেত্রে Domain, Path, Expires, HttpOnly, Secure, SameSite কলাম-সহ। এখান থেকে ম্যানুয়ালি কোনো cookie/storage entry মুছে ফেলাও সম্ভব — যা session বাতিল করার আচরণ বুঝতে সাহায্য করে।

    Security ট্যাব — Certificate তথ্য

    Chrome DevTools-এর Security ট্যাবে (বা URL বারের তালা আইকনে ক্লিক করে) বর্তমান সংযোগের TLS তথ্য দেখা যায় — কোন TLS ভার্সন ব্যবহৃত হচ্ছে, কোন cipher suite, এবং certificate-এর বিস্তারিত (Issuer, Subject, মেয়াদ) — অধ্যায় ৬–৭-এ আলোচিত তত্ত্বের সরাসরি প্রয়োগ।

    Filtering ও Throttling

    • Filter বার: টাইপ (XHR/Fetch, JS, CSS, Img, Doc) অনুযায়ী request ফিল্টার করা যায়, বড় পৃষ্ঠায় নির্দিষ্ট request খুঁজে বের করতে সহায়ক।
    • Throttling: ধীর নেটওয়ার্ক (3G) সিমুলেট করে দেখা যায় ধীরগতির সংযোগে পৃষ্ঠা কেমন আচরণ করে — performance অপ্টিমাইজেশনের জন্য গুরুত্বপূর্ণ।
    • Preserve log: এই অপশন চালু করলে পেজ নেভিগেট/রিডাইরেক্ট হলেও আগের request-গুলো তালিকা থেকে মুছে যায় না — একটি redirect চেইন পুরোপুরি ট্র্যাক করতে কাজে লাগে।

    DNS ও Connection তথ্য দেখা

    Chrome-এ chrome://net-internals/#dns বা chrome://net-export-এর মতো বিশেষ পৃষ্ঠায় গিয়ে নিম্নস্তরের DNS cache ও নেটওয়ার্ক সংযোগের তথ্য বিস্তারিতভাবে দেখা যায় — যদিও দৈনন্দিন ব্যবহারের জন্য সাধারণ Network ট্যাবই যথেষ্ট।

    অনুশীলন

    DevTools-এর Network ট্যাবে "Preserve log" চালু করে একটি লগইন ফর্ম পূরণ করে সাবমিট করুন (নিজের তৈরি/টেস্ট অ্যাকাউন্টে) — লক্ষ্য করুন লগইন request-এর response-এ কোনো Set-Cookie header আছে কি না, এবং থাকলে তার attribute-গুলো (HttpOnly, Secure, SameSite) পরীক্ষা করুন।

    সারসংক্ষেপ

    Browser DevTools-এর Network ও Application ট্যাব এই পুরো ডকুমেন্টেশনের তত্ত্বকে (HTTP request/response, headers, cookie, TLS) চোখের সামনে বাস্তবে দেখার সবচেয়ে সহজ উপায়। নিয়মিত DevTools ব্যবহার একজন ডেভেলপার/সিকিউরিটি শিক্ষার্থীর জন্য অপরিহার্য দক্ষতা।

    Frequently Asked Questions (FAQ)

    HTTP ও HTTPS-এর মধ্যে পার্থক্য কী, সংক্ষেপে?

    HTTPS হলো HTTP + TLS এনক্রিপশন। HTTP-তে ডেটা plain text-এ পাঠানো হয় (যে কেউ পড়তে পারে), HTTPS-এ এনক্রিপ্টেড থাকে এবং সার্ভারের পরিচয় certificate দিয়ে যাচাই করা যায়।

    DNS প্রতিবার query করতে হয়, নাকি cache হয়?

    Cache হয় — ব্রাউজার, OS, এবং resolver প্রতিটি স্তরে DNS উত্তর নির্দিষ্ট সময়ের (TTL) জন্য cache করে রাখে, যাতে বারবার পুরো resolution প্রক্রিয়া চালাতে না হয়।

    Cookie মুছে দিলে কি লগআউট হয়ে যাব?

    বেশিরভাগ ক্ষেত্রে হ্যাঁ — যদি লগইন state একটি session cookie দিয়ে ট্র্যাক করা হয়, cookie মুছে ফেললে ব্রাউজার আর সেই session ID পাঠাতে পারবে না, ফলে সার্ভার আপনাকে চিনতে পারবে না এবং লগ-আউট অবস্থায় দেখাবে।

    localStorage কি cookie-এর মতোই নিরাপদ?

    না, সম্পূর্ণ ভিন্ন সুরক্ষা বৈশিষ্ট্য। Cookie-তে HttpOnly attribute দিয়ে JavaScript থেকে আড়াল করা যায়, কিন্তু localStorage সবসময় JavaScript দিয়ে সম্পূর্ণভাবে অ্যাক্সেসযোগ্য — তাই sensitive token localStorage-এ রাখলে XSS-এর ঝুঁকি বেশি থাকে।

    CORS error এলে কি সার্ভারে সমস্যা, নাকি ব্রাউজারে?

    এটি আসলে ব্রাউজারের একটি সুরক্ষা ব্যবস্থা, যা সার্ভার সেই origin-কে স্পষ্টভাবে অনুমতি না দেওয়া পর্যন্ত response পড়তে বাধা দেয়। সমাধান করতে হয় সার্ভার-সাইডে, সঠিক Access-Control-Allow-Origin header যোগ করে।

    Private IP address দিয়ে কি সরাসরি ইন্টারনেট থেকে কোনো ডিভাইসে পৌঁছানো যায়?

    না, সরাসরি যায় না — private IP শুধু স্থানীয় নেটওয়ার্কে বৈধ। ইন্টারনেট থেকে পৌঁছাতে হলে NAT/port forwarding বা একটি public IP-যুক্ত সার্ভার প্রয়োজন।

    কোর্স সম্পন্ন — পরবর্তী কী করবেন

    এই ১২টি অধ্যায় সম্পন্ন করার পর, আপনি ইন্টারনেট ও ওয়েবের মৌলিক ভিত্তি — IP addressing, DNS, HTTP/HTTPS, TLS, cookie, session, এবং CORS — সম্পর্কে একটি দৃঢ় ধারণা পেয়েছেন। এই জ্ঞানই XSS, CSRF, SQL Injection-এর মতো ওয়েব সিকিউরিটি বিষয় গভীরভাবে বোঝার আসল ভিত্তি — এখন সেই ডকুমেন্টেশনগুলো আরও সহজে অনুসরণ করতে পারবেন।
