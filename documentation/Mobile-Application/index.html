    Mobile Application Security ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Mobile Application Security গাইড — Android/iOS আর্কিটেকচার থেকে শুরু করে OWASP Mobile Top 10, Reverse Engineering, Static/Dynamic Analysis, Insecure Storage/Communication, Cryptography, ও Mobile Pentesting Methodology পর্যন্ত — ১৫টি অধ্যায়ে সাজানো।

    Mobile Application Security নিয়ে সংক্ষিপ্ত কথা

    এই সিরিজের আগের ডকুমেন্টেশনগুলো (Common Web Vulnerabilities, API Security, Cloud Security) মূলত ওয়েব ও cloud-কেন্দ্রিক আক্রমণ-তল নিয়ে আলোচনা করেছে। স্মার্টফোনে চলা অ্যাপ্লিকেশনের নিরাপত্তা মডেল ভিন্ন — এখানে APK/IPA ফাইল, লোকাল ডেটা স্টোরেজ, platform permission, এবং reverse engineering-এর মতো নতুন আক্রমণ-তল যুক্ত হয়।

    এখানে ধাপে ধাপে দেখানো হয়েছে — Android/iOS অ্যাপ্লিকেশন আর্কিটেকচার ও sandboxing, OWASP Mobile Top 10, Insecure Data Storage, Insecure Communication, Authentication/Authorization দুর্বলতা, Reverse Engineering (APK/IPA বিশ্লেষণ), Static Analysis টুল (MobSF, jadx, apktool), Dynamic Analysis ও Frida, Code Tampering/Binary Protection, Insecure Cryptography, Platform-specific misuse (permission, intent, WebView), Third-party SDK ঝুঁকি, Mobile API Security, এবং একটি সম্পূর্ণ Mobile Pentesting Methodology।

    ⚖️

    আইনি নোটিশ: এই ডকুমেন্টেশনে উল্লেখিত সব রিভার্স ইঞ্জিনিয়ারিং, স্ট্যাটিক/ডায়নামিক অ্যানালাইসিস কৌশল শুধুমাত্র নিজের তৈরি/মালিকানাধীন অ্যাপ্লিকেশন, অনুমোদিত training platform (OWASP MASTG Crackmes, InsecureBankv2 ইত্যাদি), অথবা স্পষ্টভাবে scope-ভুক্ত bug bounty প্রোগ্রামে প্রয়োগ করুন। অনুমতি ছাড়া কোনো অ্যাপ্লিকেশন বা সার্ভারে প্রয়োগ করলে তা আইনত দণ্ডনীয় অপরাধ।

    Mobile Application Security-র ভিত্তি

    মোবাইল অ্যাপ্লিকেশনের নিরাপত্তা মডেল ওয়েব অ্যাপ্লিকেশনের থেকে কীভাবে আলাদা — Android ও iOS-এর স্থাপত্য পরিচিতি।

    ⚖️

    আইনি নোটিশ: এই ডকুমেন্টেশনে উল্লেখিত কৌশল শুধুমাত্র নিজের তৈরি/মালিকানাধীন অ্যাপ্লিকেশন বা অনুমোদিত training platform-এ প্রয়োগ করুন। অনুমতি ছাড়া কোনো অ্যাপ্লিকেশনে প্রয়োগ আইনত দণ্ডনীয় অপরাধ।

    কেন মোবাইল অ্যাপ্লিকেশন নিরাপত্তা আলাদা

    একটি ওয়েব অ্যাপ্লিকেশন সার্ভারে চলে এবং ব্রাউজার শুধু render করে — কিন্তু একটি মোবাইল অ্যাপ্লিকেশনের একটি উল্লেখযোগ্য অংশ (বিশেষত কোড ও লজিক) সরাসরি ইউজারের ডিভাইসে, attacker-এর নিজের হাতে থাকা একটি ডিভাইসে, ইনস্টল হয়ে থাকে। এর অর্থ attacker অ্যাপ্লিকেশনের বাইনারি ফাইল সরাসরি হাতে পান, যা reverse engineering (অধ্যায় ৬)-এর মাধ্যমে বিশ্লেষণ করা সম্ভব — একটি ঝুঁকি যা সাধারণত ওয়েব অ্যাপ্লিকেশনে থাকে না।

    Application Sandboxing

    উভয় প্ল্যাটফর্মই প্রতিটি অ্যাপ্লিকেশনকে একটি পৃথক, বিচ্ছিন্ন sandbox-এ চালায় — একটি অ্যাপ্লিকেশন সাধারণত অন্য অ্যাপ্লিকেশনের ডেটা সরাসরি পড়তে পারে না, যদি না স্পষ্টভাবে কোনো সিস্টেম-লেভেল permission বা শেয়ারিং mechanism ব্যবহার করা হয়। এই sandboxing মডেল একটি গুরুত্বপূর্ণ নিরাপত্তা স্তর, কিন্তু এটি নিখুঁত নয় — Insecure Data Storage (অধ্যায় ৩)-এর মতো ভুল এই সুরক্ষাকে অকার্যকর করে দিতে পারে।

    Permission Model

    মোবাইল অ্যাপ্লিকেশনগুলো নির্দিষ্ট ডিভাইস রিসোর্স (ক্যামেরা, লোকেশন, কন্টাক্ট) অ্যাক্সেস করতে একটি স্পষ্ট Permission ব্যবস্থার মধ্য দিয়ে যায় — ইউজারকে সরাসরি অনুমতি দিতে হয়। অতিরিক্ত বা অপ্রয়োজনীয় permission চাওয়া একটি সাধারণ নিরাপত্তা/প্রাইভেসি সমস্যা (অধ্যায় ১১-এ বিস্তারিত)।

    OWASP Mobile Security Project

    💡

    এই ডকুমেন্টেশনের কাঠামো মূলত OWASP Mobile Application Security প্রকল্পের (MASVS/MASTG) ধারণার উপর ভিত্তি করে তৈরি — একটি শিল্প-স্বীকৃত, ওপেন-সোর্স কাঠামো, যা পরবর্তী অধ্যায়ে (OWASP Mobile Top 10) বিস্তারিত আলোচিত হয়েছে।

    ওয়েব ও মোবাইলের মধ্যে সংযোগ

    অধিকাংশ আধুনিক মোবাইল অ্যাপ্লিকেশন একটি ব্যাকএন্ড REST/GraphQL API-এর সাথে যোগাযোগ করে — অর্থাৎ API Security ডকুমেন্টেশনে আলোচিত সব ঝুঁকি (Broken Object Level Authorization, Rate Limiting ইত্যাদি) এখানেও প্রাসঙ্গিক, ক্লায়েন্ট-সাইড ঝুঁকির পাশাপাশি (অধ্যায় ১৩-এ বিস্তারিত)।

    অনুশীলন

    কেন একটি মোবাইল অ্যাপ্লিকেশনের ক্লায়েন্ট-সাইড কোড একটি ওয়েব অ্যাপ্লিকেশনের চেয়ে বেশি ঝুঁকিপূর্ণ হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    মোবাইল অ্যাপ্লিকেশনের একটি উল্লেখযোগ্য অংশ ইউজারের ডিভাইসে, attacker-এর নাগালের মধ্যে থাকে, যা reverse engineering-এর ঝুঁকি তৈরি করে। Android ও iOS উভয়ই sandboxing ও permission মডেল ব্যবহার করে, কিন্তু ভুল কনফিগারেশন এই সুরক্ষাকে অকার্যকর করতে পারে।

    OWASP Mobile Top 10 — ভূমিকা

    Common Web Vulnerabilities ডকুমেন্টেশনের OWASP Top 10-এর মোবাইল সংস্করণ — এই ডকুমেন্টেশনের কাঠামোর ভিত্তি।

    OWASP Mobile Top 10 কী

    Common Web Vulnerabilities ডকুমেন্টেশনে আলোচিত ওয়েব OWASP Top 10-এর মতো, OWASP Mobile Top 10 মোবাইল অ্যাপ্লিকেশনে সবচেয়ে সাধারণ ও গুরুত্বপূর্ণ ১০টি নিরাপত্তা ঝুঁকির একটি তালিকা — এটি পেন্টেস্টার, ডেভেলপার, ও নিরাপত্তা দলের জন্য একটি সাধারণ রেফারেন্স ফ্রেমওয়ার্ক।

    ওয়েব OWASP Top 10-এর সাথে পার্থক্য

    💡

    লক্ষণীয় — Mobile Top 10-এ Insecure Data Storage ও Insufficient Binary Protections-এর মতো আইটেম আছে, যা ওয়েব OWASP Top 10-এ সরাসরি নেই। এর কারণ মোবাইল অ্যাপ্লিকেশনের ক্লায়েন্ট-সাইড প্রকৃতি (অধ্যায় ১) — ডিভাইসে সংরক্ষিত ডেটা ও বাইনারি নিজেই একটি আক্রমণ-তল।

    এই তালিকা কীভাবে ব্যবহার করবেন

    একটি পেন্টেস্টের সময়, এই তালিকা একটি চেকলিস্ট হিসেবে কাজ করে — প্রতিটি আইটেম ধাপে ধাপে যাচাই করে একটি পদ্ধতিগত কভারেজ নিশ্চিত করা যায়, যদিও বাস্তব টেস্টিং প্রায়ই এই ক্রম অনুসরণ করে না (অধ্যায় ১৪-এ একটি সম্পূর্ণ methodology আলোচিত)।

    অনুশীলন

    কেন Insecure Data Storage ও Insufficient Binary Protections ওয়েব OWASP Top 10-এ সরাসরি প্রাসঙ্গিক নয়, কিন্তু মোবাইলে গুরুত্বপূর্ণ তা ব্যাখ্যা করুন।

    একটি মোবাইল ডিভাইস হারিয়ে যেতে পারে, চুরি হতে পারে, বা malware-এ আক্রান্ত হতে পারে — এই পরিস্থিতিতে, যদি একটি অ্যাপ্লিকেশন সংবেদনশীল ডেটা (পাসওয়ার্ড, টোকেন, ব্যক্তিগত তথ্য) প্লেইনটেক্সটে, সহজে অ্যাক্সেসযোগ্য লোকেশনে সংরক্ষণ করে, সেই ডেটা সরাসরি উন্মুক্ত হয়ে যায় — এমনকি কোনো নেটওয়ার্ক আক্রমণ ছাড়াই।

    সাধারণ Insecure Storage লোকেশন

    লোকেশনসমস্যা
    SharedPreferences (Android) / UserDefaults (iOS)ডিফল্টভাবে এনক্রিপ্টেড নয় — sensitive ডেটা এখানে রাখা বিপজ্জনক
    SQLite ডেটাবেজপ্লেইনটেক্সটে থাকলে, একটি rooted/jailbroken ডিভাইসে সরাসরি পড়া যায়
    লগ ফাইলডিবাগিং-এর জন্য রাখা লগে ভুলবশত টোকেন বা পাসওয়ার্ড প্রিন্ট হওয়া
    Clipboardকপি করা সংবেদনশীল ডেটা অন্য অ্যাপ্লিকেশন পড়তে পারে
    Backup (cloud/local)ডিভাইস ব্যাকআপের মধ্যে সংবেদনশীল ডেটা অন্তর্ভুক্ত হয়ে যাওয়া

    সঠিক সমাধান

    ✅ Platform-Provided Secure Storage

    Android Keystore / iOS Keychain ব্যবহার করুন — এগুলো hardware-backed encryption সরবরাহ করে, যা SharedPreferences/UserDefaults-এর চেয়ে উল্লেখযোগ্যভাবে বেশি সুরক্ষিত।

    ✅ ন্যূনতম স্টোরেজ নীতি

    যা স্টোর করা একদমই প্রয়োজন নেই, তা স্টোর করবেন না — একটি access token দীর্ঘ সময় স্টোর না করে, প্রয়োজন অনুযায়ী refresh করুন।

    রুট/জেলব্রেক ডিটেকশনের ভূমিকা

    একটি rooted (Android) বা jailbroken (iOS) ডিভাইসে, অ্যাপ্লিকেশনের sandbox সুরক্ষা অনেকাংশে দুর্বল হয়ে যায় — attacker অনেক সহজে ফাইল সিস্টেম অ্যাক্সেস করতে পারেন। অনেক সংবেদনশীল অ্যাপ্লিকেশন (ব্যাংকিং, পেমেন্ট) root/jailbreak detection বাস্তবায়ন করে, যদিও এটি একটি নিখুঁত সমাধান নয় (অধ্যায় ৯-এ বিস্তারিত) — এটি defense-in-depth-এর একটি স্তর।

    অনুশীলন

    কেন SharedPreferences/UserDefaults-এ একটি auth token রাখা Android Keystore/iOS Keychain-এ রাখার চেয়ে কম নিরাপদ তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Insecure Data Storage ঘটে যখন সংবেদনশীল ডেটা ডিভাইসে এনক্রিপশন ছাড়া সংরক্ষণ করা হয় — SharedPreferences/UserDefaults, লগ ফাইল, এবং backup সাধারণ ঝুঁকিপূর্ণ লোকেশন। সমাধান হলো platform-provided secure storage (Keystore/Keychain) ব্যবহার এবং ন্যূনতম স্টোরেজ নীতি অনুসরণ করা।

    Insecure Communication

    Network Security ডকুমেন্টেশনের TLS নীতি মোবাইল প্রেক্ষাপটে — এবং একটি মোবাইল-নির্দিষ্ট প্রতিরক্ষা, Certificate Pinning।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র নিজের lab বা অনুমোদিত পরিবেশে নেটওয়ার্ক ট্রাফিক বিশ্লেষণ করুন।

    মূল সমস্যা — এনক্রিপশন ছাড়া বা দুর্বল যাচাই

    একটি মোবাইল অ্যাপ্লিকেশন প্রায়ই পাবলিক Wi-Fi-এর মতো অবিশ্বস্ত নেটওয়ার্কে ব্যবহার হয় — যদি অ্যাপ্লিকেশন সার্ভারের সাথে HTTP (এনক্রিপশন ছাড়া) বা সঠিকভাবে সার্টিফিকেট যাচাই না করে যোগাযোগ করে, একজন attacker একই নেটওয়ার্কে থেকে Man-in-the-Middle (MITM) আক্রমণের মাধ্যমে ট্রাফিক পড়তে বা পরিবর্তন করতে পারেন — Network Security ডকুমেন্টেশনের TLS/SSL অধ্যায়ে এই ধারণা বিস্তারিত আলোচিত।

    সাধারণ ভুল

    ভুলপরিণতি
    HTTP ব্যবহার (HTTPS না)সম্পূর্ণ ট্রাফিক প্লেইনটেক্সটে, যেকেউ পড়তে পারে
    সার্টিফিকেট যাচাই নিষ্ক্রিয় করাঅ্যাপ্লিকেশন যেকোনো (এমনকি স্ব-স্বাক্ষরিত/আপোসকৃত) সার্টিফিকেট গ্রহণ করে
    দুর্বল TLS ভার্সনপুরনো, দুর্বল ক্রিপ্টোগ্রাফিক প্রোটোকল ব্যবহার

    Certificate Pinning — একটি মোবাইল-নির্দিষ্ট প্রতিরক্ষা

    সাধারণ TLS যাচাই নিশ্চিত করে সার্টিফিকেট একটি বিশ্বস্ত Certificate Authority (CA) দ্বারা স্বাক্ষরিত — কিন্তু যদি কোনোভাবে একটি দূষিত CA বা আপোসকৃত সার্টিফিকেট অ্যাপ্লিকেশনে "বিশ্বস্ত" হিসেবে ইনস্টল হয়, MITM সম্ভব হয়ে যায়। Certificate Pinning একটি অতিরিক্ত স্তর — অ্যাপ্লিকেশন নির্দিষ্ট একটি (বা কয়েকটি) সার্টিফিকেট/public key-কেই একমাত্র বিশ্বস্ত হিসেবে "pin" করে রাখে, যেকোনো অন্য CA-স্বাক্ষরিত সার্টিফিকেট প্রত্যাখ্যান করে।

    ধারণাগত Certificate Pinning (Android, OkHttp-স্টাইল)
    CertificatePinner pinner = new CertificatePinner.Builder()
    .add("api.example.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build();
// শুধুমাত্র এই নির্দিষ্ট public key-র সাথে মেলা সার্টিফিকেট গ্রহণযোগ্য
    ⚠️

    বাস্তব ঝুঁকি: একজন পেন্টেস্টার/attacker প্রায়ই Burp Suite-এর মতো একটি proxy টুল দিয়ে মোবাইল ট্রাফিক ইন্টারসেপ্ট করার চেষ্টা করেন। যদি Certificate Pinning সঠিকভাবে বাস্তবায়িত না থাকে, এই proxy সহজেই ট্রাফিক পড়তে/পরিবর্তন করতে পারে — এমনকি HTTPS থাকা সত্ত্বেও।

    Pinning Bypass — একটি গুরুত্বপূর্ণ সীমাবদ্ধতা

    Certificate Pinning একটি শক্তিশালী প্রতিরক্ষা, কিন্তু এটি নিখুঁত নয় — একটি rooted/jailbroken ডিভাইসে, Frida-র মতো একটি dynamic instrumentation টুল (অধ্যায় ৮-এ বিস্তারিত) ব্যবহার করে runtime-এ pinning চেক বাইপাস করা সম্ভব। তাই Certificate Pinning একা যথেষ্ট নয় — এটি defense-in-depth-এর একটি স্তর, root detection-এর (অধ্যায় ৩) সাথে একত্রে ব্যবহার করা উচিত।

    অনুশীলন

    Certificate Pinning সাধারণ TLS যাচাইয়ের তুলনায় কী অতিরিক্ত সুরক্ষা দেয়, এবং কেন এটি একা যথেষ্ট নয় তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Insecure Communication ঘটে যখন একটি অ্যাপ্লিকেশন HTTP ব্যবহার করে বা সার্টিফিকেট সঠিকভাবে যাচাই করে না, যা MITM আক্রমণের সুযোগ তৈরি করে। Certificate Pinning একটি অতিরিক্ত স্তর যোগ করে, কিন্তু runtime bypass-এর কারণে এটি একা সম্পূর্ণ সুরক্ষা নয়।

    Insecure Authentication ও Authorization

    Authentication ডকুমেন্টেশনের মূল নীতি মোবাইল অ্যাপ্লিকেশনে কীভাবে ভিন্নভাবে ভুল হতে পারে।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র নিজের টেস্ট অ্যাকাউন্টে এই ধারণাগুলো যাচাই করুন।

    ক্লায়েন্ট-সাইড Authentication Logic-এর ঝুঁকি

    একটি সাধারণ ভুল হলো — একটি মোবাইল অ্যাপ্লিকেশনে কিছু authentication/authorization লজিক (যেমন "এই ইউজার প্রিমিয়াম কিনা") ক্লায়েন্ট-সাইডে (অ্যাপ্লিকেশনের কোডে) যাচাই করা, সার্ভার-সাইডে নয়। যেহেতু attacker-এর বাইনারিতে সম্পূর্ণ অ্যাক্সেস থাকে (অধ্যায় ১), এই ধরনের ক্লায়েন্ট-সাইড চেক সহজেই বাইপাস করা যায়।

    Local Authentication বনাম Server Authentication

    ধরনউদাহরণঝুঁকি
    Local (Biometric/PIN)ফিঙ্গারপ্রিন্ট/ফেস আনলক দিয়ে অ্যাপ খোলাশুধুমাত্র ডিভাইস-লেভেল সুরক্ষা — সার্ভার-সাইড auth-এর বিকল্প নয়
    Server Authenticationপ্রতিটি API request-এ সার্ভার টোকেন/session যাচাই করেপ্রকৃত নিরাপত্তা নিয়ন্ত্রণ এখানেই থাকা উচিত
    ⚠️

    সাধারণ বিভ্রান্তি: Biometric authentication (ফিঙ্গারপ্রিন্ট) শুধু নিশ্চিত করে "এই ডিভাইসটি যে ব্যবহার করছে সে-ই এই ডিভাইসের মালিক" — এটি সার্ভারকে কিছু বলে না। যদি একটি অ্যাপ্লিকেশন ভুলভাবে ধরে নেয় যে local biometric check-ই যথেষ্ট প্রমাণ, এবং সার্ভার-সাইড token যাচাই দুর্বল থাকে, তাহলে একটি গুরুতর ফাঁক তৈরি হয়।

    Session/Token ব্যবস্থাপনা

    মোবাইল অ্যাপ্লিকেশনে সাধারণত দীর্ঘস্থায়ী session থাকে (ইউজার বারবার লগইন করতে চান না) — এর জন্য প্রায়ই একটি refresh token মেকানিজম ব্যবহৃত হয় (Authentication ডকুমেন্টেশনে বিস্তারিত)। এই refresh token যদি Insecure Storage (অধ্যায় ৩)-এর শিকার হয়, attacker দীর্ঘমেয়াদী অ্যাক্সেস পেয়ে যেতে পারেন।

    Biometric Bypass-এর একটি বাস্তব প্যাটার্ন

    ধারণাগত দুর্বল implementation
    // দুর্বল: শুধু একটি লোকাল বুলিয়ান ফ্ল্যাগ সেট করে, সার্ভারকে জানায় না
if (biometricAuthSuccess) {
    isLoggedIn = true;  // শুধু ক্লায়েন্ট-সাইড state
}

    Multi-Factor Authentication (MFA)

    Authentication ডকুমেন্টেশনে আলোচিত MFA মোবাইলেও সমানভাবে প্রযোজ্য — বিশেষত সংবেদনশীল অ্যাপ্লিকেশনে (ব্যাংকিং, পেমেন্ট), একটি দ্বিতীয় প্রমাণীকরণ স্তর একক credential আপোসের impact উল্লেখযোগ্যভাবে কমায়।

    অনুশীলন

    কেন "biometric authentication সফল হলেই ইউজার authenticated" ধরে নেওয়া একটি নিরাপত্তা দুর্বলতা হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Authentication/Authorization লজিক ক্লায়েন্ট-সাইডে বাস্তবায়ন করলে তা সহজে বাইপাসযোগ্য হয়ে যায় — সার্ভার-সাইড যাচাই সবসময় চূড়ান্ত নিয়ন্ত্রণ হওয়া উচিত। Biometric authentication একটি ডিভাইস-লেভেল সুবিধা, সার্ভার-সাইড token-ভিত্তিক auth-এর বিকল্প নয়।

    Reverse Engineering — APK/IPA বিশ্লেষণ

    কীভাবে একটি মোবাইল অ্যাপ্লিকেশন ফাইল থেকে এর ভেতরের কোড ও লজিক পুনরুদ্ধার করা যায়।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র নিজের তৈরি বা স্পষ্টভাবে অনুমোদিত অ্যাপ্লিকেশনে Reverse Engineering প্রয়োগ করুন। অনুমতি ছাড়া কোনো কমার্শিয়াল অ্যাপ্লিকেশন decompile করা আইনত ও মালিকানা-সংক্রান্ত সমস্যা তৈরি করতে পারে।

    Reverse Engineering কী এবং কেন

    একটি পেন্টেস্টার বা security researcher প্রায়ই একটি অ্যাপ্লিকেশনের সোর্স কোড ছাড়াই কাজ করেন — শুধুমাত্র APK/IPA ফাইলটি হাতে থাকে। Reverse Engineering হলো সেই compiled/packaged ফাইল থেকে, যতটা সম্ভব, মূল লজিক পুনর্গঠন করার প্রক্রিয়া — hardcoded secret, API endpoint, business logic, বা দুর্বলতা শনাক্ত করার জন্য।

    APK গঠন (Android)

    অংশবিষয়বস্তু
    AndroidManifest.xmlPermission, Activity, Service ঘোষণা
    classes.dexকম্পাইল করা Java/Kotlin bytecode
    res/লেআউট, স্ট্রিং, রিসোর্স ফাইল
    lib/Native (C/C++) লাইব্রেরি, যদি থাকে

    প্রাথমিক Reverse Engineering ওয়ার্কফ্লো

    ধারণাগত Android APK বিশ্লেষণ ধাপ
    ১. apktool দিয়ে APK আনপ্যাক করা → resources ও manifest পড়া
২. jadx দিয়ে classes.dex-কে readable Java-সদৃশ কোডে decompile করা
৩. hardcoded API key, endpoint URL, বা debug flag খুঁজে বের করা
৪. AndroidManifest.xml-এ অতিরিক্ত exported component আছে কিনা পরীক্ষা করা

    iOS IPA-তে পার্থক্য

    iOS অ্যাপ্লিকেশন সাধারণত native compiled কোড (Swift/Objective-C ARM বাইনারি) আকারে প্যাকেজ হয়, যা Android-এর Java bytecode-এর চেয়ে decompile করা উল্লেখযোগ্যভাবে কঠিন — তবে class/method নাম, string, ও symbol টেবিল প্রায়ই বাইনারিতে অবশিষ্ট থাকে, যা class-dump বা Hopper-এর মতো টুল দিয়ে বিশ্লেষণযোগ্য।

    Reverse Engineering দিয়ে কী পাওয়া যায়

    • Hardcoded Secret — API key, এনক্রিপশন key, বা ব্যাকডোর credential সরাসরি কোডে পাওয়া
    • লুকানো API Endpoint — UI-তে উন্মুক্ত নয় এমন ফিচার/এন্ডপয়েন্ট আবিষ্কার
    • Business Logic — মূল্য গণনা, লাইসেন্সিং চেক, বা অন্য লজিক, যা বাইপাসযোগ্য হতে পারে
    🚨

    বাস্তব ঝুঁকি: ডেভেলপাররা মাঝে মাঝে ভুলবশত একটি API key বা এনক্রিপশন key সরাসরি কোডে hardcode করেন, ধরে নিয়ে যে "কম্পাইল করা কোড পড়া কঠিন"। কিন্তু অধ্যায় ৭ ও এই অধ্যায়ের decompile কৌশল ব্যবহার করে, এই ধরনের secret প্রায়ই মিনিটের মধ্যে খুঁজে বের করা সম্ভব।

    অনুশীলন

    কেন Android APK-তে hardcoded secret লুকিয়ে রাখা, iOS IPA-এর চেয়ে সাধারণত সহজে আবিষ্কারযোগ্য তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Reverse Engineering একটি APK/IPA ফাইল থেকে মূল কোড/লজিক পুনর্গঠনের প্রক্রিয়া — apktool/jadx-এর মতো টুল ব্যবহার করে hardcoded secret, API endpoint, ও business logic আবিষ্কার করা যায়। Android-এর bytecode iOS-এর native বাইনারির চেয়ে সাধারণত সহজে decompile হয়।

    Static বনাম Dynamic Analysis

    ধরনসংজ্ঞা

    দুটো পদ্ধতিই পরিপূরক — Static Analysis দ্রুত, broad coverage দেয়, কিন্তু কিছু দুর্বলতা শুধু runtime-এ প্রকাশ পায়, যেখানে Dynamic Analysis প্রয়োজন।

    MobSF — একটি সর্বাঙ্গীণ টুল

    MobSF (Mobile Security Framework) একটি জনপ্রিয়, ওপেন-সোর্স টুল যা একটি APK/IPA আপলোড করে স্বয়ংক্রিয়ভাবে static analysis চালায় — permission, hardcoded secret, insecure code pattern, এবং OWASP Mobile Top 10-এর (অধ্যায় ২) সাথে সম্পর্কিত অনেক সমস্যা একটি রিপোর্ট আকারে দেখায়।

    ⚠️

    একটি সাধারণ ভুল: স্বয়ংক্রিয় টুল প্রায়ই false positive রিপোর্ট করে (যেমন একটি নিরীহ স্ট্রিং-কে "hardcoded secret" হিসেবে ফ্ল্যাগ করা)। একটি দায়িত্বশীল বিশ্লেষণে, প্রতিটি স্বয়ংক্রিয় ফাইন্ডিং ম্যানুয়ালি যাচাই করা প্রয়োজন, যেমন Bug Bounty Methodology ডকুমেন্টেশনের automation-vs-manual-verification নীতি।

    Dynamic Analysis ও Frida

    অ্যাপ্লিকেশন বাস্তবে চালিয়ে, runtime-এ এর আচরণ পর্যবেক্ষণ ও এমনকি পরিবর্তন করার কৌশল।

    ⚖️

    আইনি নোটিশ: Dynamic Instrumentation শুধুমাত্র নিজের বা অনুমোদিত অ্যাপ্লিকেশনে, নিজের ডিভাইসে প্রয়োগ করুন।

    Dynamic Analysis কী

    Static Analysis (অধ্যায় ৭) কোড পড়ে দুর্বলতা অনুমান করে — কিন্তু কিছু আচরণ (encryption/decryption-এর সময় key-র মান, রানটাইমে তৈরি হওয়া নেটওয়ার্ক request, pinning চেকের প্রকৃত ফলাফল) শুধুমাত্র অ্যাপ্লিকেশন সত্যিকারভাবে চালিয়ে দেখা যায় — এটাই Dynamic Analysis।

    Frida — একটি Dynamic Instrumentation Toolkit

    Frida একটি শক্তিশালী ওপেন-সোর্স টুল, যা একটি চলমান অ্যাপ্লিকেশনের প্রক্রিয়ার মধ্যে JavaScript কোড "ইনজেক্ট" করতে দেয় — এর মাধ্যমে যেকোনো ফাংশন কল পর্যবেক্ষণ করা, তার রিটার্ন ভ্যালু পরিবর্তন করা, বা এমনকি সম্পূর্ণ লজিক বাইপাস করা সম্ভব হয়।

    Emulator বনাম বাস্তব ডিভাইস

    অনেক অ্যাপ্লিকেশন emulator ডিটেকশন বাস্তবায়ন করে (অর্থাৎ emulator-এ চললে অ্যাপ্লিকেশন কাজ করতে অস্বীকার করে) — একটি সম্পূর্ণ dynamic analysis প্রায়ই একটি বাস্তব, rooted/jailbroken টেস্ট ডিভাইসে করা উচিত, শুধু emulator-এ নয়।

    Dynamic Analysis-এর সীমাবদ্ধতা

    Dynamic Analysis একটি নির্দিষ্ট রান-টাইম পাথ (যে কোড পথ ইউজার/টেস্টার প্রকৃতপক্ষে ট্রিগার করেছেন) দেখাতে পারে — কিন্তু কোডের এমন অংশ, যা পরীক্ষার সময় কখনো এক্সিকিউট হয়নি, তা অদেখা থেকে যেতে পারে। তাই Static ও Dynamic Analysis একসাথে ব্যবহার করে সর্বোচ্চ কভারেজ নিশ্চিত করা হয়।

    অনুশীলন

    কেন Frida-র মতো একটি dynamic instrumentation টুল root detection bypass করতে সক্ষম, যেখানে শুধু কোড পড়ে (static) সেই bypass সম্ভব নাও হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Dynamic Analysis একটি অ্যাপ্লিকেশন বাস্তবে চালিয়ে runtime আচরণ পর্যবেক্ষণ/পরিবর্তন করে — Frida একটি শক্তিশালী instrumentation টুল, যা root detection ও SSL pinning বাইপাসের মতো কাজে ব্যবহৃত হয়। Static ও Dynamic Analysis পরিপূরক, একা কোনোটিই সম্পূর্ণ কভারেজ দেয় না।

    Code Tampering ও Binary Protection

    attacker একটি অ্যাপ্লিকেশন বাইনারিকে পরিবর্তন করে কীভাবে পুনঃবিতরণ করতে পারেন — এবং এর বিরুদ্ধে কী প্রতিরক্ষা আছে।

    ⚖️

    আইনি নোটিশ: Code Tampering কৌশল শুধুমাত্র নিজের বা অনুমোদিত অ্যাপ্লিকেশনে, শিক্ষামূলক উদ্দেশ্যে ব্যবহার করুন।

    Code Tampering কী

    Code Tampering হলো একটি অ্যাপ্লিকেশন বাইনারিকে (অধ্যায় ৬-এর reverse engineering কৌশল ব্যবহার করে) পরিবর্তন করা — যেমন একটি paid feature আনলক করা, একটি লাইসেন্সিং চেক বাদ দেওয়া, বা দূষিত কোড যুক্ত করে পুনরায় প্যাকেজ করা (repackaging) এবং তৃতীয়-পক্ষ স্টোর থেকে বিতরণ করা, যা ইউজারদের জন্য গুরুতর ঝুঁকি তৈরি করে।

    সাধারণ Tampering দৃশ্যকল্প

    দৃশ্যকল্পবিবরণ
    Repackagingএকটি জনপ্রিয় অ্যাপ্লিকেশনে দূষিত কোড যুক্ত করে, একই নামে/আইকনে তৃতীয়-পক্ষ স্টোরে প্রকাশ করা
    License Bypassএকটি paid অ্যাপ্লিকেশনের লাইসেন্স যাচাই কোড সরিয়ে ফ্রি-তে বিতরণ করা
    Logic Modificationএকটি গেম বা ইউটিলিটি অ্যাপ্লিকেশনের নিয়ম/সীমা বাইপাস করা (যেমন "cheat")

    প্রতিরক্ষা — Binary Protection কৌশল

    🔒 Code Obfuscation

    কোডের নাম/গঠন এমনভাবে পরিবর্তন করা যাতে decompile করা কোড পড়া ও বোঝা কঠিন হয় (ProGuard/R8-এর মতো টুল) — এটি reverse engineering-কে সম্পূর্ণ বন্ধ করে না, কিন্তু উল্লেখযোগ্যভাবে কঠিন করে তোলে।

    🔒 Integrity Check

    অ্যাপ্লিকেশন নিজে runtime-এ যাচাই করে যে তার নিজের কোড/সিগনেচার পরিবর্তিত হয়নি — যদি tampering শনাক্ত হয়, অ্যাপ্লিকেশন চালানো বন্ধ করে দেয়।

    ধারণাগত Integrity Check উদাহরণ
    // অ্যাপ্লিকেশন নিজের APK signature runtime-এ যাচাই করে
if (!verifyAppSignature(expectedSignatureHash)) {
    // signature মেলেনি — অ্যাপ্লিকেশন tampered হয়েছে
    exitApp("Application integrity check failed");
}

    একটি গুরুত্বপূর্ণ সীমাবদ্ধতা

    ⚠️

    Obfuscation/Integrity Check নিখুঁত নয়: যেহেতু সব যাচাই লজিক শেষ পর্যন্ত ক্লায়েন্ট-সাইডে, attacker-এর ডিভাইসে চলে (অধ্যায় ১), একজন দক্ষ attacker (অধ্যায় ৮-এর Frida-র মতো টুল ব্যবহার করে) এই যাচাই লজিককেও বাইপাস করতে সক্ষম হতে পারেন। এই কৌশলগুলো আক্রমণকারীর কাজ কঠিন করে তোলে, কিন্তু "অসম্ভব" করে না — Common Web Vulnerabilities ডকুমেন্টেশনের "security through obscurity একা যথেষ্ট নয়" নীতির একটি প্রয়োগ।

    অনুশীলন

    কেন Code Obfuscation ও Integrity Check একজন দক্ষ attacker-কে সম্পূর্ণভাবে থামাতে পারে না, তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Code Tampering হলো একটি অ্যাপ্লিকেশন বাইনারিকে পরিবর্তন করে পুনর্বিতরণ করা — repackaging ও license bypass সাধারণ উদাহরণ। Code Obfuscation ও Integrity Check এই ঝুঁকি কমায়, কিন্তু ক্লায়েন্ট-সাইড প্রকৃতির কারণে এগুলো নিখুঁত প্রতিরক্ষা নয়।

    2. Code Obfuscation কী করে, এবং কী করে না?
    3. কেন ক্লায়েন্ট-সাইড Integrity Check একা সম্পূর্ণ সুরক্ষা নয়?

    Insecure Cryptography

    মোবাইল অ্যাপ্লিকেশনে এনক্রিপশন বাস্তবায়নের সময় সাধারণ ভুল।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র নিজের অ্যাপ্লিকেশনে এই cryptography-সংক্রান্ত ধারণা যাচাই করুন।

    সাধারণ Cryptographic ভুল

    ভুলসমস্যা
    দুর্বল/পুরনো অ্যালগরিদম (MD5, DES)আধুনিক কম্পিউটিং ক্ষমতা দিয়ে সহজে ভাঙা সম্ভব
    Hardcoded Encryption Keyযদি key অ্যাপ্লিকেশন কোডে থাকে, attacker reverse engineering (অধ্যায় ৬)-এর মাধ্যমে সহজে পেয়ে যান
    কাস্টম/নিজের তৈরি অ্যালগরিদমCommon Web Vulnerabilities ডকুমেন্টেশনের "নিজের cryptography তৈরি করবেন না" নীতি — প্রায় সবসময় দুর্বল
    স্থির (static) IV/Saltএকই ইনপুট সবসময় একই আউটপুট তৈরি করে, যা প্যাটার্ন বিশ্লেষণযোগ্য করে তোলে

    "হার্ডকোডেড কি" সমস্যার একটি বাস্তব উদাহরণ

    ধারণাগত Insecure Cryptography উদাহরণ
    // Insecure: encryption key সরাসরি কোডে hardcoded
private static final String SECRET_KEY = "MyHardcodedKey123";
// reverse engineering দিয়ে (অধ্যায় ৬) এই key সহজেই উদ্ধারযোগ্য —
// এনক্রিপটেড ডেটার সুরক্ষা কার্যত শূন্য হয়ে যায়

    সঠিক অনুশীলন

    ✅ প্রমাণিত লাইব্রেরি ব্যবহার

    প্ল্যাটফর্মের নিজস্ব, পরীক্ষিত cryptographic লাইব্রেরি (Android Keystore API, iOS CryptoKit) ব্যবহার করুন — নিজে অ্যালগরিদম তৈরি করবেন না।

    ✅ Key Derivation, Hardcode নয়

    Encryption key ডিভাইসে hardcode না করে, একটি সার্ভার-সাইড বা hardware-backed মেকানিজম (Keystore/Keychain, অধ্যায় ৩) থেকে প্রাপ্ত করুন।

    Password Hashing — আলাদা একটি বিষয়

    লক্ষণীয়, encryption (reversible) ও password hashing (one-way) ভিন্ন জিনিস — Authentication ডকুমেন্টেশনে আলোচিত bcrypt/Argon2-এর মতো hashing অ্যালগরিদম পাসওয়ার্ড সংরক্ষণের জন্য ব্যবহৃত হয়, যা এই অধ্যায়ের encryption আলোচনা থেকে ভিন্ন, যদিও একই পরিবারের ক্রিপ্টোগ্রাফিক নীতির অংশ।

    অনুশীলন

    কেন একটি hardcoded encryption key ব্যবহারিকভাবে "no encryption"-এর সমতুল্য হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    মোবাইল অ্যাপ্লিকেশনে দুর্বল অ্যালগরিদম, hardcoded key, বা কাস্টম cryptography ব্যবহার একটি সাধারণ ও গুরুতর ভুল — সমাধান হলো প্রমাণিত প্ল্যাটফর্ম লাইব্রেরি ও hardware-backed key management ব্যবহার করা।

    2. Hardcoded Encryption Key কেন reverse engineering-এর মাধ্যমে উদ্ধারযোগ্য?

    Platform-Specific Misuse

    Permission, Intent, ও WebView — Android/iOS প্ল্যাটফর্মের নিজস্ব ফিচারের ভুল ব্যবহার থেকে উদ্ভূত ঝুঁকি।

    Excessive Permission

    অধ্যায় ১-এ আলোচিত Permission মডেল অনুযায়ী, একটি অ্যাপ্লিকেশনের প্রয়োজনের চেয়ে বেশি permission চাওয়া (যেমন একটি সাধারণ নোট অ্যাপ্লিকেশন ক্যামেরা/কন্টাক্ট অ্যাক্সেস চাওয়া) একটি প্রাইভেসি ঝুঁকি — যদি অ্যাপ্লিকেশনটি পরবর্তীতে আপোস হয়, সেই অতিরিক্ত অ্যাক্সেসও attacker-এর হাতে চলে যায়।

    Android Exported Components

    একটি Android অ্যাপ্লিকেশনের Activity, Service, বা Broadcast Receiver যদি ভুলবশত exported="true" সেট করা থাকে, অন্য যেকোনো অ্যাপ্লিকেশন (এমনকি একটি দূষিত অ্যাপ্লিকেশন) সরাসরি সেই কম্পোনেন্ট ট্রিগার করতে পারে — Application Sandboxing (অধ্যায় ১)-এর একটি গুরুত্বপূর্ণ ফাঁক।

    ধারণাগত অতিরিক্ত Exported Component
    <!-- বিপজ্জনক: সংবেদনশীল Activity ভুলবশত exported -->
<activity android:name=".AdminPanelActivity" android:exported="true" />
<!-- যেকোনো ইনস্টল করা অ্যাপ্লিকেশন সরাসরি এই Activity চালু করতে পারে -->

    Intent-ভিত্তিক ঝুঁকি (Android)

    Intent হলো Android-এর কম্পোনেন্টের মধ্যে যোগাযোগের মেকানিজম — যদি একটি অ্যাপ্লিকেশন একটি Intent-এ সংবেদনশীল ডেটা (যেমন একটি সেশন টোকেন) পাঠায়, এবং সেই Intent "implicit" (নির্দিষ্ট গ্রহীতা ছাড়া) হয়, অন্য একটি দূষিত অ্যাপ্লিকেশন সেই ডেটা ইন্টারসেপ্ট করতে পারে।

    WebView — একটি সাধারণ বিপজ্জনক কম্পোনেন্ট

    🚨

    WebView ঝুঁকি: অনেক মোবাইল অ্যাপ্লিকেশন একটি embedded ব্রাউজার (WebView) ব্যবহার করে ওয়েব কন্টেন্ট দেখায়। যদি WebView-তে JavaScript-এর জন্য নেটিভ কোডের একটি "bridge" (যেমন Android-এর addJavascriptInterface) ভুলভাবে কনফিগার করা থাকে এবং WebView অবিশ্বস্ত কন্টেন্ট লোড করে, একটি XSS-জাতীয় দুর্বলতা সরাসরি ডিভাইসের নেটিভ ফাংশনে পৌঁছে যেতে পারে — Common Web Vulnerabilities ডকুমেন্টেশনের XSS অধ্যায়ের একটি মোবাইল-নির্দিষ্ট, আরও গুরুতর রূপ।

    Security Misconfiguration-এর অন্যান্য উদাহরণ

    • Debug mode/logging প্রোডাকশন বিল্ডে চালু রাখা
    • Backup allowed flag (Android) ভুলভাবে সক্রিয় রাখা, যা ADB দিয়ে অ্যাপ্লিকেশন ডেটা এক্সট্র্যাক্ট সহজ করে
    • Debuggable flag প্রোডাকশন বিল্ডে চালু রাখা

    অনুশীলন

    কেন একটি "exported" Android কম্পোনেন্ট Application Sandboxing-এর সুরক্ষাকে দুর্বল করে দেয়, তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Platform-Specific Misuse-এ Excessive Permission, ভুলভাবে Exported Component, Intent-ভিত্তিক ডেটা leakage, এবং অনিরাপদ WebView কনফিগারেশন অন্তর্ভুক্ত — এগুলো প্রতিটি প্ল্যাটফর্মের নিজস্ব ফিচারের ভুল ব্যবহার থেকে উদ্ভূত, এবং সাবধানী কনফিগারেশন দিয়ে প্রতিরোধযোগ্য।

    Third-Party Library ও SDK ঝুঁকি

    একটি মোবাইল অ্যাপ্লিকেশনের নিরাপত্তা শুধু নিজের লেখা কোডের উপর নির্ভর করে না।

    আধুনিক অ্যাপ্লিকেশনের নির্ভরতা

    একটি আধুনিক মোবাইল অ্যাপ্লিকেশন সাধারণত দশ থেকে শত সংখ্যক তৃতীয়-পক্ষ লাইব্রেরি/SDK (analytics, advertisement, payment, crash reporting) ব্যবহার করে। প্রতিটি এই নির্ভরতা একটি অতিরিক্ত আক্রমণ-তল — এই অধ্যায় Common Web Vulnerabilities ডকুমেন্টেশনের Vulnerable Components অধ্যায়ের একটি মোবাইল-নির্দিষ্ট প্রয়োগ।

    ঝুঁকিবিবরণ
    পুরনো/আপডেট না করা SDKপরিচিত দুর্বলতাসহ একটি লাইব্রেরি ব্যবহার করা
    অতিরিক্ত ডেটা সংগ্রহকারী SDKএকটি analytics/ad SDK প্রয়োজনের চেয়ে বেশি ব্যক্তিগত ডেটা সংগ্রহ ও পাঠানো
    আপোসকৃত SDK সরবরাহকারীএকটি জনপ্রিয় SDK-এর নিজস্ব সার্ভার/আপডেট চ্যানেল আপোস হলে, এটি ব্যবহারকারী সব অ্যাপ্লিকেশন প্রভাবিত হয়
    অতিরিক্ত Permission দাবিএকটি SDK নিজের প্রয়োজনের চেয়ে বেশি permission চায়, যা মূল অ্যাপ্লিকেশনের সামগ্রিক আক্রমণ-তল বাড়ায়

    Software Bill of Materials (SBOM)

    💡

    একটি অ্যাপ্লিকেশনে ঠিক কোন কোন লাইব্রেরি, কোন ভার্সনে ব্যবহৃত হচ্ছে তার একটি স্পষ্ট তালিকা (SBOM) রাখা একটি গুরুত্বপূর্ণ অনুশীলন — এটি একটি নতুন আবিষ্কৃত vulnerability (CVE)-এর প্রভাব দ্রুত মূল্যায়ন করতে সাহায্য করে।

    Mobile API Security

    API Security ডকুমেন্টেশনের নীতি মোবাইল-নির্দিষ্ট প্রেক্ষাপটে — ব্যাকএন্ড এন্ডপয়েন্ট আবিষ্কার ও পরীক্ষা।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র নিজের বা অনুমোদিত/scope-ভুক্ত API endpoint পরীক্ষা করুন।

    মোবাইল ক্লায়েন্ট, API-কেন্দ্রিক ব্যাকএন্ড

    প্রায় প্রতিটি আধুনিক মোবাইল অ্যাপ্লিকেশন একটি REST/GraphQL API-এর ক্লায়েন্ট মাত্র — সত্যিকারের বিজনেস লজিক ও ডেটা সার্ভারে থাকে। এর অর্থ API Security ডকুমেন্টেশনে আলোচিত সব ঝুঁকি (Broken Object Level Authorization, Excessive Data Exposure, Rate Limiting অভাব) এখানে সরাসরি প্রযোজ্য — অ্যাপ্লিকেশনটি শুধু সেই API-কে কল করার একটি মাধ্যম।

    Hidden/Undocumented Endpoint আবিষ্কার

    একটি মোবাইল অ্যাপ্লিকেশনের বাইনারি (অধ্যায় ৬ ও ৭-এর কৌশল ব্যবহার করে) প্রায়ই এমন endpoint উন্মোচন করে, যা পাবলিক API ডকুমেন্টেশনে নেই — যেমন একটি admin-only ফিচার বা একটি আসন্ন ফিচারের endpoint, যা এখনও UI-তে সক্রিয় নয় কিন্তু সার্ভারে কার্যকর আছে।

    ধারণাগত endpoint আবিষ্কার ওয়ার্কফ্লো
    ১. Dynamic Analysis (Frida/Proxy)-এর সময় সব API request লগ করা
২. decompile করা কোডে (jadx) string constant হিসেবে থাকা URL/endpoint খুঁজে বের করা
৩. প্রতিটি আবিষ্কৃত endpoint-এ BOLA/IDOR-জাতীয় দুর্বলতা যাচাই করা
   (নিজের টেস্ট অ্যাকাউন্ট দিয়ে, অনুমোদিত scope-এর মধ্যে)

    Mobile-নির্দিষ্ট API ঝুঁকি

    ঝুঁকিবিবরণ
    API Key ক্লায়েন্টে hardcodedএকটি third-party API-এর key অ্যাপ্লিকেশন বাইনারিতে রাখা, যা reverse engineering দিয়ে উদ্ধারযোগ্য (অধ্যায় ৬)
    সার্ভার-সাইড ইনপুট ভ্যালিডেশনের উপর অতিরিক্ত নির্ভরতা না করামোবাইল ক্লায়েন্টে input validation থাকলেও, attacker সরাসরি API কল করতে পারেন (ক্লায়েন্ট UI বাইপাস করে)
    Rate Limiting অনুপস্থিতিএকটি মোবাইল-নির্দিষ্ট endpoint-এ (যেমন OTP verification) rate limiting না থাকলে brute-force সম্ভব
    ⚠️

    একটি গুরুত্বপূর্ণ নীতি: যেহেতু attacker মোবাইল অ্যাপ্লিকেশনের UI সম্পূর্ণভাবে বাইপাস করে সরাসরি API-তে request পাঠাতে পারেন (যেমন Burp Suite দিয়ে ক্যাপচার করা একটি request পুনরায় পাঠিয়ে), ক্লায়েন্ট-সাইড UI-তে থাকা যেকোনো ভ্যালিডেশন/নিয়ন্ত্রণকে কখনো একমাত্র নিরাপত্তা নিয়ন্ত্রণ হিসেবে বিবেচনা করা উচিত নয়। সার্ভার-সাইড-ই চূড়ান্ত সিদ্ধান্ত নেয়।

    অনুশীলন

    কেন একটি মোবাইল অ্যাপ্লিকেশনের UI-তে থাকা "input validation" একটি সত্যিকারের নিরাপত্তা নিয়ন্ত্রণ নয় তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    মোবাইল অ্যাপ্লিকেশন সাধারণত একটি API ক্লায়েন্ট মাত্র — API Security ডকুমেন্টেশনের সব ঝুঁকি এখানে প্রযোজ্য। Reverse Engineering ও Dynamic Analysis দিয়ে hidden endpoint আবিষ্কার করা যায়, এবং সার্ভার-সাইডই সবসময় চূড়ান্ত নিরাপত্তা নিয়ন্ত্রণ হওয়া উচিত।

    Knowledge-check

    1. কেন একটি মোবাইল অ্যাপ্লিকেশনের নিরাপত্তা অনেকাংশে এর ব্যাকএন্ড API-এর নিরাপত্তার সমতুল্য?
    2. Hidden/Undocumented Endpoint কীভাবে আবিষ্কৃত হতে পারে?
    3. কেন ক্লায়েন্ট-সাইড input validation একা যথেষ্ট নয়?

    Mobile Pentesting Methodology ও Checklist

    এই ডকুমেন্টেশনের সব ধারণা একত্র করে, একটি বাস্তব মোবাইল পেন্টেস্টের ধাপে-ধাপে ওয়ার্কফ্লো।

    একটি সম্পূর্ণ Mobile Pentest-এর ধাপ

    ১. Reconnaissance

    অ্যাপ্লিকেশনের metadata, permission তালিকা, এবং প্রাথমিক তথ্য সংগ্রহ (App Store/Play Store তালিকা থেকেও)।

    ২. Static Analysis

    MobSF/apktool/jadx দিয়ে বাইনারি বিশ্লেষণ — hardcoded secret, misconfiguration খোঁজা (অধ্যায় ৬-৭)।

    ৩. Dynamic Analysis

    Frida ও proxy টুল দিয়ে runtime আচরণ ও নেটওয়ার্ক ট্রাফিক পর্যবেক্ষণ (অধ্যায় ৮)।

    ৪. API Testing

    ব্যাকএন্ড API-তে BOLA, auth bypass, ও অন্যান্য দুর্বলতা যাচাই (অধ্যায় ১৩)।

    ৫. Business Logic Review

    অ্যাপ্লিকেশন-নির্দিষ্ট লজিক (পেমেন্ট, লাইসেন্সিং) manual ভাবে পরীক্ষা।

    ৬. Reporting

    Bug Bounty Methodology ডকুমেন্টেশনের নীতি অনুসরণ করে স্পষ্ট, reproducible রিপোর্ট লেখা।

    একটি সংক্ষিপ্ত চেকলিস্ট

    Cryptographyপ্রমাণিত লাইব্রেরি, কোনো hardcoded key নেই (অধ্যায় ১০)

    APIসার্ভার-সাইড validation, rate limiting, BOLA প্রতিরোধ (অধ্যায় ১৩)

    Static ও Dynamic Analysis-এর সঠিক ক্রম

    💡

    বাস্তবে, একটি দক্ষ পেন্টেস্টার Static ও Dynamic Analysis-এর মধ্যে বারবার যাতায়াত করেন — static analysis-এ পাওয়া একটি সূত্র (যেমন একটি endpoint বা ফ্ল্যাগ) dynamic analysis-এ নিশ্চিত/অস্বীকার করা হয়, এবং এর বিপরীতও সত্য। এই দুই ধাপ ধারাবাহিক নয়, বরং চক্রাকার।

    অনুশীলন

    কেন একটি সম্পূর্ণ মোবাইল পেন্টেস্টে শুধু Static Analysis বা শুধু Dynamic Analysis যথেষ্ট নয় তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    একটি সম্পূর্ণ Mobile Pentesting Methodology Reconnaissance থেকে Reporting পর্যন্ত ছয়টি ধাপ অনুসরণ করে — Static ও Dynamic Analysis পরিপূরকভাবে ব্যবহৃত হয়, এবং এই ডকুমেন্টেশনের সব অধ্যায়ের ধারণা একটি সংক্ষিপ্ত চেকলিস্টে একত্র করা হয়েছে।

    পরিভাষাব্যাখ্যা

    প্রায়শই জিজ্ঞাসিত প্রশ্ন

    একটি অ্যাপ্লিকেশন App Store/Play Store-এ আছে মানেই কি এটি নিরাপদ?

    না। Store রিভিউ প্রক্রিয়া মূলত ম্যালওয়্যার ও নীতি লঙ্ঘন শনাক্ত করার জন্য ডিজাইন করা — এটি একটি গভীর নিরাপত্তা অডিট নয়। এই ডকুমেন্টেশনে আলোচিত অনেক দুর্বলতা (Insecure Storage, Insecure Communication) স্বাভাবিকভাবেই store রিভিউ পাস করে যায়।

    একজন শিক্ষার্থী হিসেবে Mobile Security শেখা কীভাবে শুরু করব?

    OWASP-এর তৈরি ইচ্ছাকৃতভাবে ঝুঁকিপূর্ণ অ্যাপ্লিকেশন (InsecureBankv2, OWASP MASTG Crackmes) দিয়ে একটি নিজস্ব lab পরিবেশে অনুশীলন করে — কখনো অনুমতি ছাড়া কোনো real অ্যাপ্লিকেশনে এই কৌশল প্রয়োগ না করে।

    এই ডকুমেন্টেশনের সাথে এই সিরিজের অন্য কোন ডকুমেন্টেশন সম্পর্কিত?

    Common Web Vulnerabilities (XSS/Injection-এর মোবাইল সমতুল্য ধারণা), API Security (ব্যাকএন্ড এন্ডপয়েন্ট ঝুঁকি), Network Security (TLS/MITM ভিত্তি), Authentication (MFA/token ব্যবস্থাপনা), এবং Bug Bounty Methodology (reporting/scope নীতি) — এই পাঁচটি ডকুমেন্টেশনের সাথে এই গাইডের ধারণা সরাসরি সংযুক্ত।
