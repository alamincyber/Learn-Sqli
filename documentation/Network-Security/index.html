    Network Security ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Network Security গাইড — নেটওয়ার্ক কীভাবে সুরক্ষিত রাখা হয়, Firewall/VPN/IDS-IPS কীভাবে কাজ করে, এবং একটি আধুনিক প্রতিষ্ঠান কীভাবে তাদের নেটওয়ার্ক পরিকাঠামো ডিজাইন ও মনিটর করে — ১৫টি অধ্যায়ে সাজানো।

    Network Security নিয়ে সংক্ষিপ্ত কথা

    এই সিরিজের আগের ডকুমেন্টেশনগুলো (XSS, CSRF, SQLi, API Security, Common Web Vulnerabilities) মূলত অ্যাপ্লিকেশন লেয়ার-এর নিরাপত্তা নিয়ে আলোচনা করেছে। এই ডকুমেন্টেশনটি এক স্তর নিচে যায় — নেটওয়ার্ক লেয়ার-এর নিরাপত্তা, যেখানে ডেটা প্যাকেট আকারে একটি সিস্টেম থেকে আরেকটি সিস্টেমে ভ্রমণ করে, এবং সেই যাত্রাপথকে কীভাবে সুরক্ষিত রাখা হয়।

    এখানে ধাপে ধাপে দেখানো হয়েছে — OSI/TCP-IP মডেল ও নেটওয়ার্ক নিরাপত্তার ভিত্তি, Firewall-এর ধরন ও কাজ, VPN ও secure tunneling, IDS/IPS, Network Segmentation ও VLAN, Proxy/Reverse Proxy, DNS Security, Wireless Network Security, TLS/SSL-এর মতো প্রোটোকল নিরাপত্তা, DDoS ও তার প্রতিরোধ, Network Monitoring, Zero Trust Architecture, Network Access Control, এবং একটি সম্পূর্ণ hardening checklist।

    💡

    এই ডকুমেন্টেশনের প্রকৃতি: এই গাইডটি মূলত ধারণাগত ও defensive — কীভাবে নেটওয়ার্ক পরিকাঠামো ডিজাইন ও সুরক্ষিত রাখতে হয় তার উপর ফোকাস করে। Network Scanning/Nmap-এর মতো offensive টুল ও কৌশল আগের Hacking Tools ডকুমেন্টেশনে বিস্তারিত আলোচিত হয়েছে — এই দুটি ডকুমেন্টেশন একসাথে পড়লে attacker ও defender — উভয় দৃষ্টিভঙ্গি থেকে নেটওয়ার্ক নিরাপত্তা বোঝা সহজ হবে।

    Network Security ও OSI/TCP-IP মডেলের ভিত্তি

    নেটওয়ার্ক নিরাপত্তা বোঝার আগে, একটি নেটওয়ার্কে ডেটা কীভাবে স্তরে স্তরে ভ্রমণ করে তা বোঝা জরুরি।

    Network Security কী

    Network Security হলো একটি নেটওয়ার্ক পরিকাঠামো (রাউটার, সুইচ, সার্ভার, এবং তাদের মধ্যে প্রবাহিত ডেটা) কে অননুমোদিত অ্যাক্সেস, অপব্যবহার, পরিবর্তন বা ধ্বংস থেকে রক্ষা করার নীতি, প্রযুক্তি ও অনুশীলনের সমষ্টি। Web Fundamentals ডকুমেন্টেশনে HTTP/HTTPS/IP/DNS নিয়ে আলোচনা হয়েছিল — এই ডকুমেন্টেশন সেই ভিত্তির উপর দাঁড়িয়ে, কীভাবে পুরো নেটওয়ার্ক পরিকাঠামো সুরক্ষিত রাখা হয় তা আলোচনা করে।

    কেন এই মডেলটি Network Security-র জন্য গুরুত্বপূর্ণ

    🎯 নির্দিষ্ট স্তরে আক্রমণ

    প্রতিটি নিরাপত্তা হুমকি একটি নির্দিষ্ট স্তরে ঘটে — যেমন DDoS (স্তর ৩/৪), DNS spoofing (স্তর ৭) — এই ডকুমেন্টেশনের প্রতিটি অধ্যায় একটি নির্দিষ্ট স্তরের প্রতিরক্ষা নিয়ে আলোচনা করে।

    🛡️ Defense in Depth

    একাধিক স্তরে একাধিক প্রতিরক্ষা স্তর স্থাপন করলে, একটি স্তর ব্যর্থ হলেও অন্যগুলো সুরক্ষা দিতে পারে (Common Web Vulnerabilities ডকুমেন্টেশনেও এই নীতি আলোচিত হয়েছিল)।

    TCP/IP মডেল — ব্যবহারিক সংস্করণ

    বাস্তব ইন্টারনেট পরিকাঠামো OSI-এর সরলীকৃত একটি সংস্করণ, TCP/IP মডেল ব্যবহার করে — চারটি স্তর: Application, Transport, Internet, এবং Network Access। এই ডকুমেন্টেশনে আমরা যখন "নেটওয়ার্ক লেয়ার" বা "ট্রান্সপোর্ট লেয়ার" সিকিউরিটি নিয়ে আলোচনা করব, এই সরলীকৃত মডেলটিই রেফারেন্স হিসেবে ব্যবহৃত হবে।

    CIA Triad — নেটওয়ার্ক সিকিউরিটির লক্ষ্য

    Common Web Vulnerabilities ডকুমেন্টেশনে আলোচিত CIA Triad এখানেও প্রযোজ্য — একটি নেটওয়ার্ক নিরাপত্তা ব্যবস্থার লক্ষ্য থাকে ডেটা গোপনীয় রাখা (এনক্রিপশন), অখণ্ড রাখা (পরিবর্তিত না হওয়া), এবং সবসময় প্রাপ্য রাখা (DDoS-এর মতো আক্রমণের বিরুদ্ধে প্রতিরোধ)।

    💡

    এই ডকুমেন্টেশনের লক্ষ্য: প্রতিটি পরবর্তী অধ্যায়ে একটি নির্দিষ্ট নেটওয়ার্ক সিকিউরিটি টুল/কৌশল (Firewall, VPN, IDS/IPS ইত্যাদি) আলোচনা করা হবে — এটি কোন স্তরে কাজ করে, কী সমস্যা সমাধান করে, এবং কীভাবে বাস্তবে প্রয়োগ করা হয়।

    অনুশীলন

    HTTPS (Web Fundamentals ডকুমেন্টেশনে আলোচিত) OSI মডেলের কোন স্তরে কাজ করে এবং কেন তা চিন্তা করুন।

    সারসংক্ষেপ

    Network Security নেটওয়ার্ক পরিকাঠামো ও তার মধ্য দিয়ে প্রবাহিত ডেটা রক্ষা করে। OSI/TCP-IP মডেল বোঝা গুরুত্বপূর্ণ, কারণ প্রতিটি নিরাপত্তা হুমকি ও প্রতিরক্ষা একটি নির্দিষ্ট স্তরে কাজ করে, এবং CIA Triad (Confidentiality, Integrity, Availability) এই পুরো ডকুমেন্টেশনের কেন্দ্রীয় লক্ষ্য।

    Firewall — ধরন ও কাজ

    নেটওয়ার্ক নিরাপত্তার সবচেয়ে পরিচিত ও মৌলিক উপাদান — একটি নেটওয়ার্কের "গেটকিপার"।

    Firewall কী

    Firewall একটি নেটওয়ার্ক নিরাপত্তা ডিভাইস/সফটওয়্যার, যা পূর্বনির্ধারিত নিয়ম অনুযায়ী ইনকামিং ও আউটগোয়িং নেটওয়ার্ক ট্রাফিক পর্যবেক্ষণ ও নিয়ন্ত্রণ করে — একটি বিশ্বস্ত অভ্যন্তরীণ নেটওয়ার্ক এবং একটি অবিশ্বস্ত বাহ্যিক নেটওয়ার্কের (যেমন ইন্টারনেট) মধ্যে একটি বাধা হিসেবে কাজ করে।

    Firewall-এর ধরন

    ধরনকীভাবে কাজ করে
    Packet-Filtering Firewallপ্রতিটি প্যাকেটের header (source/destination IP, port) পরীক্ষা করে, নিয়ম অনুযায়ী অনুমতি/অস্বীকার — দ্রুত, কিন্তু context বোঝে না
    Stateful Inspection Firewallএকটি কানেকশনের সম্পূর্ণ অবস্থা (state) ট্র্যাক করে — শুধু individual প্যাকেট নয়, পুরো সেশনের প্রেক্ষাপট বিবেচনা করে
    Application-Layer Firewall (WAF সহ)OSI স্তর ৭ পর্যন্ত বিশ্লেষণ করে — HTTP request-এর কনটেন্ট দেখে SQLi/XSS-এর মতো প্যাটার্ন শনাক্ত করতে পারে (Common Web Vulnerabilities ডকুমেন্টেশনের দুর্বলতাগুলোর সাথে সরাসরি সম্পর্কিত)
    Next-Generation Firewall (NGFW)উপরের সব ক্ষমতার সাথে IDS/IPS, deep packet inspection একত্রিত করে

    Firewall Rule কীভাবে কাজ করে

    ধারণাগত Firewall Rule উদাহরণ
    Rule 1: ALLOW   TCP   Any → 203.0.113.10:443   (HTTPS ট্রাফিক অনুমোদিত)
Rule 2: ALLOW   TCP   Any → 203.0.113.10:22    (শুধু অফিস IP থেকে SSH)
Rule 3: DENY    ALL   Any → Any                (ডিফল্টভাবে সব ব্লক — "Deny by Default")

    নিয়মগুলো সাধারণত উপর থেকে নিচে ক্রমানুসারে প্রয়োগ হয়, এবং সবচেয়ে কার্যকর নীতি হলো "Deny by Default, Allow by Exception" — শুধু যা স্পষ্টভাবে প্রয়োজন তা-ই অনুমোদন দেওয়া, বাকি সব ডিফল্টভাবে ব্লক রাখা।

    Network Firewall বনাম Host-based Firewall

    🏢 Network Firewall

    পুরো নেটওয়ার্কের প্রবেশপথে বসানো একটি ডিভাইস — পুরো অভ্যন্তরীণ নেটওয়ার্ককে একসাথে সুরক্ষা দেয়।

    💻 Host-based Firewall

    একটি নির্দিষ্ট কম্পিউটার/সার্ভারে ইনস্টল করা সফটওয়্যার (যেমন Windows Firewall) — শুধু সেই নির্দিষ্ট মেশিনকে সুরক্ষা দেয়, defense in depth-এর একটি অতিরিক্ত স্তর।

    ⚠️

    Firewall একাই যথেষ্ট নয়: একটি Firewall শুধু নেটওয়ার্ক-লেয়ার ট্রাফিক নিয়ন্ত্রণ করে — এটি কোনো vulnerable অ্যাপ্লিকেশন কোডের দুর্বলতা (যেমন SQLi, যদি রিকোয়েস্ট অনুমোদিত পোর্টে আসে) প্রতিরোধ করে না। Firewall একটি গুরুত্বপূর্ণ, কিন্তু একক প্রতিরক্ষা স্তর নয় — Defense in Depth নীতির একটি অংশ মাত্র।

    অনুশীলন

    কেন "Deny by Default, Allow by Exception" নীতি "Allow by Default, Deny by Exception"-এর চেয়ে নিরাপদ তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Firewall নেটওয়ার্ক ট্রাফিক নিয়ন্ত্রণকারী একটি গেটকিপার — Packet-Filtering থেকে Next-Generation Firewall পর্যন্ত বিভিন্ন স্তরের সক্ষমতা আছে। "Deny by Default" নীতি সবচেয়ে নিরাপদ, কিন্তু Firewall একাই সম্পূর্ণ সুরক্ষা দেয় না — এটি Defense in Depth-এর একটি স্তর মাত্র।

    VPN ও Secure Tunneling

    একটি অবিশ্বস্ত নেটওয়ার্কের (যেমন পাবলিক Wi-Fi) মধ্য দিয়েও কীভাবে একটি নিরাপদ, ব্যক্তিগত সংযোগ তৈরি করা যায়।

    VPN কী

    VPN (Virtual Private Network) একটি এনক্রিপ্টেড "টানেল" তৈরি করে, যার মধ্য দিয়ে একটি ডিভাইসের সব ট্রাফিক প্রবাহিত হয় — এমনকি একটি অবিশ্বস্ত নেটওয়ার্কের (পাবলিক Wi-Fi, ISP) মধ্য দিয়ে গেলেও, টানেলের ভেতরের ডেটা তৃতীয় পক্ষের কাছে অদৃশ্য ও সুরক্ষিত থাকে।

    VPN-এর প্রধান ব্যবহার

    🏢 Site-to-Site VPN

    দুটি ভিন্ন অফিস/ডেটা সেন্টারের নেটওয়ার্ককে ইন্টারনেটের মাধ্যমে নিরাপদভাবে সংযুক্ত করে, যেন তারা একই অভ্যন্তরীণ নেটওয়ার্কে আছে।

    👤 Remote Access VPN

    একজন ব্যক্তিগত ইউজার (যেমন বাসা থেকে কাজ করা একজন কর্মী) তার প্রতিষ্ঠানের অভ্যন্তরীণ নেটওয়ার্কে নিরাপদে সংযুক্ত হতে ব্যবহার করেন।

    জনপ্রিয় VPN প্রোটোকল

    প্রোটোকলবৈশিষ্ট্য
    IPsecনেটওয়ার্ক স্তরে কাজ করে, এন্টারপ্রাইজ site-to-site VPN-এ বহুল ব্যবহৃত
    OpenVPNওপেন-সোর্স, অত্যন্ত নমনীয় ও বহুল সমর্থিত
    WireGuardতুলনামূলক নতুন, সরল কোডবেস, দ্রুত পারফরম্যান্স ও আধুনিক cryptography-র জন্য পরিচিত

    কীভাবে VPN নিরাপত্তা দেয়

    VPN মূলত এনক্রিপশন (Hacking Tools ডকুমেন্টেশনে প্যাকেট ক্যাপচার/Wireshark আলোচনার প্রসঙ্গে উল্লেখিত ধারণা এখানে প্রাসঙ্গিক) ব্যবহার করে — যদি কেউ টানেলের মধ্য দিয়ে যাওয়া ট্রাফিক ক্যাপচার করেন, তিনি শুধু এনক্রিপ্টেড, অর্থহীন ডেটা দেখবেন, প্রকৃত কনটেন্ট নয়।

    VPN সম্পর্কে একটি সাধারণ ভুল ধারণা

    ⚠️

    VPN "সম্পূর্ণ অদৃশ্যতা" দেয় না: একটি VPN আপনার ট্রাফিক ISP/local network থেকে লুকিয়ে রাখে, কিন্তু VPN প্রোভাইডার নিজেই আপনার ট্রাফিক দেখতে পারেন (যদি তারা সেই নীতি অনুসরণ করেন) — একজন প্রতিষ্ঠানের VPN ব্যবহার করলে, প্রতিষ্ঠান নিজের নেটওয়ার্কের মধ্য দিয়ে যাওয়া আপনার ট্রাফিক মনিটর করতে পারে। এটি "সম্পূর্ণ গোপনীয়তা" নয় — এটি একটি নির্দিষ্ট নেটওয়ার্ক অংশে এনক্রিপশন যোগ করে।

    Split Tunneling

    কিছু VPN কনফিগারেশন Split Tunneling সমর্থন করে — শুধু নির্দিষ্ট ট্রাফিক (যেমন প্রতিষ্ঠানের অভ্যন্তরীণ রিসোর্সে যাওয়া ট্রাফিক) VPN টানেলের মধ্য দিয়ে যায়, বাকি সাধারণ ইন্টারনেট ট্রাফিক সরাসরি যায় — এটি পারফরম্যান্স উন্নত করে, কিন্তু নিরাপত্তার দিক থেকে কিছু ট্রেড-অফ থাকে।

    অনুশীলন

    কেন একটি পাবলিক Wi-Fi (যেমন ক্যাফেতে) VPN ছাড়া সংবেদনশীল কাজ (ব্যাংকিং, ইমেইল) করা ঝুঁকিপূর্ণ হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    VPN একটি এনক্রিপ্টেড টানেল তৈরি করে, যা অবিশ্বস্ত নেটওয়ার্কের মধ্য দিয়েও ডেটা নিরাপদে পাঠাতে সাহায্য করে — Site-to-Site ও Remote Access এর দুটি প্রধান ব্যবহার। VPN সম্পূর্ণ অদৃশ্যতা দেয় না — এটি একটি নির্দিষ্ট নেটওয়ার্ক অংশে এনক্রিপশন যোগ করে।

    IDS ও IPS — Intrusion Detection/Prevention

    Firewall নিয়ম-ভিত্তিক ট্রাফিক ব্লক করে — IDS/IPS আরও গভীরে গিয়ে সন্দেহজনক প্যাটার্ন শনাক্ত করে।

    IDS বনাম IPS

    👁️ IDS (Intrusion Detection System)

    নেটওয়ার্ক ট্রাফিক পর্যবেক্ষণ করে সন্দেহজনক কার্যকলাপ শনাক্ত করে এবং সতর্ক করে — কিন্তু নিজে থেকে ট্রাফিক ব্লক করে না।

    🛑 IPS (Intrusion Prevention System)

    IDS-এর মতোই শনাক্ত করে, কিন্তু সক্রিয়ভাবে সেই ট্রাফিক ব্লক/প্রতিরোধ করে — একটি in-line ডিভাইস হিসেবে কাজ করে।

    Signature-Based বনাম Anomaly-Based Detection

    পদ্ধতিকীভাবে কাজ করেসীমাবদ্ধতা
    Signature-Basedপরিচিত আক্রমণ প্যাটার্নের একটি ডেটাবেজের সাথে ট্রাফিক মেলায় (Hacking Tools ডকুমেন্টেশনের vulnerability scanner-এর CVE ম্যাচিং-এর মতো নীতি)নতুন, অপরিচিত (zero-day) আক্রমণ শনাক্ত করতে পারে না
    Anomaly-Based"স্বাভাবিক" নেটওয়ার্ক আচরণের একটি baseline শেখে, তারপর সেই baseline থেকে উল্লেখযোগ্য বিচ্যুতি শনাক্ত করেFalse positive বেশি হতে পারে, কারণ স্বাভাবিক কিন্তু অস্বাভাবিক ব্যবহারও flag হতে পারে

    Network-Based বনাম Host-Based

    • NIDS/NIPS (Network-based): পুরো নেটওয়ার্ক সেগমেন্টের ট্রাফিক পর্যবেক্ষণ করে, একটি কেন্দ্রীয় পয়েন্টে বসানো
    • HIDS/HIPS (Host-based): একটি নির্দিষ্ট সার্ভার/মেশিনে ইনস্টল করা, সেই নির্দিষ্ট সিস্টেমের লগ ও কার্যকলাপ পর্যবেক্ষণ করে

    একটি বাস্তব উদাহরণ — Snort

    Snort একটি জনপ্রিয় ওপেন-সোর্স NIDS/NIPS, যা সিগনেচার-ভিত্তিক নিয়মের একটি বিশাল ডেটাবেজ ব্যবহার করে পরিচিত আক্রমণ প্যাটার্ন (যেমন একটি নির্দিষ্ট exploit-এর নেটওয়ার্ক সিগনেচার) শনাক্ত করতে পারে — এই ডকুমেন্টেশন সিরিজে আলোচিত অনেক vulnerability-র exploitation attempt নেটওয়ার্ক লেভেলে এরকম টুল দিয়ে শনাক্তযোগ্য।

    💡

    Firewall-এর সাথে সম্পর্ক: একটি Firewall সাধারণত "কে কথা বলতে পারবে" নিয়ন্ত্রণ করে (port/IP-ভিত্তিক), আর IDS/IPS "তারা কী বলছে" বিশ্লেষণ করে — অনুমোদিত ট্রাফিকের মধ্যেও একটি ক্ষতিকর প্যাটার্ন থাকতে পারে, যা শুধুমাত্র content-level বিশ্লেষণে ধরা পড়ে।

    অনুশীলন

    কেন একটি IPS (যা স্বয়ংক্রিয়ভাবে ট্রাফিক ব্লক করে) একটি false positive-এর ক্ষেত্রে IDS-এর চেয়ে বেশি ঝুঁকিপূর্ণ হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    IDS সন্দেহজনক কার্যকলাপ শনাক্ত করে সতর্ক করে, আর IPS সক্রিয়ভাবে ব্লক করে। Signature-Based Detection পরিচিত প্যাটার্ন দ্রুত শনাক্ত করে, আর Anomaly-Based Detection অপরিচিত হুমকিও ধরতে পারে, কিন্তু বেশি false positive দেয়।

    Network Segmentation ও VLAN

    পুরো নেটওয়ার্ককে একটি একক, বড় বিশ্বাসযোগ্য এলাকা না রেখে, ছোট ছোট নিয়ন্ত্রিত অংশে ভাগ করা।

    Network Segmentation কী

    Network Segmentation একটি বড় নেটওয়ার্ককে ছোট ছোট, পৃথক সাব-নেটওয়ার্কে ভাগ করার প্রক্রিয়া — প্রতিটি সেগমেন্টের মধ্যে ট্রাফিক নিয়ন্ত্রিত ও সীমাবদ্ধ থাকে, যাতে একটি সেগমেন্টে breach হলে তা পুরো নেটওয়ার্কে স্বয়ংক্রিয়ভাবে ছড়িয়ে না পড়ে।

    কেন Segmentation গুরুত্বপূর্ণ — "Flat Network"-এর ঝুঁকি

    🚨

    Flat Network সমস্যা: যদি একটি পুরো অফিসের সব ডিভাইস (কর্মীর ল্যাপটপ, সার্ভার, প্রিন্টার, IoT ডিভাইস) একই নেটওয়ার্কে থাকে, কোনো বিভাজন ছাড়া — একটি একক আপোসকৃত (compromised) ডিভাইস (যেমন একটি phishing-এর শিকার হওয়া ল্যাপটপ) থেকে attacker সহজেই পুরো নেটওয়ার্কে "lateral movement" করে সবচেয়ে সংবেদনশীল সার্ভার পর্যন্ত পৌঁছাতে পারেন — Hacking Tools ডকুমেন্টেশনের Post-Exploitation অধ্যায়ে আলোচিত Lateral Movement ধারণা এখানে সরাসরি প্রাসঙ্গিক।

    VLAN (Virtual LAN)

    VLAN একটি প্রযুক্তি, যা একটি একক ফিজিক্যাল নেটওয়ার্ক পরিকাঠামোর উপর একাধিক যৌক্তিক (logical), পৃথক নেটওয়ার্ক তৈরি করতে দেয় — একই সুইচে সংযুক্ত ডিভাইসগুলো, যদি ভিন্ন VLAN-এ থাকে, একে অপরের সাথে সরাসরি যোগাযোগ করতে পারে না, যদি না স্পষ্টভাবে রাউটিং/ফায়ারওয়াল নিয়ম দিয়ে অনুমতি দেওয়া হয়।

    একটি সাধারণ Segmentation কাঠামোর উদাহরণ

    সেগমেন্টকী থাকেঅ্যাক্সেস নীতি
    Corporate/User VLANকর্মীদের কম্পিউটারইন্টারনেট ও নির্দিষ্ট অভ্যন্তরীণ সার্ভিস অ্যাক্সেস
    Server/DMZ VLANপাবলিক-facing সার্ভার (ওয়েব সার্ভার)সীমিত, শুধু প্রয়োজনীয় পোর্টে ইনকামিং, কঠোরভাবে নিয়ন্ত্রিত আউটগোয়িং
    Database VLANডেটাবেজ সার্ভারশুধু নির্দিষ্ট application server থেকে অ্যাক্সেস অনুমোদিত, সরাসরি ইন্টারনেট থেকে নয়
    IoT/Guest VLANIoT ডিভাইস, গেস্ট Wi-Fiসম্পূর্ণ পৃথক, কোনো অভ্যন্তরীণ রিসোর্সে অ্যাক্সেস নেই

    DMZ (Demilitarized Zone)

    DMZ একটি বিশেষ নেটওয়ার্ক সেগমেন্ট, যেখানে পাবলিক-facing সার্ভিস (ওয়েব সার্ভার, মেইল সার্ভার) রাখা হয় — এটি অভ্যন্তরীণ নেটওয়ার্ক ও বাহ্যিক ইন্টারনেটের মাঝে একটি "বাফার জোন" হিসেবে কাজ করে, যাতে একটি পাবলিক সার্ভার আপোসকৃত হলেও, attacker সরাসরি সংবেদনশীল অভ্যন্তরীণ নেটওয়ার্কে প্রবেশ করতে না পারেন।

    💡

    Zero Trust-এর ভিত্তি: Network Segmentation এই ডকুমেন্টেশনের পরবর্তী অংশে আলোচিত Zero Trust Architecture-এর একটি মৌলিক বিল্ডিং ব্লক — Zero Trust নীতিতে প্রতিটি সেগমেন্টের মধ্যে যোগাযোগকেও "অবিশ্বস্ত" ধরে নিয়ে আলাদাভাবে যাচাই করা হয়।

    অনুশীলন

    কেন একটি Database Server-কে সরাসরি ইন্টারনেট থেকে অ্যাক্সেসযোগ্য না রেখে, শুধু Application Server-এর মাধ্যমে অ্যাক্সেসযোগ্য রাখা একটি গুরুত্বপূর্ণ নিরাপত্তা অনুশীলন তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Network Segmentation একটি বড় নেটওয়ার্ককে ছোট, নিয়ন্ত্রিত অংশে ভাগ করে, একটি compromised অংশ থেকে পুরো নেটওয়ার্কে ছড়িয়ে পড়া প্রতিরোধ করে। VLAN এই বিভাজন বাস্তবায়নের একটি প্রযুক্তি, এবং DMZ পাবলিক-facing সার্ভিসের জন্য একটি বিশেষ বাফার জোন তৈরি করে।

    Proxy ও Reverse Proxy

    ক্লায়েন্ট ও সার্ভারের মাঝে একটি মধ্যস্থতাকারী — নিরাপত্তা, পারফরম্যান্স ও প্রাইভেসির জন্য ব্যবহৃত।

    Forward Proxy

    Forward Proxy ক্লায়েন্টের পক্ষে কাজ করে — একজন ইউজারের সব request প্রথমে proxy সার্ভারে যায়, তারপর proxy সেটি প্রকৃত destination-এ ফরওয়ার্ড করে। এটি Hacking Tools ডকুমেন্টেশনে আলোচিত Burp Suite-এর মতোই একটি proxy ধারণা, কিন্তু এখানে উদ্দেশ্য টেস্টিং নয় — নিয়ন্ত্রণ, ফিল্টারিং, বা anonymity।

    Reverse Proxy

    Reverse Proxy সার্ভারের পক্ষে কাজ করে — ক্লায়েন্টের request সরাসরি backend সার্ভারে না গিয়ে, প্রথমে reverse proxy-তে আসে, যা তারপর অভ্যন্তরীণভাবে সঠিক backend সার্ভারে request পাঠায়। ক্লায়েন্ট কখনো জানে না প্রকৃত backend সার্ভারের IP/অবস্থান কী।

    ⚖️ Load Balancing

    একাধিক backend সার্ভারের মধ্যে ট্রাফিক ভাগ করে দেয়, যা একটি single server-কে DDoS-এর সহজ টার্গেট হওয়া থেকে রক্ষা করতেও সাহায্য করে।

    SSL/TLS Termination

    অনেক প্রতিষ্ঠানে reverse proxy-তে SSL/TLS Termination হয় — মানে ক্লায়েন্ট থেকে reverse proxy পর্যন্ত HTTPS এনক্রিপশন থাকে, কিন্তু proxy থেকে backend সার্ভার পর্যন্ত (যদি একই নিরাপদ অভ্যন্তরীণ নেটওয়ার্কে থাকে) সাধারণ HTTP ব্যবহার করা যেতে পারে, যা encryption/decryption-এর computational চাপ কেন্দ্রীভূত করে।

    DNS Security

    Web Fundamentals ডকুমেন্টেশনে DNS-এর মৌলিক কাজ আলোচিত হয়েছিল — এখানে দেখা হবে কীভাবে এই গুরুত্বপূর্ণ সিস্টেমকে আক্রমণ ও সুরক্ষিত করা হয়।

    কেন DNS একটি আকর্ষণীয় আক্রমণ টার্গেট

    DNS একটি ডোমেইন নামকে IP address-এ রূপান্তর করে — প্রায় প্রতিটি অনলাইন কার্যকলাপের প্রথম ধাপ। যদি একজন attacker DNS resolution প্রক্রিয়া কারসাজি করতে পারেন, তিনি একজন ইউজারকে, তার অজান্তেই, একটি সম্পূর্ণ ভুয়া সার্ভারে পাঠাতে পারেন — এমনকি ইউজার সঠিক ডোমেইন নাম টাইপ করলেও।

    সাধারণ DNS আক্রমণ

    আক্রমণবর্ণনা
    DNS Spoofing/Cache Poisoningএকটি DNS resolver-এর cache-এ ভুয়া তথ্য প্রবেশ করিয়ে, ইউজারকে একটি ভুয়া IP-তে redirect করা
    DNS Hijackingএকটি ডোমেইনের DNS সেটিংস অননুমোদিতভাবে পরিবর্তন করা (প্রায়ই domain registrar অ্যাকাউন্ট আপোসের মাধ্যমে)
    DNS TunnelingDNS প্রোটোকলের মধ্যে গোপনে ডেটা লুকিয়ে পাঠানো — ফায়ারওয়াল bypass করে ডেটা exfiltration-এর একটি কৌশল
    Typosquattingজনপ্রিয় ডোমেইনের ভুল বানানো সংস্করণ রেজিস্টার করে, ভুলবশত টাইপ করা ইউজারদের টার্গেট করা

    DNSSEC — DNS-এর জন্য Digital Signature

    DNSSEC (DNS Security Extensions) DNS response-এ একটি digital signature যোগ করে, যা প্রমাণ করে response-টি প্রকৃত, অনুমোদিত উৎস থেকে এসেছে এবং পথের মধ্যে পরিবর্তিত হয়নি — এটি DNS Spoofing/Cache Poisoning-এর বিরুদ্ধে একটি মূল প্রতিরক্ষা, Authentication ডকুমেন্টেশনে আলোচিত digital signature-এর ধারণা এখানে DNS-এর প্রেক্ষাপটে প্রয়োগ হয়েছে।

    DNS over HTTPS (DoH) ও DNS over TLS (DoT)

    ঐতিহ্যগতভাবে DNS query প্লেইনটেক্সটে পাঠানো হয় — এর মানে নেটওয়ার্কে যে কেউ (Hacking Tools ডকুমেন্টেশনের Wireshark-এর মতো টুল দিয়ে) দেখতে পারেন একজন ইউজার কোন ওয়েবসাইট ভিজিট করছেন। DoH ও DoT DNS query-কে এনক্রিপ্ট করে, প্রাইভেসি ও সততা (integrity) বৃদ্ধি করে।

    💡

    বাস্তব উদাহরণ: একটি কর্পোরেট নেটওয়ার্কে, এমনকি একটি সঠিকভাবে কনফিগার করা Firewall থাকলেও, যদি DNS resolution-এ দুর্বলতা থাকে, একজন ইউজার একটি সম্পূর্ণ বৈধ মনে হওয়া ডোমেইনে গিয়ে একটি phishing সাইটে (Hacking Tools ডকুমেন্টেশনের Social Engineering অধ্যায়ে আলোচিত) পৌঁছে যেতে পারেন — এটি দেখায় কেন DNS Security একটি গুরুত্বপূর্ণ, প্রায়ই অবহেলিত স্তর।

    অনুশীলন

    DNSSEC কীভাবে DNS Spoofing প্রতিরোধ করে — digital signature-এর নীতি এখানে কীভাবে কাজ করে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    DNS একটি গুরুত্বপূর্ণ ও আকর্ষণীয় আক্রমণ টার্গেট — Spoofing, Hijacking, Tunneling সাধারণ হুমকি। DNSSEC digital signature দিয়ে DNS response-এর সততা যাচাই করে, এবং DoH/DoT DNS query-কে এনক্রিপ্ট করে প্রাইভেসি বৃদ্ধি করে।

    Wireless Network Security

    Hacking Tools ডকুমেন্টেশনে Wi-Fi আক্রমণ কীভাবে কাজ করে তা দেখা হয়েছিল — এখানে দেখা হবে একটি প্রতিষ্ঠান কীভাবে তার wireless পরিকাঠামো defend করে।

    Enterprise Wi-Fi বনাম Home Wi-Fi

    🏠 Home/Personal Wi-Fi

    সাধারণত WPA2/WPA3-Personal ব্যবহার করে — একটি একক shared পাসওয়ার্ড, সব ডিভাইসের জন্য একই।

    🏢 Enterprise Wi-Fi

    WPA2/WPA3-Enterprise ব্যবহার করে — প্রতিটি ইউজারের নিজস্ব ক্রেডেনশিয়াল, একটি কেন্দ্রীয় authentication সার্ভারের (RADIUS) মাধ্যমে যাচাই হয়।

    RADIUS — Enterprise Authentication-এর ভিত্তি

    RADIUS (Remote Authentication Dial-In User Service) একটি কেন্দ্রীয় সার্ভার, যা Wi-Fi access point-কে প্রতিটি ইউজারের পরিচয় যাচাই করতে সাহায্য করে — এর সুবিধা হলো, যদি একজন কর্মী প্রতিষ্ঠান ছেড়ে দেন, শুধু তার RADIUS অ্যাকাউন্ট বন্ধ করলেই চলে, পুরো Wi-Fi পাসওয়ার্ড পরিবর্তনের প্রয়োজন হয় না (যা Home Wi-Fi-তে করতে হতো)।

    Guest Network — একটি গুরুত্বপূর্ণ Segmentation অনুশীলন

    অধ্যায় ৫-এ আলোচিত Network Segmentation-এর একটি সরাসরি প্রয়োগ — একটি প্রতিষ্ঠানের Guest Wi-Fi সবসময় প্রধান অভ্যন্তরীণ নেটওয়ার্ক থেকে সম্পূর্ণ আলাদা (পৃথক VLAN) থাকা উচিত, যাতে একজন অতিথি বা একটি আপোসকৃত ব্যক্তিগত ডিভাইস কখনো সংবেদনশীল অভ্যন্তরীণ রিসোর্সে পৌঁছাতে না পারে।

    Rogue Access Point শনাক্তকরণ

    Hacking Tools ডকুমেন্টেশনে আলোচিত Evil Twin/Rogue Access Point আক্রমণের বিরুদ্ধে, প্রতিষ্ঠানগুলো Wireless Intrusion Detection System (WIDS) ব্যবহার করে — এটি ক্রমাগত আশেপাশের সব Wi-Fi সিগনাল মনিটর করে, এবং কোনো অননুমোদিত access point (যা প্রতিষ্ঠানের নেটওয়ার্কের নাম নকল করছে) শনাক্ত হলে সতর্ক করে।

    Wireless Security Best Practices

    • সর্বদা WPA3 (বা অন্তত WPA2) ব্যবহার করা, WEP সম্পূর্ণ এড়িয়ে চলা (Hacking Tools ডকুমেন্টেশনে আলোচিত দুর্বলতার কারণে)
    • Default SSID ও router admin password পরিবর্তন করা
    • MAC Address Filtering (একটি অতিরিক্ত, কিন্তু একক নির্ভরযোগ্য নয় এমন স্তর — MAC address spoof করা সম্ভব)
    • নিয়মিত firmware আপডেট রাখা (Common Web Vulnerabilities ডকুমেন্টেশনের Vulnerable Components অধ্যায়ের একই নীতি)
    ⚠️

    IoT ডিভাইসের ঝুঁকি: অনেক IoT ডিভাইস (স্মার্ট ক্যামেরা, প্রিন্টার) দুর্বল ডিফল্ট ক্রেডেনশিয়াল নিয়ে আসে এবং কম নিয়মিত আপডেট পায় — এই ধরনের ডিভাইস সবসময় একটি পৃথক, সীমিত-অ্যাক্সেস VLAN-এ রাখা উচিত, প্রধান নেটওয়ার্ক থেকে বিচ্ছিন্ন।

    অনুশীলন

    কেন একটি প্রতিষ্ঠানে একাধিক কর্মীর জন্য একটি একক, shared Wi-Fi পাসওয়ার্ডের বদলে RADIUS-ভিত্তিক individual authentication ব্যবহার করা বেশি নিরাপদ তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    Enterprise Wi-Fi RADIUS-ভিত্তিক individual authentication ব্যবহার করে, যা Home Wi-Fi-র shared পাসওয়ার্ডের চেয়ে বেশি নিরাপদ ও নমনীয়। Guest Network সবসময় segmented রাখা উচিত, এবং WIDS Rogue Access Point-এর মতো আক্রমণ শনাক্ত করতে সাহায্য করে।

    TLS/SSL ও Secure Protocols

    কীভাবে ইন্টারনেটে প্রবাহিত ডেটা এনক্রিপ্ট করা হয় — HTTPS-এর পেছনের প্রযুক্তি বিস্তারিতভাবে।

    TLS/SSL কী

    Web Fundamentals ডকুমেন্টেশনে HTTPS-এর পরিচিতি দেওয়া হয়েছিল — TLS (Transport Layer Security), যার পুরনো নাম SSL, হলো সেই প্রোটোকল যা HTTPS-কে নিরাপদ করে তোলে। এটি OSI মডেলের Presentation স্তরে কাজ করে এবং ক্লায়েন্ট-সার্ভার যোগাযোগকে এনক্রিপ্ট করে।

    TLS Handshake — সংক্ষিপ্ত প্রক্রিয়া

    উচ্চ-স্তরের ধারণা
    ১. Client Hello    — ক্লায়েন্ট সমর্থিত encryption পদ্ধতির তালিকা পাঠায়
২. Server Hello    — সার্ভার একটি পদ্ধতি বেছে নেয় ও তার সার্টিফিকেট পাঠায়
৩. Certificate যাচাই — ক্লায়েন্ট সার্টিফিকেটটি একটি বিশ্বস্ত CA থেকে এসেছে কি না যাচাই করে
৪. Key Exchange    — উভয়পক্ষ একটি shared secret key তৈরি করে
৫. Encrypted Communication শুরু হয়

    Certificate Authority (CA) ও বিশ্বাসের শৃঙ্খল

    একটি SSL সার্টিফিকেট একটি Certificate Authority (CA) দ্বারা ইস্যু করা হয় — একটি বিশ্বস্ত তৃতীয় পক্ষ, যা যাচাই করে একটি ডোমেইনের মালিকানা প্রকৃতপক্ষে সেই প্রতিষ্ঠানের। ব্রাউজারে প্রি-ইনস্টল করা একটি তালিকা থাকে কোন CA-কে বিশ্বাস করা হবে — এই "বিশ্বাসের শৃঙ্খল" (Chain of Trust) না থাকলে, যে কেউ যেকোনো ডোমেইনের জন্য একটি ভুয়া সার্টিফিকেট তৈরি করতে পারতেন।

    Certificate Pinning

    সাধারণত একটি অ্যাপ্লিকেশন যেকোনো বিশ্বস্ত CA থেকে ইস্যু করা সার্টিফিকেট গ্রহণ করে। Certificate Pinning একটি অতিরিক্ত নিরাপত্তা স্তর — অ্যাপ্লিকেশনটি শুধুমাত্র একটি নির্দিষ্ট, পূর্বনির্ধারিত সার্টিফিকেট/public key গ্রহণ করে, এমনকি যদি একটি ভিন্ন, বিশ্বস্ত CA থেকে ইস্যু করা সার্টিফিকেটও উপস্থাপন করা হয় — এটি man-in-the-middle আক্রমণের ঝুঁকি আরও কমায়, বিশেষত মোবাইল অ্যাপে ব্যবহৃত হয়।

    পুরনো TLS ভার্সন ও Cipher Suite-এর ঝুঁকি

    ভার্সন/উপাদানঅবস্থা
    SSL 2.0/3.0, TLS 1.0/1.1Deprecated — পরিচিত দুর্বলতা আছে, আধুনিক ব্রাউজার/সার্ভারে নিষ্ক্রিয় রাখা উচিত
    TLS 1.2এখনও বহুল ব্যবহৃত, নিরাপদ বিবেচিত সঠিক cipher suite-এর সাথে
    TLS 1.3সর্বশেষ স্ট্যান্ডার্ড — দ্রুত, আরও নিরাপদ, পুরনো দুর্বল cipher বাদ দেওয়া হয়েছে
    ⚠️

    Security Headers ডকুমেন্টেশনের সংযোগ: Common Web Vulnerabilities ডকুমেন্টেশনে আলোচিত Strict-Transport-Security (HSTS) header সরাসরি TLS-এর সাথে সম্পর্কিত — এটি ব্রাউজারকে বাধ্য করে সবসময় HTTPS ব্যবহার করতে, এমনকি ইউজার ভুলবশত http:// টাইপ করলেও, একটি downgrade আক্রমণ প্রতিরোধ করে।

    অনুশীলন

    কেন একটি পুরনো TLS ভার্সন (যেমন TLS 1.0) সার্ভারে সক্রিয় রাখা একটি নিরাপত্তা ঝুঁকি, এমনকি যদি বেশিরভাগ ক্লায়েন্ট TLS 1.3 ব্যবহার করে তাও?

    সারসংক্ষেপ

    TLS/SSL একটি handshake প্রক্রিয়ার মাধ্যমে ক্লায়েন্ট-সার্ভার যোগাযোগ এনক্রিপ্ট করে, CA-ইস্যু করা সার্টিফিকেট দিয়ে পরিচয় যাচাই করে। Certificate Pinning অতিরিক্ত নিরাপত্তা দেয়, এবং পুরনো TLS ভার্সন/cipher suite নিষ্ক্রিয় রাখা গুরুত্বপূর্ণ।

    DDoS ও Mitigation কৌশল

    CIA Triad-এর "Availability" অংশকে সরাসরি টার্গেট করা একটি আক্রমণ — এবং এর বিরুদ্ধে প্রতিরক্ষা।

    DoS বনাম DDoS

    1️⃣ DoS (Denial of Service)

    একটি একক উৎস থেকে একটি সার্ভার/সার্ভিসকে অতিরিক্ত request দিয়ে অকেজো করার চেষ্টা।

    🌐 DDoS (Distributed DoS)

    একই সাথে অসংখ্য (প্রায়ই হাজার হাজার, কখনো লক্ষাধিক) ভিন্ন উৎস থেকে একটি টার্গেটে আক্রমণ — প্রতিরোধ করা অনেক কঠিন, কারণ ট্রাফিক বৈধ ও ক্ষতিকর উৎসের মধ্যে পার্থক্য করা কঠিন।

    Botnet — DDoS-এর পেছনের শক্তি

    একটি বড় DDoS আক্রমণ সাধারণত একটি Botnet থেকে আসে — হাজার হাজার আপোসকৃত (malware-আক্রান্ত) ডিভাইসের একটি নেটওয়ার্ক, যা একজন attacker দূর থেকে নিয়ন্ত্রণ করেন। প্রতিটি ডিভাইস (প্রায়ই অরক্ষিত IoT ডিভাইস, Wireless Security ডকুমেন্টেশনে আলোচিত দুর্বল ডিফল্ট ক্রেডেনশিয়ালের কারণে) জানেও না যে এটি একটি আক্রমণের অংশ হিসেবে ব্যবহৃত হচ্ছে।

    DDoS আক্রমণের ধরন

    ধরনটার্গেট স্তরবর্ণনা
    Volumetric Attackনেটওয়ার্ক (স্তর ৩/৪)বিশাল পরিমাণ ট্রাফিক দিয়ে ব্যান্ডউইথ সম্পূর্ণ পূর্ণ করে ফেলা
    Protocol Attackট্রান্সপোর্ট (স্তর ৪)যেমন SYN Flood — TCP handshake অসম্পূর্ণ রেখে সার্ভার রিসোর্স শেষ করে দেওয়া
    Application-Layer Attackঅ্যাপ্লিকেশন (স্তর ৭)বৈধ-দেখতে request দিয়ে (যেমন বারবার একটি ভারী ডেটাবেজ কোয়েরি ট্রিগার করা), কম ট্রাফিকেও সার্ভার অকেজো করা

    DDoS Mitigation কৌশল

    সাধারণ প্রতিরক্ষা স্তর
    ১. Rate Limiting      — একটি নির্দিষ্ট সময়ে একটি উৎস থেকে request সংখ্যা সীমিত করা
২. Traffic Scrubbing  — একটি বিশেষায়িত সার্ভিস (CDN/cloud provider) সব ট্রাফিক
                         ফিল্টার করে, শুধু বৈধ ট্রাফিক backend-এ পাঠায়
৩. Anycast Routing    — ট্রাফিককে ভৌগোলিকভাবে বিভিন্ন ডেটা সেন্টারে ছড়িয়ে দেওয়া,
                         একক পয়েন্ট অতিরিক্ত চাপ এড়ানো
৪. Auto-Scaling       — চাহিদা বৃদ্ধি পেলে স্বয়ংক্রিয়ভাবে আরও সার্ভার রিসোর্স যোগ করা

    CDN-এর ভূমিকা

    অধ্যায় ৬-এ আলোচিত Reverse Proxy/CDN সার্ভিস (যেমন Cloudflare) DDoS Mitigation-এর একটি গুরুত্বপূর্ণ স্তর — যেহেতু সব ট্রাফিক প্রথমে CDN-এর বিশাল, বিতরণকৃত পরিকাঠামোর মধ্য দিয়ে যায়, একটি একক origin server-কে সরাসরি আক্রমণ করা অনেক কঠিন হয়ে যায়, এবং CDN নিজেই ক্ষতিকর প্যাটার্ন ফিল্টার করতে পারে।

    💡

    বাস্তব প্রস্তুতি: একটি সুপরিকল্পিত প্রতিষ্ঠান শুধু "আক্রমণ হলে কী করব" ভাবে না — তারা একটি Incident Response Plan (Hacking Tools ডকুমেন্টেশনের Forensics অধ্যায়ে আলোচিত) আগে থেকে তৈরি রাখে, যাতে একটি বড় DDoS আক্রমণের সময় দ্রুত, সংগঠিতভাবে প্রতিক্রিয়া জানানো যায়।

    অনুশীলন

    কেন একটি Application-Layer DDoS আক্রমণ, কম ট্রাফিক ভলিউম সত্ত্বেও, একটি Volumetric আক্রমণের মতোই কার্যকর হতে পারে তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    DDoS একটি Botnet ব্যবহার করে বহু উৎস থেকে একযোগে আক্রমণ চালায় — Volumetric, Protocol, ও Application-Layer এই তিন ধরনের আক্রমণ হতে পারে। Rate Limiting, Traffic Scrubbing, Anycast Routing, ও CDN ব্যবহার মূল প্রতিরোধ কৌশল।

    Network Monitoring ও SIEM

    প্রতিরক্ষা স্তরগুলো স্থাপন করাই যথেষ্ট নয় — ক্রমাগত পর্যবেক্ষণ ছাড়া একটি breach সপ্তাহ বা মাস পর্যন্ত অলক্ষিত থাকতে পারে।

    কেন Continuous Monitoring প্রয়োজন

    Firewall, IDS/IPS-এর মতো টুল (অধ্যায় ২, ৪) পৃথকভাবে ঘটনা শনাক্ত করে, কিন্তু একটি বড় নেটওয়ার্কে প্রতিদিন হাজার হাজার লগ এন্ট্রি তৈরি হয় — একজন মানুষের পক্ষে সব ম্যানুয়ালি পর্যালোচনা করা অসম্ভব। একটি কেন্দ্রীভূত মনিটরিং সিস্টেম এই বিশাল তথ্য থেকে প্রকৃত হুমকি আলাদা করতে সাহায্য করে।

    SIEM কী

    SIEM (Security Information and Event Management) একটি সিস্টেম, যা পুরো নেটওয়ার্কের বিভিন্ন উৎস (Firewall, IDS, সার্ভার, অ্যাপ্লিকেশন) থেকে লগ ডেটা কেন্দ্রীয়ভাবে সংগ্রহ করে, বিশ্লেষণ করে, এবং সন্দেহজনক প্যাটার্ন বা পারস্পরিক সম্পর্কিত ঘটনা (correlation) শনাক্ত করে সতর্ক করে।

    Log Aggregation ও Correlation

    📥 Log Aggregation

    বিভিন্ন সিস্টেমের লগ একটি কেন্দ্রীয় স্থানে একত্রিত করা — একটি সম্পূর্ণ চিত্র পেতে।

    🔗 Correlation

    বিচ্ছিন্নভাবে "স্বাভাবিক" মনে হওয়া একাধিক ঘটনা একসাথে বিশ্লেষণ করে একটি সম্পূর্ণ আক্রমণের প্যাটার্ন শনাক্ত করা — যেমন একটি failed login, তারপর একটি সফল login অস্বাভাবিক সময়ে, তারপর একটি বড় ডেটা ডাউনলোড — প্রতিটি আলাদাভাবে সন্দেহজনক নয়, কিন্তু একসাথে একটি স্পষ্ট প্যাটার্ন তৈরি করে।

    একটি SIEM Alert-এর উদাহরণ (ধারণাগত)

    ধারণাগত Correlation Rule
    IF (একই IP থেকে ৫০+ failed login, ৫ মিনিটের মধ্যে)
   AND (তারপর একটি সফল login একই IP থেকে)
THEN ALERT: "সম্ভাব্য Brute-Force Attack সফল হয়েছে"

    এই ধরনের নিয়ম Hacking Tools ডকুমেন্টেশনে আলোচিত Hydra-এর মতো brute-force টুলের আচরণ শনাক্ত করতে সাহায্য করে, এবং Authentication ডকুমেন্টেশনে আলোচিত Credential Stuffing আক্রমণের প্যাটার্নও ধরতে পারে।

    Mean Time to Detect (MTTD) ও Mean Time to Respond (MTTR)

    একটি সিকিউরিটি টিমের কার্যকারিতা প্রায়ই দুটি মেট্রিক দিয়ে পরিমাপ করা হয় — একটি হুমকি শনাক্ত হতে কত সময় লাগে (MTTD), এবং শনাক্ত হওয়ার পর তা সমাধান করতে কত সময় লাগে (MTTR)। একটি ভালো SIEM সিস্টেম উভয় মেট্রিক উল্লেখযোগ্যভাবে কমাতে সাহায্য করে।

    💡

    SOC-এর ভূমিকা: একটি বড় প্রতিষ্ঠানে, SIEM সাধারণত একটি Security Operations Center (SOC)-এর কেন্দ্রে থাকে — একটি নিবেদিত টিম, যারা ২৪/৭ SIEM alert পর্যবেক্ষণ করেন এবং Hacking Tools ডকুমেন্টেশনের Incident Response প্রক্রিয়া অনুসরণ করে প্রতিক্রিয়া জানান।

    অনুশীলন

    কেন একক, বিচ্ছিন্ন লগ এন্ট্রির চেয়ে Correlation (একাধিক ঘটনার মধ্যে সম্পর্ক) একটি আক্রমণ শনাক্ত করতে বেশি কার্যকর হতে পারে তা একটি উদাহরণ দিয়ে ব্যাখ্যা করুন।

    সারসংক্ষেপ

    SIEM বিভিন্ন উৎসের লগ কেন্দ্রীয়ভাবে সংগ্রহ ও বিশ্লেষণ করে, Correlation-এর মাধ্যমে বিচ্ছিন্ন ঘটনা থেকে একটি সম্পূর্ণ আক্রমণ প্যাটার্ন শনাক্ত করে। MTTD ও MTTR একটি সিকিউরিটি টিমের কার্যকারিতা পরিমাপ করে, এবং একটি SOC সাধারণত SIEM-কেন্দ্রিক ক্রমাগত পর্যবেক্ষণ পরিচালনা করে।

    Zero Trust Architecture

    আধুনিক নেটওয়ার্ক সিকিউরিটির একটি দৃষ্টিভঙ্গি-পরিবর্তনকারী নীতি — "কখনো বিশ্বাস করো না, সবসময় যাচাই করো"।

    ঐতিহ্যগত "Castle-and-Moat" মডেলের সমস্যা

    পুরনো নেটওয়ার্ক সিকিউরিটি দর্শন একটি দুর্গের মতো কাজ করত — একবার firewall-এর (দুর্গের দেয়াল) ভেতরে প্রবেশ করলে, একজন ইউজার/ডিভাইসকে "বিশ্বস্ত" ধরে নেওয়া হতো, এবং অভ্যন্তরীণ নেটওয়ার্কের মধ্যে তুলনামূলক মুক্তভাবে চলাফেরা করতে পারত। সমস্যা হলো — একবার attacker কোনোভাবে (phishing, একটি দুর্বল VPN ক্রেডেনশিয়াল) ভেতরে প্রবেশ করলে, তিনি প্রায় বাধাহীনভাবে পুরো নেটওয়ার্কে lateral movement করতে পারতেন।

    Zero Trust-এর মূল নীতি

    💡

    "Never Trust, Always Verify": Zero Trust Architecture-এ, নেটওয়ার্কের অবস্থান (অভ্যন্তরীণ বা বাহ্যিক) কখনোই বিশ্বাসের ভিত্তি নয় — প্রতিটি request, প্রতিটি ইউজার, প্রতিটি ডিভাইস, প্রতিবার আলাদাভাবে যাচাই করা হয়, এমনকি যদি তারা "ভেতরের" নেটওয়ার্ক থেকে আসে।

    Zero Trust-এর মূল উপাদান

    উপাদানবর্ণনা
    Identity Verificationপ্রতিটি অ্যাক্সেস অনুরোধে শক্তিশালী authentication (MFA সহ — Authentication ডকুমেন্টেশনে আলোচিত)
    Least Privilege Accessপ্রতিটি ইউজার/সিস্টেমকে শুধু ঠিক ততটুকু অ্যাক্সেস দেওয়া, যতটুকু তার কাজের জন্য প্রয়োজন — না বেশি, না কম
    Micro-segmentationঅধ্যায় ৫-এর Network Segmentation-কে আরও সূক্ষ্মভাবে প্রয়োগ করা — প্রতিটি individual রিসোর্স/অ্যাপ্লিকেশনের চারপাশে পৃথক নিরাপত্তা সীমানা
    Continuous Monitoringএকবার অনুমোদিত হলেই চিরকাল বিশ্বস্ত নয় — ক্রমাগত আচরণ পর্যবেক্ষণ করা (অধ্যায় ১১-এর SIEM-এর সাথে সরাসরি সম্পর্কিত)

    Zero Trust বনাম ঐতিহ্যগত Perimeter Security

    🏰 Perimeter Security

    একটি শক্তিশালী বাহ্যিক সীমানা (Firewall), ভেতরে তুলনামূলক মুক্ত চলাফেরা — "একবার ভেতরে, সবসময় বিশ্বস্ত"।

    🔐 Zero Trust

    কোনো একক "ভেতর/বাহির" ধারণা নেই — প্রতিটি রিসোর্সের নিজস্ব নিরাপত্তা সীমানা, প্রতিটি অ্যাক্সেস পৃথকভাবে যাচাই।

    কেন Zero Trust ক্রমবর্ধমান প্রাসঙ্গিক

    আধুনিক কর্মপরিবেশে (remote work, cloud সার্ভিস, BYOD — কর্মীদের নিজস্ব ডিভাইস ব্যবহার) একটি স্পষ্ট "নেটওয়ার্ক সীমানা" ধারণাটাই অস্পষ্ট হয়ে গেছে — একজন কর্মী বাসা থেকে, তার নিজস্ব ডিভাইস দিয়ে, একটি cloud-হোস্টেড অ্যাপ্লিকেশনে অ্যাক্সেস করতে পারেন, যেখানে কোনো একক, সুস্পষ্ট "ভেতরের নেটওয়ার্ক" নেই। Zero Trust এই বাস্তবতার জন্য ডিজাইন করা একটি আধুনিক দৃষ্টিভঙ্গি।

    অনুশীলন

    কেন "Castle-and-Moat" মডেলে, একবার একজন attacker ভেতরে প্রবেশ করলে, lateral movement তুলনামূলক সহজ হয়ে যায় তা ব্যাখ্যা করুন, এবং Zero Trust এটি কীভাবে প্রতিরোধ করে।

    সারসংক্ষেপ

    Zero Trust Architecture "Never Trust, Always Verify" নীতি অনুসরণ করে — নেটওয়ার্কের অবস্থান কখনো বিশ্বাসের ভিত্তি নয়। Identity Verification, Least Privilege Access, Micro-segmentation, ও Continuous Monitoring এর মূল উপাদান, এবং আধুনিক remote/cloud-কেন্দ্রিক কর্মপরিবেশে এটি ক্রমবর্ধমান গুরুত্বপূর্ণ।

    Network Access Control (NAC) ও 802.1X

    একটি ডিভাইস নেটওয়ার্কে সংযুক্ত হওয়ার আগেই তার পরিচয় ও স্বাস্থ্য (health) যাচাই করা।

    Network Access Control (NAC) কী

    NAC একটি নিরাপত্তা ব্যবস্থা, যা নির্ধারণ করে কোন ডিভাইস একটি নেটওয়ার্কে সংযুক্ত হতে পারবে এবং কী শর্তে — এটি শুধু "কে" (identity) নয়, বরং "কী অবস্থায়" (device posture — আপডেটেড antivirus আছে কি না, OS patch করা আছে কি না) তাও যাচাই করে।

    802.1X — Port-Based Network Access Control

    802.1X একটি স্ট্যান্ডার্ড প্রোটোকল, যা একটি ডিভাইসকে নেটওয়ার্ক পোর্টে (ফিজিক্যাল ইথারনেট পোর্ট বা Wi-Fi access point) সংযুক্ত হওয়ার আগে authentication সম্পন্ন করতে বাধ্য করে — যতক্ষণ না একটি ডিভাইস সফলভাবে যাচাই হয়, ততক্ষণ সেই পোর্ট দিয়ে কোনো সাধারণ নেটওয়ার্ক ট্রাফিক (authentication ট্রাফিক ছাড়া) যেতে দেওয়া হয় না।

    802.1X-এর তিনটি অংশ

    অংশভূমিকা
    Supplicantযে ডিভাইস নেটওয়ার্কে সংযুক্ত হতে চায় (ল্যাপটপ, ফোন)
    Authenticatorনেটওয়ার্ক ডিভাইস, যা অ্যাক্সেস নিয়ন্ত্রণ করে (সুইচ, Wi-Fi access point)
    Authentication Serverপরিচয় যাচাই করে (সাধারণত RADIUS — অধ্যায় ৮-এ আলোচিত)

    Device Posture Assessment

    আধুনিক NAC সিস্টেম শুধু "কে তুমি" প্রশ্ন করে না, বরং "তোমার ডিভাইস কতটা নিরাপদ" তাও যাচাই করে — যেমন একটি কর্পোরেট ল্যাপটপে, সংযুক্ত হওয়ার আগে, antivirus আপডেটেড কি না, disk encryption সক্রিয় কি না, বা পরিচিত malware-এর উপস্থিতি আছে কি না পরীক্ষা করা হয়। একটি "অসুস্থ" (non-compliant) ডিভাইসকে সম্পূর্ণ ব্লক করা, বা একটি সীমিত-অ্যাক্সেস "quarantine" নেটওয়ার্কে পাঠানো যেতে পারে।

    বাস্তব প্রয়োগ: একটি BYOD (Bring Your Own Device) নীতিতে, যেখানে কর্মীরা নিজস্ব ফোন/ল্যাপটপ ব্যবহার করেন, NAC প্রতিষ্ঠানকে নিশ্চিত করতে সাহায্য করে যে শুধুমাত্র নিরাপত্তা মানদণ্ড পূরণকারী ডিভাইসগুলোই সংবেদনশীল অভ্যন্তরীণ রিসোর্সে অ্যাক্সেস পাচ্ছে — এটি Zero Trust Architecture (অধ্যায় ১২)-র "Identity Verification" নীতির একটি ব্যবহারিক বাস্তবায়ন, যা ইউজার পরিচয়ের পাশাপাশি ডিভাইসের অবস্থাও বিবেচনা করে।

    Quarantine VLAN

    একটি ডিভাইস যদি NAC চেক পাস না করে, তাকে সম্পূর্ণ ব্লক না করে, প্রায়ই একটি Quarantine VLAN-এ পাঠানো হয় — যেখানে শুধুমাত্র প্রয়োজনীয় আপডেট/patch ডাউনলোড করার মতো সীমিত অ্যাক্সেস দেওয়া হয়, যতক্ষণ না ডিভাইসটি compliant হয় এবং পূর্ণ নেটওয়ার্ক অ্যাক্সেস পাওয়ার যোগ্য হয়।

    অনুশীলন

    কেন শুধু "ইউজার পরিচয়" যাচাই করা যথেষ্ট নয় — ডিভাইসের "health/posture" যাচাই করাও কেন গুরুত্বপূর্ণ তা ব্যাখ্যা করুন।

    সারসংক্ষেপ

    NAC একটি ডিভাইসের পরিচয় ও নিরাপত্তা অবস্থা উভয়ই যাচাই করে নেটওয়ার্ক অ্যাক্সেস নিয়ন্ত্রণ করে। 802.1X port-based authentication প্রয়োগ করে, এবং Quarantine VLAN অ-compliant ডিভাইসকে সীমিত অ্যাক্সেস দিয়ে আলাদা রাখে।

    Network Hardening Checklist

    এই ডকুমেন্টেশনে আলোচিত সব ধারণা একত্রিত করে, একটি বাস্তব, প্রয়োগযোগ্য checklist।

    Network Hardening কী

    Network Hardening হলো একটি নেটওয়ার্ক পরিকাঠামোর আক্রমণ-পৃষ্ঠতল (attack surface) কমিয়ে আনার প্রক্রিয়া — অপ্রয়োজনীয় সার্ভিস বন্ধ করা, ডিফল্ট সেটিংস পরিবর্তন করা, এবং এই ডকুমেন্টেশনে আলোচিত প্রতিটি নিরাপত্তা স্তর সঠিকভাবে কনফিগার করা।

    একটি সম্পূর্ণ Hardening Checklist

    ক্যাটাগরিচেকলিস্ট আইটেম

    SegmentationGuest/IoT ডিভাইস পৃথক VLAN-এ, Database সরাসরি ইন্টারনেট-অ্যাক্সেসযোগ্য নয় (অধ্যায় ৫)
    DNSDNSSEC সক্রিয়, বিশ্বস্ত DNS resolver ব্যবহার (অধ্যায় ৭)
    WirelessWPA3/WPA2-Enterprise, default SSID/password পরিবর্তিত (অধ্যায় ৮)
    TLSপুরনো TLS ভার্সন নিষ্ক্রিয়, শুধু TLS 1.2+ সমর্থিত (অধ্যায় ৯)

    🔄 একবারের কাজ নয়

    Network Hardening একবার করে ভুলে যাওয়ার মতো কাজ নয় — নতুন ডিভাইস যোগ হয়, নতুন দুর্বলতা আবিষ্কৃত হয়, তাই নিয়মিত পুনর্মূল্যায়ন প্রয়োজন।

    📋 Audit ও Compliance

    নিয়মিত নিরাপত্তা অডিট (অধ্যায় ৫-এ আলোচিত vulnerability scanner-এর মতো টুল দিয়ে) hardening checklist প্রকৃতপক্ষে মেনে চলা হচ্ছে কি না যাচাই করে।

    Network Hardening-এর সাথে এই সিরিজের অন্যান্য ডকুমেন্টেশনের সংযোগ

    একটি শক্তিশালী নেটওয়ার্ক পরিকাঠামো (এই ডকুমেন্টেশন), একটি সুরক্ষিত অ্যাপ্লিকেশন কোড (Common Web Vulnerabilities, XSS, CSRF, SQLi ডকুমেন্টেশন), ও সচেতন ইউজার আচরণ (Social Engineering, Hacking Tools ডকুমেন্টেশন) — এই তিনটি একসাথে একটি সম্পূর্ণ নিরাপত্তা কৌশল তৈরি করে। শুধু একটি স্তর নিখুঁত হলেই একটি প্রতিষ্ঠান নিরাপদ নয়।

    ⚠️

    সাধারণ ভুল: একটি প্রতিষ্ঠান প্রায়ই সব বাজেট একটি নির্দিষ্ট টুলে (যেমন একটি দামি Next-Generation Firewall) ব্যয় করে, কিন্তু মৌলিক hardening (যেমন default password পরিবর্তন করা, বা নিয়মিত patch management) অবহেলা করে — একটি ব্যয়বহুল টুল একটি মৌলিক hardening ফাঁকের ঘাটতি পূরণ করতে পারে না।

    এই checklist ব্যবহার করে, একটি কাল্পনিক ছোট অফিস নেটওয়ার্কের জন্য একটি সংক্ষিপ্ত hardening পরিকল্পনা তৈরি করুন — কোন তিনটি আইটেম আপনি সবার আগে প্রয়োগ করবেন এবং কেন?

    প্রায়শই জিজ্ঞাসিত প্রশ্ন (FAQ)

    একটি ছোট প্রতিষ্ঠান কোথা থেকে শুরু করবে?

    সবচেয়ে basic কিন্তু গুরুত্বপূর্ণ ধাপগুলো দিয়ে শুরু করা ভালো — একটি সঠিকভাবে কনফিগার করা Firewall (Deny by Default), নিয়মিত patch management, এবং Guest/IoT ডিভাইসের জন্য আলাদা VLAN। এরপর ধাপে ধাপে IDS/IPS, SIEM-এর মতো আরও উন্নত স্তর যোগ করা যায়।

    Zero Trust কি সব প্রতিষ্ঠানের জন্য প্রয়োজনীয়?

    Zero Trust একটি দর্শন/আর্কিটেকচার, রাতারাতি বাস্তবায়নযোগ্য কোনো একক প্রোডাক্ট নয় — ছোট প্রতিষ্ঠানগুলো ধীরে ধীরে এর নীতিগুলো (MFA, Least Privilege) প্রয়োগ শুরু করতে পারে, সম্পূর্ণ আর্কিটেকচার পরিবর্তনের চাপ না নিয়ে।

    এই ডকুমেন্টেশন পড়ার পর পরবর্তী ধাপ কী?

    এই সিরিজের Hacking Tools ডকুমেন্টেশনে Nmap/Wireshark-এর মতো টুল হাতে-কলমে প্র্যাকটিস করে, এই ডকুমেন্টেশনে আলোচিত defensive ধারণাগুলো আরও গভীরভাবে বোঝা যায় — attacker ও defender উভয় দৃষ্টিভঙ্গি একসাথে শেখা সবচেয়ে কার্যকর।

    এই ডকুমেন্টেশন সিরিজের সম্পূর্ণ চিত্র

    এই "Network Security" ডকুমেন্টেশন এই সিরিজে একটি নতুন স্তর যোগ করে — আগের ডকুমেন্টেশনগুলো (XSS, CSRF, SQLi, Common Web Vulnerabilities, API Security) অ্যাপ্লিকেশন-লেয়ার নিরাপত্তা নিয়ে, আর এটি নেটওয়ার্ক-লেয়ার নিরাপত্তা নিয়ে আলোচনা করে। একসাথে, এই ডকুমেন্টেশনগুলো একটি প্রতিষ্ঠানের সম্পূর্ণ নিরাপত্তা স্ট্যাকের একটি পূর্ণাঙ্গ চিত্র দেয়।

    💡

    চূড়ান্ত পরামর্শ: নেটওয়ার্ক নিরাপত্তা কোনো একক টুল বা একক সমাধান নয় — Defense in Depth নীতি অনুযায়ী, একাধিক স্তরের (Firewall, Segmentation, Monitoring, Access Control) সমন্বিত প্রয়োগই দীর্ঘমেয়াদে সবচেয়ে কার্যকর সুরক্ষা দেয়।

    সম্পূর্ণ ডকুমেন্টেশনের সারসংক্ষেপ

    একটি সুরক্ষিত নেটওয়ার্ক পরিকাঠামো তৈরি হয় Firewall ও VPN দিয়ে সীমানা নিয়ন্ত্রণ করে, IDS/IPS দিয়ে হুমকি শনাক্ত করে, Segmentation দিয়ে ক্ষতি সীমিত রেখে, DNS/TLS Security দিয়ে ডেটা সুরক্ষিত রেখে, DDoS Mitigation দিয়ে প্রাপ্যতা নিশ্চিত করে, SIEM দিয়ে ক্রমাগত পর্যবেক্ষণ করে, এবং Zero Trust/NAC দিয়ে প্রতিটি অ্যাক্সেস যাচাই করে — এই সবগুলো একসাথে একটি সম্পূর্ণ Defense in Depth কৌশল গঠন করে।
