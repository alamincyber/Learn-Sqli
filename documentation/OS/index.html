    অপারেটিং সিস্টেম ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Basic থেকে Advanced পর্যন্ত Operating System শেখার গাইড — Linux, Windows ও macOS কীভাবে কাজ করে, ফাইল সিস্টেম, পারমিশন, প্রসেস ম্যানেজমেন্ট, কমান্ড লাইন থেকে ভার্চুয়ালাইজেশন ও সিকিউরিটি ওভারভিউ পর্যন্ত, ১৫টি অধ্যায়ে সাজানো।

    অপারেটিং সিস্টেম নিয়ে সংক্ষিপ্ত কথা

    আপনার কম্পিউটার, ফোন, সার্ভার — প্রতিটি ডিভাইসে হার্ডওয়্যার ও আপনার চালানো অ্যাপ্লিকেশনের মাঝখানে একটি অদৃশ্য স্তর কাজ করে, যাকে বলে অপারেটিং সিস্টেম (OS)। এটি নির্ধারণ করে কীভাবে CPU, মেমরি, ডিস্ক, নেটওয়ার্ক ব্যবহৃত হবে, কোন প্রোগ্রাম কখন চলবে, এবং কে কোন ফাইল পড়তে/লিখতে পারবে। একজন ডেভেলপার বা সিকিউরিটি পেশাদারের জন্য OS কীভাবে কাজ করে তা বোঝা অপরিহার্য — কারণ বেশিরভাগ গুরুতর সিকিউরিটি ঘটনা (privilege escalation, malware persistence, misconfiguration) শেষমেশ OS-স্তরের কোনো না কোনো ধারণার সাথে যুক্ত।

    এই ডকুমেন্টেশনে ধাপে ধাপে দেখানো হয়েছে — OS-এর মূল উপাদান (kernel, shell, process, file system), Linux-এর আর্কিটেকচার ও ফাইল সিস্টেম, Linux permission ও ইউজার ম্যানেজমেন্ট, Linux প্রসেস ও সার্ভিস, Windows-এর আর্কিটেকচার, ফাইল সিস্টেম (NTFS) ও রেজিস্ট্রি, Windows ইউজার অ্যাকাউন্ট ও পারমিশন, macOS/Unix-based সিস্টেম ওভারভিউ, নেটওয়ার্কিং বেসিক, OS সিকিউরিটি ওভারভিউ, কমন কমান্ড লাইন টুলস, এবং ভার্চুয়ালাইজেশন/কনটেইনার-এর মৌলিক ধারণা।

    💡

    কেন এই ডকুমেন্টেশন গুরুত্বপূর্ণ: এটি একটি foundational ডকুমেন্টেশন — এখানে কোনো আক্রমণ-কৌশল শেখানো হয়নি। বরং এটি learn.alamincyber.com-এর অন্যান্য সিকিউরিটি ডকুমেন্টেশনগুলোর (API Security, Authentication/Authorization, এবং ভবিষ্যতের OS-নির্দিষ্ট সিকিউরিটি কন্টেন্ট) পূর্বশর্ত (prerequisite) — কারণ OS কীভাবে প্রসেস, ফাইল ও ইউজার পরিচালনা করে তা না জানলে, কোনো সিস্টেমের দুর্বলতা বা hardening কৌশল বোঝা সম্ভব নয়।

    অপারেটিং সিস্টেম কী

    একটি অপারেটিং সিস্টেম (OS) হলো একটি সফটওয়্যার, যা কম্পিউটারের হার্ডওয়্যার (CPU, RAM, ডিস্ক, নেটওয়ার্ক কার্ড) পরিচালনা করে এবং অন্য সব অ্যাপ্লিকেশনকে (ব্রাউজার, গেম, টেক্সট এডিটর) সেই হার্ডওয়্যার ব্যবহারের একটি নিরাপদ, সংগঠিত উপায় দেয়। OS ছাড়া প্রতিটি অ্যাপ্লিকেশনকে নিজে থেকে সরাসরি হার্ডওয়্যারের সাথে কথা বলতে হতো — যা অবাস্তব জটিল ও অনিরাপদ হতো।

    OS-এর মূল দায়িত্ব

    ⚙️ Resource Management

    CPU সময়, মেমরি, ডিস্ক স্পেস — কোন প্রোগ্রাম কতটুকু ও কখন ব্যবহার করবে তা নিয়ন্ত্রণ করে, যাতে একাধিক প্রোগ্রাম একসাথে চললেও একে অপরের সাথে সংঘর্ষ না হয়।

    🔐 Abstraction ও নিরাপত্তা

    প্রতিটি অ্যাপ্লিকেশনকে হার্ডওয়্যারের জটিল বিবরণ না জানিয়ে, একটি সহজ interface (file, process, network socket) দেয়, এবং একটি প্রোগ্রামকে অন্য প্রোগ্রামের মেমরি/ডেটা থেকে আলাদা রাখে (isolation)।

    📁 File ও Data ব্যবস্থাপনা

    ডেটা কীভাবে ডিস্কে সংরক্ষিত, সংগঠিত ও অ্যাক্সেস করা হয় তা নিয়ন্ত্রণ করে (file system)।

    👥 User ও Permission ব্যবস্থাপনা

    একাধিক ইউজার/প্রোগ্রাম থাকলে, কে কী করতে পারবে তা নিয়ন্ত্রণ করে — এটিই OS-স্তরের authorization-এর ভিত্তি।

    OS ছাড়া একটি কম্পিউটার কল্পনা করুন

    OS ছাড়া, "একটি ফাইল সেভ করা" মানে সরাসরি ডিস্কের নির্দিষ্ট sector-এ bit লেখার নির্দেশ পাঠানো; "একটি প্রোগ্রাম চালানো" মানে CPU-কে সরাসরি instruction address বলে দেওয়া। OS এই সব জটিলতা মুছে দিয়ে আমাদের দেয় সহজ ধারণা — ফাইল, ফোল্ডার, প্রোগ্রাম, উইন্ডো — যা দিয়ে আমরা কম্পিউটার ব্যবহার করি।

    কেন সিকিউরিটিতে OS জ্ঞান গুরুত্বপূর্ণ: প্রায় প্রতিটি সাইবার আক্রমণের শেষ লক্ষ্য হলো কোনো না কোনোভাবে OS-স্তরে অ্যাক্সেস পাওয়া — একটি ফাইল পড়া, একটি প্রসেস চালানো, বা privilege বাড়ানো (privilege escalation)। OS কীভাবে কাজ করে তা না জানলে, এই আক্রমণগুলো কীভাবে কাজ করে এবং কীভাবে প্রতিরোধ করতে হয় তা বোঝা সম্ভব নয়।

    অনুশীলন

    আপনার নিজের কম্পিউটার বা ফোনে কোন অপারেটিং সিস্টেম চলছে তা শনাক্ত করুন, এবং সেটি কোন "পরিবার"-এর (Windows/Unix-like/mobile) অন্তর্ভুক্ত তা লিখুন।

    সারসংক্ষেপ

    OS হলো হার্ডওয়্যার ও অ্যাপ্লিকেশনের মধ্যবর্তী একটি স্তর, যা resource management, abstraction, নিরাপত্তা, file ও user ব্যবস্থাপনার দায়িত্ব পালন করে। Windows, Unix-like (Linux/macOS), ও mobile OS — প্রধান তিনটি পরিবার, যাদের মধ্যে Unix-ভিত্তিক সিস্টেমগুলো অনেক মৌলিক ধারণা শেয়ার করে।

    OS-এর মূল উপাদান

    Kernel, Shell, Process, File System — এই চারটি ধারণা যেকোনো অপারেটিং সিস্টেম বোঝার ভিত্তি।

    Kernel — OS-এর কেন্দ্র

    Kernel হলো OS-এর সবচেয়ে গভীর, সবচেয়ে বিশেষাধিকারপ্রাপ্ত অংশ, যা সরাসরি হার্ডওয়্যারের সাথে যোগাযোগ করে। এটি CPU scheduling, মেমরি ব্যবস্থাপনা, ডিভাইস ড্রাইভার, এবং প্রসেসের মধ্যে যোগাযোগ নিয়ন্ত্রণ করে। সাধারণ অ্যাপ্লিকেশন সরাসরি kernel-এর সাথে কথা বলে না — বরং একটি নিয়ন্ত্রিত interface, system call ব্যবহার করে।

    User Space

    সাধারণ অ্যাপ্লিকেশন (ব্রাউজার, টেক্সট এডিটর) এখানে চলে, সীমিত অনুমতি নিয়ে — একটি ক্র্যাশ হলেও পুরো সিস্টেম প্রভাবিত হয় না।

    Kernel Space

    সর্বোচ্চ privilege-এ চলে, হার্ডওয়্যারের সরাসরি অ্যাক্সেস আছে — এখানে একটি bug/vulnerability পুরো সিস্টেমকে প্রভাবিত করতে পারে।

    Shell — ইউজার ও Kernel-এর মধ্যে সেতু

    Shell একটি প্রোগ্রাম, যা ইউজারের কমান্ড গ্রহণ করে এবং সেগুলো kernel-এর কাছে translate করে পাঠায়। Linux-এ bash, zsh, fish জনপ্রিয় shell; Windows-এ cmd.exe ও PowerShell। একটি GUI (Graphical User Interface) মূলত shell-এর একটি visual রূপ — মাউস ক্লিক ও আইকনের পেছনেও একই ধরনের system call ঘটে।

    Process — চলমান প্রোগ্রাম

    একটি প্রোগ্রাম (যেমন ডিস্কে থাকা একটি .exe ফাইল) যখন চালানো হয়, OS এর জন্য মেমরিতে একটি process তৈরি করে — যার নিজস্ব মেমরি স্পেস, একটি unique Process ID (PID), এবং execution state থাকে। একাধিক process একসাথে চলতে পারে (multitasking), এবং OS-এর scheduler দ্রুত পালাক্রমে প্রতিটি process-কে অল্প সময়ের জন্য CPU দেয়, যা মানুষের কাছে "একসাথে চলছে" বলে মনে হয়।

    ধারণাব্যাখ্যা
    PID (Process ID)প্রতিটি process-এর unique সংখ্যাসূচক পরিচয়
    Threadএকটি process-এর ভেতরে একাধিক সমান্তরাল কাজের ধারা, মেমরি শেয়ার করে
    Parent/Child Processএকটি process অন্য একটি নতুন process তৈরি করলে (fork/spawn), সেটি হয় child, মূলটি parent
    Zombie/Orphan ProcessParent শেষ হয়ে গেলেও child process-এর তথ্য সিস্টেমে রয়ে যাওয়া (zombie), বা parent ছাড়া child চলতে থাকা (orphan)

    File System — ডেটা সংগঠনের নিয়ম

    File System নির্ধারণ করে ডিস্কে ডেটা কীভাবে সংরক্ষিত, নামকরণ ও সংগঠিত হবে — ফোল্ডার/ডিরেক্টরি গঠন, ফাইল metadata (তৈরি হওয়ার তারিখ, মালিক, পারমিশন), এবং ডেটা দ্রুত খুঁজে পাওয়ার পদ্ধতি। বিভিন্ন OS ভিন্ন file system ব্যবহার করে — Linux-এ ext4, Windows-এ NTFS, macOS-এ APFS — পরবর্তী অধ্যায়গুলোতে এগুলো বিস্তারিত আলোচিত হবে।

    এই চারটি উপাদান একসাথে কীভাবে কাজ করে

    একটি সহজ উদাহরণ — "একটি ফাইল খোলা"
    1. ইউজার টার্মিনালে টাইপ করেন: cat notes.txt
2. Shell কমান্ডটি পড়ে, "cat" প্রোগ্রাম চালানোর জন্য kernel-কে বলে
3. Kernel একটি নতুন Process তৈরি করে "cat" প্রোগ্রামের জন্য
4. সেই process একটি system call পাঠায়: "notes.txt ফাইলটি খুলুন"
5. Kernel File System-এর মাধ্যমে ডিস্ক থেকে ফাইলের ডেটা খুঁজে পড়ে
6. ডেটা ফেরত আসে, terminal-এ প্রদর্শিত হয়

    সারসংক্ষেপ

    Kernel হার্ডওয়্যার নিয়ন্ত্রণ করে সর্বোচ্চ privilege-এ, Shell ইউজার কমান্ড গ্রহণ করে, Process একটি চলমান প্রোগ্রামের instance, এবং File System ডেটা সংগঠিত রাখে। এই চারটি উপাদান একসাথে মিলে একটি সম্পূর্ণ অপারেটিং সিস্টেম অভিজ্ঞতা তৈরি করে।

    Linux কী

    Linux একটি kernel — ১৯৯১ সালে Linus Torvalds দ্বারা তৈরি, ওপেন-সোর্স। "Linux" বলতে সাধারণত একে GNU টুলস ও অন্যান্য সফটওয়্যারের সাথে মিলিয়ে তৈরি একটি সম্পূর্ণ OS ("distribution" বা "distro") বোঝানো হয় — Ubuntu, Debian, Fedora, Arch, CentOS/Rocky Linux এই রকম বিভিন্ন distro।

    কেন Linux সার্ভার/ক্লাউডে এত জনপ্রিয়

    🆓 Open Source ও ফ্রি

    Linux ফাইল সিস্টেম ও ডিরেক্টরি স্ট্রাকচার

    Linux-এর সুপরিচিত root (/) থেকে শুরু হওয়া একক ডিরেক্টরি গাছ, এবং এর গুরুত্বপূর্ণ ফোল্ডারগুলোর ভূমিকা।

    একক Root — Windows-এর মতো একাধিক Drive Letter নেই

    Windows-এ আমরা C:\, D:\-এর মতো আলাদা drive letter দেখি, কিন্তু Linux-এ সবকিছু একটি একক গাছের (tree) অংশ, যার শুরু / (root) দিয়ে। একটি আলাদা হার্ড ডিস্ক বা USB drive-ও এই একই গাছের একটি নির্দিষ্ট ফোল্ডারে "mount" করা হয়, আলাদা drive letter হিসেবে নয়।

    গুরুত্বপূর্ণ টপ-লেভেল ডিরেক্টরি

    ডিরেক্টরিকী থাকে
    /bin, /usr/binমৌলিক ও ইউজার কমান্ড প্রোগ্রাম (ls, cp, bash)
    /etcসিস্টেম-ব্যাপী কনফিগারেশন ফাইল (text-based)
    /homeপ্রতিটি সাধারণ ইউজারের ব্যক্তিগত ফোল্ডার (/home/rahim)
    /rootশুধুমাত্র root (super user)-এর হোম ডিরেক্টরি
    /varপরিবর্তনশীল ডেটা — লগ ফাইল (/var/log), ডেটাবেজ, ক্যাশ
    /tmpঅস্থায়ী ফাইল, সাধারণত reboot-এ মুছে যায়
    /devডিভাইস ফাইল (হার্ড ডিস্ক, USB — "everything is a file" নীতির প্রতিফলন)
    /procএকটি virtual file system, যা চলমান process ও kernel তথ্য real-time দেখায়
    /optঐচ্ছিক, তৃতীয়-পক্ষের সফটওয়্যার প্যাকেজ

    Absolute বনাম Relative পাথ

    Absolute Path

    /home/rahim/documents/notes.txt — সবসময় root (/) থেকে শুরু হয়, আপনি যেখানেই থাকুন না কেন একই জায়গা নির্দেশ করে।

    Relative Path

    documents/notes.txt — বর্তমান অবস্থান (current working directory)-এর সাপেক্ষে, . (বর্তমান) ও .. (এক স্তর উপরে) ব্যবহার করে।

    Hidden ফাইল ও কনফিগারেশন

    নাম যদি ডট (.) দিয়ে শুরু হয়, সেটি Linux-এ একটি hidden file, সাধারণ ls কমান্ডে দেখা যায় না (ls -a দরকার)। প্রায় সব ইউজার-নির্দিষ্ট কনফিগারেশন ফাইল এভাবে লুকানো থাকে, যেমন ~/.bashrc, ~/.ssh/।

    ফাইল সিস্টেম নেভিগেশন — মৌলিক কমান্ড
    pwd              # বর্তমান ডিরেক্টরির পাথ দেখায়
ls -la           # hidden ফাইলসহ বিস্তারিত তালিকা
cd /var/log      # নির্দিষ্ট ডিরেক্টরিতে যাওয়া
cd ~             # নিজের হোম ডিরেক্টরিতে ফেরা
cd ..            # এক স্তর উপরে যাওয়া

    Linux-এ ব্যবহৃত File System ফরম্যাট

    ডিরেক্টরি স্ট্রাকচার (উপরে যা আলোচিত হলো) এক জিনিস, আর ডিস্কে ডেটা কীভাবে সংরক্ষিত হয় (file system format) আরেকটি — ext4 বর্তমানে সবচেয়ে বহুল ব্যবহৃত Linux file system format, যা journaling সমর্থন করে (হঠাৎ পাওয়ার-অফ হলেও ডেটা করাপশনের ঝুঁকি কমায়)। নতুন বিকল্প হিসেবে Btrfs ও XFS-ও জনপ্রিয়।

    সারসংক্ষেপ

    Linux পারমিশন ও ইউজার ম্যানেজমেন্ট

    Linux-এর বিখ্যাত read/write/execute পারমিশন মডেল, এবং root ও সাধারণ ইউজারের মধ্যে পার্থক্য।

    Linux-এ ইউজারের ধরন

    👑 root (Super User)

    সর্বোচ্চ privilege, সিস্টেমের যেকোনো ফাইল/সেটিং পরিবর্তন করতে পারে। দৈনন্দিন কাজে সরাসরি root হিসেবে কাজ করা অত্যন্ত ঝুঁকিপূর্ণ (একটি ভুল কমান্ডও পুরো সিস্টেম নষ্ট করতে পারে)।

    👤 সাধারণ ইউজার

    সীমিত permission — নিজের হোম ডিরেক্টরি ও স্পষ্টভাবে অনুমোদিত জায়গায় কাজ করতে পারে।

    ⚙️ System/Service ইউজার

    কোনো ব্যক্তি নয় — একটি নির্দিষ্ট সার্ভিস (যেমন www-data ওয়েব সার্ভারের জন্য) চালানোর জন্য তৈরি, যাতে সেই সার্ভিস compromise হলেও ক্ষতির পরিধি সীমিত থাকে।

    Read, Write, Execute — তিনটি মৌলিক পারমিশন

    ls -l আউটপুট ব্যাখ্যা
    -rwxr-xr-- 1 rahim developers 1024 Nov 5 10:00 script.sh

[-][rwx][r-x][r--]
 │    │    │    │
 │    │    │    └── Others (সবার জন্য): r-- (শুধু read)
 │    │    └──────── Group "developers"-এর জন্য: r-x (read + execute)
 │    └───────────── Owner "rahim"-এর জন্য: rwx (read + write + execute)
 └────────────────── ফাইলের ধরন (- = সাধারণ ফাইল, d = ডিরেক্টরি)
    পারমিশনফাইলে অর্থডিরেক্টরিতে অর্থ
    r (read)ফাইলের বিষয়বস্তু পড়া যাবেডিরেক্টরির ভেতরের তালিকা দেখা যাবে
    w (write)ফাইল পরিবর্তন/মোছা যাবেডিরেক্টরিতে নতুন ফাইল তৈরি/মোছা যাবে
    x (execute)ফাইলটি প্রোগ্রাম/স্ক্রিপ্ট হিসেবে চালানো যাবেডিরেক্টরিতে প্রবেশ (cd) করা যাবে

    chmod — পারমিশন পরিবর্তন

    chmod — উদাহরণ
    # Symbolic পদ্ধতি
chmod u+x script.sh       # owner-কে execute পারমিশন যোগ করা
chmod g-w report.txt      # group থেকে write পারমিশন সরানো

# Numeric (octal) পদ্ধতি — rwx = 4+2+1
chmod 755 script.sh       # owner: rwx(7), group: r-x(5), others: r-x(5)
chmod 644 report.txt      # owner: rw-(6), group: r--(4), others: r--(4)

    chown ও sudo

    chown দিয়ে ফাইলের owner/group পরিবর্তন করা যায় (যেমন chown rahim:developers file.txt)। sudo ("superuser do") একজন সাধারণ ইউজারকে সাময়িকভাবে, নির্দিষ্ট কমান্ডের জন্য root privilege ব্যবহার করতে দেয় — এটি সরাসরি root হিসেবে লগইন করার চেয়ে অনেক নিরাপদ, কারণ প্রতিটি sudo ব্যবহার লগ হয় এবং শুধু নির্দিষ্ট কমান্ডে প্রযোজ্য।

    ⚠️

    বিপজ্জনক প্যাটার্ন: chmod 777 (সবাইকে সব পারমিশন) ব্যবহার করা একটি অত্যন্ত সাধারণ কিন্তু বিপজ্জনক "ঠিক করার" অভ্যাস — এটি Least Privilege নীতির সরাসরি বিপরীত, এবং যেকোনো ইউজার/প্রসেস সেই ফাইল পড়তে, লিখতে ও চালাতে পারবে। সবসময় সর্বনিম্ন প্রয়োজনীয় পারমিশন দিন।

    /etc/passwd ও /etc/shadow

    Linux-এ ইউজারের তথ্য (username, UID, হোম ডিরেক্টরি) সংরক্ষিত থাকে /etc/passwd-এ (সবাই পড়তে পারে), কিন্তু প্রকৃত পাসওয়ার্ড হ্যাশ থাকে /etc/shadow-এ, যা শুধুমাত্র root পড়তে পারে — এই বিভাজন একটি গুরুত্বপূর্ণ নিরাপত্তা ডিজাইন সিদ্ধান্ত।

    অনুশীলন

    chmod 640 secret.txt চালানোর পর owner, group ও others-এর ঠিক কী কী পারমিশন থাকবে তা বের করুন।

    সারসংক্ষেপ

    Linux-এ প্রতিটি ফাইলের owner, group ও others-এর জন্য আলাদা read/write/execute পারমিশন থাকে, যা chmod/chown দিয়ে নিয়ন্ত্রিত হয়। sudo নিয়ন্ত্রিতভাবে সাময়িক root privilege দেয়, এবং chmod 777-এর মতো overly-permissive সেটিং এড়িয়ে চলা একটি মৌলিক নিরাপত্তা অভ্যাস।

    2. sudo সরাসরি root হিসেবে লগইন করার চেয়ে কেন বেশি নিরাপদ?
    3. পাসওয়ার্ড হ্যাশ /etc/passwd-এর বদলে /etc/shadow-এ রাখা হয় কেন?

    Linux প্রসেস ও সার্ভিস ম্যানেজমেন্ট

    একটি Linux সিস্টেমে কী কী চলছে তা কীভাবে দেখবেন, নিয়ন্ত্রণ করবেন, এবং ব্যাকগ্রাউন্ড সার্ভিস কীভাবে পরিচালিত হয়।

    চলমান প্রসেস দেখা

    প্রসেস পর্যবেক্ষণ কমান্ড
    ps aux           # সব চলমান প্রসেসের তালিকা (স্ন্যাপশট)
top              # রিয়েল-টাইম, ইন্টারেক্টিভ প্রসেস মনিটর
htop             # top-এর আরও সুন্দর, রঙিন বিকল্প (আলাদা ইনস্টল প্রয়োজন)
pgrep nginx      # নাম দিয়ে নির্দিষ্ট প্রসেস খোঁজা

    প্রসেসকে সিগন্যাল পাঠানো

    একটি চলমান প্রসেসকে নিয়ন্ত্রণ করতে, OS তাকে signal পাঠায়। সবচেয়ে পরিচিত কমান্ড kill (নাম সত্ত্বেও এটি শুধু "বন্ধ করা" নয়, যেকোনো signal পাঠাতে পারে)।

    Signalনম্বরঅর্থ
    SIGTERM15Graceful shutdown request — প্রসেসকে নিজের কাজ গুছিয়ে বন্ধ হওয়ার সুযোগ দেয় (ডিফল্ট)
    SIGKILL9অবিলম্বে, বাধ্যতামূলক বন্ধ — প্রসেস কোনো "cleanup" করার সুযোগ পায় না
    SIGHUP1অনেক সার্ভিসে এটি "নিজেকে রিলোড করো" হিসেবে ব্যবহৃত হয়
    SIGSTOP / SIGCONT19 / 18প্রসেসকে সাময়িকভাবে স্থগিত/পুনরায় চালু করা
    kill কমান্ড — উদাহরণ
    kill 4521            # PID 4521-কে SIGTERM পাঠানো (graceful)
kill -9 4521         # PID 4521-কে SIGKILL পাঠানো (বাধ্যতামূলক)
killall nginx        # নাম দিয়ে সব nginx প্রসেস বন্ধ করা

    systemd — আধুনিক Linux-এর Service Manager

    বেশিরভাগ আধুনিক Linux distro (Ubuntu, Fedora, Debian) ব্যাকগ্রাউন্ড সার্ভিস (যেমন ওয়েব সার্ভার, ডেটাবেজ) পরিচালনার জন্য systemd ব্যবহার করে — এটি বুট-টাইমে সার্ভিস শুরু করা, crash হলে পুনরায় চালু করা, এবং dependency অনুযায়ী সঠিক ক্রমে সার্ভিস চালু করার দায়িত্ব নেয়।

    systemctl — সার্ভিস নিয়ন্ত্রণ
    sudo systemctl status nginx      # সার্ভিসের বর্তমান অবস্থা দেখা
sudo systemctl start nginx       # সার্ভিস চালু করা
sudo systemctl stop nginx        # সার্ভিস বন্ধ করা
sudo systemctl restart nginx     # সার্ভিস পুনরায় চালু করা
sudo systemctl enable nginx      # বুটের সময় স্বয়ংক্রিয়ভাবে চালু হবে

    Foreground বনাম Background প্রসেস

    Terminal-এ একটি কমান্ড স্বাভাবিকভাবে foreground-এ চলে (terminal দখল করে রাখে)। কমান্ডের শেষে & যোগ করলে এটি background-এ চলে, এবং terminal তখনই নতুন কমান্ডের জন্য মুক্ত থাকে। nohup দিয়ে একটি প্রসেসকে terminal বন্ধ হওয়ার পরেও চলতে দেওয়া যায়।

    💡

    সিকিউরিটিতে প্রাসঙ্গিকতা: একটি malware/backdoor প্রায়ই নিজেকে একটি systemd service হিসেবে persist করে, যাতে সিস্টেম রিবুট হলেও এটি স্বয়ংক্রিয়ভাবে আবার চালু হয়ে যায়। সন্দেহজনক, অপরিচিত সার্ভিস (systemctl list-units --type=service দিয়ে তালিকা দেখা যায়) নিয়মিত পর্যালোচনা করা একটি গুরুত্বপূর্ণ security hygiene অভ্যাস।

    অনুশীলন

    একটি প্রসেস SIGTERM-এ সাড়া দিচ্ছে না (বন্ধ হচ্ছে না)। পরবর্তী ধাপে আপনি কোন signal ব্যবহার করবেন, এবং এই দুই ধরনের signal-এর আচরণগত পার্থক্য কী?

    সারসংক্ষেপ

    ps/top দিয়ে প্রসেস পর্যবেক্ষণ করা যায়, kill দিয়ে signal পাঠানো যায় (SIGTERM graceful, SIGKILL বাধ্যতামূলক)। systemd আধুনিক Linux-এ ব্যাকগ্রাউন্ড সার্ভিস পরিচালনা করে — বুট-টাইম স্টার্টআপ, crash recovery, এবং dependency management-সহ।

    Windows — ভিত্তি ও আর্কিটেকচার

    বিশ্বের সবচেয়ে বেশি ব্যবহৃত ডেস্কটপ অপারেটিং সিস্টেম — এর আর্কিটেকচার, GUI-কেন্দ্রিক ডিজাইন দর্শন, ও এন্টারপ্রাইজে ব্যবহার।

    Windows কী

    Microsoft Windows একটি proprietary (closed-source) অপারেটিং সিস্টেম, যা ১৯৮৫ সাল থেকে ক্রমাগত বিকশিত হয়ে আজকের Windows 11/Windows Server পর্যন্ত পৌঁছেছে। এটি ব্যক্তিগত কম্পিউটার, অফিস ওয়ার্কস্টেশন ও এন্টারপ্রাইজ সার্ভারে সবচেয়ে বেশি ব্যবহৃত ডেস্কটপ OS, এবং এর ডিজাইন দর্শন মূলত GUI-কেন্দ্রিক ও ব্যবহারকারী-বান্ধবতার উপর ভিত্তি করে তৈরি (Linux-এর কমান্ড লাইন-কেন্দ্রিক দর্শনের বিপরীতে)।

    Windows আর্কিটেকচারের স্তর

    Windows আর্কিটেকচার — স্তরবিন্যাস (সরলীকৃত)
    ┌─────────────────────────────────┐
│   অ্যাপ্লিকেশন (Excel, Chrome)    │  ← User Mode
├─────────────────────────────────┤
│   Win32 API / Subsystems         │
├─────────────────────────────────┤
│   Windows Executive               │  ← Kernel Mode
│   (Process Manager, I/O Manager) │
├─────────────────────────────────┤
│   HAL (Hardware Abstraction Layer)│
├─────────────────────────────────┤
│   হার্ডওয়্যার (CPU, RAM, Disk)    │
└─────────────────────────────────┘

    Linux-এর "User Space/Kernel Space"-এর মতোই, Windows-এ এই বিভাজনকে বলা হয় User Mode ও Kernel Mode — একই মৌলিক নীতি, ভিন্ন পরিভাষা। HAL (Hardware Abstraction Layer) Windows-কে বিভিন্ন হার্ডওয়্যার কনফিগারেশনের উপর একইভাবে চলতে সাহায্য করে।

    Windows Serverসার্ভার পরিবেশ — Active Directory, file/print sharing, hosting

    GUI-কেন্দ্রিক, কিন্তু Command Line-ও আছে

    Windows ঐতিহ্যগতভাবে GUI-নির্ভর হলেও, এর নিজস্ব শক্তিশালী কমান্ড লাইন টুলস আছে — পুরনো cmd.exe (Command Prompt) ও আধুনিক PowerShell, যা অবজেক্ট-ভিত্তিক scripting ভাষা হিসেবে অনেক বেশি শক্তিশালী ও Linux-এর shell-এর অনেক ক্ষমতার সমতুল্য বা কিছু ক্ষেত্রে বেশি flexible।

    Active Directory — এন্টারপ্রাইজ Windows-এর মেরুদণ্ড

    বড় প্রতিষ্ঠানে একাধিক Windows কম্পিউটার কেন্দ্রীয়ভাবে পরিচালনা করতে Active Directory (AD) ব্যবহৃত হয় — এটি ইউজার অ্যাকাউন্ট, গ্রুপ, পারমিশন ও নীতি (policy) একটি কেন্দ্রীয় ডিরেক্টরি থেকে নিয়ন্ত্রণ করে। AD সিকিউরিটি একটি বিশাল স্বতন্ত্র বিষয়, কারণ একটি compromise হওয়া AD সার্ভার মানে পুরো প্রতিষ্ঠানের নেটওয়ার্ক ঝুঁকিতে পড়া।

    💡

    Linux বনাম Windows — একটি ভারসাম্যপূর্ণ দৃষ্টিভঙ্গি: কোনো OS সার্বিকভাবে "বেশি নিরাপদ" নয় — প্রতিটির নিজস্ব attack surface ও hardening পদ্ধতি আছে। Linux সার্ভার-সাইডে প্রাধান্য পায় কারণ এটি হালকা, স্ক্রিপ্ট-বান্ধব ও ফ্রি; Windows এন্টারপ্রাইজ ডেস্কটপে প্রাধান্য পায় কারণ ব্যবহারকারী-বান্ধবতা, সফটওয়্যার সামঞ্জস্য (compatibility) ও Active Directory-এর মতো পরিপক্ব ব্যবস্থাপনা টুলের কারণে।

    সারসংক্ষেপ

    Windows একটি closed-source, GUI-কেন্দ্রিক OS, যার আর্কিটেকচারে User Mode/Kernel Mode বিভাজন Linux-এর User/Kernel Space-এর মতোই। PowerShell আধুনিক, শক্তিশালী command-line টুল, এবং Active Directory এন্টারপ্রাইজ পরিবেশে কেন্দ্রীয় ইউজার/নীতি ব্যবস্থাপনার ভিত্তি।

    Windows ফাইল সিস্টেম ও রেজিস্ট্রি

    NTFS কীভাবে কাজ করে, drive letter মডেল, এবং Windows-এর কেন্দ্রীয় কনফিগারেশন ডেটাবেজ — রেজিস্ট্রি।

    Drive Letter মডেল

    Linux-এর একক root tree-এর বিপরীতে, Windows প্রতিটি storage device-কে একটি আলাদা drive letter (C:, D:, E:) দিয়ে প্রতিনিধিত্ব করে। সাধারণত C:\ হলো primary drive, যেখানে OS নিজেই ইনস্টল থাকে।

    NTFS — Windows-এর প্রধান File System

    NTFS (New Technology File System) বর্তমান Windows-এর ডিফল্ট file system। এটি journaling সমর্থন করে (Linux-এর ext4-এর মতো), এবং অতিরিক্ত ফিচার দেয় — ফাইল-লেভেল এনক্রিপশন (EFS), কম্প্রেশন, এবং একটি বিস্তারিত permission মডেল (NTFS permissions), যা Linux-এর সাধারণ rwx-এর চেয়ে অনেক বেশি granular (প্রতিটি ফাইলে একাধিক ইউজার/গ্রুপের জন্য আলাদা, সূক্ষ্ম অনুমতি সেট করা যায়)।

    গুরুত্বপূর্ণ Windows ফোল্ডার

    ফোল্ডারকী থাকে
    C:\WindowsOS-এর মূল ফাইল, system32 (গুরুত্বপূর্ণ system binary ও DLL)
    C:\Program Filesইনস্টল করা (৬৪-বিট) অ্যাপ্লিকেশন
    C:\Program Files (x86)৩২-বিট অ্যাপ্লিকেশন (৬৪-বিট Windows-এ)
    C:\Users\<username>Linux-এর /home-এর সমতুল্য — প্রতিটি ইউজারের ব্যক্তিগত ফোল্ডার
    C:\ProgramDataসব ইউজারের জন্য শেয়ার্ড অ্যাপ্লিকেশন ডেটা

    Windows Registry — কেন্দ্রীয় কনফিগারেশন ডেটাবেজ

    Linux-এ কনফিগারেশন সাধারণত /etc-এ আলাদা, মানুষের পড়ার যোগ্য text ফাইলে থাকে। Windows-এ এর পরিবর্তে একটি কেন্দ্রীয়, hierarchical, বাইনারি ডেটাবেজ ব্যবহৃত হয় — Registry। এখানে OS সেটিংস, ইনস্টল করা সফটওয়্যারের কনফিগারেশন, ড্রাইভার তথ্য, স্টার্টআপ প্রোগ্রাম — সবকিছু সংরক্ষিত থাকে।

    Registry Hiveকী থাকে
    HKEY_LOCAL_MACHINE (HKLM)সম্পূর্ণ মেশিনের সেটিংস, সব ইউজারের জন্য প্রযোজ্য
    HKEY_CURRENT_USER (HKCU)বর্তমানে লগইন করা ইউজারের ব্যক্তিগত সেটিংস
    HKEY_CLASSES_ROOT (HKCR)ফাইল টাইপ ও অ্যাপ্লিকেশন association তথ্য
    ⚠️

    Registry-এর সিকিউরিটি প্রাসঙ্গিকতা: Malware প্রায়ই Registry-তে নিজেকে স্টার্টআপ এন্ট্রি হিসেবে যোগ করে persistence অর্জন করে (HKLM\...\Run key-এর মতো জায়গায়) — Linux-এ systemd service-এর মাধ্যমে persistence অর্জনের মতোই একটি সমতুল্য কৌশল। Registry সরাসরি এডিট করা (regedit দিয়ে) ঝুঁকিপূর্ণ — ভুল পরিবর্তন সম্পূর্ণ সিস্টেমকে অস্থির করে দিতে পারে, তাই এডিটের আগে সবসময় backup নেওয়া উচিত।

    অনুশীলন

    Linux-এর /etc ডিরেক্টরি ও Windows-এর Registry-এর মধ্যে কী মৌলিক ধারণাগত মিল আছে, এবং কী আর্কিটেকচারাল পার্থক্য আছে (text-based বনাম binary database)?

    সারসংক্ষেপ

    Windows-এ NTFS প্রধান file system, drive letter মডেল ব্যবহৃত হয় (Linux-এর একক root-এর বিপরীতে), এবং কনফিগারেশন একটি কেন্দ্রীয়, hierarchical Registry ডেটাবেজে সংরক্ষিত থাকে — যা Linux-এর বিক্ষিপ্ত, text-based /etc কনফিগারেশনের থেকে আর্কিটেকচারালভাবে ভিন্ন।

    Windows ইউজার অ্যাকাউন্ট ও পারমিশন

    Administrator বনাম Standard ইউজার, UAC (User Account Control), এবং NTFS permission-এর বাস্তব ব্যবহার।

    Windows-এ ইউজারের ধরন

    👑 Administrator

    সিস্টেম-ব্যাপী পরিবর্তনের ক্ষমতা — সফটওয়্যার ইনস্টল, সিস্টেম সেটিংস পরিবর্তন, অন্য ইউজার ম্যানেজ করা। Linux-এর root-এর মোটামুটি সমতুল্য।

    👤 Standard User

    সীমিত privilege — নিজের ফাইল ও বেশিরভাগ অ্যাপ্লিকেশন ব্যবহার করতে পারে, কিন্তু সিস্টেম-ব্যাপী পরিবর্তন করতে পারে না।

    ⚙️ Built-in/Service Account

    SYSTEM, Local Service, Network Service — নির্দিষ্ট Windows সার্ভিস চালানোর জন্য ব্যবহৃত বিশেষ অ্যাকাউন্ট, সাধারণ ইউজার লগইনের জন্য নয়।

    UAC (User Account Control)

    এমনকি একজন Administrator ইউজারও ডিফল্টভাবে প্রতিদিনের কাজে "standard" privilege-এ চলে — একটি action যদি সিস্টেম-ব্যাপী পরিবর্তন করতে চায় (যেমন সফটওয়্যার ইনস্টল), UAC একটি নিশ্চিতকরণ prompt দেখায় ("আপনি কি নিশ্চিত?")। এটি অনেকটা Linux-এর sudo-এর মতোই একটি ধারণা — administrator হলেও, প্রতিটি privileged action স্পষ্টভাবে অনুমোদন করতে হয়, যাতে malware নীরবে সিস্টেম-ব্যাপী পরিবর্তন করতে না পারে।

          [Yes/No]

    NTFS Permission — বাস্তব প্রয়োগ

    NTFS permission Linux-এর rwx-এর চেয়ে অনেক বেশি সূক্ষ্ম — একটি ফাইলে একাধিক ইউজার/গ্রুপের জন্য আলাদা অনুমতি (Read, Write, Modify, Full Control, এবং আরও বিস্তারিত "Special Permissions") সেট করা যায়। এছাড়া NTFS permission inherit হতে পারে — একটি parent ফোল্ডারে পরিবর্তন করলে সেটি ভেতরের সব ফাইল/সাবফোল্ডারে স্বয়ংক্রিয়ভাবে প্রযোজ্য হতে পারে (যদি inheritance বন্ধ না করা হয়)।

    Local Account বনাম Microsoft Account বনাম Domain Account

    ধরনব্যবহৃত হয়
    Local Accountশুধুমাত্র একটি নির্দিষ্ট কম্পিউটারে বৈধ, অন্য কোনো ডিভাইসে sync হয় না
    Microsoft Accountএকটি Microsoft Online পরিচয়ের সাথে যুক্ত, একাধিক ডিভাইসে সেটিংস sync করে
    Domain Account (Active Directory)প্রতিষ্ঠানের কেন্দ্রীয় Active Directory সার্ভার থেকে নিয়ন্ত্রিত, এন্টারপ্রাইজ পরিবেশে ব্যবহৃত
    ⚠️

    সাধারণ ভুল: প্রতিদিনের ব্যবহারের জন্য একটি Administrator অ্যাকাউন্ট দিয়ে লগইন করা (বিশেষ করে UAC prompt বারবার "Yes" চাপার অভ্যাস তৈরি হয়ে গেলে) — এটি একটি malware-এর জন্য সিস্টেম-ব্যাপী পরিবর্তন করা সহজ করে তোলে। Least Privilege নীতি অনুযায়ী, দৈনন্দিন কাজে একটি Standard অ্যাকাউন্ট ব্যবহার করা এবং প্রয়োজনে UAC-এর মাধ্যমে elevate করাই নিরাপদ অভ্যাস।

    অনুশীলন

    UAC ও Linux-এর sudo — উভয়ই "Least Privilege" নীতি বাস্তবায়নের চেষ্টা করে, কিন্তু UX-এ ভিন্ন। প্রতিটির একটি সুবিধা ও একটি সীমাবদ্ধতা লিখুন।

    সারসংক্ষেপ

    Windows-এ Administrator ও Standard User-এর মধ্যে privilege পার্থক্য আছে, এবং UAC প্রতিটি privileged action-এ নিশ্চিতকরণ চায় (sudo-এর সমতুল্য ধারণা)। NTFS permission অত্যন্ত granular ও inheritance সমর্থন করে। দৈনন্দিন কাজে Standard অ্যাকাউন্ট ব্যবহার করা Least Privilege নীতির একটি বাস্তব প্রয়োগ।

    macOS-এর Unix ভিত্তি

    অনেকের কাছে macOS একটি সম্পূর্ণ "আলাদা" OS মনে হলেও, এর ভেতরের স্তর — Darwin — আসলে একটি সার্টিফায়েড Unix সিস্টেম, যা BSD (Berkeley Software Distribution) Unix-এর উপর ভিত্তি করে তৈরি। এই কারণে macOS-এর Terminal-এ Linux-এর মতোই bash/zsh shell, একই rwx permission মডেল, এবং একই রকম /-ভিত্তিক ডিরেক্টরি গঠন দেখা যায়।

    অন্যান্য Unix-based সিস্টেম

    Unix দর্শনের প্রভাব আরও অনেক দূর বিস্তৃত — Android (Linux kernel-ভিত্তিক, কিন্তু উপরে সম্পূর্ণ ভিন্ন application layer), FreeBSD/OpenBSD (সরাসরি BSD থেকে, নিরাপত্তা-কেন্দ্রিক ডিজাইনের জন্য পরিচিত, অনেক নেটওয়ার্ক অ্যাপ্লায়েন্সে ব্যবহৃত), এবং অসংখ্য IoT/embedded ডিভাইসের firmware — সবই মূলত Unix-এর মৌলিক নীতির (process, file, permission মডেল) উত্তরাধিকার বহন করে।

    💡

    কেন এই সাদৃশ্য গুরুত্বপূর্ণ: একবার আপনি Linux-এর rwx permission, process মডেল, ও shell কমান্ড ভালোভাবে শিখলে, সেই জ্ঞানের বেশিরভাগই সরাসরি macOS Terminal-এ প্রযোজ্য, এবং আংশিকভাবে Android-এর internal structure বুঝতেও কাজে লাগে — কারণ সবগুলোরই মূল ভিত্তি একই পারিবারিক শিকড় থেকে আসে।

    macOS-এর XNU kernel-কে "hybrid kernel" বলা হয় কেন, এবং এটি Linux-এর monolithic kernel থেকে ধারণাগতভাবে কীভাবে আলাদা?

    OS-স্তরের নেটওয়ার্কিং বেসিক

    একটি OS কীভাবে নেটওয়ার্ক সংযোগ পরিচালনা করে — port, socket, firewall-এর মৌলিক ধারণা।

    Port ও Socket

    একটি কম্পিউটারের একটি IP address থাকতে পারে, কিন্তু একসাথে অনেক নেটওয়ার্ক সার্ভিস (ওয়েব সার্ভার, SSH, ডেটাবেজ) চালাতে হলে, OS প্রতিটি সার্ভিসকে একটি আলাদা port নম্বর (0-65535) বরাদ্দ করে। একটি socket হলো একটি নির্দিষ্ট IP+port সংমিশ্রণের একটি active সংযোগ বিন্দু, যা দিয়ে প্রকৃত ডেটা আদান-প্রদান হয়।

    কোন পোর্ট শোনা হচ্ছে তা দেখা

    Open port দেখার কমান্ড
    # Linux / macOS
sudo ss -tulnp          # বা পুরনো সিস্টেমে netstat -tulnp
sudo lsof -i :80        # 80 পোর্টে কোন প্রসেস শুনছে তা দেখা

# Windows (PowerShell)
Get-NetTCPConnection -LocalPort 80
netstat -ano | findstr :80

    Firewall — OS-স্তরের নেটওয়ার্ক গেটকিপার

    একটি firewall নির্ধারণ করে কোন নেটওয়ার্ক ট্রাফিক একটি সিস্টেমে প্রবেশ (inbound) বা বের (outbound) হতে পারবে। Linux-এ iptables/nftables (ও সহজতর ফ্রন্টএন্ড ufw), Windows-এ built-in Windows Defender Firewall — উভয়েই একই মৌলিক নীতিতে কাজ করে: নির্দিষ্ট নিয়ম (rule) দিয়ে port/IP/protocol-ভিত্তিক ট্রাফিক অনুমোদন বা ব্লক করা।

    Firewall — ধারণাগত নিয়মের উদাহরণ
    # Linux ufw উদাহরণ
sudo ufw allow 22/tcp         # SSH অনুমোদন
sudo ufw allow from 203.0.113.0/24 to any port 3306  # নির্দিষ্ট subnet থেকে DB অ্যাক্সেস
sudo ufw default deny incoming  # ডিফল্টভাবে সব inbound ব্লক (deny-by-default)
    ⚠️

    Deny-by-default নীতি: একটি নিরাপদ firewall কনফিগারেশন সবসময় "ডিফল্টভাবে সব ব্লক, শুধু প্রয়োজনীয়গুলো অনুমোদন" নীতি অনুসরণ করা উচিত — আগের ডকুমেন্টেশনগুলোতে আলোচিত "Deny by Default" authorization নীতির মতোই একই দর্শন, কিন্তু network-স্তরে প্রয়োগ করা।

    DNS Resolution — সংক্ষিপ্ত পুনরালোচনা

    যখন একটি অ্যাপ্লিকেশন example.com-এ সংযোগ করতে চায়, OS প্রথমে স্থানীয় DNS resolver-এর মাধ্যমে ডোমেইনকে একটি IP address-এ রূপান্তর করে, তারপর সেই IP-তে socket সংযোগ স্থাপন করে — এই প্রক্রিয়া OS-এর নেটওয়ার্ক স্ট্যাকের একটি মৌলিক অংশ।

    অনুশীলন

    একটি সার্ভারে আপনি দেখলেন পোর্ট 3306 (MySQL) পুরো ইন্টারনেট থেকে (0.0.0.0) অ্যাক্সেসযোগ্য, কোনো firewall রুল ছাড়াই। এটি কী নিরাপত্তা ঝুঁকি তৈরি করে এবং কীভাবে ঠিক করবেন?

    সারসংক্ষেপ

    OS port ও socket ব্যবহার করে একাধিক নেটওয়ার্ক সার্ভিস একসাথে পরিচালনা করে, এবং firewall নির্ধারণ করে কোন ট্রাফিক অনুমোদিত। Deny-by-default নীতি — শুধু প্রয়োজনীয় port/IP স্পষ্টভাবে অনুমোদন করা — নেটওয়ার্ক-স্তরের নিরাপত্তার একটি মৌলিক ভিত্তি।

    Privilege Escalation — সাধারণ ইউজার থেকে root/Administrator

    একজন attacker প্রায়ই প্রথমে একটি সীমিত-privilege অ্যাক্সেস পান (যেমন একটি দুর্বল ওয়েব অ্যাপ্লিকেশনের মাধ্যমে), তারপর লক্ষ্য থাকে সেই সীমিত অ্যাক্সেসকে root/Administrator-এ "escalate" করা। সাধারণ কারণ:

    • পুরনো, patch না করা kernel/software — পরিচিত vulnerability ব্যবহার করে সরাসরি privilege বৃদ্ধি।
    • ভুলভাবে কনফিগার করা sudo/SUID — Linux-এ একটি প্রোগ্রাম যদি SUID bit সহ owner root-এর হয়, এবং সেই প্রোগ্রামে কোনো দুর্বলতা থাকে, সাধারণ ইউজার root privilege পেতে পারেন।
    • দুর্বল সার্ভিস অ্যাকাউন্ট পারমিশন — একটি সার্ভিস যদি প্রয়োজনের চেয়ে বেশি privilege-এ চলে, সেই সার্ভিস compromise হলে বেশি ক্ষতি হয়।
    • Windows UAC bypass — কিছু পরিচিত কৌশল Administrator অ্যাকাউন্টের UAC prompt এড়িয়ে নীরবে সিস্টেম-ব্যাপী পরিবর্তন করতে পারে।

    Malware Persistence — কীভাবে "টিকে থাকে"

    একটি malware শুধু একবার চালু হয়ে ক্ষান্ত হয় না — এটি নিশ্চিত করতে চায় সিস্টেম রিবুট হলেও এটি আবার চালু হবে। আগের অধ্যায়গুলোতে উল্লেখিত দুটি কৌশল আবার স্মরণ করুন:

    🐧 Linux

    একটি systemd service যোগ করা, cron job সেট করা, বা ~/.bashrc-এর মতো startup script-এ কমান্ড ইনজেক্ট করা।

    🪟 Windows

    Registry-তে Run key যোগ করা, একটি Scheduled Task তৈরি করা, বা নিজেকে একটি Windows Service হিসেবে ইনস্টল করা।

    OS Hardening — মৌলিক চেকলিস্ট

    🔄 নিয়মিত আপডেট

    Kernel, OS package ও সব সফটওয়্যার নিয়মিত patch করুন — অধিকাংশ privilege escalation known, ইতিমধ্যে-ফিক্স হওয়া vulnerability ব্যবহার করে।

    🔒 Least Privilege

    সার্ভিস অ্যাকাউন্টকে ন্যূনতম প্রয়োজনীয় পারমিশন দিন, দৈনন্দিন কাজে কখনো সরাসরি root/Administrator ব্যবহার করবেন না।

    🧱 Firewall ও Attack Surface হ্রাস

    অপ্রয়োজনীয় সার্ভিস/পোর্ট বন্ধ রাখুন — যা চলছে না, তা exploit করাও যাবে না।

    📋 Logging ও Monitoring

    Login attempt, sudo ব্যবহার, নতুন service/scheduled task তৈরি — এসব লগ নিয়মিত পর্যালোচনা করুন, যাতে অস্বাভাবিক কার্যকলাপ দ্রুত ধরা পড়ে।

    💡

    এই সিরিজের সংযোগ: লক্ষ করুন, Least Privilege, Deny-by-default, ও regular patching — এই নীতিগুলো শুধু OS-স্তরে নয়, বরং এই ডকুমেন্টেশন সিরিজের API Security ও Authentication/Authorization ডকুমেন্টেশনেও একইভাবে প্রযোজ্য। সিকিউরিটির অনেক মূল নীতি একটি স্তর থেকে আরেকটিতে পুনরাবৃত্ত হয় — এটি কোনো কাকতালীয় ব্যাপার নয়, বরং defense-in-depth-এর একটি স্বাভাবিক ফলাফল।

    অনুশীলন

    একটি Linux সার্ভারে একটি প্রোগ্রামের SUID bit সেট করা আছে, এবং owner root। এই প্রোগ্রামে যদি একটি কমান্ড-ইনজেকশন দুর্বলতা থাকে, একজন সাধারণ ইউজার কীভাবে root privilege পেতে পারেন তা ধারণাগতভাবে ব্যাখ্যা করুন।

    Privilege escalation ঘটে পুরনো software, ভুল কনফিগারেশন বা দুর্বল permission-এর কারণে। Malware persistence-এর কৌশল OS-ভেদে ভিন্ন রূপ নেয় (systemd/cron বনাম Registry/Scheduled Task), কিন্তু মূল লক্ষ্য একই — "টিকে থাকা"। নিয়মিত patching, Least Privilege, firewall ও logging একসাথে একটি হার্ডেনড OS-এর ভিত্তি তৈরি করে।

    ভার্চুয়ালাইজেশন ও কনটেইনার

    একটি হার্ডওয়্যারে একাধিক "কম্পিউটার" চালানো কীভাবে সম্ভব, এবং VM ও কনটেইনারের মধ্যে মৌলিক পার্থক্য।

    Virtual Machine (VM) কী

    একটি Virtual Machine হলো একটি সফটওয়্যার-ভিত্তিক "কম্পিউটার", যা একটি প্রকৃত (physical) কম্পিউটারের ভেতরে চলে। একটি hypervisor (VMware, VirtualBox, Hyper-V, KVM) ফিজিক্যাল হার্ডওয়্যার (CPU, RAM, ডিস্ক) ভাগ করে একাধিক VM-কে বরাদ্দ করে, এবং প্রতিটি VM-এ সম্পূর্ণ আলাদা, independent একটি OS চলে (এমনকি host-এর থেকে ভিন্ন OS-ও, যেমন একটি Linux host-এ একটি Windows VM চালানো সম্ভব)।

    Container কী — এবং কেন VM থেকে আলাদা

    একটি Container (Docker সবচেয়ে পরিচিত উদাহরণ) একটি অ্যাপ্লিকেশন ও তার সব dependency একসাথে প্যাকেজ করে, কিন্তু — VM-এর বিপরীতে — একটি সম্পূর্ণ আলাদা OS কপি চালায় না। সব container host OS-এর একই kernel শেয়ার করে, শুধু process-level isolation ব্যবহার করে একে অপরের থেকে আলাদা থাকে।

    ⚠️

    সিকিউরিটি বিবেচনা: যেহেতু container একই host kernel শেয়ার করে, একটি container "escape" vulnerability (container থেকে বের হয়ে host-এ পৌঁছানো) VM escape-এর চেয়ে তাত্ত্বিকভাবে বেশি সম্ভাবনাময় এবং বেশি গুরুতর — কারণ host kernel-এ সরাসরি অ্যাক্সেস মানেই সব container-এ প্রভাব। তাই container-কে কখনোই "VM-এর মতো সমান শক্তিশালী নিরাপত্তা boundary" হিসেবে ধরে নেওয়া উচিত নয় — বরং অতিরিক্ত সতর্কতা (least privilege container configuration, নিয়মিত base image আপডেট) প্রয়োজন।

    সার্ভার/DevOps ক্যারিয়ারের জন্য Linux শেখা কি বাধ্যতামূলক?

    কার্যত হ্যাঁ — বিশ্বের বেশিরভাগ সার্ভার, ক্লাউড ইনফ্রাস্ট্রাকচার ও কনটেইনার (Docker images) Linux-ভিত্তিক। Windows ডেস্কটপ/এন্টারপ্রাইজে প্রাধান্য পেলেও, DevOps/সার্ভার/ক্লাউড ক্যারিয়ারে Linux জ্ঞান প্রায় অপরিহার্য।

    macOS শেখা কি Linux শেখার সমতুল্য?

    অনেকটাই — কারণ macOS Unix-ভিত্তিক, Terminal কমান্ড, permission মডেল ও ডিরেক্টরি গঠন Linux-এর সাথে অনেক মিল রাখে। তবে GUI অ্যাপ্লিকেশন ম্যানেজমেন্ট ও কিছু system-level টুল আলাদা, তাই সম্পূর্ণ অভিন্ন নয়।

    এই ডকুমেন্টেশন পড়ার পর পরবর্তী ধাপ কী?

    একটি ফ্রি Linux distro (Ubuntu) VirtualBox-এ ইনস্টল করে হাতে-কলমে কমান্ড লাইন প্র্যাকটিস করুন, এবং learn.alamincyber.com-এর Authentication/Authorization ও API Security ডকুমেন্টেশনের সাথে এই OS জ্ঞান যুক্ত করুন — কারণ privilege escalation, file permission, ও service hardening-এর ধারণা পরবর্তী সিকিউরিটি বিষয়গুলো বোঝার ভিত্তি তৈরি করে।

    কোন OS "সবচেয়ে নিরাপদ"?

    কোনো OS সার্বিকভাবে "সবচেয়ে নিরাপদ" নয় — প্রতিটির নিজস্ব attack surface, hardening পদ্ধতি ও ব্যবহারের প্রেক্ষাপট আছে। প্রকৃত নিরাপত্তা নির্ভর করে কীভাবে OS কনফিগার, patch ও monitor করা হচ্ছে তার উপর, শুধু OS-এর নাম বা "খ্যাতি"-র উপর নয়।

    চূড়ান্ত মনে রাখার কথা

    Linux, Windows ও macOS — তিনটিই একই মৌলিক সমস্যার (হার্ডওয়্যার পরিচালনা, process/file/user ব্যবস্থাপনা) ভিন্ন সমাধান। একবার মূল ধারণাগুলো (kernel, permission, process, file system) বুঝে ফেললে, যেকোনো নতুন OS-এ সেই জ্ঞান প্রয়োগ করা অনেক সহজ হয়ে যায় — এবং এই ভিত্তিই পরবর্তী যেকোনো সিকিউরিটি বিষয় শেখার পূর্বশর্ত।
